# SPEC 161 — исполняемая проверка проектной раскладки

## Публичный шов и среда

`bash fixtures/workshop_project/proektnaja_raskladka_161/red_proektnaja_raskladka_161.sh [--model|--stabs]` → `probe.py` (после реализации). До probe.py — дверь rc 2 `NOT_IMPLEMENTED`, не `exit 0`. В проектных мирах вызывать **настоящие** `scripts/{make_task,spawn_agent,verify_ci_parity,check_precision_gate,pre_critic,zamok_predmeta,gitw_teg_130,connect_project,land_agent,done_contract}.sh` из установки; подмена исполняемых — только в режиме `--model/--stabs`. Удалить мир сразу после случая, не более трёх одновременно. Реальные network/GitHub/omp/эмуляторы не нужны: git bare-origin + локальные project-worktree, внешние бинарники с детерминированными двойниками лишь там, где субъект (shell-скрипт) должен договориться с внешним провайдером. Отсутствие необходимого бинарника или допуска к конформному fixture → rc 2 `NOT_IMPLEMENTED`, не зелёный skip.

ДВА независимых корня: `R_m` (код `mobile/`, `.harness/contracts/`, `.harness/registry/`, `.harness/fixtures/`, свой `AGENTS.md`) и `R_x` (код `client/`, тоже `.harness/`, другой профиль/AGENTS); станция `R_h` (код и contracts в корне). В `R_m`/`R_x` нет корневого `package.json` и npm-делегатора. Для проверки чужого слоя оба проекта используют ОДИН относительный `projectLayer.profilePath` и разные байты `contextPack.rows`, projectId, repoId, правил и манифестов; ожидания своего/чужого значения снимаются в память ДО вызова каждого субъекта. Профили, CI `.github/workflows/mobile.yml` и `ci_parity_exceptions.txt` — конформные значения существующего `profile_resolver.sh`. Прозрачные `npm run ...` и bash script path проверяются по эффективному working-directory, opaque command substitution/heredoc/backtick — отдельные негативные шаги (не выполнять при анализе). Манифест и ожидаемый pack хранятся в памяти `probe.py` ДО субъекта; output-файл субъекта не перечитывать как источник истины. Секции/токены сверять самостоятельными строками в своих полях (не подстрокой), AGENTS.md проектов — по содержимому исходного дерева, снятому в память.

## Независимые входы и ожидаемые причины

Каждый case и каждый шаг конечной таблицы precedence — отдельный вызов настоящего субъекта; не засчитывать случай по первому отказу другого. Зелёный контроль и соседняя порча различаются ровно одним script/слоем/файлом. `--model` запускает честный контроль rc 0 перед КАЖДЫМ мутантом, затем ожидает rc 1 со своей причиной (для намеренного fail-closed честного отказа сравнивать с ожидаемым отказом и указанным состоянием). Без флага установленная реализация обязана зелёной быть на всех честных входах; все красные стенки печатаются поимённо, итог rc 1.

## Грамматика и граница валидного контрпримера

Конформный вход: валидный `harness.project.json` с двумя workflowPaths раскладками из `profile_resolver`, `ci.workflow` существующий, npm scripts — JSON-строки, YAML jobs.steps.run и `defaults.run.working-directory` на workflow/job и `working-directory` на шаге — строки GitHub Actions, path внутри дерева без `..`, у проекта есть вложенные package.json для каждого выбранного каталога, у станции — корневой. Для CI C01–C03 конечное множество precedence — workflow inherited (C01), job overrides workflow (C02), step overrides job (C03); отдельная порча каждого script обязательна. В паритетном позитивном шаге команды прозрачны (`npm run <script>` либо конкретный `bash <путь>`); opaque-шаги конформны как отдельный **отрицательный** вход до переноса, не как исключение из исполнения. `contextPack.rows` валиден по текущей грамматике ролей и kind; обязательность optional НЕ разрешает объявлять несуществующий файл. Свежий проект C10a без профиля — конформен именно как вход `connect_project`, в отличие от уже подключённого C10b. Git-identity и теги разрешены в изолированном bare-origin fixture; project-layer с чужим корнем отклоняется до записи. Валидный контрпример от адверсария: (1) не зависит от названий `R_m`, `R_x`, значений projectId и имён каталогов из конформной грамматики; (2) честная реализация отвергает/принимает его по инварианту; (3) кандидат даёт другой rc/причину/состояние на ТОМ ЖЕ конформном входе. Неконформный YAML/профиль или чужой формат значения сам по себе не является обходом.
