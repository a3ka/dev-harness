# SPEC 161 — исполняемая проверка проектной раскладки

## Публичный шов и среда

`bash fixtures/workshop_project/proektnaja_raskladka_161/red_proektnaja_raskladka_161.sh [--model|--stabs]` → `probe.py` (после реализации). До probe.py — дверь rc 2 `NOT_IMPLEMENTED`, не `exit 0`. В проектных мирах вызывать **настоящие** `scripts/{make_task,spawn_agent,verify_ci_parity,check_precision_gate,pre_critic,zamok_predmeta,gitw_teg_130,connect_project,land_agent,done_contract}.sh` из установки; подмена исполняемых — только в режиме `--model/--stabs`. Удалить мир сразу после случая, не более трёх одновременно. Реальные network/GitHub/omp/эмуляторы не нужны: git bare-origin + локальные project-worktree, внешние бинарники с детерминированными двойниками лишь там, где субъект (shell-скрипт) должен договориться с внешним провайдером. Отсутствие необходимого бинарника или допуска к конформному fixture → rc 2 `NOT_IMPLEMENTED`, не зелёный skip.

ДВА независимых корня: `R_m` (название рабочей поддиректории `mobile/`, `.harness/contracts/`, `.harness/registry/`, `.harness/fixtures/`, свой `AGENTS.md`) и `R_x` (название `client/`, тоже `.harness/`, другой профиль/AGENTS); станция `R_h` (код и contracts в корне). В `R_m`/`R_x` нет корневого `package.json`, нет корневого npm-делегатора. Профили и CI `.github/workflows/mobile.yml` и `ci_parity_exceptions.txt` — конформные значения из существующего `profile_resolver.sh`; `working-directory` соответствует каталогу исходника. Структура CI с прозрачным `npm run ...` и bash script path, отдельные fixture-шаги с command substitution/heredoc/backtick (не выполнять как код при анализе). Манифест и ожидаемый pack хранятся в памяти `probe.py` ДО субъекта; как истину output-файл на диске проверяемого субъекта не перечитывать. Дословные секции проверять отдельными строками (не поиском подстроки по всему тексту), и сравнивать AGENTS.md двух проектов не по фиксированному имени, а по байтовому содержимому, снятому из авторитетного исходного дерева в память.

## Независимые входы и ожидаемые причины

Каждый case — собственный вызов субъекта; не засчитывать случай по первой красной точке другого. Для каждого зелёного — соседний отрицательный вход с одной порчей. На предъявлении красной реализации `--model` работает с честным эталоном в памяти: rc 0 на всех честных ветвях и rc 1 с ровно своей причиной на порче. На установленной реализации без флага честный контроль обязан rc 0; если ещё красный — напечатать названия всех стенок и итог rc 1.

## Грамматика и граница валидного контрпримера

Конформный вход: валидный `harness.project.json` с двумя workflowPaths раскладками из `profile_resolver`, `ci.workflow` существующий, npm scripts — JSON-строки, YAML jobs.steps.run и опциональный working-directory — строки GitHub Actions, path внутри дерева без `..`, у проекта есть вложенный `package.json`, а у станции корневой. В паритетном позитивном шаге команды прозрачны (`npm run <script>` либо конкретный `bash <путь>`); opaque-шаги конформны как отдельный **отрицательный** вход до переноса, не как исключение из исполнения. `contextPack.rows` валиден по текущей грамматике ролей и kind; обязательность optional НЕ разрешает объявлять несуществующий файл. Git-identity и теги разрешены в изолированном bare-origin fixture; project-layer с чужим корнем отклоняется до записи. Валидный контрпример от адверсария: (1) не зависит от названий `R_m`, `R_x`, значений projectId и имён каталогов из конформной грамматики; (2) честная реализация отвергает/принимает его по инварианту; (3) кандидат даёт другой rc/причину/состояние на ТОМ ЖЕ конформном входе. Неконформный YAML/профиль или чужой формат значения сам по себе не является обходом.
