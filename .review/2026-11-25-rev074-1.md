# Находки 074 (mob-tmpdir), реализация, reviewer вызов 1

Один блок (Б-1) и шесть советов. Б1/Б2 адверсария здесь не повторяются: по слову консультанта они идут остатком, см. вердикт §Остатки.

- [ ] **Б-1 (implementer; БЛОК). Гонка mkdir→chown→chmod по пути внутри каталога, принадлежащего harness: root отдаёт harness'у любой файл станции.**
  - **Фрагмент.** `ops/server/install.sh:635-637` (`mobtmp_dir`): `mkdir -p -- "$1"`, затем `chown "$MOBTMP_OWNER:$MOBTMP_GROUP" -- "$1"`, затем `chmod 700 -- "$1"`. Обе команды берут путь, без `-h`, и идут по символьной ссылке.
  - **Почему достижимо.** Родитель `/var/lib/ci-runner` на станции — `harness:harness 750` (замер `stat`). Писать в него могут все процессы harness: агенты и код PR в моб-CI. По `systemctl cat gh-runner-complior` юнит раннера идёт под `User=harness` с `ReadWritePaths=/var/lib/ci-runner /tmp`, а комментарий юнита прямо называет код PR недоверенным: «Код из PR не видит /home … и не пишет в систему». Защита `fs.protected_symlinks=1` здесь не работает: каталог не sticky и не world-writable. Ставит консультант через `sudo … mob-tmpdir` сразу после влития, пока раннеры и агенты живы (сейчас активны 4 раннера).
  - **Доказательство (своя мера, честный субъект).** Шимов в окне нет: `mkdir`, `chown` и `chmod` настоящие, шим `id -u`→0 срабатывает до окна. Атакующий — отдельный процесс того же uid: python в цикле делает `rename(tmp1)` и `symlink(victim)`. Результат: `RACE: trials=30 attacker-swapped=30 victim-mode/owner-changed=30`. Жертва `644 harness:kvm` стала `700 harness:harness`, `tmp1 -> victim`. При шиме только для `chown root:root` drop-in'а (то, что под root проходит само) установщик печатает `установлено: mob-tmpdir (юнитов моб-раннеров: 1)` и даёт rc 0.
  - **Нарушенное обязательство.** Слово владельца в контракте 074 (frozen/contracts/074/2, §Предмет п.2): root-файлы `root:root`, «harness не должен иметь права его менять». Под root гонка делает `chown harness:harness` любого пути станции, например `/usr/local/sbin/orch-peak`, который systemd исполняет от root. Нарушено и собственное обязательство кода: «символьная ссылка — ОТКАЗ» (`install.sh:627-629`, README «расходящийся существующий tmp-каталог — именованный отказ»). Под гонкой выходит rc 0 «установлено».
  - **Чем отличается от прецедента 196.** `ciart_provision_root` создаёт каталог в `/var/lib/ci-artifacts`, а это `root:root 755` (замер). Harness туда не пишет, поэтому окна там нет. Окно появилось с этим диффом.
  - **Простая форма, проходящая те же сценарии.** `mkdir -m 700 -- "$1"` плюс `chown -h "$MOBTMP_OWNER:$MOBTMP_GROUP" -- "$1"`, без `chmod` по пути. Проверено на копии (`wt-fix`): гонка `victim-mode/owner-changed=0` из 30. Все мои 13 сценариев дали тот же результат, что OBJECT: установка 700 harness, идемпотентность, отказ на 755 и на ссылке, гард, «не применимо», daemon-reload без restart, отказ при порче cp. Другой вариант той же силы — создавать каталог от имени владельца (`runuser -u "$MOBTMP_OWNER" -- mkdir -m 700`), тогда root не делает chown по пути вовсе.
