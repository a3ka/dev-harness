# ops/server — серверная обвязка станции (единый источник в репо)

Контракты 074/081/085: 9 файлов обвязки лежат в этом каталоге побайтно
(сверяются sha256 с живой станцией — `bash ops/server/install.sh verify`),
установщик ставит их из репо на `/home/harness/.local/bin/orch-loop` и
`/usr/local/sbin/orch-peak` + `/etc/systemd/system/*`, а `README` —
инвентарь для сессии, которая раньше обвязку не видела.

## Инвентарь механизмов (9 файлов, копии побайтно со станции 2026-10-05)

- **orch-loop** — обёртка хоста: перезапуск ведущей сессии по маркеру
  (`/tmp/dev-harness-verify/orch-restart`); живёт в tmux-сессии `orch` под
  harness. user-часть, режим 755, путь — `~/.local/bin/orch-loop`.
  Контракт 085 (И-2, И-3, И-5): стартовая обёртка — станционная
  (ebc53f30), плюс потолок памяти сессии (И-5, см. ниже) и общий счёт
  нештатных завершений подряд (И-3, см. «Семантика цикла»).
- **orch-peak** — пауза оркестратора на пиковые часы z.ai (команды
  `warn`, `stop`, `start`, `check`, `ctx`); root-часть, режим 755, путь —
  `/usr/local/sbin/orch-peak`, владелец `root:root` (harness не имеет права
  менять). Контракт 085: слияние станции (b3e354cd) и версии 080; три
  конфликта разрешены объединением намерений (подпись сторожа + транзакция
  маркера + PHRASE_OK 080).
- **orch-peak@.service** — oneshot-шаблон systemd: `ExecStart=/usr/local/sbin/orch-peak %i`;
  параметр `%i` — имя действия (`warn`, `stop`, `start`, `ctx`).
- **orch-peak-warn.timer** — Mon..Fri 13:40 Asia/Singapore: предупреждение в
  панель оркестратора за 20 мин до пика.
- **orch-peak-stop.timer** — Mon..Fri 14:00 Asia/Singapore: проверка «всё
  закоммичено и отправлено», при необходимости ожидание, затем гашение omp.
- **orch-peak-start.timer** — Mon..Fri 18:00 Asia/Singapore: ввод команды
  запуска цикла в ту же панель (`cd ~/dev-harness && orch-loop`).
- **orch-peak-reenable.timer** — однократное включение паузы 2026-10-08 00:00
  Asia/Singapore (Persistent=true).
- **orch-peak-reenable.service** — oneshot-сервис: включает
  `orch-peak-warn/stop/start.timer`, выключает сам reenable.
- **orch-ctx.timer** — `*:0/15` (раз в 15 мин): сторож контекста ведущей
  сессии; > CTX_SOFT (500 000, контракт 085 И-4б) — сообщение в панель,
  > CTX_HARD (600 000, И-4б) — проверка сохранения с отсрочкой, потом
  маркер перезапуска. Был 300K/500K (080), стал 500K/600K (станция + 085).

Все юниты — `root:root` 644 в `/etc/systemd/system/`; `Persistent=false` на
регулярных таймерах.

## Семантика цикла (orch-loop, контракт 085 И-3)

Сессия считается нештатно завершившейся в двух случаях: (а) маркер
перезапуска поставлен раньше `MIN_LIFE` (ранний маркер) или (б) выход
с rc≠0 без маркера и без стоп-файла. Счёт нештатных завершений подряд —
**общий** для (а) и (б): смена вида события его не обнуляет и не
разводит по видам. Обычный перезапуск по маркеру (жизнь ≥ MIN_LIFE) —
обнуляет. Падение после жизни ≥ 5×MIN_LIFE — счёт с единицы. Счёт
достиг `EARLY_MAX` (3 по умолчанию) — останов с ненулевым rc.

Остальные исходы сессии: (в) выход rc 0 без маркера — останов
(нормальный `/exit`); (г) стоп-файл `ORCH_STOP` (`$UHOME/orch-loop.stop`)
при выходе без маркера — останов, файл снят; (д) маркер снят до
истечения `GRACE` — сессия не получает сигнал, перезапуск отменён;
(е) маркер принят (сессии послан сигнал) — перезапуск состоится, даже
если маркер сняли после.

Ветка наблюдателя: маркер виден раз в 5 с, после GRACE перепроверяется;
если не снят — ставится `$MARK.go` (принятие необратимо), затем SIGTERM
omp, через 30 с SIGKILL. `touch "$MARK"` после сессии — только при
наличии `$MARK.go` (дверь примет и поведёт чистый рестарт).

## Сторож (orch-peak, контракт 085 И-4)

- **Пороги** (И-4б): `CTX_SOFT=500000` (500 000), `CTX_HARD=600000`
  (600 000). Превышение CTX_SOFT — одно сообщение в панель (PHRASE_OK
  080 встроен). Превышение CTX_HARD — сообщение + отсрочка
  `ORCH_PEAK_GRACE` (900 с) + polling живых субагентов до
  `ORCH_HARD_GRACE` (1800 с) + атомарная запись отчёта о погибших
  субагентах + маркер перезапуска. Маркер ставится ТОЛЬКО против той же
  сессии (Н-189): пока ждали GRACE, журнал мог смениться — тогда маркер
  не ставится вообще.
- **Простой** (И-4г): журнал верхнего уровня молчит ≥ `IDLE` (1800 с,
  IDLE_MAX=3 подряд при неизменном origin/main), субагентского журнала
  моложе `SUB_LIVE` (300 с) нет, маркера нет, дерево чисто (`unsaved`
  пуст) → маркер. Счётчик IDLE_MAX сбрасывается при изменении origin/main.
  «Несохранённое» — не простой, маркер не ставится.
- **Подпись** (И-4в, Н-200): каждое сообщение в панель начинается
  `СТОРОЖ СТАНЦИИ (автоматически, ...)` и несёт `это НЕ слово владельца`.
  Литерал `ВЛАДЕЛЕЦ (автоматически` НЕ доставляется ни одним сообщением.
- **Стоп-файл** (И-4д): `stop` создаёт стоп-файл цикла ДО сигнала omp.
  Путь — шов `ORCH_LOOP_STOP`, по умолчанию `$UHOME/orch-loop.stop`. В
  шве `ORCH_PEAK_TEST` (тест-мир) стоп-файл создаётся тоже (шов подменяет
  только сигналы). Цикл при виде стоп-файла выходит rc 0.
- **Поведение под швом** `ORCH_PEAK_TEST` (080 инв. 4): `as_u/say/pane/
  omp_pids/kill_session` подменяются на работу с `$ORCH_PEAK_TEST/`
  (`say.log`, `omp-pids`, `killed.log`, `pane`); `kill_session` всё равно
  трогает стоп-файл цикла по `LOOP_STOP` (иначе тест с1 не зелёный).
- **Сохранение** (072): сообщение отложенной остановки (wait_saved)
  содержит список несохранённого и гард-напоминание «не обходи».

## Потолок памяти (orch-loop, контракт 085 И-5)

Каждая сессия запускается `systemd-run --user --scope` со свойствами
`MemoryMax=$ORCH_MEM_MAX` (по умолчанию `32G`) и `MemorySwapMax=0`.
`XDG_RUNTIME_DIR` выставляется в `/run/user/$(id -u)`, если не задан
выше. Опции `systemd-run` идут ДО `--`; команда после `--` — exec'ом
в том же процессе приходит к вызову `workshop` (omp остаётся прямым
потомком цикла, `pgrep -P`/`pkill -P` сторожа и цикла не меняются).

Поведение:

- **scope создан, omp убит rc 137** — пишется строка журнала
  `OOM: omp убит потолком памяти (MemoryMax=$ORCH_MEM_MAX, rc=137)`,
  цикл идёт веткой падения (И-3б) — не отказ systemd-run, не стоп.
- **scope не создан** (systemd-run отказал rc≠0 до исполнения команды,
  в том числе после успешной пробы `-- true`) — сессия запускается
  напрямую БЕЗ потолка; пишется строка
  `БЕЗ ПОТОЛКА ПАМЯТИ — systemd-run --user --scope не создал scope`;
  следующая сессия — снова по основному правилу. Отказ — не нештатное
  завершение (счёт И-3 не растёт). Нет scope (нет user-bus) — сессия
  стартует без потолка, не останов: «ночью остановка = потерянные часы».
- **Свидетель факта исполнения** `$MARK.scoped` пишет префикс команды
  до `exec workshop`; его наличие = scope создан И команда исполнена.
  rc сессии неразличим с rc отказа systemd-run, поэтому различение —
  по факту исполнения, не по rc.

## Снятие временного сторожа (контракт 085 И-8)

До приёмки 085 на станции стоял временный cgroup-сторож
`orch-memcap` (три файла вне репо + systemd-юниты). После приёмки и
переноса потолка в orch-loop он снимается. Должны быть удалены
(под root):

- `/usr/local/sbin/orch-memcap` — исполняемый файл cgroup-сторожа.
- `/etc/systemd/system/orch-memcap.service` — oneshot-юнит переноса.
- `/etc/systemd/system/orch-memcap.timer` — таймер раз в минуту.

После `daemon-reload` оба юнита `orch-memcap` должны быть
`LoadState=not-found` и не активны. На их место встаёт
`ORCH_MEM_MAX` внутри `orch-loop` (см. выше). Временный сторож
ограничивал только omp; orch-loop от его cgroup не зависел, поэтому
потолок внутри orch-loop действует шире (на всю сессию omp).

## tmux (контракт 085, И-9)

Для работоспособности наблюдения (`tmux attach -t orch` под root
с последующим `su - harness`) и send-keys из orch-peak: `escape-time`

## Журналы и состояние

- `~/orch-loop.log` — вывод обёртки `orch-loop` под harness (старт/стоп
  сессии, маркер, перезапуск, обе строки потолка памяти).
- `/var/log/orch-peak.log` — вызовы `orch-peak` под root (warn/stop/start/ctx,
  send-keys в панель, маркер).
- `~/orch-peak-report.txt` — отчёт по несохранённому на момент stop'а
  (и принудительном перезапуске по контексту — «живые субагенты
  погибнут: <имена>» принудительно дописывается, не затирает основной
  отчёт).
- `/var/lib/orch-peak/{pane,state}` — состояние орк-peak (найденная
  панель tmux, прочие служебные файлы: `ctx-$sess`, `ctx-$sess.warned`,
  `idle`, `warned`).
- `journalctl -u 'orch-peak@*' -t systemd` — журнал systemd по юнитам
  orch-peak (запуск таймером).

## Включение/выключение

**Включить** (root): `systemctl enable --now orch-peak-warn.timer
orch-peak-stop.timer orch-peak-start.timer`. До этого однократно
`systemctl enable --now orch-peak-reenable.timer` (если пауза ещё не
включена).

**Выключить** (root): `systemctl disable --now orch-peak-warn.timer
orch-peak-stop.timer orch-peak-start.timer`. Не трогать `orch-ctx.timer` —
сторож контекста работает независимо от пиковой паузы.

**Стоп обёртки** (harness): `touch ~/orch-loop.stop` (или шов
`ORCH_STOP`) — следующая итерация цикла `orch-loop` снимет файл и
завершится с rc 0.

## Касание сессии (send-keys / гашение omp / маркер)

- **send-keys в панель** — `orch-peak` через `tmux send-keys -t $pane -l "..."
+ Enter` отправляет сообщения владельцу (warn, «всё закоммичено?»,
  подсказка перезапуска). Панель с циклом ищется `find_pane` (PID-дерево
  `orch-loop` ↔ tmux-панели), запоминается в `/var/lib/orch-peak/pane`.
  Каждое сообщение начинается `СТОРОЖ СТАНЦИИ (автоматически` и несёт
  `это НЕ слово владельца` (Н-200) — не путать со словом владельца.
- **гашение omp** — kill процесса `omp --profile` (pgrep по PID родителя
  orch-loop, дочерние через `pgrep -P`): SIGTERM с ожиданием, затем SIGKILL.
  Маркер при этом не ставится — цикл сам проверяет наличие процесса и при
  отсутствии выходит. `kill_session` ДО сигналов ставит стоп-файл цикла
  `ORCH_LOOP_STOP` (И-4д), чтобы цикл завершился «останов», а не «падение».
- **маркер** — `/tmp/dev-harness-verify/orch-restart`. Ставится
  ЕДИНСТВЕННОЙ дверью `scripts/orch_restart.sh` (контракт 072) либо
  сторожем контекста `orch-peak ctx` при CTX_HARD (после polling
  живых субагентов и атомарной записи отчёта о погибших — контракт
  080 инв. 8). Маркер против НОВОЙ сессии не ставится (Н-189). Обёртка
  `orch-loop` видит маркер, ждёт GRACE (20 с) и инициирует рестарт с
  чистым контекстом; новая сессия читает HANDOFF и продолжает автономно.

## Настройка станции (harness@148.251.131.204)

Параметры окружения, без которых обвязка не работает или работает не на ту
сессию:

- **Пользователь `harness` без sudo** — все root-операции (orch-peak,
  systemd-юниты, /var/log, /var/lib) делаются под root отдельным вызовом
  `sudo bash ops/server/install.sh root`; под harness sudo не нужен.
- **Rootless Docker** — `docker context` указывает на `rootless`; харнесс
  не нуждается в `/var/run/docker.sock`.
- **Node 26** — `node --version` начинается с `v26.`; `omp` запускается
  `node --enable-source-maps .../omp.js --yolo --profile dev ...`.
- **omp по пину** — версия `omp` зафиксирована в `package.json` (`omp`),
  без `^v` — никакого автоматического обновления.
- **Потолок памяти сессии** — `ORCH_MEM_MAX` (по умолчанию 32G) для
  systemd-run внутри orch-loop. Под harness `systemd-run --user --scope`
  требует работающего user-менеджера systemd (`Linger=yes`).
- **`gh` вход как a3ka** — `gh auth status` показывает `a3ka`; PR открывается
  `gh pr create`, токен берётся из `/home/harness/dev-harness/.env`
  абсолютным путём (`~/` гвардом переписывается).
- **`GITHUB_TOKEN` в `.env`** — файл `/home/harness/dev-harness/.env` хранит
  `GITHUB_TOKEN` для `gh`/`git push`; коммитится только `.env.example`.
- **Клоны `~/odelix/*`** — соседние каталоги `~/odelix/odx-stack`,
  `~/odelix/odx-rshnn`, и т. п. (по числу пилотных репозиториев), на них
  может указывать пилот A3 — обвязка не лезет в них сама, но `orch-loop`
  стартует `workshop --yolo` именно в текущем `~/dev-harness`.

## Установка из репо

```sh
# user-часть (под harness): ~/.local/bin/orch-loop, режим 755
bash ops/server/install.sh user

# root-часть (под root): /usr/local/sbin/orch-peak + 7 юнитов /etc/systemd/system/
sudo bash ops/server/install.sh root

# сверка установленного с репо (любой пользователь, только читает):
# rc 0 + «сверка: 9/9» — установленное == репо; rc != 0 — зовёт файл по имени.
bash ops/server/install.sh verify
```

Шов `OPS_SERVER_SRC` (умолчание — каталог скрипта) позволяет подставить
другой источник; `OPS_SERVER_BIN_DST`, `OPS_SERVER_SBIN_DST`,
`OPS_SERVER_ETC_DST` — другие адресаты (тесты, песочница). Шов
`OPS_SERVER_MAIN` (081) указывает на корень основного чекаута, чей
`.git/config` запирается `chattr +i` (по умолчанию
`/home/harness/dev-harness`).

## Пользователь агента (контракт 093, И-3)

Автономная сессия запускается под ОТДЕЛЬНЫМ uid агента (по умолчанию
`orchagent`, HOME — `/var/lib/orch-agent`), а не под uid владельца
`/home/harness`. Это даёт изоляцию от контрольных файлов станции
(`~/.ssh/github-rw-cwd`, `~/.config/omp/*`, живое состояние
`$UHOME/.local/state/dev-harness-sessions/**`, `/var/lib/orch-peak/**`)
и от публикационного ключа (Н-196). HOME сессии — вне `/home/harness`:
credent публикации в среде сессии НЕ доступны, `GIT_SSH_COMMAND` с
rw-identity не строится.

Швы `ORCH_AGENT_USER` / `ORCH_AGENT_HOME` (или эквивалентные
`ORCH_LOOP_AGENT_USER` / `ORCH_LOOP_AGENT_HOME`) переопределяют
идентичность агента в тест-мире. По умолчанию цикл требует, чтобы
пользователь `orchagent` и каталог `/var/lib/orch-agent` существовали
на станции (создаются один раз владельцем sudo, не обвязкой).

Публикация — ТОЛЬКО через установленную дверь под другим
пользователем; агенту ключ публикации НЕ доступен.

## Проверка старта юнита (контракт 093, И-6a)

Установка корневой части (`install.sh root`) завершена ⟺ поставленный
юнит реально стартует и активен. Отдельная подкоманда `verify-start`
проверяет это живой командой `systemctl is-active`:

```sh
sudo bash ops/server/install.sh verify-start
# rc 0: "установлено и активно: orch-peak@0"
# rc 1: "юнит не стартует: orch-peak@0 (состояние: …)" — отказ
```

Швы `OPS_SERVER_UNIT` (умолчание `orch-peak@0`) и
`OPS_SERVER_SYSTEMCTL` (умолчание `systemctl`) позволяют указать
другой юнит и путь к systemctl (тест-миры с shim'ом).

## Откат установленной версии (контракт 093, И-6b)

Подкоманда `rollback` побайтно восстанавливает предыдущую установленную
версию из `${OPS_SERVER_ROLLBACK_BACKUP-/usr/local/sbin/.rollback}/` —
каталог, куда `install.sh root` сохраняет предыдущие копии (создаётся
при первой установке). Откат САМ выполняет `systemctl daemon-reload`
и `systemctl restart` (находка 2 круга 2: без daemon-reload юнит
остаётся на старой версии в памяти демона) — никакого `install`
между откатом и наблюдением не требуется.

```sh
sudo bash ops/server/install.sh rollback
# rc 0: "откат выполнен: orch-peak + 7 юнитов из /usr/local/sbin/.rollback"
# rc 1: именованный отказ (нет каталога, расхождение, euid≠0)
```

Живая последовательность без маскировки:

```sh
# v1: установка (сохраняет текущее как .rollback)
sudo bash ops/server/install.sh root
# v2: правка + установка (тот же каталог, новая версия)
# …
# откат: восстановление v1 побайтно + reload + restart
sudo bash ops/server/install.sh rollback
# активен ИМЕННО v1 (sha256 = пин v1)
sudo bash ops/server/install.sh verify-start   # rc 0
```

Шов `OPS_SERVER_ROLLBACK_BACKUP` (умолчание `/usr/local/sbin/.rollback`)
переопределяет каталог предыдущей версии.

## Обслуживание .git/config (снятие/возврат +i)

Контракт 081 запирает общий `<OPS_SERVER_MAIN>/.git/config` ядром ФС
(`chattr +i` ставится root-частью `install.sh root` после копии+sha256
и проверки предусловий). Защита держится, пока атрибут `i` стоит; снять
и вернуть его может ТОЛЬКО root (или процесс с CAP_LINUX_IMMUTABLE) —
обычные сессии получают EPERM на любую запись в config. Между снятием
и возвратом защита отсутствует, поэтому порядок строгий, и каждый
шаг подтверждается прогоном детектора.

Процедура обслуживания (например, добавить новый remote, сменить
`branch.<name>.remote`):

1. **Снять** атрибут (root):
   `chattr -i <OPS_SERVER_MAIN>/.git/config`.
2. **Внести правку** обычным `git -C <OPS_SERVER_MAIN> config …` или
   редактором — теперь запись в общий config проходит.
3. **Вернуть** атрибут (root):
   `chattr +i <OPS_SERVER_MAIN>/.git/config`.
4. **Подтвердить** зелёный детектор — пока атрибут снят, детектор
   красен по ноге (а) «+i отсутствует»; возврат подтверждается прогоном,
   а не словом:
   `bash scripts/check_git_config_immut.sh <OPS_SERVER_MAIN>`.
   rc 0 — защита на месте; rc 1 — диагностирует именованную причину
   (нет `i` / `extensions.worktreeConfig` / `config.worktree существует`).

Если после снятия и правки забыли вернуть `+i`, детектор поймает это на
следующем прогоне церемонии (нога (а) «+i отсутствует»). Сам
`install.sh root` при переустановке требует `core.hooksPath=.githooks`
и `branch.autoSetupMerge=false` уже в config — после снятия атрибута
эти записи тоже могут быть обновлены тем же путём, после чего
`install.sh root` снова поставит `+i` (вызвать его под root).

## Чего обвязка НЕ делает

- Не коммитит и не пушит в репо (только проверяет «всё ли закоммичено» в
  `stop`).
- Не открывает PR и не зовёт владельца напрямую — только `send-keys` в
  панель tmux (сообщения подписаны `СТОРОЖ СТАНЦИИ (автоматически`).
- Не редактирует `~/odelix/*` (обвязка знает только `~/dev-harness`).
- Не сжимает роль и не перезапускает сессию изнутри майлстоуна — это
  решение оркестратора после `done` пары майлстоунов.
- Не считает общий OOM хоста: tmux-scope с циклом может пасть как
  17:57 (вне scope); потолок 085 защищает только omp-сессию.
- Не различает OOM omp и внешний SIGKILL без маркера — оба дают ветку
  И-3б (падение) и при scoped-сессии — строку И-5б.
