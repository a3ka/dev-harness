## НОВЫЙ БЛОКЕР (тот же класс A-098-2): предъявлено 1 из 3 полей происхождения — полевые обходчики проходят всё

Вердикт адверсария требует предъявление «НОВЕЙШИЙ ЗЕЛЁНЫЙ одноимённый прогон чужого происхождения (**app.slug≠ciApp / wfsha≠принятой / head_sha≠M**)» поверх валидной зелёной истории. Клетка предъявляет ТОЛЬКО вариант `app.slug≠ciApp` (`_d98_ci_add … "ci-a:success:@foreign-ci"`, jq-проверка мира сама фиксирует: `.app.slug != $app` ПРИ `.wfsha == $w` И `.head_sha == $m` — расходение ровно в одном поле). Чужие wfsha/head_sha предъявляются в других клетках ТОЛЬКО одиночно (ответ перезаписан: `red_odnoimennoj:39,49`, `red_progon_ne_togo:35-36`) — валидного прогона под ними нет, отступаться не к чему, полевой обходчик ведёт себя честно.

Собраны два обманщика тем же методом, что и M7 (отличие от честной модели — ТОЛЬКО `best=`): M11wfsha (отступление к старому валидному только при `wfsha≠w` у новейшего зелёного) и M11head (только при `head_sha≠m`). Живьём на ПОСЛЕ (`2e41b63e`):

## Что требуется от архитектора

Предъявить ОСТАЛЬНЫЕ ДВА поля происхождения на той же базе «валидная зелёная история + НОВЕЙШИЙ зелёный»: (а) чужая wfsha при доверенных slug/head_sha → отказ «проверка не доверенной версии: ci-a» rc 1 без строки; (б) чужой head_sha при доверенных slug/wfsha → отказ «прогон не того коммита: ci-a» rc 1 без строки (построение — как в `red_progon_ne_togo_kommita:35-36`, но БЕЗ перезаписи валидной истории под ним); в обоих — дверь без строки, main неизменен, и парный позитив (ok с run НОВОГО прогона, публикация M). Форма — расширение новой клетки циклом по трём полям или две новые клетки; стаб-пак — по стабу на поле (привязка в коде, якорь РОВНО один), замер синхронизировать. До этого критерий пропускает полевых «переборщиков».
