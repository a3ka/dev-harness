## Б1. Предъявления признания судят не того автора

БЛОКИРУЕТ contracts/031-strazh-semejstvo-mint-i-bazlajn.md:212 — в11/в12 объявлены предъявлениями коммитов orchestrator, но оба создают коммиты автора `Фикстура`; требуемое признание orchestrator ими не различается.
ОБХОД: реализовать staged-дверь и retake правильно, а в `check_zones` добавить только обработку манифестных коммитов автора `Фикстура`: валидные добавления разрешать, правку существующей строки отвергать с именем пути. Признание для настоящего orchestrator оставить отсутствующим. Тогда в11 получает rc 0, в12 — rc 1 с требуемым именем, остальные новые ворота эту подмену автора не упражняют; первый настоящий минт orchestrator по-прежнему красит CI. Это контрреализация критерия [INFERENCE], а ошибочное авторство предъявлений подтверждено исполнением.

Причина — не догадка об identity. В
`fixtures/check_staged/red_dver_minta_orkestratora.sh:441,473` коммиты идут
через `g`. Этот помощник в `fixtures/check_staged/_repo.sh:19` передаёт
`-c user.name=Фикстура -c user.email=fixture@local`; предшествующий
`set_author ... orchestrator` меняет локальный конфиг, который эти параметры
перекрывают.

В одноразовой пробе исполнены построения в11 и в12 из предъявленного файла
против настоящего `check_zones`, отдельно от ранней остановки red-файла:

```text
в11: author=<Фикстура>, check_zones rc=0, проверено по зонам: 0
в12: author=<Фикстура>, check_zones rc=0, проверено по зонам: 0
в11 после смены только автора последнего коммита на orchestrator:
check_zones rc=1
FAIL коммит вне зоны: orchestrator ... registry/contracts.tsv
```

Следовательно, в11 **сегодня уже зелёный без реализации**, вопреки :213–214.
В12 сегодня тоже не предъявляет заявленный отказ: rc 0 вместо rc 1.
Исправление реализации под такие входы способно закрепить ошибочную границу
автора вместо требуемого признания.

Достаточное закрытие — предъявления с проверенным фактическим `%an = orchestrator`
в судимых коммитах: честный минт сегодня красный, после реализации зелёный;
не-минтная дельта того же пути красная до и после. Требование не назначает
стабам ветви: привязка остаётся у архитектора по коду.

## Б4. Ненулевой отказ читателя всё ещё не предъявлен

БЛОКИРУЕТ contracts/031-strazh-semejstvo-mint-i-bazlajn.md:133 — контракт теперь правильно различает `zones_load rc ≠ 0` и `rc 0 + отсутствие судейских зон`, но р9 на :237–241 упражняет только второе состояние. Первое обязательное условие по-прежнему не имеет различающего входа.
ОБХОД: на успешном вызове `zones_load` честно запрещать пустой реестр, а при ненулевом rc разрешать переснятие закоммиченного пути `verdicts/review/*` автора reviewer по запасному префиксу или кэшу. Р0–р8 работают с доступным реестром; р9 даёт rc 0 и пустой результат, поэтому эта контрреализация проходит все десять ворот. На реальном `missing-remote`, где `zones_load` возвращает 2, она переснимает базлайн без доказанного авторитета зон. Контрреализация — [INFERENCE]; различие двух состояний воспроизведено живой библиотекой.

Р9 действительно создаёт полезный новый вход — это не плацебо само по себе.
Однако **отказ на пустом успешном результате не доказывает отказ на ошибке**.
Проверено в двух отдельных toy-репозиториях:

```text
р9, chmod 000 .git/refs/tags:
  zones_load rc=0
  zones_scoped: 0 байт
  --check rc=1: verdicts/review/blind.md

origin несёт frozen/contracts/002/1, отсутствующий локально:
  zones_load rc=2
  NOT_IMPLEMENTED: реестр заморозок недоступен: missing-remote
  porcelain=<>
  --check rc=1: verdicts/review/unavailable.md
```

Во втором случае origin настроен до снимка, вердикт закоммичен reviewer
после снимка, дополнительный frozen-тег создан только на origin. Поэтому
отказ читателя не подменён грязным porcelain или второй дельтой рабочего дерева.

Достаточное закрытие — отдельное rc-предъявление ненулевого отказа настоящего
читателя: retake возвращает 1 с именем «реестр зон недоступен», снимок не
меняется, последующий check остаётся красным. Р9 следует сохранить как другую
ветвь. Утверждение :241, что р9 убивает любой запасной путь «при отказе
читателя», неверно именно для названного обхода. По Н-39 контракт должен
нести инвариант и rc-наблюдение, а не назначать этому входу обманный стаб.
