## Закрытие Б2 — новизна не исчезает после пред-фризового коммита

Проверен настоящий `scripts/next_id.sh`, не имитация его вывода. В отдельном
toy-репозитории:

1. Коммит основания → `next_id.sh <toy> CONTRACT` выдаёт `001` и тег.
2. После минта закоммичен `scripts/new_parser.sh`, заморозки ещё нет.
3. `git cat-file -e HEAD:scripts/new_parser.sh` → **0**.
4. `git cat-file -e 'id/CONTRACT/001^{commit}:scripts/new_parser.sh'` → **128**,
   путь отсутствует именно в дереве минта.
5. `git merge-base --is-ancestor 'id/CONTRACT/001^{commit}' HEAD` → **0**.

Таким образом обход v1 «штатно предъявить код до заморозки и перестать
считаться новым» новым определением не допускается. База действительно
раньше пред-фризового кода и не движется вместе с HEAD.

### Запрошенная проверка отсутствующего / пересозданного тега

В тексте 041 отдельного fallback нет. Нельзя молча заменять отсутствующий
тег текущим HEAD или считать неизвестную новизну отсутствием нового гарда.
Однако отсутствие fallback само по себе не предъявляет обход: старшие
правила уже требуют механизм выдачи номера и согласованность реестра.

Проверено двумя разными мерами:

* На минимальном toy `check_ids.sh <toy>`: честный тег → **0**; удалённый
  тег при живом контракте → **1**, `номер 1 назначен рукой, а не механизмом`;
  пересозданный тег над более поздним деревом → **0**. Последнее важно:
  **один check_ids не доказывает неизменность базы**. Прямой `cat-file`
  после переноса тега видит гард в базе, rc **0**, вместо исходного **128**.
* На отдельном toy со штатным манифестом 031 и активным окном зон:
  основание с `frozen/contracts/001/1`; реальный `next_id` выдаёт `002`;
  orchestrator коммитит `002 → <исходный tag-object-sha>`;
  implementer коммитит новый гард в своей зоне `scripts/`;
  architect коммитит draft 002. `check_zones.sh <toy>` → **0**.
  Удаление тега → **1**, `дверь минта 031: тег id/CONTRACT/002 не жив локально`.
  Пересоздание тега над деревом с гардом → **1**,
  `дверь минта 031: sha строки ≠ tag-object-sha живого тега`.
  Восстановление исходного tag-object через `update-ref` → **0**.

Все удаления/пересоздания были только в созданных мной toy-репозиториях;
теги судимого клона и основного репозитория не менялись. Номер, никогда не
выданный механизмом, не является законным альтернативным способом ввода
будущего контракта по AGENTS.md, правило 5 и шаг 1 workflow. Отсутствие
локального тега требует восстановления регистра, а не смены определения
«новый». Гарантию неизменности нельзя приписывать одному существованию ref;
совет С1 точно называет эту границу.

## Пять обязательных вопросов

1. **Критерий слабее предмета?** Предъявленный в v1 имитатор сохранения
   данных теперь отвергается. Область нормы больше не самоуничтожается от
   штатного предъявления кода. Нового действительного обхода не найдено.
2. **Готовность доказуема?** Изменённые критерии проверены исполнением:
   честный/обманный гард, обе батареи, self-application, оба preflight.
   Р15 — проверяемый rc-инвариант с конкретизацией по коду, не навязанная
   реализация стаба; факт отдельных демонстраций предыдущего круга не
   переименован здесь в новый прогон. Смысл модели угроз остаётся явно
   cognitive-only, а не выводится из кода возврата.
3. **Что оставлено исполнителю?** Способ построения стаба законно остаётся
   автору живой демонстрации. Неявность восстановления mint-базы отмечена
   С1 с существующим внешним барьером; не требует нового алгоритма 041.
4. **Границы?** `:226` называет architect и все предметные роли, гард,
   обе семьи, агрегат. Зоны не расширены v2; по-прежнему проверяются
   `check_zones.sh`. Префризовое draft-признание не даёт зоны всему коду.
5. **Старшая норма?** Противоречие Р15 из v1 устранено. Норма не добавляет
   кап кругов, не меняет AGENTS.md, не правит ретроактивно 038. Нового
   противоречия, достаточного для FAIL, не установлено.
