## Новые дефекты

### 1. `verify_consultant.sh` допускает основание вне `--root`

В одноразовом игрушечном git-корне создан внешний файл `../outside.txt`; честная
тройка ответа `КОМАНДА: cat ../outside.txt`, `RC: 0` и sha256 его содержимого
принята барьером (`rc=0`). Затем внешний файл был достигнут через содержимое
проверяемого дерева: симлинк `evidence-link -> ../outside.txt` и честная тройка
`КОМАНДА: cat evidence-link` также принята (`rc=0`).

Это не PATH/TCB-находка: именно ответ и содержимое дерева выбирают объект,
который барьер читает и по которому выносит зелёный вердикт. Запуск «в каталоге
ROOT» не является границей для абсолютных, `..`- и симлинк-путей. Тем самым
`ОСНОВАНИЕ-ДЕРЕВО` может быть честным ответом о чужом файле, а не о дереве
`--root`; Г1–Г5 этого не судят. Требуется fail-closed граница аргументов файловых
операндов относительно `--root` (включая резолв симлинков) либо исключение таких
операндов из интерфейса.

Воспроизведение: `bash /tmp/dev-harness-verify/adv029r4/scope-probes.sh` →
`scope-escape: both traversal and tree symlink accepted`, `rc=0`.

### 2. Неработающий `git` в `check_fork_route.sh` даёт зелёный `rc=0`

На конформном журнале подставлен `git`, который разрешается `command -v`, но
немедленно выходит `1`. Маршрутный барьер вернул `rc=0`. Его проверка `git` —
только `command -v`; далее этот инструмент вообще не вызывается. Это нарушает
заявленную семантику обоих барьеров «нет git → rc=2» и требование круга проверить
другие формы неработоспособного инструмента. Это не довод об исполнении кода из
caller-PATH: подмена использована только как воспроизводимая симуляция
неработоспособного prereq.

Воспроизведение: `route-broken-git rc=0 text=` в
`bash /tmp/dev-harness-verify/adv029r4/rc-probes.sh`.

### 3. Неработающий `cat` в `verify_consultant.sh` даёт зелёный `rc=0`

Обёртка `cat` вывела без изменений честный файл ответа, затем вышла с `1`.
`RESP="$(cat "$OTVET")"` сохраняет текст, но его код возврата не проверяется;
барьер продолжил проверку и завершился `rc=0`. Поздняя проверка наличия
`/usr/bin/cat` не проверяет тот вызов, которым реально прочитан ответ. Это та же
непривязанная rc-семантика инструмента в иной утилите, прямо затребованная кругом;
сломанный инструмент обязан дать `rc=2`, а не принять вердикт.

Воспроизведение: `verify-broken-cat rc=0 text=` в
`bash /tmp/dev-harness-verify/adv029r4/rc-probes.sh`.

До исправления этих трёх путей круг 4 не принимает предмет.
