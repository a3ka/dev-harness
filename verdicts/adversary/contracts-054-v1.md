## Финальные канонизационные векторы

Отдельная временная проба строила честный toy repo/layer и запускала реальный
`scripts/profile_resolver.sh`.

```text
PASS internal-relative-symlink
PASS internal-absolute-symlink
PASS symlink-farm-inside-35
PASS symlink-farm-outside-35
PASS proc-self-fd-external
PASS proc-self-fd-inside
PASS missing-readlink-127-fail-closed
BYPASS tocou-swap-external: rc=0, canonical check saw in-repo file then jq merged external repoId=r_external
CLASS hardlink-external-alias: rc=0, alias is not pathname-observable as a symlink
```

* Относительная ссылка внутри repo и абсолютная ссылка на файл внутри repo
  законно дают `rc=0`.
* Ферма из 35 внутренних ссылок законно даёт `rc=0`; такая же ферма с внешней
  финальной целью даёт `rc=1` с P-фразой. Цикл не нужен для обхода: `readlink
  -f` на нём даёт пустой канон и тот же отказ.
* `/proc/self/fd/9`, открытый на внешний профиль, отклонён именованно; тот же
  носитель, открытый на внутренний файл, принят (`rc=0`).
* При отсутствии `readlink` в `PATH` команда возвращает 127, но пустой
  канонический результат не принимается: резолвер заканчивает `rc=1` с P-фразой.
* Внешний hardlink-алиас принимается. Это класс
  **неотличимого hardlink-внешнего алиаса**: у hardlink нет цели и на входе
  `harness.project.json` является обычным pathname внутри repo; `readlink -f`
  не может установить владельца другого имени того же inode. Контракт требует
  «не symlink на внешний файл», а не provenance inode, поэтому без нового
  инварианта это не блокер.

## Круг 4 — исполнимый TOCTOU-обход (блокер)

Проба начала с валидного обычного
`<repo>/harness.project.json` (`repoId=r_internal`). Shim `readlink` сначала
передал реальный вывод `/usr/bin/readlink -f` без подмены результата. Сразу
после этого единственного канонического чтения он атомарно заменил проверенный
путь symlink на полностью валидный внешний JSON (`repoId=r_external`). Это
детерминированная оркестрация момента между строками 136 и 149 резолвера, а не
ложный ответ `readlink`.

`case "$REPO_JSON_ABS"` уже принял прежний внутренний pathname; последующий
`jq -e . "$REPO_JSON"` разыменовал новую внешнюю цель. Реальный резолвер
вернул `rc=0`; merged JSON содержал `repoId.value = "r_external"`. Так
внешний владелец снова поставляет `commands`, CI, remote, barriers и pin после
заявленной проверки границы.

Требуемое закрытие — привязать проверку и чтение к одному уже открытому inode:
открыть repo-layer один раз, канонизировать `/proc/self/fd/<fd>` (либо
эквивалентно проверить открытый дескриптор) относительно `REPO_ABS`, и все
`jq`-чтения выполнять через тот же дескриптор. Проверка pathname с последующим
повторным открытием не закрывает этот интервал. Нужна отдельная красная клетка,
которая заменяет файл строго после канонизации и требует именованный отказ,
а также зелёный контроль для неизменённого внутреннего файла.
