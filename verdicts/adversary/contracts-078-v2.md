В качестве дополнительной пробы я проверил `timeout 10s git`. Он также возвращает `rc 1` с красной `л21` (плюс тем же отказом применения СТАБ-Т из-за исчезнувшего якоря); занижение границы не проходит.

## Принятый проверкой новый обход: timeout fail-open в mint и freeze

Я построил обманный субъект без изменения библиотеки, таймаута или батареи. В `mint_line.sh` и `freeze_contract.sh` непосредственно перед сохранённой fail-closed ветвью добавлено ровно:

```sh
if [ "$active_rc" -eq 124 ]; then active_rc=0; fi
if [ "$active_rc" -ne 0 ]; then
```

То есть обычные отказы `active_contracts_list` (включая проверяемый сегодня rc=1 от PATH-шима) по-прежнему останавливают операцию, но timeout-результат библиотеки (`rc=124` внутри диагностируемой причины) ошибочно переводится в успешный пустой список. В реальном timeout-сценарии такой субъект продолжит mint/freeze при неизвестном множестве активных контрактов: `mint_line` создаст запись, `freeze_contract` создаст тег/реестр. Это прямой fail-open И-2 только для двух писателей.

Полный живой запуск против этого мутанта:

```sh

```

дал **`rc 0`** и итог **`красных 0, зелёных 75, не исполнено 0`**. Мутант сохраняет исходные строковые якоря Фм/Фф/Т, так что применения, диффпробы и нарушения стаб-пака тоже зелёны: это не обход через отключение проверки.
