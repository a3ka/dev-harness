# Адверсарий 078 — ограниченный timeout, круг 4

Предмет: `wip/078/implementer` на `c19ad80ba098e2d56d9d4c24f77d6918e35ab5bf`; контракт остаётся `frozen/contracts/078/1`. Замороженный `contracts/078-limit-aktivnyh-kontraktov.md` не менялся.

## Позитивный контроль

```sh
bash fixtures/_krasnye_078.sh
```

На честном предмете: `rc 0`, итог `красных 0, зелёных 89, не исполнено 0`. Тем самым живы новые SLA-клетки `л23`–`л26`, а также применяемость, диффпробы и нарушения стабов `124м`/`124ф`.

## Прежний обход timeout fail-open

Я воспроизвёл обход из v2 отдельным мутантным предметом. В `lib_active_contracts.sh` ветвь сетевой ошибки была изменена с `return 1` на дословное `return "$ls_rc"`; в `mint_line.sh` и `freeze_contract.sh` непосредственно перед сохранённой fail-closed ветвью добавлено:

```sh
if [ "$active_rc" -eq 124 ]; then active_rc=0; fi
if [ "$active_rc" -ne 0 ]; then
```

Это именно составной прежний обход: при 17-секундном делегирующем PATH-шиме `timeout` даёт `124`, библиотека передаёт его писателю, а писатель считает неизвестное множество успешным пустым и делает запись.

```sh
bash fixtures/_krasnye_078.sh /tmp/dev-harness-verify/adv078k4/mutant-composite
```

Дал `rc 1`, `красных 9, зелёных 80, не исполнено 0`. Главное наблюдение: `л24` красная с `rc=0`, `MINTED`, одной строкой реестра и диагностикой исходного `rc=124`; `л26` красная с `rc=0`, `v1` и созданным тегом/реестром. Значит требуемые клетки ловят именно реализацию fail-open, а не только статический маркер. Остальные семь красных — следствие того, что батарея намеренно строит свои субъектные стабы из уже испорченной библиотеки; они не ослабляют самостоятельные наблюдения `л24` и `л26`.

## Наивный потребительский гаситель — самостоятельно проверен

Проверил утверждение архитектора не по коду, а живым 17-секундным PATH-шимом `git` против немодифицированной `active_contracts_list`. Вызов напечатал:

```text
ОТКАЗ: лимит активных контрактов: авторитет недоступен (ls-remote origin rc=124), данные неизвестны — fail-closed
```

и завершился `rc 1`, а не `124`. Это соответствует реальной ветви `return 1` библиотеки.

Затем я добавил только `active_rc=124 → 0` в обоих потребителях, не меняя ядро, таймаут или батарею. Полный запуск дал `rc 0`, `красных 0, зелёных 89, не исполнено 0`: гаситель действительно не срабатывает на реальном `rc=1` и потому этот наивный субъект не является обходом.

## Потребительский обход по реальному признаку timeout

Проверен более сильный вариант без ядерной правки: каждый потребитель перенаправляет stderr `active_contracts_list` во временный файл, сохраняет настоящий `active_rc=1`, но при литеральном `ls-remote origin rc=124` в диагностике ставит `active_rc=0`, возвращая stderr пользователю перед продолжением. Он использует действительный rc и timeout-специфичный признак, а не нежизненный `active_rc=124`.

Батарея запущена на этом мутанте без изменения fixtures. Повторный последовательный запуск дал `rc 1`, `красных 6, зелёных 83, не исполнено 0`; его ошибочный mint/freeze на 17-секундном входе делает `л24`/`л26` красными (успех и мутация там, где требуются `rc 1` и отсутствие записи). Следовательно, путь распознавания timeout через stderr также не проходит проверку.

## Дополнительная собственная проба: нейтрализация инструмента timeout

В отдельном мутанте внутри `active_contracts_list` определена shell-функция:

```sh
timeout() { shift; "$@"; }
```

Она сохраняет командную строку `timeout 15s git …`, но фактически снимает SLA-ограничение. На 17-секундном shim авторитет отвечает поздно и все три операции ошибочно продолжаются.

```sh
bash fixtures/_krasnye_078.sh /tmp/dev-harness-verify/adv078k4/mutant-shadow-timeout
```

Дал `rc 1`, `красных 8, зелёных 81, не исполнено 0`; среди самостоятельных предметных клеток красны `л22`, `л24` и `л26`: номер выдан, mint сделал строку, freeze создал `v1` вместо требуемого fail-closed `rc=124`. Значит нейтрализация вызываемого timeout не проходит.

## Неблокирующее наблюдение о воспроизводимости батареи

В первом прогоне stderr-мутанта генератор выбрал `SEED=999`. Это независимая от мутанта ошибка тестовых данных: `random.sample(range(985, 1000), 12)` допускает 999, а `next_id.sh` корректно отказывает следующий номер 1000. Поэтому тот запуск имел посторонние ложные красные. Повторный последовательный запуск выше выбрал допустимый seed и подтвердил целевые `л24`/`л26`.

Это не путь к ложному зелёному и не меняет данного ACCEPT по timeout-обходу, но делает батарею случайно ложно-красной с вероятностью 1/15; её пул стоит отдельно ограничить максимумом 998. Предмет, frozen-контракт и fixtures этим вердиктом не правились.

## Вердикт

Ни один проверенный неверный субъект не получил зелёный результат. В частности, новые `л24`/`л26` наблюдают прежний составной timeout fail-open, а также вариант на реально возвращаемом `rc=1` с распознаванием timeout по stderr. Новой дыры той же timeout-причины нет, поэтому повода для арбитража по повтору причины нет.

Вердикт: **ACCEPT**.
