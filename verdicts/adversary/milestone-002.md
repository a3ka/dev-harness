**Место:** `scripts/check_decisions.sh:127-129, 160-218`; нарушены контракт 002, критерий 2 и раздел «Перечень семи решений» (реестр содержит ровно 001–007; лишний файл обязан вернуть 1).

Сырой вывод:

Это прямо расходится с комментарием самого барьера: «лишний файл — отказ». Заглушка вводит новый всеохватный прецедент и получает зелёный; должна была упасть с кодом 1 и путём `decisions/008-proizvolnyj.md`.

### 2. «Грамматика даты» сводится к непустой строке

**Класс:** зашитая неполная проверка поля.

**Место:** `scripts/check_decisions.sh:145-168`; нарушен контракт 002, критерий 2: запись обязана быть в объявленной грамматике, включая дату.



Парсер собирает текст после `дата:`, а цикл проверяет только его непустоту; формата даты нет. Непригодная для порядка прецедентов дата проходит. Должен быть код 1 с именем записи и поля `дата`.

### 3. Обещанная фикстура поведения `always-ask` отсутствует

**Класс:** нейтрализация проверки.

**Место:** контракт 002, критерий 1 («правка без подтверждения не проходит (фикстура)»); `fixtures/`, `package.json`, `.github/workflows/ci.yml`.

В `fixtures/` есть группы для 17 проверяемых механизмов, но нет фикстуры или проверяющего сценария для `workshop`/`approvalMode`; в `package.json` нет команды такого сценария, а CI запускает лишь `check:gen`, статические барьеры и их фикстуры. Поэтому удалить из `workshop` политику подтверждения либо передать запуску конфиг без `always-ask` не имеет красного контрпримера.

Статическая часть действительно присутствует и генератор её не трогает: в чистом клоне `tools.approvalMode: always-ask` был сохранён побайтно после `npm run gen:harness` (`обновлено файлов: 0`). Это не заменяет обещанную фикстуру поведения лаунчера: конфигурация может лежать в файле, который живой запуск не читает. Должен существовать положительный контроль и подставной запуск, где действие записи без подтверждения возвращает отказ; сейчас такого гейта нет.
