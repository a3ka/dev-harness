## Проверенные неблокирующие направления

### Малый cap без знания новых N

Построен отдельный стаб `check_threat_model.sh`, который честно выполняет проверки формы, но ограничивает каждый напечатанный счётчик буллетов `min(фактическое_число, 3)`. Он не требует знания текущих `N=6/5/4`.

- `npm run check:threat-model-selftest` на таком стабе зелёный: 10/10 case-файлов.
- `bash fixtures/parsing_hygiene_battery/run_battery.sh check_threat_model` на нём красный (`rc 1`): `delimiter-collision — ПРОБИТ`, итог `3/4`. Генерируемый вход `6/5` ожидает строку счётчиков, собранную из тех же переменных, поэтому стаб с cap=3 пойман.

Следовательно, структурный фикс действительно ловит общий малый-cap обход; эта часть не является находкой.

## Независимое чтение реализации для произвольного N

`check_threat_model.sh` читает файл в `all_lines` через `mapfile`, собирает тело в `section_lines`, а `collect_bullets` добавляет каждую строку в `BULLETS`; затем оба списка копируются в независимые массивы и обходятся по фактической длине. Фиксированного верхнего предела или join+split структурных данных нет. Встроенный Python `text.split()` применяется только к одному тексту буллета для подсчёта слов порога, а не к представлению списка.

`check_provodka.sh` собирает каналы в `channel_lines`, затем раскладывает каждую строку параллельно в `channel_kinds`, `channel_rests`, `channel_lns`; проверки обходят `for ((i=0; i<${#channel_kinds[@]}; i++))`. Фиксированной границы длины и внутренней delimited-строки для каналов нет. Следовательно, обе честные реализации структурно работают для произвольного N; находка относится к недостаточности конкретного negative control, а не к join+split или cap в самих guards.
