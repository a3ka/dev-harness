## Находки

### 1. Резервацию можно удалить, и номер выдаётся повторно

**Файл и строки:** `scripts/next_id.sh:27-29, 205, 273-275`.

Шапка обещает, что номер с существующим тегом не выдаётся «НИКОГДА». Но `id/<КЛАСС>/<NNN>` — обычный локальный ref: `git tag -d` его удаляет, после чего источник максимума пуст для этого номера, а скрипт снова создаёт тот же тег. Ни запрета удаления, ни удалённого append-only регистра, ни записанной границы «теги должны быть защищены» нет.

Команда:

```sh
cd ./tmp/ids2/repo
git config user.name 'Adversary Round 2'
git config user.email 'adversary-round2@local'
bash scripts/next_id.sh PLAN
git tag -l 'id/PLAN/*'
git tag -d id/PLAN/007
bash scripts/next_id.sh PLAN
git tag -l 'id/PLAN/*'
git tag -d id/PLAN/007
```

Сырой вывод:

```text
007
id/PLAN/005
id/PLAN/006
id/PLAN/007
Deleted tag 'id/PLAN/007' (was b88f341)
007
id/PLAN/005
id/PLAN/006
id/PLAN/007
Deleted tag 'id/PLAN/007' (was b88f341)
```

Это дефект правила, а не удобства Git: история выдачи должна не позволять второе значение того же номера. Граница не записана и ничем не удержана.

Это повторяет **причину уровня правила** из первого круга, находка 6 (`разрешённое удаление освобождает номер`): регистр выдачи допускает стирание уже выданного номера. Технический носитель изменён (раньше исчезал файл, теперь удаляется тег), но инвариант «выданное нельзя освободить» всё ещё не держится; две стороны должны не считать это закрытым тем же объяснением.

### 2. «Атомарный» тег атомарен только внутри одного `.git`; два клона получают 007 одновременно

**Файл и строки:** `scripts/next_id.sh:205, 273-275`.

`git tag` не является общей резервацией между независимыми клонами. Скрипт не получает и не публикует ref на общем сервере, поэтому оба обычных получателя видят одинаковый последний тег и локально успешно создают свой `id/PLAN/007`.

Команда:

```sh
cd ./tmp/ids2/repo
# shared-origin.git — bare-копия предмета; issuer-a и issuer-b — свежие клоны от неё.
bash scripts/next_id.sh /home/aka/Documents/dev-harness/tmp/ids2/issuer-a PLAN >../issuer-a/out 2>../issuer-a/err &
bash scripts/next_id.sh /home/aka/Documents/dev-harness/tmp/ids2/issuer-b PLAN >../issuer-b/out 2>../issuer-b/err &
wait
printf 'a='; cat ../issuer-a/out
printf 'b='; cat ../issuer-b/out
printf 'a-tag-007='; git -C ../issuer-a tag -l 'id/PLAN/007'
printf 'b-tag-007='; git -C ../issuer-b tag -l 'id/PLAN/007'
printf 'errors-a='; cat ../issuer-a/err
printf 'errors-b='; cat ../issuer-b/err
```

Сырой вывод:

```text
a=007
b=007
a-tag-007=id/PLAN/007
b-tag-007=id/PLAN/007
errors-a=errors-b=
```

Это прямой дубль, если получатели — разные рабочие клоны (обычное значение слова «параллельные» для Git). Локальная блокировка ref не заменяет общую атомарную резервацию. Это не та техническая причина, что находка 1 первого круга (там следа не было вообще): след есть, но он не общий.

### 4. Сверка принимает четырёхзначный `0007-x.md` как корректный выданный трёхзначный 007

Контракт выдачи и её предел — ровно три цифры. Но проверка нормализует любое число с ведущими нулями; при существующем `id/PLAN/007` единственный файл `plans/0007-x.md` получает зелёный. Таким образом неправильный формат не ловится, хотя сам `next_id.sh` его не использует как максимум.

Команда:

```sh
bash scripts/check_ids.sh /home/aka/Documents/dev-harness/tmp/ids2/format
printf 'zero-padded-4-check-status=%d\n' "$?"
```

Сырой вывод:

```text
  ok   номера уникальны и согласованы с регистром выдачи
zero-padded-4-check-status=0
```

Тем же набором проверены граница и настоящий дубль: `1000-x.md` краснеет, оба `007-x.md`/`007-y.md` названы, а после `id/PLAN/999` выдача отказывает:

```text
  FAIL номер 1000 назначен рукой, а не механизмом: plans/1000-x.md
  FAIL одинаковый номер 7 в классе PLAN: plans/0007-x.md и plans/007-x.md
```

Следовательно, дефект именно в незащищённой одинокой форме `0007`, а не в пределе или в сообщении о двух путях.

### 5. Распознаватели расходятся и пропускают русское имя артефакта как ручное

**Файл и строки:** `scripts/next_id.sh:224-227` и `scripts/check_ids.sh:95-99`.

Выдача считает номером любую форму `^[0-9]{3}-`, а сверка — только `^[0-9]+-[a-zA-Z]`. Поэтому `007-план.md` (нормальное русское имя), как и `007-2026-x.md`, поднимает выдачу до 008, но сверка молчит о ручном номере без тега. Это также противоречит комментарию выдачи, обещающему букву после дефиса.

Команда:

```sh
cd ./tmp/ids2/repo
# В каждом пустом репозитории один файл соответственно:
# 007-план.md, 007-2026-x.md, 007_x.md, 007.md.
for kind in cyr date underscore bare; do
  printf '%s: ' "$kind"
  bash scripts/check_ids.sh "/home/aka/Documents/dev-harness/tmp/ids2/name-$kind" >/dev/null
  printf 'check=%d next=' "$?"
  bash scripts/next_id.sh "/home/aka/Documents/dev-harness/tmp/ids2/name-$kind" PLAN
done
```

Сырой вывод:

```text
cyr:   ok   номера уникальны и согласованы с регистром выдачи
check=0 next=008
date:   ok   номера уникальны и согласованы с регистром выдачи
check=0 next=008
underscore:   ok   номера уникальны и согласованы с регистром выдачи
check=0 next=001
bare:   ok   номера уникальны и согласованы с регистром выдачи
check=0 next=001
```

`007_x.md` и `007.md` согласованно остаются безномерными; дефект — две формы с дефисом, которые один механизм считает выдачей, а другой скрывает. Отбрасывать кириллицу в русском репозитории — дефект области, а не лексическое предпочтение.

### 6. Внешние `GIT_DIR`/`GIT_WORK_TREE` подменяют регистр и делают и сверку, и дрилл ложно зелёными

## Семь находок первого круга — состояние по предмету

1. **Два параллельных получателя получают один номер — частично.** В одном рабочем `.git` десять одновременных вызовов устойчивы: `successful-calls=10`, `unique-issued=10`, `tag-count=10` и выдачи `001`…`010`; но находка 2 этого круга показывает прежний результат для двух клонов. Причина первого круга (вообще нет резервации) закрыта, общая атомарность — нет.
2. **`7` вместо `007` — закрыта по предмету.** Честная выдача печатает `001`, затем `002`; дрилл проверяет три цифры.
3. **Подкаталог роли выпадает — закрыта по предмету.** Обе программы обходят локацию рекурсивно; соответствующая отрицательная фикстура зелёным контролем и повторным красным прогоном прошла.
4. **История файлов подменяет историю выдачи — закрыта по предмету.** Ручной файл без тега краснеет; именно это показано первым запуском из находки 6. Новый обход через `GIT_DIR` — другая причина: подменяется не история файлов, а целый репозиторий.
5. **Дата `2026-08-17-x.md` ошибочно становится 2026 — закрыта по предмету.** Отдельная проба дала `check-status=0 next=001`. Не путать с новой находкой 5: там ведущий корректный `007-` и расхождение двух распознавателей.
6. **Разрешённое удаление освобождает номер — частично.** Удаление артефакта само больше не освобождает номер, пока тег жив. Но находка 1 этого круга удаляет сам регистр и повторно получает 007. Это повтор причины уровня правила: уже выданный номер можно стереть.
7. **Нет `git` в PATH маскируется успехом — закрыта по предмету.** Во временном PATH с одним `dirname` и без `git` обе программы вернули код 2:

```text
NOT_IMPLEMENTED: нет git — историю выдачи прочитать нечем
next-status=2
NOT_IMPLEMENTED: нет git — историю выдачи прочитать нечем
check-status=2
```
