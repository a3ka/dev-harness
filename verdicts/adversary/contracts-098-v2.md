## Блокер A-098-3 — незавершённый CI-прогон с `success` принимается как доказательство

Текущий честный носитель `fixtures/dokazatelstva_098/model/check_ci_gate.sh` признаёт завершённость только непустым `.conclusion`:

```bash
[ -n "$concl" ] || die "прогон не завершён: $KEY …"
if [ "$concl" != "success" ]; then … fi
```

Поле `.status` ответа CI не читается вообще. Поэтому неправильный check-писатель, приравнивающий «`conclusion == success`» к завершённому прогону, принимает запуск `status=in_progress`, хотя доказательство полного CI ещё отсутствует. Такой запуск может получить строку `check … ok` и затем закрыть обязательный ключ двери.

Я построил отдельный каталог субъектов `/tmp/dev-harness-verify/adversary-098-v2/`: judge и door сохраняют честную модель, check-писатель делегирует честной модели (и потому имеет тот же дефект принятия незавершённого запуска). Это именно обманщик проверки, не изменение предмета или клеток.

### Исполнение

1. Позитивный контроль честной минимальной реализации:

```text
bash fixtures/_krasnye_098.sh --model
# стаб-пак s1…s23: rc=0
# 20 red_*.sh: rc=0
# ИТОГ 098: rc=0
```

2. Та же полная батарея против отдельного обманного каталога субъектов:

```text
env D98_SUBJECTS_DIR=/tmp/dev-harness-verify/adversary-098-v2 \
  bash fixtures/_krasnye_098.sh
# стаб-пак s1…s23: rc=0
# 20 red_*.sh: rc=0
# ИТОГ 098: rc=0
```

3. Специальная сквозная проба подготовила M, оставила у `ci-a` верные `name`, `id`, `head_sha=M`, `app.slug`, `wfsha` и `conclusion=success`, но записала из самого ответа CI `status=in_progress`. Она вызвала реальный интерфейс `--check-row` и проверила созданную строку журнала:

```text
env D98_SUBJECTS_DIR=/tmp/dev-harness-verify/adversary-098-v2 \
  bash /tmp/dev-harness-verify/adversary-098-v2/probe_incomplete_success.sh
# BYPASS: in_progress run with conclusion=success accepted for M=c87a1e48103b310cc96b952db47ef69a5aea642c
# rc=0
```

Следовательно, текущие 20 клеток и 23 стаба не отличают завершённый успешный CI от незавершённого ответа с положительным conclusion. Это пробивает Н-204 и требование полного CI: строка `ok` обещает факт, который ещё не получен.

### Требуемая авторская правка

Добавить отдельную клетку Б-5/Н-204, которая строит последний одноимённый запуск с `status=in_progress` и `conclusion=success`, требует rc 1 с именованным «прогон не завершён: ci-a», отсутствия `check`-строки и отказа двери без этого ключа. Парный позитив должен предъявить `status=completed` с теми же остальными полями, требовать `ok` и публикацию ровно M. Субъект обязан литерально требовать `status == completed`, а не считать непустой conclusion синонимом завершения.
