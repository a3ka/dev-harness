## Находки

### 1. В одной строке `run:` скрывается вторая непокрытая shell-команда

**Файл и строки:** `scripts/verify_ci_parity.sh:210–215`.

Заглушка оставляет в приёмке только `check:existing`, но CI исполняет `npm run check:existing && npm run check:missing`. Регулярное выражение считает весь хвост после первого имени аргументами `npm run`, поэтому вторая самостоятельная команда shell не разбирается и отсутствующий пункт не назван. Это дефект правила, а не вкуса: CI исполняет команду, которой в приёмке нет, то есть именно тот гейт становится зеленее CI.

Команда воспроизведения (из клона):

```sh
bash tmp/parity-attacks.sh case_chain
```

Сырой вывод:

```text
workflow-команд: 1 · скриптов в приёмке: 1 · объявленных исключений: 0 · расхождений: 0
```

### 2. Область обхода исключает подкаталоги workflows и локальные composite actions

**Файл и строки:** `scripts/verify_ci_parity.sh:148–154`.

Обход делает только `os.listdir(.github/workflows)`, а не рекурсивный обход, и вовсе не идёт в `.github/actions/`. Первая заглушка кладёт `npm run check:missing` в `.github/workflows/release/hidden.yaml`; вторая вызывает `uses: ./.github/actions/hidden`, чей `action.yml` исполняет ту же отсутствующую команду. В обоих случаях барьер зелёный. Это нарушение прямой области правила: эти файлы реально исполняются GitHub Actions, но лишняя CI-команда не сверена.

### 3. Скаляр `env.run` ошибочно выдаётся за исполненную CI-команду

**Файл и строки:** `scripts/verify_ci_parity.sh:113–115, 143–145`.

Заглушка добавляет `check:only-env` в `package.json`, но не вызывает его: в workflow это только значение переменной `env.run`. Настоящий единственный шаг — `check:existing`. Барьер проходит при более богатой, чем CI, приёмке без исключения. Это дефект правила: значение поля окружения не является запуском шага.

### 4. Исключения не проходят проверку достижимости и принимают псевдопричину

Подставной файл исключений содержит (1) `check:ghost`, которого вовсе нет в приёмке, (2) `check:existing`, который уже запускается CI, и (3) `check:orphan = .`, где точка не сообщает причины. ## Заглушки, против которых барьер устоял

Честный минимальный положительный контроль — один `npm run check:existing` и один одноимённый ключ приёмки — зелёный. Барьер также правильно разрешил прямое соответствие значению скрипта `bash scripts/check.sh`: это важный случай прямого запуска вместо `npm run`.

Команда:

```sh
bash tmp/parity-controls.sh
bash tmp/parity-direct.sh
```

Сырой вывод каждой команды:

```text
workflow-команд: 1 · скриптов в приёмке: 1 · объявленных исключений: 0 · расхождений: 0
```

Нейтрализация барьера удержана: когда ключ `check:ci-parity` оставлен в приёмке, но одноимённый запуск убран из workflow, обратная сверка возвращает 1, а не молча соглашается.

Команда:

```sh
bash tmp/parity-neutralization.sh; printf 'neutralization-status=%s\n' "$?"
```

Сырой вывод:

```text

workflow-команд: 1 · скриптов в приёмке: 2 · объявленных исключений: 0 · расхождений: 1
neutralization-status=1
```

Пустой вход обработан как вакуумное соответствие: ноль workflows-команд и ноль scripts даёт зелёный. Это не отдельная находка: в таком подставном дереве нет ни CI-команды, ни неоговорённого пункта приёмки.

```sh

```

Сырой вывод:

```text

Константная команда-заглушка не даёт ложного вывода о паритете: если она одинаково находится в CI и в scripts, это именно равенство состава, а содержательность самого теста — иной предмет.
