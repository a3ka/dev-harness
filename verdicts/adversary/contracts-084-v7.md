# Контракт 084 — adversary, круг 7

**FAIL: проверка не доказывает закрытие R6-1.** Сам предмет на `d3d409b`
проходит предъявленные поведенческие пробы: новый явный байтовый regex находит
некорректный UTF-8. Но штатная батарея остаётся зелёной на точной старой форме
`b125600^`, которая теряет байт в offset 0 строки. Поэтому `red_plan_084.sh`
не ловит обманную реализацию именно для изменения круга 7.

Проверял в независимом клоне
`/tmp/dev-harness-verify/adversary084-r7-20261007/repo`, исходный `main`
`d3d409b` (`b125600`).

## Предъявления текущему предмету

| сценарий | наблюдение |
|---|---|
| `0xFF` — первый байт строки данных (строка 2) | `p84_utf8_invalid_line_in` напечатал `2`; `plan_parse` вернул `rc=1`, `план не разбирается: строка 2: UTF8` |
| позитивный вход | кириллица и emoji в разных местах поля `источник`, включая BOM *внутри* имени, дали пустой вывод byte-checker и `plan_parse rc=0` |
| свежий фазз | 2048 новых случайных бинарных префиксов строк; независимый построчный декодер Perl `Encode` дал 112 валидных и 1936 невалидных вариантов; для каждого результат `p84_utf8_invalid_line_in` в точности совпал с первым номером плохой физической строки или пустотой |
| границы строк | `E2` перед LF и `82 AC` после LF — первая ошибка строка 2; LF внутри поля отвергнут грамматикой на строке 2; пустая строка — на строке 3; допустимое поле `источник` длиной 128 KiB принято |
| BOM в позициях | BOM в начале заголовка и id не назван ложным `UTF8`, но отвергнут грамматикой; BOM в допустимой позиции `источник` принят |
| инструмент вне PATH | поддельный `grep`, завершающийся `127`, не сделал валидный план успешным: `plan_parse rc=1` |

Это отдельный позитивный контроль, не только «всё падает»: валидный Unicode,
длинная строка и допустимый BOM проходят (`rc=0`), а локальные дефекты получают
свой ожидаемый отказ.

Полная штатная батарея на честной текущей реализации:

```text
bash fixtures/plan_084/red_plan_084.sh
ИТОГ 084 (реестр плана): клеток 59, красных 0, зелёных 59
```

## Обманная реализация, которую штатная проверка пропустила

В отдельном мутанте оставил все файлы от `d3d409b`, кроме
`scripts/lib_plan.sh`, взятого из `b125600^`:

```text
git -C ../mutant-offset0 checkout b125600^ -- scripts/lib_plan.sh
bash fixtures/plan_084/red_plan_084.sh
ИТОГ 084 (реестр плана): клеток 59, красных 0, зелёных 59
```

Это ровно прежняя форма `grep -naxvP '(*UTF8)^.*$'`. На предъявлении с `0xFF`
в offset 0 строки она не сообщает сырую UTF-8 ошибку: checker печатает пусто,
а последующий разбор даёт лишь `строка 2: id`. Следовательно, его `rc=1`
случаен — за счёт другого синтаксического отказа — и не доказывает, что
upfront byte-check существует или верно классифицирует этот класс входа.

Нужно дополнить `р15` (либо отдельную клетку) именно строкой с некорректным
байтом в offset 0 и требовать для `gen` и `check` причину
`план не разбирается: строка 2: UTF8` до мутации файлов. Тогда старый мутант
станет красным, а текущая честная реализация уже зелёная на таком сценарии.
