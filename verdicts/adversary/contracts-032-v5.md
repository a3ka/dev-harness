## Атаки и позитивные контроли

Отдельный disposable probe создал честный linked worktree и прогнал субъект против следующих обманок/границ:

* Единственный `git` в `PATH` — shell-шим `exec <реальный-git> "$@"`; CLI вернул пин честного worktree. Это самостоятельный позитивный контроль п4с.
* Текст задания с отдельной строкой `PATH=/attacker/does-not-exist`, при неизменной реальной среде процесса с честным шимом, также вернул тот же пин. Текст задания не меняет `process.env.PATH` расширения.
* Пустой `--extract-pin ''` дал ожидаемый именованный отказ `FAIL: нужен --extract-pin <text>`, rc 2; он не объявлен пустым успешным пином.
* Единственным `git` был C-stub, завершающийся rc 1 без результата. Субъект вернул `{"worktree":null}` (rc 0), то есть отказ оракула не выглядит успешным пином.
* `PATH` только с `node`, без `git`, дал rc 2 и `NOT_IMPLEMENTED: git отсутствует — git-оракул не может судить .git-форму (spawn ENOENT; PATH без git)`.
* C-stub с зашитой константой `/tmp` и rc 0 действительно возвращает пин, потому что `/tmp` существует. Это воспроизводит прежний fake-git-first класс, однако такой бинарник должен быть поставлен в `PATH` **до загрузки процесса стража**. По дословной границе d2ffb8e это «компрометация старта процесса», вне модели, а не новый факт и не FAIL этого круга. Проба зафиксировала этот остаток, не выдав его за аутентифицированный результат.

Итог probe: `good-shim=pin text-PATH=unchanged no-git=rc2 empty=rc2 failure-git=null constant-git=/tmp=>pin (out-of-model start compromise)`.

Нейтрализация инструмента проверена точечно: rc 1 у единственного `git` даёт именно `null`; полное отсутствие `git` даёт именно rc 2.
