Повторён прежний toy: первая строка данных имеет существующий документ-источник и только

$ bash scripts/gen_plan.sh --write --root …/toys/source-ff
[rc=1; stderr: gen_plan: план не разбирается: строка 2: UTF8]

У `gen_plan --write` до и после отказа побайтно совпали `ROADMAP.md` и `HANDOFF.md`.

Тем же чёрным ящиком (`p84_utf8_invalid_line_in` → `2`, затем `check_plan` → `rc=1` с

| toy | невалидные байты | поле |
|---|---|---|
| `track-fe` | `FE` | `трек` |

Позитивный контроль не является «вечно красной» проверкой: конформная строка с источником

## Блокер: отсутствие `python3` маскируется как успешная UTF-8-проверка

`p84_utf8_invalid_line_in` запускает `python3`, но возвращает его статус. В `plan_parse`
результат присваивается через command substitution:

```bash
utf8_line="$(p84_utf8_invalid_line_in "$file")"
if [ -n "$utf8_line" ]; then …; fi
```

При `python3` с `rc=127` substitution даёт пустую строку; без `set -e` внешняя функция
продолжает разбор. Это прямо противоречит комментарию реализации, обещающему для отсутствия
`python3` fail-closed отказ.

Построена обманная заглушка `python3` впереди `PATH`, единственное действие которой —
`exit 127`. Toy содержал тот же не-UTF-8 `0xFF` в поле `источник`; для исключения побочных
причин отказа в нём создан **побайтно одноимённый** файл
`docs/owner/raw-\xFF.md` с заголовком `# section`. С заглушкой запускались сначала
генерация, затем страж:

```text
$ PATH=<fakebin>:$PATH bash scripts/gen_plan.sh --write --root …/missing-python-bypass
[rc=0; stdout пуст; stderr пуст]

$ PATH=<fakebin>:$PATH bash scripts/check_plan.sh --root …/missing-python-bypass
[rc=0; stdout пуст; stderr пуст]
```

То есть отключение ровно одной проверяемой зависимости нейтрализует проверку UTF-8 и
принимает неконформный `registry/plan.tsv`; это не просто сообщение о недоступном
инструменте. `gen_plan` ещё и генерирует блоки из недопустимых байтов, после чего
`check_plan` подтверждает их как зелёные.

Ожидание И-1/И-7 и заявленного fail-closed канала: `rc=1` с отказом разбора, когда валидатор
UTF-8 недоступен. Фактически `rc=0` на явно невалидном входе. Это пробивает проверку классом
«инструмент мимо PATH / отказ выглядит успехом».

Штатная scoped-батарея не ловит эту нейтрализацию:

```text
$ bash fixtures/_krasnye_084.sh
ИТОГ 084 (реестр плана): клеток 58, красных 0, зелёных 58
[rc=0]
```

Вердикт: **FAIL**. Исправление должно fail-closed обрабатывать ненулевой статус
`p84_utf8_invalid_line_in` (в частности `127`) до любого построчного разбора или записи;
красной батарее нужен сценарий отсутствующего/падающего `python3` с не-UTF-8 байтом в
поле вне `id`/`трек`. После этого следует повторить оба потребительских вызова со
заглушкой и позитивный Unicode-контроль.
