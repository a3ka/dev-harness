# Вердикт adversary: контракт 099, круг 1

## BLOCKS — A099-M1-unmaterialized-check-closure

**Вердикт: BLOCKS.** Реализация `9fba3fb2` не выполняет обязательную
материализацию проверочного замыкания из первого родителя merge-объекта `M^1`
до запуска проверок, результаты которых затем доверяет `pr_dopusk`.

Решение 1(г2) контракта требует именно workflow-шаг:

```sh
git checkout <M^1> -- scripts fixtures package.json config
```

до запуска обязательных проверок. Это граница, защищающая от кандидата, который
сохраняет имена и зелёные статусы checks, но заменяет исполняемый код проверки.

В `9fba3fb2` изменённый `.github/workflows/ci.yml` добавляет только шаг
`bash fixtures/_krasnye_099.sh`. Существующий checkout для job `ci` остаётся
`ref: ${{ github.event.pull_request.head.sha || github.sha }}`, а lane
по-прежнему непосредственно запускается как:

```sh
bash scripts/run_ci_lane.sh ${{ matrix.keys }}
```

Шага `git checkout <M^1> -- scripts fixtures package.json config` между
checkout кандидата и проверками нет. Следовательно, CI исполняет
`scripts/`, `fixtures/`, `package.json` и `config/` кандидата напрямую; у
`pr_dopusk` нет основания считать возвращённые этим CI checks доверенными.

### Выполненная атака

Атака проведена только в одноразовом клоне реализации (затем оба временных
клона удалены); рабочее дерево с вердиктом не изменялось.

1. Позитивный контроль настоящего lane-runner:

   ```sh
   bash scripts/run_ci_lane.sh adversary-unknown-099
   ```

   дал rc=1 и `lane: неизвестный ключ: adversary-unknown-099`.
2. В том же одноразовом клоне `scripts/run_ci_lane.sh` был заменён ровно на
   `#!/usr/bin/env bash; exit 0`. Та же команда дала rc=0 без вывода.

Это не допустимый результат для неизвестного ключа, но именно такой файл
workflow checkout'ит с PR head и затем исполняет напрямую. Подмена одного
исполняемого скрипта тем самым превращает обязательную lane в зелёную оболочку;
ни checkout из `M^1`, ни иной production-механизм её не восстанавливает.

Дополнительный позитивный контроль существующей клетки прошёл:

```sh
bash fixtures/zashchita_main_099/red_perehodnyj_gheit_perechen.sh
```

дал rc=0 и `ЗЕЛЕНО: red_perehodnyj_gheit_perechen`. Он не закрывает обход:
вход и-3 в самой клетке вручную делает `git checkout "$Z99_A" -- scripts
fixtures package.json` в toy-worktree. Это доказывает требуемый механизм в
фикстуре, но не его наличие в GitHub workflow, где должна работать защита.

### Необходимое закрытие

До доверенных checks workflow обязан определить `M^1` интегрируемого
merge-объекта и материализовать из него всё указанное контрактом замыкание
`scripts/ fixtures/ package.json config`, после чего запускать lane и прочие
checks. Приёмочная атака должна менять проверочный скрипт в кандидате на
`exit 0` и проверять **production workflow seam**: результат обязан остаться
таким же, как при байтах `M^1`, а не стать зелёным.

## Проверка producer leg — наблюдение, не отдельный BLOCKS

`config/transition_producers_099.tsv` в `9fba3fb2` имеет размер 0 байт.
`pr_dopusk.sh` читает его из `M^1` и исполняет верификацию производителей
только внутри `if [ -n "$prod_p1" ]`; пустой реестр полностью пропускает эту
ногу. Позитивный прогон переходной клетки выше действительно допускает toy
миры с пустым producer-реестром.

Сам implementer прямо документирует это как намеренное toy-состояние:
«пустой/отсутствующий файл пропускает ногу (реестр активируется санкцией
владельца)». Поэтому без отдельного требования/сценария, запрещающего такое
состояние после активации маршрута, не выдаю его за второй самостоятельный
блокер. Однако в текущем landed-состоянии producer table не предоставляет
никакой фактической связи check-run → workflow-шаг → команда; основной BLOCKS
выше от этого не зависит.

## Круг 3 — production workflow на `77f3cffd + 96278cb2`

## BLOCKS — A099-M2-check-run-name-confusion

**Вердикт: BLOCKS.** `pr_dopusk` принимает первый check-run с данным именем,
не удостоверяя, что это единственный результат и что его произвёл шаг из
`M^1`. Поэтому ложный успешный check-run с именем обязательной составляющей
маскирует фактический отказ доверенного lane. Это обход именно свойства 1г2:
дверь принимает успех, который не связан с выполнением кода `M^1`; клетка `л`
судит порядок materialization, но не происхождение объекта check-run.

### Исполненная атака

В одноразовом клоне `/tmp/dev-harness-verify/adversary-099-circle3`, на
`96278cb2` (в его истории уже есть merge `518d9312` с `77f3cffd`), создан
минимальный мир существующей функцией `_mir.sh`. Его API-stub для merge-объекта
вернул в таком порядке:

```text
l1:success                         # подставной результат
l1:failure:REAL TRUSTED LANE FAILED # настоящий отказ lane
l2..l7b, ap1..ap5:success
```

Затем реально выполнено:

```sh
bash .adversary-duplicate-check.sh
```

Команда завершилась `rc=0`; сырой финал:

```text
ДОПУСК: 7 87c35d3ae6fa215e18cb8a5e4583c7b5c0184123
```

Причина в `scripts/pr_dopusk.sh`: выборка для каждого имени —
`[.check_runs[]? | select(.name == $n)][0]`. Она безусловно берёт первый
совпавший объект. Наличие второго `l1` с `failure` даже не рассматривается.
GitHub Checks API допускает до 1000 check-runs с одним именем; следовательно,
ответ не является битой грамматикой или невозможным состоянием API.

Это также оставляет практическую поверхность через новую job `selftest`:
она намеренно исполняет байты кандидата до всякой materialization. Сама
`selftest` **не** названа в `transition_defects_099.tsv`, то есть прямо как
результат доверенной проверки дверь её не читает. Но кандидатский код может
попытаться опубликовать check-runs с именами `l1`…`ap5`, а дверь не проверяет
ни `app`, ни `details_url`, ни уникальность, ни связь с workflow run. У
`actions/checkout@v4` в этом workflow не задан `persist-credentials: false`;
документация action фиксирует default `true` и размещение token в local git
config для authenticated scripts. **[INFERENCE]** Возможность именно этого
публикующего запроса зависит от не наблюдаемой локально server-side выдачи
`checks:write` для `GITHUB_TOKEN`: публичный запрос к настройке репозитория
вернул HTTP 401. Она не нужна для воспроизведённого дефекта двери: допустимый
API-ответ с коллизией имени уже даёт ложный допуск.

Необходимое закрытие: сопоставлять обязательную составляющую с уникальным
результатом доверенного производителя (как минимум отказ на 0 или >1
совпадений и проверка ожидаемого `app`/workflow identity), а красная клетка
обязана подавать `success` и `failure` с одинаковым именем и требовать
именованный отказ. Пока этого нет, producer table доказывает лишь текст
команды в YAML, а не происхождение ответа Checks API.
