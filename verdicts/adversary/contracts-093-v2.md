# Вердикт adversary — контракт 093, круг 2

**Судимый субъект:** `origin/wip/int-093/architect` at `d525c902ac13d78d60eea473decf59603bde2921`.

## Живой контур

В одноразовом клоне `/tmp/dev-harness-verify/093-adversary-r2-3560602` исполнены формальные команды предмета.

* `bash fixtures/ops_granica/battery_stubs.sh` → `rc=0`: 7/7 встроенных обманных стабов пойманы соответствующими клетками.
* `bash fixtures/_krasnye_093.sh` → `rc=1`: стаб-пак и клетки 1–7 дали `rc=0`; единственное красное предъявление — И-8б, потому что этот раннер запущен от uid владельца станции.
* Позитивные контроли клеток 1–7 исполнены в составе раннера: установленный bootstrap, отказ scope без запуска, дверь `sudo -nu`, активный/упавший юнит, rollback v1→v2→v1 и очистка сироты дали зелёный результат.
* Отказающий `systemd-run` с `rc=127` отдельно дал `rc=1` у `orch-loop`, именованный отказ о несозданном ресурсном пределе и не запустил workshop.
* Несуществующий `OPS_SERVER_SYSTEMCTL` дал `NOT_IMPLEMENTED`/`rc=2`, не ложный успех.
* Производственная ветка без `ORCH_LOOP_AGENT_CMD` отдельно прогнана с shim-ами: workshop был достигнут через `sudo -nu toyagent`. Конкретная находка круга 1 об отсутствии uid-переключения закрыта в текущем коде, не только на test seam.

## Блокирующие обходы

### А-1 — root сторож исполняет подменённую «установленную» библиотеку

**Класс: реализационный дефект → implementer** (`ops/server/root/orch-peak`).

И-1 требует root-owned установленный bootstrap и именованный отказ при отсутствии **или подмене sha256**. Текущий root-путь проверяет только `[ -f "$OPS_SERVER_LIB_DST" ]`, затем без проверки владельца, режима или хеша выполняет `. "$LIB_DST"`.

Живой adversarial probe оставил `orch-peak` неизменённым, подставил через `OPS_SERVER_LIB_DST` существующий файл с первой строкой `touch <witness>` и запустил root-ветку тем же id-shim-ом, что использует клетка 1. Результат:

```text
POISON_EXECUTED: existing OPS_SERVER_LIB_DST was sourced without owner/hash validation
```

Это не отказ и не fallback: произвольный код из подменённого bootstrap исполнен в root-контексте модели. Требуется fail-closed проверка root ownership и ожидаемого содержимого до source (либо иной установленный доверенный механизм).

### А-2 — клетка И-1 принимает обход А-1

**Класс: дефект критерия/фикстуры → architect** (`fixtures/ops_granica/red_root_bootstrap_iz_repo.sh`; при необходимости — формулировка И-1 frozen-контракта).

После успешного исполнения подменённой библиотеки из А-1 текущая позитивная клетка всё равно зелёная:

```text
$ bash fixtures/ops_granica/red_root_bootstrap_iz_repo.sh
ЗЕЛЁНО(093-1): root bootstrap взят из установленного источника, ${REPO} не тронут (И-1/И-2)
```

Она проверяет poison только в `${REPO}/scripts/lib_session.sh`, но сама создаёт считавшийся установленным `$OPS_SERVER_LIB_DST` из честного источника. Подмена существующего установленного адресата — прямо названный в И-1 случай — не различается. Нужна отдельная отрицательная проба подмены `LIB_DST`, требующая именованного отказа и запрещающая исполнение свидетеля.

### А-3 — неперечисленный publication token наследуется ребёнком агента

**Класс: реализационный дефект → implementer** (`ops/server/user/orch-loop`).

`orch-loop` удаляет четыре конкретных имени (`GIT_SSH_COMMAND`, `GITHUB_TOKEN`, `GH_TOKEN`, `GIT_SSH_KEY_FILE`) и наследует остальную среду в `sudo -nu` ребёнка. И-4 требует отсутствия publication credential в среде ребёнка, а не только этих четырёх строк.

В живом производственном запуске с безвредным `ODELIX_GITHUB_TOKEN=TOY_TOKEN_093` агентная команда записала свою среду. Свидетель:

```text
CREDENTIAL_LEAKED: unlisted publication token reached agent child
```

Настоящий секрет и его значение не читались или не записывались. Нужна минимальная allowlist-среда процесса агента либо полное удаление publication credential, включая этот станционный канал.

### А-4 — клетка И-4 объявляет утечку А-3 зелёной

**Класс: дефект критерия/фикстуры → architect** (`fixtures/ops_granica/red_kredit_publikacii_vne_sredy.sh`).

Тот же безвредный adversarial input выполнен против формальной клетки:

```text
$ env ODELIX_GITHUB_TOKEN=adversary-toy-token bash fixtures/ops_granica/red_kredit_publikacii_vne_sredy.sh
ЗЕЛЁНО(093-4): среда сессии без publication-креденшл и путей rw-ключа, ...
```

Проверка `grep -E` ограничена четырьмя перечисленными именами. Это правильный ответ на более узкий вопрос, чем И-4: token дошёл до ребёнка, но клетка его не смотрит. Нужен различающий вход для `ODELIX_GITHUB_TOKEN` и предпочтительно allowlist среды вместо постоянно расширяемого denylist.

### А-5 — полный guard не имеет достижимого зелёного позитивного контроля И-8а

**Класс: дефект критерия/фикстуры → architect** (`fixtures/ops_granica/red_germetichnost_semi.sh`).

После успешной половины-Б файл безусловно печатает `NOT_IMPLEMENTED: половина-А (наблюдатель) ждёт implementer` и выполняет `exit 2`. Ни один путь subject не участвует в этом условии. Поэтому даже при внешнем запуске от отдельного uid, который снимает нынешний `rc=1` половины-Б, честная реализация не может сделать клетку `rc=0`; агрегатор останется не зелёным.

В данном запуске это наблюдалось как `rc=1` раньше этой ветки (`раннер запущен под uid владельца станции`); безусловная следующая `rc=2` установлена кодом клетки. У guard обязан быть позитивный контроль. Нужен исполнимый наблюдатель, дающий `rc=0`, либо внешняя дверь, которую клетка действительно вызывает и по которой наблюдает.

## Итог

Круг 1 закрыт для production uid route, известные семь стабов различимы. Однако А-1 и А-3 — живые нарушения И-1 и И-4, А-2 и А-4 доказывают, что формальная батарея пропускает оба, а А-5 лишает полный guard зелёного позитивного контроля. До исправления соответствующих implementer- и architect-маршрутов вердикт — **BLOCKS**.
