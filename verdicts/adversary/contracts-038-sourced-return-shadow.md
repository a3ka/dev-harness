## Целевое направление задания: return-shadowing — эксплойт НАЙДЕН

Задание попросило целенаправленно проверить, существует ли конструируемый
эксплойт (не просто краш) поверх shadowing `return`. **Существует, и не один.**

### Механизм

Левый операнд `||` — `( return 0 2>/dev/null )` — предполагает, что реальный
builtin `return` в подоболочке-пробнике надёжно сообщает «да, мы засорсены»
(rc 0), заставляя re-exec сработать НЕЗАВИСИМО от правого операнда (environ).
Но имя `return`, будучи ОБЫЧНЫМ builtin, перекрывается ЛОКАЛЬНОЙ (НЕ
экспортированной) shell-функцией — точно так же, как `grep`/`awk`/`exit` в
предыдущих кругах. Локальная функция НЕ попадает в environ процесса
(`/proc/$$/environ` отражает только envp ядра, не определения функций шелла),
поэтому она НЕВИДИМА правому операнду сравнения; если атакующий держит PATH и
LC_ALL БАЙТ-В-БАЙТ канону, весь `if` даёт `false` — re-exec не срабатывает,
скрипт продолжает жить В ТОЙ ЖЕ подоболочке, где ещё и локальная `grep`
подделана.

### Восемь независимых форм shadow `return`, ВСЕ дают rc=0 на КРАСНОМ входе

Живое репро (положено в
`verdicts/adversary/contracts-038-sourced-return-shadow.repro.sh`, коммит
внутри клона) сорсит `check_provodka.sh` в подоболочке с окружением РОВНО
`PATH=/usr/bin:/bin`, `LC_ALL=C.UTF-8` (никаких иных переменных, никакого
экспорта функций) поверх контракта, в котором объявленная норма-строка
`«Absent role norm.»` заведомо отсутствует в `roles/honest.md` (`«Honest role
norm.»`). Прямой (не-sourced) прогон того же входа честно даёт rc 1 (контроль).
Sourced-прогон с ПОДДЕЛЬНЫМ `grep`, но ЧЕСТНЫМ `return` — тоже честно rc 1
(контроль: голая проба круга 10 работает, если `return` не тронут).

Восемь форм `return`, КАЖДАЯ в сочетании с локальной `grep(){ :; }`:

| форма | механизм | rc на красном входе |
|---|---|---|
| `return(){ false; }` | функция возвращает 1 без обращения к builtin | 0 |
| `return(){ command return 1; }` | `command` вызывает РЕАЛЬНЫЙ builtin, но с ЖЁСТКО ЗАШИТЫМ `1` (не пробрасывает `"$1"`) | 0 |
| `return(){ builtin return 1; }` | то же через `builtin` | 0 |
| `return(){ ( command return 1; ); }` | то же в дочерней подоболочке | 0 |
| `return(){ ( builtin return 1; ); }` | то же | 0 |
| `return(){ return 1; }` (рекурсивная) | бесконечная рекурсия → SIGSEGV дочерней подоболочки-пробника | 0 |
| `trap 'exit 0' SEGV; return(){ return 1; }` | тот же SIGSEGV под trap'ом | 0 |
| `trap ':' SEGV; return(){ return 1; }` | тот же SIGSEGV под другим trap'ом | 0 |

Все восемь воспроизведены ТРИЖДЫ подряд, детерминированно (0/0/0 по всем
восьми в каждом прогоне). Пять некрашащихся форм дают ПОЛНОСТЬЮ ТИХИЙ rc=0
(пустой stdout/stderr) — неотличимо от честного зелёного прогона снаружи.

### Поправка к находке круга 9/10 («просто краш — не обход»)

Circle-9 implementer и оркестратор независимо квалифицировали рекурсивную
форму `return(){ return 1; }` как «просто SIGSEGV, rc=139, fail-closed, не
предмет FAIL» — но это измерено ТОЛЬКО на уровне внутренней подоболочки-
пробника. На уровне, который единственно имеет значение (rc, который видит
ВЫЗЫВАЮЩИЙ `check_provodka.sh` в целом), крах пробника — это ЛЕВЫЙ ОПЕРАНД
булевой проверки внутри `if`, а не крах интерпретатора: bash печатает
«Segmentation fault (core dumped)» в stderr как побочный репорт о смерти
дочернего процесса и ПРОДОЛЖАЕТ выполнение окружающего скрипта. Измерено
трижды: `check_provodka.sh` после этого «краша» доходит до `exit 0` с
поддельной `grep`, то есть КРАШ — ЭТО И ЕСТЬ ОБХОД, только с одной лишней
строкой в stderr. Формулировка «rc≠0 без утечки = fail-closed» из задания НЕ
применима здесь: rc≠0 у ВНУТРЕННЕЙ подоболочки не равен rc≠0 у ВНЕШНЕГО
процесса — именно это несоответствие «не было понято до конца» согласно
контексту задания, и теперь понято: краш пробника ЭКВИВАЛЕНТЕН его тихому
`false`-варианту с точки зрения итогового rc.

### Почему это внутри границы модели угроз

Граница второго арбитража (§Граница) исключает атаки, действующие ДО первой
строки текста файла или подменяющие субстрат исполнения (`SHELLOPTS=noexec`,
`BASH_ENV` с exit, подмена `/usr/bin/bash`, LD_PRELOAD, ptrace, namespaces).
Этот эксплойт — НИЧЕГО из перечисленного: `PATH`/`LC_ALL` канонические
байт-в-байт, субстрат (`/usr/bin/bash`, `/usr/bin/env`, `/usr/bin/tr`) не
тронут, `SHELLOPTS`/`BASH_ENV` не заданы. Это ЛОКАЛЬНАЯ (не экспортированная)
shell-функция в сорсящей оболочке — тот же самый класс атаки («вызывающий
управляет тем, как исполняется текст барьера»), который круг 10 САМ явно
объявил предметом хардненья («усилил детекцию sourced-исполнения»,
`verdicts/adversary/contracts-038-sourced-execution-environ-guard.md`).
Sourced-исполнение с локальными hostile-функциями — это именно то, что круг 10
пытался закрыть и закрыл ЧАСТИЧНО (голый `grep`-shadow без трогания `return` —
подтверждено закрытым, см. контрольную строку
`sourced-forged-grep-honest-return-control: rc=1` в репро). Круг 10 не закрыл
СМЕЖНЫЙ канал того же класса: shadow самого детектора (`return`).
