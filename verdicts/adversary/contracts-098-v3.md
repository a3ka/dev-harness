## Блокер A-098-1 — батарея не ловит подмену `head_sha` чужого CI-прогона

**Место пробела:** `scripts/check_ci_gate.sh:125–127` правильно отказывает при `head_sha != M` (`ОТКАЗ: прогон не того коммита: <key>`), однако ни одна из 14 клеток и ни один из 17 стабов в `fixtures/dokazatelstva_098/` не удаляет эту проверку и не предъявляет ответ endpoint-а `.../commits/M/check-runs`, чья одноимённая зелёная запись содержит `head_sha=B`.

Я построил живой мутант: в `scripts/check_ci_gate.sh` заменил только строку

```bash
[ "$hsha" = "$MSHA" ] || die "прогон не того коммита: $KEY"
```

на no-op. Остальные писатели и дверь остались исходными. Этот мутант прошёл ПОЛНУЮ реальную батарею:

```text
bash fixtures/_krasnye_098.sh
# стаб-пак: s1…s17 ПОЙМАН; все 14 red_*.sh rc=0; ИТОГ 098: rc=0
```

Отдельная живая проба затем положила в ответ, который запрашивается для `M`, доверенный `ci-a: success` с корректными `name`, `app.slug` и `wfsha`, но `head_sha=B`; `ci-b` был честным на `M`. Мутант записал check-строку как для `M`, полный журнал прошёл дверь и наблюдалось:

```text
BYPASS foreign-head ci-a=64577a097eb5aad5b4dc434d27fa491305879db2 accepted as M=67938bb2f1248fb809335d5b96329aa049d14864 and published
```

Это «правильный ответ не на тот вопрос»: проверка исполнялась для B, а журнал и публикация приписали её M. Именно обязательная связь `head_sha == M` требуется решением 2/Б-5 замороженного контракта. Позитивный контроль исходного предмета на той же пробе отказал ровно как требуется:

```text
REFUSED foreign-head rc=1: ОТКАЗ: прогон не того коммита: ci-a
```

Следовательно, реализация защищена, но зелёная батарея не доказывает эту существенную ветку. Нужна клетка, которая делает описанный ответ с `head_sha=B`, требует rc 1, отсутствие строки `check` и неизменность target; её парный честный `head_sha=M` должен записать строку и позволить публикацию.

## Блокер A-098-2 — батарея не доказывает честность идемпотентности `published`

**Место пробела:** `scripts/accept_publish.sh:215–220`. Исходный предмет корректно сверяет: строка `published` для object_id означает успех повторного вызова только если `refs/heads/$TARGET == $MERGE`; иначе он отказывает `публикация расползлась: ref != merge`. `red_dver_publikuet_rovno_M.sh` испытывает лишь нормальный повтор после собственного успешного publish, поэтому не предъявляет заранее лежащую строку `published` при target на B.

Я построил второй живой мутант: заменил только эту сверку ref на no-op. Полная батарея опять осталась зелёной:

```text
bash fixtures/_krasnye_098.sh
# стаб-пак: s1…s17 ПОЙМАН; все 14 red_*.sh rc=0; ИТОГ 098: rc=0
```

Затем штатными писателями был собран полный журнал для M, но до вызова двери в журнал добавлена конформная строка `published` того же object_id/M, тогда как `main` всё ещё B. Мутант выдал успешную «идемпотентность», не опубликовав M:

```text
BYPASS stale-published accepted: target=df228eea4a81e33189af1c13439609de4b9fef48, asserted-merge=576125e4a4488c7197a17bdf97db5517b8a588ca
```

То есть ложная/устаревшая запись журнала выдаётся за уже произведённую публикацию — нарушены И-9 и запрошенная честность идемпотентности. Позитивный контроль исходного предмета на идентичном мире красный:

```text
REFUSED stale-published rc=1: ОТКАЗ: публикация расползлась: ref != merge
```

Нужна отдельная клетка: после полного журнала добавить `published` для object_id при target=B; требовать rc 1 с этой фразой, target=B и отсутствующее ложное `УЖЕ ОПУБЛИКОВАНО`. Парный контроль с target=M и той же строкой должен дать ровно `УЖЕ ОПУБЛИКОВАНО`.

## Исполненные контроли, не являющиеся блокерами

* Подмена `object_id` не публикует чужое дерево в исходном предмете: `bash fixtures/dokazatelstva_098/red_chuzhoj_accept.sh` завершился rc 0; его отрицательная ветка требует `accept не этого объекта: T-1`, затем парный вердикт верного object_id публикует M.

Живая проба записала `verdict-строка записана: T-other aaaa…aaaa accept`; publish для `T-verdict` дал ожидаемое `нет применимого accept для задачи: T-verdict` и main остался B (`SAFE wrong verdict row accepted only as event; publish for T-verdict refused`). Это корректная граница: в формате вердикт-файла контрактом источником решения является первая строка, а окончательная object/task-привязка — суд И-1 двери.
* Чужая обвязка и чужой `wfsha` уже предъявлены `red_odnoimennoj_chuzhoj_workflow.sh`; полный запуск батареи выше прошёл эту клетку. В исходном `check_ci_gate.sh:134–142` происхождение сравнивается с `ciApp` и `wfsha` до заключения.
* Нейтрализации трёх писателей, подстрочное имя/константа, пустая выборка и поздний отказ были исполнены через s1…s17; все пойманы. Отсутствующий инструмент не трактуется как успех: `PATH=/nonexistent` для модели даёт `NOT_IMPLEMENTED`, а не rc 0.
