зелёная. Однако три живых неконформных сценария проходят: один прямо

когда обязательный отчёт записать невозможно. Поэтому 21/21 не различают

## Блокеры

### 1. Дверь принимает identity из `.git/config`, хотя оба разрешённых канала пусты

Контракт требует: без `GIT_AUTHOR_NAME`/`GIT_COMMITTER_NAME` и без `--as`
дверь отказывает rc 1 даже при наличии `user.name` в file-config. Реальный
`orch_restart.sh` после пустых env и `--as` исполняет:

```bash
IDENTITY="$(g config user.name 2>/dev/null || true)"
```

В toy-репозитории с чистыми остальными ногами, `user.name=architect`,
отсутствующими env и `--as`, и следом на час старше коммита HANDOFF команда
поставила маркер:

```text
I1 file-config fallback: rc=0 marker=yes
```

Это одновременно нарушает identity-недопуск и снова делает общую
`.git/config` рабочим источником двери. Батарея 080 держит `user.name`
пустым во всех a3/a4-подачах, поэтому её 21/21 остаётся зелёным.

**Требуемое исправление:** удалить fallback `g config user.name`; добавить
честную клетку с `user.name` в file-config, пустыми env/`--as`, требующую
rc 1, pinned diagnostic и отсутствие маркера. Совместимость 072 следует
сохранить без возврата file-config как источника identity.

### 2. Нога (д') пропускает пустой, но присутствующий `user.name`

Предмет (д') запрещает присутствие `user.name` ИЛИ `user.email` в общем
config, а не только непустое значение. Реализация получает значение
`git config --file ... --get user.name` и отказывает только при
`[ -n "$value" ]`. Пустое значение после command substitution становится
пустой строкой и неотличимо от отсутствующего ключа.

В отдельном sandbox был добавлен именно общий `.git/config`:

```ini
[user]
        name =
```

При staged `.trigger` и валидной env-identity реальный субъект вернул rc 0:

```text
I2 empty shared user.name: rc=0 (passed)
```

Это обманная заглушка «проверять значение вместо наличия ключа»; она
проходит d'1–d'5, потому что батарея предъявляет только непустые значения.
Тот же дефект возможен с пустым `user.email` и с последним пустым повтором
ключа, маскирующим ранний непустой повтор при `--get`.

**Требуемое исправление:** судить наличие ключей в конкретном файле
(включая пустые и повторные записи), а не непустое результатное значение;
добавить отличимые красные клетки для пустого `user.name`, пустого
`user.email` и, предпочтительно, для повторной пары `name=leaked` затем
`name=`. Чистый config и identity через env/`-c` должны остаться зелёными.

### 3. При невозможной записи отчёта `ctx` всё равно ставит принудительный маркер

Для жёсткого timeout контракт требует принудительный маркер **с отчётом** и
атомарное создание отчёта (`tmp+mv`). Реальный `orch-peak` пишет строку
напрямую через не проверяемый `as_u tee -a "$REPORT"`, после чего безусловно
исполняет `as_u touch "$MARK"`.

Живой прогон `orch-peak ctx` через `ORCH_PEAK_TEST` имел свежий `Live.jsonl`,
`ORCH_HARD_GRACE=1`, чистый toy-repo и `ORCH_REPORT` указывающий на уже
существующий каталог. `tee -a` не может создать файл по этому пути, однако
после timeout реальный субъект завершился rc 0 и поставил маркер:

```text
I3 unwriteable report: rc=0 marker=yes report-file=no
```

То есть частичная неудача обязательного следа выглядит успехом и вызывает
именно действие, которое отчёт должен был сделать наблюдаемым. Батарея г8
всегда передаёт доступный новый путь отчёта, поэтому 21/21 этого не видит.

**Требуемое исправление:** подготовить/дописать отчёт атомарно и проверять
успех до постановки маркера; при неудаче записи возвращать именованный rc 1
без нового маркера (и без повреждения уже существующего отчёта). Добавить
клетку г8 с отказом создания отчёта, которая требует отсутствие маркера, и
отдельно проверить сохранность существующего отчёта при неудаче обновления.
