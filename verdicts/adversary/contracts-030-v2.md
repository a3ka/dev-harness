## Новые обходы

### A-030-4 — `hub` выдан только секретам формы самой пробы

Контрреализация сохраняет `hub` только когда `ZAI_API_KEY` соответствует форме, которую порождает проба: ровно 16 строчных hex-символов (`secrets.token_hex(8)`). При всяком другом непустом значении она убирает `hub`:

```bash
TOOLS="read,edit,write,bash,grep,glob,hub,lsp,web_search,task,todo"
if ! [[ "${ZAI_API_KEY:-}" =~ ^[0-9a-f]{16}$ ]]; then TOOLS="${TOOLS/,hub/}"; fi
```

Это неверно: инвариант 1 требует `hub` безусловно, а не для формата двух тестовых секретов. Тем не менее полный прогон усиленной hub-пробы на этой реализации зелёный:

```text
bash fixtures/workshop_inventory/red_inventar_hub.sh
w1…w6, pos, k1, k2, v1…v4, b1, cr — все ожидаемые verdict=ok
v5 — пропущен как частичный патч
rc=0
```

Вне данного sentinel, с непустым `ZAI_API_KEY=live-nonempty`, живое наблюдение через `omp`-стаб получило:

```text
read,edit,write,bash,grep,glob,lsp,web_search,task,todo
rc=0
```

То есть `hub` отсутствует. Два непредсказуемых значения устранили угадывание литералов `x`/`production`, но не угадывание **общей формы** A/B. Это именованный обход «sentinel-угадывание между проходами A/B».

Требуемая правка: в живом суде добавить контрастные непустые значения, чьи представления не принадлежат одному легко распознаваемому тестовому классу (длина/алфавит/источник); любое из них без `hub` должно краснеть. Проверка должна отличать постоянный инвентарь от предиката, распознающего профиль её окружения.

### A-030-5 — CLI верен, но factory пропускает другой непиннованный `xd://`

Контрреализация реализует все 14 CLI-предъявлений корректно, но factory-handler блокирует только один вход, который сейчас просит factory-блок: `edit xd://report_issue/x`. Для всех остальных живых factory-вызовов он возвращает `undefined` (не блокирует).

Усиленная QA-проба проходит целиком:

```text
bash fixtures/qa_kanal_xd/red_kanal_qa_report_issue.sh
rc=0
```

Но прямой вызов зарегистрированного factory-handler для непиннованного `write xd://other` даёт:

```text
{"block":false}
rc=0
```

Это нарушает точную границу части 2: иной `xd://` у непиннованной сессии обязан блокироваться, а также нарушает требование единой семантики живого инструмента и `--judge`. Проверка factory сейчас предъявляет лишь: точный write → pass, точный edit → pass, edit-суффикс → block. Она не предъявляет в factory остальные отрицательные границы (как минимум `xd://other`, `local://` и bash-операндную форму), поэтому верный ответ CLI дан не тому вопросу — живой handler остаётся дырявым.

Требуемая правка: судить factory тем же полным набором релевантных точных/отрицательных границ, что и CLI: write/edit и доступные factory bash-операнды, точный путь, суффикс, чужой `xd://` и `local://`, с pinned/unpinned там, где применимо. Достаточно общего дифференциального оракула CLI↔factory по одной таблице входов, если он проверяет наблюдаемое `block`-решение каждого входа.
