## Блокер B1 — fail-open неканонических gitfile после A1

`isLiveLinkedWorktree()` теперь убрал `/m`, но его новая связка

```ts
const trimmed = text.trim();
const m = trimmed.match(/^gitdir:\s*(\S+)$/);
```

не проверяет gitfile в формате, который распознаёт Git. `trim()` удаляет BOM и начальный ASCII-пробел, а `\s*` разрешает ноль ASCII-пробелов и Unicode-пробел. Поэтому она признаёт «живым linked worktree» каталог с невалидным `.git`, если указанная цель существует.

Я построил настоящий linked worktree, взял существующую цель `gitdir`, затем создал отдельные каталоги `wip-101-aa` с поддельным `.git`. Для каждого входа запускались как `node path-guard.ts --extract-pin <каноническое assignment>`, так и настоящий factory seam: `register()` → `session_start` с этим assignment → `tool_call write` внутрь кандидата. Одновременно `git -C <кандидат> rev-parse --git-dir` служил независимым оракулом, признаёт ли Git сам gitfile.

Все следующие формы **отвергнуты Git**, но CLI возвратил непустой пин, а фабрика возвратила `pass`:

| содержимое `.git` | Git | CLI | factory |
|---|---:|---|---|
| `gitdir:<существующий-путь>\n` | reject: `invalid gitfile format` | `{"worktree":"…/wip-101-aa"}` | pass |
| `\uFEFFgitdir: <существующий-путь>\n` | reject: `invalid gitfile format` | непустой пин | pass |
| `gitdir:\u00A0<существующий-путь>\n` | reject: `invalid gitfile format` | непустой пин | pass |
| ` gitdir: <существующий-путь>\n` | reject: `invalid gitfile format` | непустой пин | pass |

Полная выполненная фабричная сводка для каждого из четырёх входов имела `gitParses:false`, `factory:"pass"`; у первого CLI дословно был `{"worktree":"/tmp/adv032-factory-…/no_ascii_space/wip-101-aa"}`.

Дополнительные границы:

- каноническая `gitdir: <path>\n` принята и Git, и subject — честный положительный контроль;
- `gitdir: <path>\r\n` и `gitdir: <path>\r` также приняты Git и subject, поэтому CR/LF сам по себе не является заявленным дефектом;
- `gitdir:  <path>\r` Git отвергает (`fatal: not a git repository: (null)`), subject всё равно возвращает пин.

Это нарушает М1: `.git` обязан быть **файлом с содержимым-строкой формата `gitdir: <путь>`**, а путь обязан быть **живым linked worktree**. Поддельный каталог не является linked worktree для Git, но получает assignment pin и неограниченную в пределах каталога запись. Это именно fail-open guard, не косметическая разница парсера.

Причина, почему существующая приёмка зелена: `п4`–`п4в` судят отсутствие `.git`, мёртвую цель, полностью мусорный текст и каталог `.git`; `п4г` судит multiline-мусор. Ни один вход не судит неканонические пробелы/кодировку/отсутствующий ASCII-разделитель при **существующей** `gitdir`-цели. Поэтому `21/21` не опровергает B1.

Закрытие за автором: валидировать ровно Git-совместимую однострочную gitfile-грамматику, не нормализуя BOM/начальный пробел и не разрешая Unicode/нулевой разделитель; сохранить признание настоящей CRLF-формы. В `red_pin_spawn_zadanie.sh` добавить каждый отрицательный вход минимум через CLI и factory; false pin обязан дать `null`/`block`.

## Замороженный живой пункт — красный

Критерий «После реализации» требует: команда 1 (`write` в **свой** worktree) → `succeeded`; команда 2 (`write` в main-чекаут той же сессии) → блок.

`HANDOFF.md` содержит два сырых результата попыток 1–2 и отдельный сырой результат попытки 3 после варианта D из `54f6cf9`. Во всех трёх команда 1 дословно блокирована:

```text
write /tmp/dev-harness-worktrees/775e24e1/wip-032-implementer/probe.txt
  → блок «запись в чекаут из непиннованной сессии запрещена — Н-85/А-122 … не в null-allowlist»
```

Команда 2 на main-чекауте также заблокирована, то есть её отрицательная половина ожидаема, но она не заменяет обязательный `succeeded` команды 1. Следовательно, живой критерий **не закрыт**.

Диагноз из приложенной стенограммы согласован с результатом: `--extract-pin` на каноническом тексте работает, а фабричный `drv-live.mjs` зелёный лишь потому, что вручную конструирует ветку. Реальный omp-провод не доставляет текст sonic-задания ни lifecycle, ни `getBranch()` на `tool_call`; вариант D поэтому не поднимает pin в живой сессии.

Маршрут: **арбитр по дизайну проводки** (это третий круг данного класса) либо **владелец по v2-зонам**, потому что практический маршрут через `scripts/spawn_agent.sh` лежит вне зон заморозки `032/1`. Ни A1-фиксом, ни ложным объявлением фабричной зелени этот живой пункт закрыть нельзя.
