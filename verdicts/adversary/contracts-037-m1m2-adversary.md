## Блокер M1: уже допущенный владелец подделывает owner.json для вложенного репозитория

`isSelfContainedCwdEligible()` читает артефакт не из самого кандидата, а из
`dirname(canonicalActual)/.omp-isolation-owner.json`. У легитимно допущенного
самодостаточного клона `Outer` разрешена запись во всё `Outer`. Поэтому он
может создать в нём самостоятельное `Inner` с `.git`-каталогом и записать
`Outer/.omp-isolation-owner.json`: этот путь находится снаружи `Inner`, но
внутри уже разрешённого `Outer`. Для `Inner` тот же файл выглядит как
доказательство, якобы созданное harness, хотя его создал код владельца Outer.

Живая проба `tmp/adversary037_m1_nested_forgery.sh` построила два git-репозитория
`$HOME/outer` и `$HOME/outer/inner` и выполнила настоящий
`.omp/extensions/path-guard.ts --judge`:

```
контроль Outer {"decision":"pass"}
атака Inner {"decision":"pass"}
ОБХОД M1 воспроизведён: owner Outer подменил owner.json Inner и открыл его чужой сессии
```

Контроль сначала доказывает, что `Outer` с `sessionName=Owner037` действительно
проходит p.1–p.5. Затем запись `Outer/.omp-isolation-owner.json` с
`{"id":"Owner037.NestedBare"}` даёт непиннованной другой сессии
`sessionName=Owner037.NestedBare` запись в `$HOME/outer/inner/pwned.txt`.
Это именно «владелец создаёт/подменяет owner.json внутри своего уже
разрешённого cwd и открывает ещё более вложенного ребёнка» из направления
проверки.

Красная фикстура M1 этого не ловит: `bash fixtures/self_contained_cwd/red_self_contained_cwd.sh .`
завершился `rc=0`, `ветвей 7, красных 0, зелёных 7`, хотя обход проходит.
Это не уже объявленный остаточный риск «вложенное репо/submodule»: тот риск
говорит лишь о записи внутрь такого репозитория тем же владельцем и прямо
обещает, что чужого дерева не затрагивается. Здесь подделывается машинное
доказательство владения и разблокируется другой unpinned caller.

## Блокер M2: диапазон из двух честных коммитов не принимается

Скрипт сохраняет вывод `git rev-list` в одну многострочную строку
`RANGE_SHAS`, а затем вызывает:

```
git ... cherry-pick "$RANGE_SHAS"
```

Для двух SHA это один argv с embedded newline, а не два аргумента `git
cherry-pick`. В итоге честный линейный диапазон из двух коммитов, каждый с
`%an=implementer` и `%ae=implementer@dev-harness.local`, проходит всю
identity-проверку, но завершается отказом cherry-pick; целевая ветка не
сдвигается. Это нарушает М2 п.5: приёмник обязан cherry-pick-нуть весь
диапазон `<branch>..FETCH_HEAD`, а не только одно-коммитный частный случай.

Живая проба `tmp/adversary037_m2_cases.sh` против настоящего скрипта:

```
позитив rc=0 ACCEPTED branch=wip/201/implementer tip=1283261df8a5944df4c9a293defcc2ee7957c037
два-честных rc=1 ОТКАЗ: cherry-pick отказал (конфликт или иная ошибка)
честный-merge rc=1 ОТКАЗ: cherry-pick отказал (конфликт или иная ошибка)
конфликт rc=1 ОТКАЗ: cherry-pick отказал (конфликт или иная ошибка)
Конфликт M2 очищает временный worktree; M2 не принимает честные диапазоны из нескольких коммитов и merge.
```

Первый ряд — обязательный позитивный контроль: один честный коммит принимается.
Второй — различающий отрицательный контроль для реализации «принимает только
один SHA»: два последовательных честных коммита не приняты. Третий ряд
отдельно подтверждает поставленное направление про merge: identity всех
reachable-коммитов честная, но merge тоже не имеет пути принятия (даже после
исправления передачи списка для merge потребуется явная политика mainline или
именованный предварительный отказ). Четвёртый ряд — нейтрализация очистки:
конфликт оставляет ветку неизменной и не оставляет `$TMPDIR/accept_task_commit.*`;
эта часть защищена.

Обе существующие M2-проверки зелёные при дефекте, потому что принимают только
один честный коммит и используют смешанный диапазон лишь для раннего отказа
identity:

```
bash fixtures/accept_task_commit/red_accept_task_commit.sh .  # rc 0, 5/5
bash fixtures/parsing_hygiene_battery/run_battery.sh accept_task_commit  # rc 0, 4/4
```

Следовательно, текущий набор не различает контрактную реализацию диапазона и
неправильную одно-коммитную реализацию.

## Проверенные неблокирующие направления

- `tmp/adversary037_m1_home_variants.sh` дал `pass` для корректного owner при
  `$HOME` с trailing slash, символьной ссылкой и `..`-сегментом. `safeRealpath`
  перед `isWithin` защищает эти три формы; это не обход.
- Конфликт cherry-pick очищает временный worktree (четвёртый ряд живой пробы
  M2 выше); сирота при этом пути не найдена.
- Основные scoped-фикстуры M1 и M2 и parsing-hygiene battery перечислены выше
  как зелёные, но их зелёность не опровергает два воспроизведённых обхода.

Нужны правки автора M1/M2 и красные сценарии на подмену owner-артефакта через
вложенное репо, на линейный диапазон из двух честных коммитов и явная
контрактная обработка merge-коммита. Этот вердикт гейт нормы не закрывает.
