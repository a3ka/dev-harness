## B3 закрыт для исходного входа

Одноразовый мир `tee-no-reread` заменяет только user-копирование на

```sh

chmod 755 "$BIN_DST/orch-loop"
# намеренно нет check_one после записи
```

и сохраняет остальное дерево. Выполнено:

```sh
REPO_ROOT=/tmp/dev-harness-verify/adv074k3/repo \
OPS_ROOT=/tmp/dev-harness-verify/adv074k3/tee-no-reread \
bash fixtures/_krasnye_074.sh
```

Результат: `rc=1`, `k1b: rc=0 на испорченной записи (interposer: 1,
шины: cp/cat/install) — user-часть не перечитывает sha256`, затем
`КРАСНО: cell_k1b`; прочая честная часть осталась `7/7`, стаб-пак `7/7`,
каналы `6/6` честных и `6/6` ленивых. Следовательно, исходный B3 (tee без
перечитывания) более не проходит и порча действительно была внесена.

Тем же способом повторены прежние входы `cat-no-reread` и
`install-no-reread`. Каждый дал `rc=1`, ту же именованную причину к1b со
счётчиком interposer `1`, `КРАСНО: cell_k1b`, при `честная часть: 7/7` и
`стаб-пак: 7/7`.

## Новый живой обход — Python standard library вне перехватов

Порог B3 не закрыт для любого механизма записи. Построены три отдельных
одноразовых мира. В каждом менялся только user-копирующий фрагмент
`install.sh`: запись корректно получает байты из `"$SRC_ROOT/user/orch-loop"`,
затем выполняет штатный `chmod 755`, но намеренно не вызывает `check_one`.
Не добавлялись бинарники или какие-либо изменения батареи. Все команды ниже
используют уже обязательный для раннера `python3` и его штатную библиотеку.

1. `python-pwritev-no-reread`: `python3 -c` читает источник блоками и пишет
   каждый блок в открытый адресат через `os.pwritev(fd, [buf], offset)`.
2. `python-splice-no-reread`: `python3 -c` переносит источник в pipe и pipe
   в адресат циклом `os.splice`.
3. `python-mmap-no-reread`: `python3 -c` открывает адресат `O_RDWR`, делает
   `ftruncate`, записывает байты в `mmap(..., ACCESS_WRITE)` и вызывает
   `flush()` (`msync`).

Для каждого по отдельности исполнено:

```sh
REPO_ROOT=/tmp/dev-harness-verify/adv074k3/repo \
OPS_ROOT=/tmp/dev-harness-verify/adv074k3/python-<механизм>-no-reread \
bash fixtures/_krasnye_074.sh
```

Все три дали **`rc=0`** и одинаково приняли неверного субъекта:

```text
k1b: все каналы порчи инертны (субъект не пишет байты — rename-класс,
остаточный предел) — проба не судит, перечитывание судится стабом s7 и
канальными пробами
честная часть: 7/7 зелёная
стаб-пак: 7/7 поймано, диффпроба: 7/7
к1b-каналы: честные 6/6, ленивые пойманы 6/6
итог 074: красных клеток=0 стабы=7/7
```

Это не отказ инструмента и не «пустой» успех: до запуска адресата нет,
после него `cell_k1` подтверждает его SHA-256, пин и `755`; во время к1b
запись реально происходит, но `ORCH074_CORRUPT_LOG` остаётся пуст, поскольку
interposer не перехватывает `pwritev`, `splice` либо грязные страницы
`mmap`/`msync`. Затем к1b ошибочно приравнивает отсутствие записи в журнале
к rename-классу и возвращает зелёное. Неверная ветка (`check_one` удалён)
работает, а проверка не падает.

Это блокер, а не названный недостижимый предел: `install.sh` остаётся обычным
shell-скриптом, а `python3` уже является штатной зависимостью батареи и
отдельно охвачен её «python3»-каналом. Реализовать каждую из трёх веток можно
без статически слинкованного субъекта, внешнего инструмента или добавленного
файла в предмет.

## Попытки именованного предела

Для полноты также построены отдельные одноразовые субъекты без
`check_one`:

* `mv-no-reread` переносит два заранее подготовленных побайтных кандидата
  через `mv` (по одному на каждое user-выполнение батареи);
* динамический helper с `pwritev`, helper с pipe+`splice`, helper с
  `mmap`+`msync`, а также `cc -static` helper, вызывающий прямой
  `SYS_pwritev`.

Каждый из них прошёл полный раннер с `rc=0` и той же строкой «все каналы
порчи инертны». Они подтверждают ровно объявленный остаточный предел
rename/direct-syscall и обходы `pwritev`/`splice`; сами по себе helper-варианты
не нужны для вердикта. Решающее предъявление выше сильнее: три Python-варианта
не требуют helper и потому опровергают, что предел не реализуем в обычном
предмете.

## Вердикт

**FAIL.** Структурный interposer устранил конкретный tee-обход B3 и сохранил
положительные/отрицательные контроли, но новый живой обход через

допустимый механизм нормативно и проверяемо, закрытие B3 не принято.
