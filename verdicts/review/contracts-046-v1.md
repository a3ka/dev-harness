## 1. Реализация повторяет ФИНАЛЬНЫЙ прецедент, а не устаревший `unset`-перечень

Блок «ГЕРМЕТИЧНОЕ ОКРУЖЕНИЕ» — три исполняемые строки. Побайтовая сверка
с двумя прецедентами (сравнение хешем, не глазами):

```
$ sed -n '139,142p' scripts/check_protected.sh | md5sum
c44d39468404f8b79360e6b66887be8f  -
$ sed -n '202,205p' scripts/check_zones.sh     | md5sum
c44d39468404f8b79360e6b66887be8f  -
$ sed -n '123,126p' scripts/check_provodka.sh  | md5sum
c44d39468404f8b79360e6b66887be8f  -
```

То есть форма ИДЕНТИЧНА `check_zones.sh` и `check_provodka.sh` байт-в-байт:

```sh
if ( return 0 2>/dev/null ) || [[ "$(/usr/bin/tr '\0' '\n' < /proc/$$/environ)" != $'PATH=/usr/bin:/bin\nLC_ALL=C.UTF-8' ]]; then
  POSIXLY_CORRECT=1
  exec /usr/bin/env -i PATH=/usr/bin:/bin LC_ALL=C.UTF-8 /usr/bin/bash "${BASH_SOURCE[0]}" "$@"
fi
```

Прецедент — именно ФИНАЛЬНЫЙ. Строка `POSIXLY_CORRECT=1` попала в
`check_zones.sh` ровно одним коммитом:

```
$ git log --oneline -S'POSIXLY_CORRECT=1' -- scripts/check_zones.sh

```

— это v7, редакция ПОСЛЕ падения `unset -f`-перечня (v5, `d46a615`) и после
fail-open `if/else` (v6). Устаревшего подхода не осталось ни в одном из трёх
барьеров:

```
$ grep -n '^[^#]*unset -f' scripts/check_protected.sh ; echo rc=$?   → rc=1 (нет)
$ grep -n '^[^#]*unset -f' scripts/check_zones.sh     ; echo rc=$?   → rc=1 (нет)
$ grep -n '^[^#]*unset -f' scripts/check_provodka.sh  ; echo rc=$?   → rc=1 (нет)
```
