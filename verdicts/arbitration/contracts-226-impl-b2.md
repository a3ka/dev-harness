## Решение

1. **Б-1 / К-08, К-09, К-10, К-16 обоснован. Прав adversary. Исправить способом канон/инструмент + клетка.** Дословный мутант условия входа в валидацию принимает CR, полный W его пропускает. Это дефект различимости батареи и исполнения первого арбитража, не найденный обход честной production. На том же поддерживаемом профиле честная production отказывает правильно.
2. **Полная сетка через публичный resolver не обязательна.** Автор прав, что независимый A/B-оракул и быстрый пакетный прогон полезны и что бесконечную полноту конечная батарея не обещает. Но вынутый jq — наблюдаемый внутренний субъект, НЕ оракул и НЕ результат публичного resolver. Оставить пакетную сетку; добавить независимый публичный слой по каждой оси и каждой различающей позиции/ветви, с адресными мутациями управления. Просто одна CR-клетка или одна клетка на крупный заголовок «строки» недостаточна. Конечный перечень ниже заменяет неопределённое требование «каждый следующий сосед».
3. **Возражение автора записано:** 933 полных запуска в каждом режиме дороги; прежние публичные клетки покрывают представителей; новый мутант меняет управление, а не вынутый предикат. Последнее верно и является причиной исправления, а не оправданием пропуска. Первый арбитраж требовал rc 1 / пустой stdout / предметную причину именно наблюдаемого отказа; `jq` с stdout `false\n` и пустым stderr этим свидетельством не является.
4. **Инженерная очередь: один узкий ремонт Architect226f → готовый зелёный кандидат → один первый полный Rev226, проверяющий весь diff и исполнение этой границы. Adversary повторно не назначать.** Но переход без его accept имеет отдельное условие полномочия: текущие нормы и машинная дверь НЕ разрешают арбитру заменить обязательную подпись. Поэтому автоматический маршрут «ремонт → reviewer → done» из постановки спора отклонён в части полномочий; до такого перехода нужно адресное слово владельца, сформулированное ниже. Ремонт этим не блокируется. Настоящее решение не принимает обнаруженный остаток, не выдаёт accept и не назначает четвёртый adversary.

### 2. Почему внутренняя сетка не наблюдает обход

`probe.py:183-215` запускает resolver на одном корректном `ab/cd` и получает из bash xtrace argv валидатора/слияния. `probe.py:219-238` подставляет прочие значения прямо в отдельно запущенный jq. Публичный resolver вызывается только при уже найденном расхождении (`probe.py:239-249`). У CR-мутанта вынутый предикат не меняется: оракул и jq согласны об отказе, поэтому публичный вызов на CR вообще не происходит.

Управление production отдельно от грамматики: `scripts/profile_resolver.sh:951-964` — defaults guard, `has("hooks")`, форма объекта, `has("archBrief")`, тип листа, `else false`, обработка отказа. `die_p` в строке 228 печатает причину и завершает rc 1; merged в строках 1096-1099 не исправляет пропущенную валидацию. Следовательно, доказательство `P(v)=false` в отдельном jq не доказывает, что публичный путь вызвал P(v) и правильно обработал false.

Полная конечная сетка через CLI исключила бы пропуск на её входах, но тоже не доказала бы все строки. Более дешёвое достаточное обязательство батареи — публичные свидетели разделений входов и всех названных управляющих операций плюс независимый полный внутренний набор. Это граница метода, не разрешение принимать неверный профиль.

## Что делать автору/оркестратору

### 1. Один ремонт существующей семьи, не новая батарея

Architect226f меняет только свою семью 226. Сохраняет все прежние клетки, 47 носителей мутаций, 63 связи, независимый `grammar_accepts`, всю пакетную сетку и интеграционные проверки дверей/пина/слоя. Production и frozen-текст ради этого блока не меняются. В SDACHA различает «внутреннее исполнение jq» и «публичный CLI»; зелёный внутренний отрицательный результат не описывается как пустой stdout/диагностика публичного отказа.

Публичные свидетели исполняются **без условия `if errors`**, для каждого выбранного входа. Можно переиспользовать готовый мир, перезаписывая только профиль перед новым процессом resolver; ожидания вычисляются до субъекта. Нельзя кешировать итог resolver между разными входами/носителями. Для каждого отрицательного значения: rc ровно 1, stdout строго пуст, stderr с предметным `hooks.archBrief` и истинной причиной. Для допустимого значения: rc 0, полный merged JSON с точным значением/типом и origin=repo; не только флаг «включено». Сохраняются проверки отсутствия побочных эффектов. Инфраструктурный rc 2/126/127 не считается пойманной предметной мутацией.

Не «одна строка на ось вообще», а следующие представители разделений. Все названные значения ниже уже выводятся из инварианта/сетки; перекрывающиеся существующие публичные клетки засчитываются, дублировать их не требуется. Ожидание для значений — прежний независимый A/B-оракул, не production-regex.

Полный декартов продукт ошибок, все длины и все Unicode-коды не требуются.

### 3. Мутации управления, обязанные краснеть публично

Каждая — отдельно, изменение существующей операции, без подгонки ожидаемого ответа. Architect связывает её с достижимым входом по коду; в catalogue/source.json различается, на каком уровне исполняется свидетель.

1. **Дословный CR-мутант Adv226c**, приведённый выше. Обязательное наблюдение: красный публичный CR-свидетель, а не только сбой извлечения jq.
2. Внешний `has("hooks")`: нейтрализация входа в проверку; отдельно инверсия условия. Проверить отрицательный лист и корректное отсутствие hooks, не принимать краш jq за требуемый отказ.
3. Проверка `.hooks | type == "object"`: снятие её отказа. Отрицательная форма должна отличаться по точному rc/именованной причине/выходу, даже если более поздний jq тоже ругается.
4. Внутренний `has("archBrief")`: уже существующий st06 с заменой на `!= null`; отдельно условие, допускающее в проверку только строки, и нейтрализация входа целиком. Эти изменения проверяют различение наличия, null и других типов, не только false.
5. Ветви значения: boolean false → любой boolean; JSON 0 вместо false; `else false` → true; снятие/инверсия проверки строкового типа. Прежние соответствующие стабы сохранить; у новых управляющих замен должен быть публичный свидетель.
6. Отказ результата валидатора: нейтрализация `|| die_p`, изменение отказного rc 1 на 0 и на 2 (последний не засчитывать как корректный предметный отказ); удаление предметной причины или вывод ошибки в stdout вместо stderr. Это проверки существующих каналов отказа, не добавление новых правил грамматики. Если тот же эффект уже предъявлен адресным стабом, второй носитель не нужен.
7. Сохранить все дословные исторические мутации предиката (конечный SP, начальный `_`, FALSE/False) и остальные действующие связи. Для новых guard-стабов `--stabs` обязан вызывать публичный CLI на адресном входе даже при зелёном вынутом предикате; не весь публичный набор на каждом стабе.

Честная production, model и эквивалентные записи предиката/guard должны оставаться зелёными. Эквивалентность проверять по публичному результату, не по совпадению текста xtrace; смена вида честного предиката не должна ложно красить семантический контроль. Отказ инфраструктуры пакетного шва сообщать как rc 2, не выдавать за обнаруженную неправильную грамматику.

Н-39 дословно: стабы к ветвям привязывает architect по коду, НЕ проза контракта; контракт несёт инварианты + rc-команды. Приведённый перечень — требуемые семейства свидетельств арбитража; исполняемые замены, якоря и связи остаются в build.py/source.json у архитектора. Я их не реализую и не утверждаю пока красными.

### 4. Сдать одну завершённую пачку и один замер
