## Замеры арбитра (клон HEAD `f9ea6fb`, git 2.55.0, игрушки в /tmp/dev-harness-verify/arb029)

1. **Обход критика ПОДТВЕРЖДЁН лично (M1).** Игрушка: tracked `before`→`after`,
   `diff.external=./write-diff.sh` (скрипт пишет файл). Голый `git diff`: rc=0,
   stdout+stderr 0 байт, sha256 = `e3b0c442…b855` (пустой вывод), маркер-файл СОЗДАН.
   Без драйвера тот же argv даёт непустой патч (131 байт). Критик прав в факте целиком.
2. **Меры (1)+(3) сами по себе обход НЕ останавливают (M2).** Тот же прогон под
   `env -i PATH LC_ALL GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null`:
   rc=0, sha честный, скрипт ИСПОЛНЕН — `diff.external` живёт в ЛОКАЛЬНОМ конфиге,
   которого эти меры не касаются. Несущая мера — (2).
3. **Мера (2) работает для конфиго-носимых каналов (M3, M4, M8).**
   `git -C <root> config --list --local` под скрабом печатает `diff.external=…` БЕЗ
   исполнения. Той же природы и той же поимкой: `core.fsmonitor=<скрипт>` исполняется
   на `git status` (M4, маркер создан); `filter.<x>.clean` + `.gitattributes` исполняется
   на `git diff` (M8, маркер создан). Оба — неизвестные ключи → default-deny отказывает.
4. **`include.path` и `.git`-файл ловятся ТОЛЬКО при скане через git (M7a, M7b).**
   `--list --local` печатает сам ключ `include.path=…` (включённое содержимое НЕ
   инлайнится — но ключ неизвестен → отказ). Репозиторий с `.git`-ФАЙЛОМ
   (`--separate-git-dir`): `git config --list --local` резолвит gitfile и показывает
   `diff.external` реального gitdir; чтение `.git/config` как сырого пути этот случай
   ТЕРЯЕТ.
5. **КАНАЛ ВНЕ кандидат-фикса №1 — голые хуки (M5, M5c).** Конфиг корня ПУСТ (четыре
   init-ключа), исполняемый `.git/hooks/post-index-change` пишет маркер. Плоский
   `git status --porcelain` под полным скрабом ИСПОЛНИЛ хук. Остальные шесть глаголов
   перечня — нет. Подавление измерено двумя способами: `GIT_OPTIONAL_LOCKS=0` и
   `-c core.hooksPath=<пустой каталог>`; вывод status при подавлении байт-в-байт равен
   неподавленному (маркеры вычищены перед обоими прогонами).
6. **КАНАЛ ВНЕ кандидат-фикса №2 — субмодуль (M6, M6b, M10).** Superproject с гитлинком,
   локальный конфиг корня НЕВИННЫЙ (ровно четыре init-ключа, `submodule.*` удалены);
   в конфиге субмодуля (`.git/modules/sub/config`) `core.fsmonitor=<скрипт>`, в его
   hooks — `post-index-change`. `git status --porcelain` в корне ИСПОЛНИЛ ОБА. Скан
   `--list --local` корня канал не видит по построению. Барьерное
   `-c core.hooksPath=<пустой>` пропагируется в дитя-git субмодуля (хук подавлен, M10),
   но config-fsmonitor субмодуля ИСПОЛНЕН И ПОД НЕЙ: конфиго-пространство субмодуля
   недостижимо для скана корня и не закрывается `-c`-переопределениями без чёрного
   списка ключей — дырявого по построению (тот же довод, каким круг 1 отверг чёрный
   список опций).
7. **Обнаружение гитлинка механично:** `git ls-files -s` содержит mode `160000`
   (замер: ровно 1 строка). `git init` кладёт в локальный конфиг ровно
   `core.repositoryformatversion, core.filemode, core.bare, core.logallrefupdates` —
   существующие игрушки `_konsult.sh` под whitelist этих четырёх проходят.

## Решение по вопросам

**1. Факт критика.** Подтверждён лично (замер 1). Оба круга — одна причина, созыв
арбитра правомерен.

**2. Достаточность кандидат-фикса.** НЕДОСТАТОЧЕН как заявлен. Меры (1)–(3) необходимы
и закрывают все КОНФИГО-носимые каналы корня (diff.external, fsmonitor, filter/textconv,
include/includeIf, hooksPath, pager — всё ключи, default-deny их отказывает), но измерены
два канала ВНЕ них: голый хук `post-index-change` при пустом конфиге (замер 5) и
конфиг/хуки СУБМОДУЛЯ при невинном конфиге корня (замер 6). Плюс два уточнения к самой
мере (2), без которых она дырява: скан ОБЯЗАН идти через git (`git -C <root> config
--list --local`), не сырым чтением файла `.git/config` (иначе `.git`-файл уводит конфиг
из-под скана, замер 4); нечитаемый конфиг (rc скана ≠ 0) — отказ, не пропуск.

**3. Достаточная и механически проверяемая граница** (обязательна к реализации; способ
разбивки по файлам — за автором):

- **Г1 (среда).** Каждый git-вызов барьера в `--root` — и скан-гейты, и переисполнение —
  под закрытым env-allowlist (`env -i` + PATH, LC_ALL) с
  `GIT_CONFIG_GLOBAL=/dev/null GIT_CONFIG_SYSTEM=/dev/null GIT_OPTIONAL_LOCKS=0`.
- **Г2 (конфиг-гейт, ДО первого переисполнения).** `git -C <root> config --list --local`
  под Г1; ключи судятся ЗАКРЫТЫМ перечнем
  {`core.repositoryformatversion`, `core.filemode`, `core.bare`, `core.logallrefupdates`}
  (расширение платформенно-скучными `core.ignorecase`, `core.precomposeunicode`,
  `core.symlinks` — на усмотрение автора; все перечисленные не исполняют код ни при
  каком значении). ЛЮБОЙ иной ключ, включая `include.*`/`includeIf.*` — rc 1
  «конфиг вне белого списка» БЕЗ исполнения, с именем ключа. Скан упал (rc ≠ 0) — тот же
  отказ. Судятся КЛЮЧИ; скан — через git, не сырым путём.
- **Г3 (хуки).** Каждая переисполняемая команда несёт барьерное
  `-c core.hooksPath=<пустой каталог ВНЕ --root, созданный барьером>`. Замер 5: канал
  жив без этого при ПУСТОМ конфиге; вывод команд не меняется.
- **Г4 (субмодули, ДО первого переисполнения).** `git -C <root> ls-files -s` под Г1;
  любая строка mode `160000` — rc 1 поимённый отказ (пиннованная подстрока — выбор
  автора, например «субмодуль вне границы») БЕЗ переисполнения. Замеры 6/M10: канал
  недостижим для Г2 и не закрывается Г3. ТРЕЙДОФФ записан: честное дерево-основание с
  субмодулем отвергается — ограничение интерфейса того же класса, что уже принятый
  трейдофф инв. 9 по опциям.

Отвергнутые альтернативы (чтобы круг 3 их не переизобретал): изоляция клоном ломает
семантику предмета — честный позитивный контроль (вход 5 `red_lozhnyj_rc.sh`) судит
ГРЯЗНОЕ дерево, которого в клоне нет; `-c`-переопределения опасных ключей
(`core.fsmonitor=false`, …) — чёрный список, дыряв по построению; рекурсивный скан
`.git/modules/**/config` — открытая рекурсия (вложенные субмодули, worktree-конфиги,
gitfile-индирекция), закрытая форма — отказ Г4.

**Красные входы** (обязан предъявить автор, красными на текущем HEAD `f9ea6fb`, в
круге 3; раскладка — расширение `red_lozhnyj_rc.sh` входами 8–10 либо новый red-файл с
правкой счёта в приёмке — выбор автора):

- **вход «чужой конфиг» (именованный вход этого арбитража):** игрушка с изменённым
  tracked-файлом, `git config diff.external ./write-diff.sh`, скрипт пишет маркер;
  ответ консультанта ЧЕСТЕН (`КОМАНДА: git diff`, `RC: 0`, sha пустого вывода
  `e3b0c442…b855`) → rc 1 «конфиг вне белого списка», маркера в корне НЕТ. Комментарий
  входа обязан фиксировать: числа честны по построению — сверка rc/sha этот обход не
  ловит, ловит только Г2.
- **вход «голый хук»:** конфиг игрушки пуст, исполняемый `.git/hooks/post-index-change`
  пишет маркер, тройка для `git status --porcelain` на грязном дереве ЧЕСТНАЯ →
  rc 0 И маркера НЕТ (позитивный контроль, обязанный пройти БЕЗ исполнения хука; ловит
  реализацию без Г3).
- **вход «субмодуль»:** гитлинк при невинном локальном конфиге корня; в конфиге
  субмодуля `core.fsmonitor=<скрипт-маркер>`, в его hooks — маркер-хук; тройка честная →
  rc 1 с пиннованной подстрокой Г4 И обоих маркеров НЕТ.

**4. Круги.** Вопрос достаточности readonly-границы этим вердиктом ЗАКРЫТ. Круг 3
критика судит ТОЛЬКО применение: соответствие контракта и предъявлений границе Г1–Г4 и
живость трёх входов. Повтор причины «граница недостаточна» без НОВОГО измеренного
канала вне Г1–Г4 — повтор закрытой причины; новый измеренный канал вне Г1–Г4 — законная
новая находка, не повтор.

## Остаточные риски (записаны, не блокируют)

  (как субмодульный) закрытыми списками не гарантируется — триггер перезамера: смена
  мажорной версии git в среде барьера.
