## Решение по пунктам

### П1 (повтор кругов 1–2): critic прав — Г7 НЕ закрывает Г1/Г2, нужны две новые исполняемые клетки

**Почему Г7 не закрывает.** У трёх клеток три разных субъекта: Г1 — `gen_ci_steps.sh`, Г2 —
`ci.yml`, Г7 — `run_ci_lane.sh`. Г7 доказывает «раннер работает», Г2 — «раннер упомянут в
теле джобы», и между ними нет стыка «ШАГ workflow ВЫЗЫВАЕТ раннер» — обход 2 живёт ровно в
этом зазоре (замер 2). Г1 с Г7 не связан вовсе — обход 1 живёт в Г1 нетронутым с круга 1
(замер 1). Довод автора «Г7 закрывает исполняемость lane» верен для класса «noop-раннер» и
только для него; круг 2 закрыл этот класс, но не причину блокера — «критерий принимает
упоминание за исполнение, а сверку за генерацию».

**Требует ли критик невозможного.** Нет. Оба недостающих критерия исполнимы на уже
существующем каркасе батареи (toy Г1, L7 Г7) и измерены (замер 3); порог не «доказать
GitHub-прогон локально», а «исполнить то, что написано в `ci.yml`, и то, что называется
генератором». Это та же планка, что уже применена к раннеру в Г7, — её просто не довели до
двух остальных субъектов.

**Что обязано появиться (инварианты обязательны; нумерация/имена клеток — на усмотрение
автора, но каждое предъявление — своя строка `ok`/`FAIL`):**

**(а) Генерация, не сверка — клетка «Г1-генерация» (или Г8).** Контракт в инв. 1 называет
только `--check`; write-режим подразумевается инв. 3 («файлы не трогаются») и нигде не
назван — батарея не может звать то, чего нет в грамматике. Контракт ОБЯЗАН назвать
write-режим (например `bash scripts/gen_ci_steps.sh --write [--root <dir>]`; имя флага —
выбор автора, но он фиксируется в инв. 1, а не выводится исполнителем). Клетка на toy-копии
(`ci.yml` + реестр + `package.json` + генератор):
  1. тело ОБОИХ блоков между маркерами удалено (маркеры оставлены) → `--check --root toy` →
     rc 1 с именованным дрейфом; затем write-режим `--root toy` → rc 0; затем ОРАКУЛ БАТАРЕИ
     (собственный парсер, не повторный вызов субъекта) судит записанный блок: lane-строк
     ровно K toy-реестра, ключи всех lane == step-ключам toy-реестра каждый ровно один раз,
     граница баланса инв. 4, шарды поключево == shard-строкам; затем `--check --root toy` →
     rc 0;
  2. дифференциал по реестру: toy-реестр изменён (K → другое значение в 6..8 И один
     step-ключ переименован) → write → блок изменился соответственно (lane-строк = новое K,
     новый ключ присутствует, старый отсутствует); блок — ФУНКЦИЯ реестра, а не хранимая
     константа;
  3. `--check --root <НЕИЗМЕНЁННАЯ toy-копия>` → rc 0 (ловушка для арность-считающей
     заглушки; стоит одну строку, закрывает буквально предъявленный обход, но сам по себе
     НЕ достаточен — заглушка-сверялка без генерации его проходит, потому 1–2 обязательны).

**(б) Исполнение шага workflow, не упоминание — клетка «Г2-исполнение» (или Г7-г).**
Батарея извлекает из тела джобы `ci` `run:`-значение ЕДИНСТВЕННОГО lane-шага (однострочный
скаляр; `run: |`/`>` или иное неизвлекаемое значение — именованное красное «lane-шаг не
извлекаем», никогда не зелёное — форма шага в зоне автора, он вправе её ужесточить в инв.
2), заменяет ЛИТЕРАЛЬНЫЙ токен `${{ matrix.keys }}` на `k2 k4 k6`; любой оставшийся `${{`
— именованное красное; исполняет `bash -eo pipefail -c "<команда>"` из корня toy L7 (тот
же toy-реестр и sk-скрипты, что в Г7); зелёное — rc 0 И журнал `k2 k4 k6` по порядку.
Второе предъявление через тот же путь с `k1 k5 k3` (rc≠0, причина именует k5, k3 не
исполнен) — желательно, но не обязательно: fail-fast раннера уже доказан Г7, стык
«шаг → раннер» доказывается одним прогоном.

Отклонённая альтернатива: ужесточить grep Г2 до литерала `run: bash scripts/run_ci_lane.sh
${{ matrix.keys }}`. Это снова текст: закрывает предъявленный экземпляр (`echo`), не класс
(`true # bash scripts/run_ci_lane.sh …`, `: && …`, обёртка-скрипт, печатающая строку).
Исполнение извлечённой команды на одну строку длиннее и закрывает класс.

**Что остаётся как есть.** Г7 (три предъявления) — правильная клетка, не трогать. Структурные
проверки Г2 (маркеры внутри тела, `strategy:`/`matrix:`, ≤1 `npm run`) — нужны как
именованная диагностика формы, остаются; они не ЗАМЕНЯЮТ (б).

**Контракт.** Текст Г1/Г2 в §Приёмка и инв. 1 (write-режим) правятся вместе с батареей: прозу
Г2 «ровно один `run:`-шаг с `run_ci_lane.sh`, потребляющий `${{ matrix.keys }}`» сегодня
удовлетворяет `echo` — дефект критерия, не только кода. Замер «ДО круга N» в А1 после правки
пересчитывается автором живым прогоном (ok/FAIL сменятся).

### П2 (А3, новая находка v2): critic прав — неполное окно не бывает зелёным

`timing_083.sh:37` `|| continue` противоречит собственному контракту А3 (`:271-277`: «rc 2 —
данных нет … НЕ зелёное, приёмка не проходит „по умолчанию“») и §Остаточный риск
(«недоступность — rc 2 „не судимо“»). Обязательное поведение: любой отказ `gh run view`
(и отказ `jq` на его ответе) по ЛЮБОМУ прогону окна → немедленный rc 2 с причиной,
называющей id прогона и stderr gh (сейчас `2>/dev/null` — stderr терять нельзя,
прецедент `gh run list` в той же сцене `:31-33` уже пишет его в файл и печатает). Максимум
и счётчик отмен считаются ТОЛЬКО по полностью прочитанному окну; «исключить непрочитанный
прогон из max» — запрещено. Приёмка ждёт данных (повтор команды), не обнуляет порог.
Попутно (не предмет спора, решения не требует): контракт А3 говорит «на первом
ЗАКОНЧЕННОМ прогоне», скрипт судит до 20 законченных прогонов ветки — автору стоит
согласовать формулировку с кодом, чтобы следующий круг не спорил о размере окна.

### Вне решения

судится; закрывает автор по своему усмотрению.
