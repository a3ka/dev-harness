# Арбитраж 027 — граница после трёх кругов (изоляция probe, грамматика OID, O_NOFOLLOW)

## Предмет и триггер

Контракт 027 (`contracts/027-doc-priemka.md`, тег `frozen/contracts/027/3`), три
круга проверяющего: к1 (5 находок, закрыты `75f0c0d`), к2 (4 находки, закрыты
`fcaaf60`), к3 (`verdicts/adversary/contracts-027-k3.md`, судимая база `910b848`).
Три круга по одному предмету, каждый находит расширяющиеся грани реализации, —
созван арбитраж границы: что правится, что фиксируется именованным остаточным
риском. Клон арбитра `/tmp/dev-harness-verify/arb-027b/repo` от HEAD `936fba5`.
Граница threat-model для класса in-process `LD_PRELOAD`-интерпозера принята
владельцем (`verdicts/adversary/contracts-026-k5.md`, раздел «Остальные новые
атаки», последний пункт: интерпозер исполняет код внутри процесса и контролирует
окружение самого вызывающего) — здесь ПРИМЕНЯЕТСЯ, не пересуживается.

## Замеры арбитра

1. `validateProbeArgv` (`doc_contract.ts:198-215`) прогнан напрямую (node
   v26.5.1): `["node","--input-type=module","--import=data:…","-"]` → `null`
   (принят), как и `python3 -m json.tool x.json` и `node -r ./hook.cjs probe.js`;
   `python3 -c` отвергнут именованно. Факт к3 подтверждён и расширен: поверхность
   загрузки кода интерпретаторов (`--import`, `-m`, `-r`, `--require`, env-каналы)
   не перечислима по построению.
2. `git rev-parse --verify <UPPER-HEX-40>^{commit}` в клоне → canonical
   lower-case OID, rc=0: git действительно принимает полный upper-case SHA как
   имя того же объекта. `GIT_OID_RE` (`doc_contract.ts:32`) — только `[0-9a-f]`:
   отказ upper-case подтверждён чтением кода.
3. `doc_contract.ts:169` — `fsConstants.O_NOFOLLOW ?? 0`: fail-open fallback
   подтверждён чтением. На Linux константа определена (замер: 131072), ветвь
   недостижима; на платформах без неё (Windows-сборки node) защита исчезает
   молча при сохранении зелёного.

## Квалификация находок к3

### 1. `node --import=data:` — остаточный риск; поведение верно, правится только заявление

Замороженный текст обещает про probe механизм: «без shell», cwd изолированного
чекаута, «без подразумеваемой сети», JSON stdout + rc-дисциплина, оракул в
памяти, сохранность проекта. Probe контрактно ОПРЕДЕЛЁН как argv: «probe (argv —
непустой массив строк, pointer, expected)»; требования «код только в файле» в
тексте нет, и «подмены probe» нет — argv и есть probe, замороженный и видимый
ревьюеру при freeze дословно, нагляднее кода в файле чекаута. Все обещанные
свойства инвариантны к месту размещения текста программы: `python3 probe.py`
исполняет столь же произвольный код в той же изоляции. `--import=data:` — не
shell и не сеть. Значит rc=0 на этом конформном входе не нарушает ни одного
замороженного инварианта: находка фиксирует не false-accept, а ложность
ЗАЯВЛЕНИЯ фикса `fcaaf60`, будто запрет `-c`/`-e`/`--eval` закрывает
«исполнение кода в обход argv-модели». Замер 1 показывает: перечислимой границы
нет, гонка по флагам проигрышна по построению. Расширение блоклиста по одному
флагу этим решением ЗАПРЕЩАЕТСЯ — оно отвергало бы конформные входы, не давая
границы.

Правка (границы достаточности): только заявление, не поведение. Комментарий
блока валидации argv в `doc_contract.ts` перестаёт называть запрет флагов
границей безопасности и называет честную границу: изоляция чекаута + оракул в
памяти + freeze + суд ревьюера над argv как над кодом. Запрет `-c`/`-e`/`--eval`
и allowlist argv[0] остаются как гигиена наиболее вероятных форм, без претензии
на полноту.

Residual-строка для ревьюера: «probe.argv — исполняемая программа ЦЕЛИКОМ,
включая флаги интерпретатора (`--import`/`-m`/`-r`/data:-URI); allowlist и
запрет `-c`/`-e` — гигиена, не граница. Судить содержимое argv при freeze как
код.»

### 2. Upper-case полный hex OID — остаточный риск (долг текста контракта); правка кода не требуется

Строго по тексту: контракт говорит «commit (полный OID), blob (полный OID)» и о
написании OID больше ничего; «(40/64 hex)» — формулировка сообщения реализации,
не контракта. Явная ID-грамматика контракта (`[A-Za-zА-Яа-яЁё0-9]…`) на OID не
распространяется: в sources `id` — отдельное поле от `commit`/`blob`.
Демаркация контракта: «Конформный вход соответствует ОПИСАННОЙ … грамматике» —
грамматика написания OID текстом не описана, а «полный» противопоставлен
сокращённому (закрытая находка к2-1), не регистру. Каноническое имя объекта в
git — lower-case hex (вывод `rev-parse`/`cat-file`); upper-case — принимаемое
git-ом альтернативное написание того же объекта (замер 2). Реализация выбрала
единственное детерминированное каноническое написание, и это направление
fail-closed: именованный rc=1, ложного принятия нет, автор doc-контракта
получает OID из вывода git и исправляет вход тривиально. Асимметрия
верификатора: реализация вправе быть строже недоговорённого текста в сторону
ОТКАЗА (rc=1 не порождает основания принятия), но не в сторону принятия.
Принятие upper-case без нормализации сломало бы сравнение с выводом
`^{commit}` (отмечено самим к3) — выбранная строгость дешевле и безопаснее.

Остаток — долг ТЕКСТА: при следующей версии/разморозке контракта architect
именует грамматику явно («полный OID — canonical lower-case hex, 40/64
символа»). До того residual-строка для ревьюера: «Написание OID — канонический
lower-case hex; полный upper-case SHA git-разрешим, но отвергается схемой
именованным rc=1 (fail-closed, не false-accept); грамматика подлежит именованию
в следующей версии текста контракта.»

### 3. `O_NOFOLLOW ?? 0` — ПРАВКА (fail-closed rc=2)

Транспорт демонстрации к3 (preload снимает флаг у `open`) принадлежит классу
in-process интерпозера, принятому владельцем в 026-k5, — сама демонстрация
правку не вынуждает и не пересуживается. Но конструкция `?? 0` дефектна
независимо от транспорта: платформа без `fsConstants.O_NOFOLLOW` реальна
(Windows-сборки node), и на ней гарантия «без выхода через симлинк» при чтении
исчезает молча при сохранении rc=0. Это прямо противоречит rc-семантике
контракта: «2 — нечем проверить». Невозможность выполнить обещанную проверку
обязана быть именованным rc=2, не тихим продолжением без защиты.

Границы достаточности: в `resolveSafePath` при неопределённом
`fsConstants.O_NOFOLLOW` — именованный отказ до `open`, отображаемый в rc=2
(«платформа без O_NOFOLLOW: чтение без TOCTOU-защиты невозможно»). Больше
НИЧЕГО: защита от in-process интерпозеров не требуется (принятый класс);
повторная верификация fstat/realpath не требуется; постоянная фикстура не
требуется — ветвь недостижима на Linux-CI, а мок `fsConstants` пиновал бы
реализацию. Достаточность предъявляется чтением диффа и зелёным
`bash scripts/verify_antiplacebo.sh --scope check_document render_document
freeze_contract check_check_contract_ready`.

## Решение

Правится: находка 3 (fail-closed rc=2 при отсутствующем `O_NOFOLLOW`) и
заявление по находке 1 (комментарий валидации argv). Находки 1 и 2 закрыты этим
вердиктом как остаточные риски с приведёнными residual-строками; долг текста по
OID — architect при следующей версии, реализацию не блокирует. Повтор причин 1
и 2 без НОВОГО обхода — то есть без нарушения инварианта изоляции/оракула/
сохранности (не очередной формы кода в argv) и без false-ACCEPT по OID (не
false-reject) — основанием FAIL следующего круга не является.
