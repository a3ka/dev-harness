# Арбитраж 063-Б4: локальный критерий исполнимости CI слабее предмета — класс, а не форма

Созван КРИТИКОМ (`verdicts/critic/contracts-063-v2.md`, коммит `c73619a`) по норме «два
отказа по одной причине»: круг 1 (`62b8243`, Б1) — heredoc-транспорт делает команды данными
неисполняемого шага; круг 2 (`c73619a`, Б4) — та же причина в новой форме: `jobs.harness.if:
${{ false }}` выключает джобу, а локальный раннер И-9 условие не читает. Автор конструкции
(architect, `anthropic`) — сторона; я на модели того же семейства, асимметрия записана в роли.
Предмет судим на HEAD `5c9655f` (контракт `ce59a42` неизменен с судимого критиком `07ca317`),
клон `/tmp/dev-harness-verify/arb063`. Каждый спорный факт ниже проверен прогоном, не
пересказом.

Решение обязательно к исполнению обеими сторонами. Исполняет автор конструкции; новые круги
по причине, решённой здесь, не открываются — несоответствие предъявляется ссылкой на этот
файл.

## Суть спора

Критик: критерий И-9 (`contracts/063-ci-proekta-iz-profylja-vorota-slijanija.md:155-165`)
доказывает исполнение извлечённых тел `run: |`, но не то, что workflow их запускает; предмет
(строки 51-62) — «CI-шаблон, гоняющий команды и барьеры». Предложенное направление лечения —
раннер, различающий job-level `if: ${{ false }}`. Автор (по тексту контракта, строка 163):
«способ локального предъявления — раннер батареи, извлекающий шаги по фиксированному лейауту
И-4; внешний GitHub в круге судьи не требуется» — отключённая джоба ни в И-4, ни в И-9 не
названа, значит по нынешней редакции она конформна.

Вопрос арбитража: (1) прав ли критик, что критерий слабее предмета; (2) если да — чем
закрывать: чтением условий раннером, закрытой формой файла, или обоими.

## Замеры

1. **Б4 воспроизведён на функции батареи без её модификации.** `wf_run` (батарея
   `:187-201`) извлечена `sed -n '/^wf_run() {/,/^}/p'` и вызвана над workflow с
   `jobs.harness.if: ${{ false }}` и честными телами шагов: rc 0, эффекты всех шагов
   наблюдены. Утверждение критика подтверждено.
2. **Класс открыт: шесть форм одного дефекта, все зелёные для wf_run** (прогон над семью
   workflow, честный контроль в том же прогоне):

   | форма (при честных телах шагов) | wf_run | GitHub Actions |
   |---|---|---|
   | `jobs.harness.if: ${{ false }}` (Б4) | rc 0, эффекты есть | джоба пропущена |
   | `steps[].if: false` | rc 0, эффекты есть | все шаги пропущены |
   | `continue-on-error: true` на шаге `exit 9` (вход к12) | rc 9, эффект `test` | джоба ЗЕЛЁНАЯ |
   | `on: workflow_dispatch` | rc 0, эффекты есть | на push/PR не запускается |
   | `defaults.run.shell: python` | rc 0, эффекты есть | тела — не bash |
   | `runs-on: no-such-runner` | rc 0, эффекты есть | джоба вечно в очереди |

   Третья строка показывает, что дефект не сводится к «пропуску»: `continue-on-error`
   проходит к12 (ожидает rc 9 локально) при всегда-зелёной настоящей джобе. Чтение `if:`
   закрывает одну строку из шести.
3. **Дефект, не названный ни одной стороной: `wf_run` не читает файл-аргумент.** Цикл
   `while … read … done` (`:189-198`) не имеет `< "$wf"` — функция читает STDIN батареи,
   второй аргумент не используется. Прогоны: аргумент-файл при stdin=/dev/null → rc 0, эффектов
   нет; аргумент = несуществующий файл при stdin=workflow → rc 0, эффекты есть. Раннер
   `bash fixtures/check_judge_gate/krasnye_063.sh`: при stdin=/dev/null — «стабов 5,
   поймано 5»; при stdin=поток `run: |`-шага, пишущего `test` в лог игрушки — «поймано 4,
   ускользнуло: s4-heredoc-transport»; при stdin=FIFO без писателя — батарея ВИСИТ
   (`timeout 5` → rc 124). Следствия: (а) «s4 пойман 5/5» обоих кругов — vacuous: вердикт s4
   зависит от stdin раннера, не от файла стаба; (б) после честной реализации к11/к12 в CI
   (stdin=/dev/null) останутся красными с ложным диагнозом «эффектов нет»; (в) в терминале
   батарея зависает. Живое предъявление критика (`tmp/krit063-proof.cjs`, «workflow в
   памяти») подавало workflow потоком и потому дефект замаскировало; замер 1 выше —
   тоже (stdin=файл). Стороны судили функцию по исходнику, не по вызову с аргументом.
4. **Прецедент про `if:` читается в пользу критика, а не автора.**
   `verdicts/arbitration/oblast-i-porog.md`, вопрос 1: «выражения `if:` не читаются вовсе,
   каждый шаг сверх-приближается как исполняемый — это корректное направление ошибки ДЛЯ
   ПАРИТЕТА». Там сверх-приближение безопасно (лишний шаг проверен строже). Здесь угроза —
   генератор-мутант, и сверх-приближение «всё, чего раннер не понимает, — исполняется»
   направлено ПРОТИВ защиты. Тот же прецедент даёт и ответ: вычисление выражений — толкование
   чужого языка, запрещено; закрытие идёт со стороны ОБЪЯВЛЕНИЯ — «мёртвый текст в CI обязан
   быть удалён либо исключён с причиной».
5. **Формы файла контракт не фиксирует.** И-4 (`:120-134`) задаёт шаги и «ровно два ключа
   name и run» у шага; контур джобы (события, `runs-on`, checkout, ключи джобы) не назван —
   критик круга 1 это отметил как СОВЕТ (вопрос 3). Батарея: к6 (`:246-263`) — `grep -F`
   маркеров и `grep -Fx` строк команд; ни одной проверки отсутствия чужих строк; `cmp -s`
   в батарее — только логи к11/к12. Стабы s2/s4 сами пишут один и тот же контур
   (`name: harness / on: [push, pull_request] / runs-on: ubuntu-latest / uses:
   actions/checkout@v4`), то есть контур де-факто есть, де-юре — нет.
6. **Семантика тела: `bash -c` ≠ shell GitHub по умолчанию.** Тело `false\necho after`:
   `bash -c` → rc 0 (печатает `after`); `bash --noprofile --norc -eo pipefail -c` (форма
   GitHub для `shell: bash` по умолчанию) → rc 1. Направление ошибки здесь безопасное
   (локально зеленее, чем в GitHub), но «локальное исполнение = семантика GitHub» контракт
   утверждает (И-9: «семантика GitHub Actions»), и утверждение неточно.

Счёт фактов: утверждение критика (Б4) подтверждено; посылка ОБЕИХ сторон «wf_run исполняет
сгенерированный файл» опровергнута замером 3. Это третий проверенный арбитражем случай
фактической ошибки стороны (теперь — обеих сразу).

## Варианты

- **(а) раннер читает `if:`-условия.** Отвергнуто. Закрывает одну из шести измеренных форм
  (замер 2), требует толкования языка выражений GitHub (открытого — `${{ false }}`,
  `false`, `"false"`, `${{ 0 }}`, `github.event_name == 'x'`), что прецедент
  `oblast-i-porog` прямо запрещает. Это тот же путь «по форме за раз», что дал два круга:
  heredoc → `if` → `continue-on-error` → `on:` → …
- **(б) сверка файла против эталона-структуры с запретом `if` вне allowlist.** Отвергнуто в
  редакции «чёрный список ключей»: чёрный список — та же погоня за формами (замер 2 даёт
  пять ключей помимо `if`, и это не полный перечень схемы workflow). Принято в редакции
  «закрытая форма»: файл-цель = литеральный контур + шаги И-4 и НИЧЕГО больше.
- **(в) комбинированный: закрытая форма (И-10) + исполнение тел (И-9, исправленный).**
  ПРИНЯТО. Обоснование: раннер, не толкующий чужой язык, доказывает исполнение только в
  паре с формой, в которой чужого языка нет. Закрытая форма делает раннер ПОЛНЫМ
  интерпретатором сгенерированного файла: каждая строка — либо литерал контура (семантика
  зафиксирована контрактом и известна: push/PR → ubuntu → checkout → шаги подряд, отказ
  первого = отказ джобы), либо тело `run: |`, которое раннер исполняет. Ни одной строки,
  семантику которой раннер «сверх-приближает». Это норма прецедента `oblast-i-porog`
  («неразобранное объявление — красное, не молчаливый приём») в применении к генератору:
  сгенерированное — тоже объявление авторства самого харнесса, и автор всегда может
  привести его к грамматике.
- **(г) внешний GitHub-прогон как исполнитель (по образцу 065 v3 — CI как исполнитель
  тяжёлой пробы).** Отвергнуто как замена локальному критерию. Прецедент 065 v3 переносит
  в CI работу по СТОИМОСТИ (таймаут 60 с спец-гейта), а не по семантике: CI dev-harness
  исполняет ту же батарею тем же `wf_run` и семантического покрытия не добавляет; workflow
  игрушки GitHub не запускает — игрушка не репозиторий GitHub. Единственный настоящий
  внешний прогон — на odelix-workstation, и это вопрос «чего мы хотим» (см. «К сведению
  владельца»), а не инженерной правоты.

## Решение по пунктам

**П1. Критерий слабее предмета — критик прав; класс назван верно.** Класс — «локальный
исполнитель считает исполняемым всё, чего не понимает». Закрытие класса — не в раннере, а в
форме: сгенерированный файл обязан не содержать ничего, чего раннер не интерпретирует.

**П2. Лечение — (в), не (а).** Чтение `if:` раннером запрещается как толкование открытого
языка; допускается только литеральное сравнение с контуром.

**П3. Дефект раннера (замер 3) — блокирующий, лечится в той же правке.** `wf_run` обязан
читать файл-аргумент; результат клеток не зависит от stdin батареи. Стаб s4 в нынешнем
виде ничего не доказывает — его «поймано» восстанавливается тем же исправлением.

**П4. Семантика тела приближается к GitHub (замер 6).** Тело шага исполняется с флагами
формы GitHub по умолчанию (`--noprofile --norc -eo pipefail`), не голым `bash -c`; текст
И-9 «семантика GitHub Actions» становится верным для контура, зафиксированного И-10.

## Что меняется в контракте, приёмке и батарее

Носитель привязок стаб↔клетка — код батареи (Н-39); здесь названы СВОЙСТВА и rc-команды,
не пары.

**Инварианты.**

- **И-10 (закрытая форма файла-цели) — новый.** Контракт приводит контур ЛИТЕРАЛЬНО, построчно
  (первая строка И-6; `name:`; `on:` с перечисленными событиями; `jobs:` → единственная джоба
  `harness` с единственным ключом `runs-on:` и `steps:`; первый шаг — pinned `uses:` checkout;
  далее ТОЛЬКО шаги И-4). Файл-цель = контур + шаги И-4, других строк нет: любой ключ джобы
  или шага сверх контура (`if`, `continue-on-error`, `defaults`, `env`, `timeout-minutes`,
  `shell`, `strategy` — перечень иллюстративный, правило — «ничего сверх контура») делает
  генератор неконформным. Точные значения контура (события, образ, версия checkout) —
  автор; арбитраж требует литеральности и закрытости, не конкретных значений.
- **И-9 — исправляется.** (i) Раннер читает файл, переданный аргументом; поведение клеток
  инвариантно к stdin батареи. (ii) Тело шага исполняется `bash --noprofile --norc -eo
  pipefail -c` в корне репо (форма `shell: bash` по умолчанию GitHub); И-4 продолжает
  запрещать генератору выставлять `shell:`. (iii) Раннер условий не вычисляет: строка вне
  контура и вне тела шага — не «пропускается», а делает файл неконформным по И-10 (раннер
  вправе отказать сам либо положиться на предшествующую сверку И-10 — выбор автора, но
  предъявление обязано быть красным на любой такой строке).
- **Демаркация.** Положительная область дополняется: значения маркерных команд и имя барьера
  игрушки исполнимости — СЛУЧАЙНЫЕ (суффикс `mktemp`/`$RANDOM`), чтобы эталон И-10 был
  функцией входа, а не подсмотренной константой (`verdicts/arbitration/
  orakul-podsmotrennaya-konstanta-024.md`, решение 1). Отрицательные входы серии: «нарушен
  ровно один инвариант И-1..И-10».

**Приёмка (rc-команды).**

- к6 и к11 (генерация непустого профиля): к существующим проверкам добавляется `cmp -s
  <файл-цель> <эталон>` → rc 0, где эталон рендерится БАТАРЕЕЙ из контура (литерал контракта)
  и значений игрушки (случайных) по правилу И-4. Отказ — с `diff` в stderr.
- к11/к12: без изменения ожиданий (rc 0 ∧ лог байт-в-байт; rc 9 ∧ только `test`), но
  предъявление обязано быть тем же при `bash fixtures/check_judge_gate/krasnye_063.sh
  </dev/null` и при stdin = поток `run: |`-шага, пишущего `test` в лог (счётные строки
  «честных/стабов/диффпроб» совпадают построчно); раннер не блокируется на stdin (`timeout
  60` не срабатывает). Эти три прогона — команды готовности контракта.
- Новая честная клетка исполнения тела по семантике GitHub: команда профиля
  `false; echo after >> <лог>` в одном теле → rc локального исполнения 1, `after` в логе
  отсутствует (`-e`), шаги после не исполняются.

**Стаб-пак (свойства, не пары).** Добавляется обман класса «выключатель контура»: генератор
честен по резолву, vacuous, отсутствию барьера, маркерам к6, телам шагов и их эффектам, но
файл-цель содержит строку сверх контура, отключающую джобу/шаг/триггер либо гасящую отказ
(форму выбирает автор из замера 2 — любая из шести). Свойство смерти: неконформность по
И-10 при наблюдаемых эффектах И-9 (диффпроба: ТОТ ЖЕ стаб на входе исполнимости даёт лог
эффектов, идентичный честному, — доказательство, что И-9 без И-10 обход не ловит).
Существующий стаб s4 (heredoc) сохраняется — после исправления И-9 его «поймано» впервые
становится содержательным.

**Модель угроз.** ЗАЩИЩАЕТ: «ключ workflow сверх литерального контура (отключение джобы или
шага, подавление отказа, смена shell, смена события) не проходит приёмку — форма файла
закрыта (И-10), раннер интерпретирует всё, что в ней есть (И-9)». НЕ ЗАЩИЩАЕТ: «семантика
самого контура в GitHub (что push/PR на ubuntu-latest с checkout исполняет `run:`-шаги подряд
с отказом на первом ненулевом) — TCB «платформа CI», локально не воспроизводится; генератор,
различающий игрушку и живой репо по значениям (input-discriminating мутант), — вне
демаркации, случайные значения делают подсмотр констант непрактичным, остаток — ревью кода
харнесса».

## Границы решения

- Решение не выбирает значения контура (события, образ, pin checkout) — это автор; не
  требует внешнего GitHub-прогона игрушки — его нет по построению.
- Решение не пересматривает Б1/Б2/Б3 круга 1 (закрыты критиком в круге 2) и не открывает
  проверку качества команд профиля («тесты-пустышки» — предмет ревью, как записано).
- Проводка (check_provodka красен до реализационной пачки) — законный долг, стороны
  согласны, не предмет арбитража.
- Замер 3 — не «третий круг по новому предмету»: дефект лежит в том же критерии И-9 и
  лечится в той же правке; отдельный круг критика по нему не открывается, предъявление
  после правки — три rc-команды приёмки выше.

**К сведению владельца (не решение, не блокер).** Слово «обе полярности на
odelix-workstation, rc в отчёте» покрывает гейт и ленд. Хочет ли владелец ещё и живого
GitHub-прогона сгенерированного workflow на odelix-workstation (одна джоба, один push) как
свидетельства TCB «платформа CI» — вопрос цены и желания, здесь только зафиксирован как
единственное, что локальная приёмка после этого решения не доказывает.

## Счёт по сторонам

Вопрос «слабее ли критерий» — критику целиком. Вопрос «чем лечить» — ни одной стороне:
предложенное критиком чтение `if:` отклонено, позиция автора «раннер по лейауту И-4
достаточен» отклонена; принят третий путь (закрытая форма + полный интерпретатор). Дефект
замера 3 не назван ни одной стороной.
