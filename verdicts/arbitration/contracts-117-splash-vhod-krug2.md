## 2. Дизайн splash — инженерное решение

Что реально показывается:
- (а) Expo Go SDK 57: системный splash с ИКОНКОЙ приложения (С1). Композит плагина не виден.
  Единственный «наш» кадр splash, который Expo Go может показать, — JS-экран сразу после.
- (б) dev-client/release на Android: нативный splash = `windowSplashScreenBackground` (цвет блока
  схемы) + `windowSplashScreenAnimatedIcon` = сгенерированный `splashscreen_logo` 288dp-холст
  с картинкой, вписанной в `imageWidth×imageWidth` (С2). На dev-client «не все свойства плагина»
  (документация). Затем — первый JS-кадр.
- (в) «скриншот = макет» проверяется ТОЛЬКО на release APK: `.github/workflows/mobile.yml`
  android-e2e делает `expo prebuild` + `assembleRelease` и гонит Maestro с `takeScreenshot`
  (прочитано, стр. 199–221). Пилотный стенд с Expo Go — не свидетель splash.

РЕШЕНИЕ по конструкции (вариант «нативный знак + JS-оверлей», отвергнуты «целиком нативный
композит» и «JS-кадр state-machine»):

1. Нативный splash (плагин expo-splash-screen): ОДИН знак канона на ground схемы — корень
   `backgroundColor #F3F2EE` + `image` = растр знака (светлый ink #121211 + точка #d6f75a),
   вложенный `dark` = `#0A0A0A` + растр знака тёмный ink #f2f1ec; `imageWidth` = ширина знака
   на артборде в масштабе окна (замер критика/автора: 181 px при 390) — литерал source.json;
   `resizeMode contain`; `userInterfaceStyle automatic`. Без wordmark/tagline в нативе: платформа
   показывает иконку, не кадр (С2). Вертикальное положение знака в нативе — центр экрана
   (платформа), а на артборде центр знака y≈357 при окне 844: расхождение ≈65 px — ПРИНЯТЫЙ
   остаточный риск платформы, cognitive-only, ловец — ревьюер по скриншоту android-e2e.
2. JS-оверлей splash: компонент, рендерящийся ПОВЕРХ дерева оболочки (последний ребёнок корня
   PilotApp, `StyleSheet.absoluteFill`, `pointerEvents="none"`, фон `tokens.ground`), содержимое —
   `Image` композита кадра окна `splash-composite-{dark,light}.png` (тот же 390×844 из Splash.png/
   Splash-Hell.png, `resizeMode contain`), БЕЗ `Text`-узлов (wordmark и tagline — растр). Оверлей
   НЕ кадр state-machine (`Frame` не расширяется, `frame` стартует с `'first-run'` как на B),
   автоскрытие по таймеру-литералу (дельта выбирает архитектор, напр. 900 мс) с очисткой в
   cleanup; `SplashScreen.preventAutoHideAsync()` на модуле, `hideAsync()` — в effect оверлея
   ПОСЛЕ его монтирования (порядок наблюдаем мок-вызовами: hide после первого коммита с
   оверлеем; это и есть защита от пустого кадра между нативом и JS).
   Доказательство неразрушения frozen-семей — мой прогон на R (B + оверлей ровно такой формы,
   таймер 1200 мс; композиты модели скопированы в `assets/images`): `npx jest
   src/bootstrap/__tests__/pilot.test.tsx --runInBand` → rc0 14/14 (byte-frozen 995 не тронут);
   `first_run_111/first_run_probe.py --repo R` → rc0 19/19 (К6/К7/К8 и текстовые листья целы:
   оверлей без Text, корневой host-узел прежний); throwaway-тест `arbiter-overlay.test.tsx`:
   `splash-overlay` смонтирован И `first-run-continue` находится/нажимается сквозь него, после
   перехода `auth-email` достижим — RNTL видит дерево под оверлеем (зелёный). `tsc --noEmit` чист.
3. Обязательно к макету: оверлей = Splash.png/Splash-Hell.png по всей поверхности (критерий п. 3,
   Б1); нативный знак = канон (целое изображение, как иконка). Остаточный риск (cognitive-only,
   ловец ревьюер по скриншотам/записи android-e2e на release APK): смещение знака натив→оверлей,
   маска Android 12+, длительность/мигание; Expo Go показывает иконку + оверлей — это НЕ дефект
   реализации, а свойство SDK, и контракт обязан это назвать, а не обещать нативный кадр в Expo Go.

Почему не «целиком нативный композит»: замер С2 — масштаб 0.46, место другое; слово владельца
18:18 требует совпадения со Splash.png и прямо допускает «JS-экран сразу после него, ЕСЛИ

## 3. КЛАСС критериев для Б1–Б3 (формулировки, допуски, что cognitive-only)

Б1 — «композит = артборд» судится ЭТАЛОНОМ, а не формой bbox:
- Эталон: `screens/Splash.png` и `screens/Splash-Hell.png` из read-only `docs/` ПРИПИНЕНЫ
  sha256-литералами в source.json (сняты ДО субъекта, правило 8/Н-351); проба читает эталон из R
  только после совпадения sha (несовпадение → rc2 `ORACLE_TAMPERED`, не зелень). Допустимая
  замена: архитектор кладёт в source.json производную маску (RLE) — тоже литерал.
- Ожидаемый композит E = артборд, у которого пиксели с |RGB−фон|≤40 прозрачны, остальные
  непрозрачны с RGB артборда. Субъект C (390×844 либо тот же aspect, масштаб s): на множестве
  M = {E непрозрачен}: доля пикселей, где C непрозрачен и |RGB(C)−RGB(E)|≤40 — ≥ 0.98 (recall);
  на множестве {C непрозрачен}: доля попавших в M — ≥ 0.98 (precision). Без ±8 px: композит —
  производная артборда по построению; антиалиасинг укладывается в 2 %. Семь пикселей дают
  recall ≈ 0; «знак без надписей» — recall ниже порога на полосах; сдвиг на 9 px — тоже красен.
  Полосные bbox и точка #d6f75a остаются дешёвой первой линией, не критерием.
- Тот же класс (эталон целым изображением) — для нативного растра знака: аналитическая
  растеризация SVG-канона уже есть у иконки (инвариант 3) — применить к знаку splash.

Б2 — «эффективный платформенный ассет» судится РЕЗУЛЬТАТОМ ВЫЗОВА настоящего генератора:
- Проба вызывает из node_modules продукта `getAndroidSplashConfig(props)` и
  `setSplashImageDrawablesAsync(conf, tmp)` (пути `./assets/...` резолвятся от `mobile/`) и
  судит ПРОИЗВЕДЁННЫЕ файлы `drawable-{mdpi..xxxhdpi}/splashscreen_logo.png` и
  `drawable-night-*/…`: размер 288×288×множитель; содержимое = знак канона (аналитическая
  растеризация, согласие ≥ 0.97, альфа-bbox = `imageWidth`-литерал × множитель ± 3 px);
  цвета ink схемы и точка. Любой override (basename, другой путь, density-ключ, `android.imageWidth`)
  меняет произведённый файл — и краснеет без перечисления способов.
- iOS: `getIosSplashConfig(props)` → читать файл по ЭФФЕКТИВНОМУ пути (light/dark) и судить его
  содержимое тем же растровым критерием; `imageWidth`/`resizeMode` — из эффективной конфигурации,
  не из props; `enableFullScreenImage_legacy` отсутствует. Фоны — как сейчас, из резолвера.
- Критерий никогда не сравнивает basename; путь — только для чтения содержимого. Мой `native.cjs`
  показывает, что вызов генератора в node работает за ~4 с без устройства.

Б3 — «кадр целиком внутри окна» — измерение layout, а не список полей:
- Единственный настоящий измеритель в продукте — рендер на устройстве: android-e2e (release APK)
  + Maestro `assertVisible` по testID КАЖДОГО элемента таблицы «Состав кадров входа» (F03.01:
  заголовок, `auth-email`, `auth-demo-entry`; F03.02: заголовок, `auth-code`, `auth-verify`,
  `auth-resend`, `auth-change-email`, `auth-no-access`) × тема устройства, в сценарии 117 в
  `mobile/.maestro/` (граница зоны исправляется: действующие сценарии там, не в `.maestro/` —
  совет критика подтверждён `ls`). Maestro возвращает rc≠0 при невидимости — это механизм, не
  cognitive-only. `takeScreenshot` этих кадров — для ревьюера (правило В).
- В Jest-семье клетка В3 остаётся ПЕРВОЙ ЛИНИЕЙ и так и называется в контракте: кумулятивный
  эффективный стиль по цепи корень→элемент — translate, margin*, padding*, left/top/right/bottom,
  `position:'absolute'` с вылетом, `display:'none'`, `opacity 0`, `overflow` — любой сдвиг ≥ окна
  красен. Это защита от дешёвых обходов, НЕ доказательство свойства; доказательство — Maestro.
  Записать в НЕ ЗАЩИЩАЕТ: «layout в Jest не вычисляется; окно — только android-e2e».

Общее: контракт обязан назвать среду каждого утверждения о видимом (Expo Go / dev-client /
release) и не обещать то, что среда не показывает.
