## РЕШЕНИЕ 1. Конечная таблица достаточна как граница испытаний, не как универсальное доказательство

По прежним блокам прав критик: m1/m2, затем m3/m4/m6/m9 были заменами имеющихся операций на достижимых входах, а не произвольными новыми запретами. Они должны были закрываться до freeze и, по подписанному Crit199V3 и проверенному устройству клеток, закрыты.

По необходимости остановить расширение прав автор: для данного OBJECT принимается конечная область — таблица 37 + 23 операций, существующие 44 клетки, 18 стабов и явно обоснованные строки «=». Accept вызова 3 остаётся итогом **содержательного суда этой батареи**. Новый полный поиск мутаций не нужен.

Точное значение «замкнут»: для перечисленных предметных операций имеются различающие наблюдения либо названная причина ненаблюдаемости рассматриваемого удаления/замены при сохранённых соседних операциях и предпосылках. Не принимается более сильное утверждение «любая замена любой из 60 операций обязательно поймана» или «вся строка доказана одним зелёным/красным прогоном». Его не доказывают ни конечные примеры, ни 18 стабов, ни выборочная атака критика. Строки с `—` опираются также на чтение кода и потому несут когнитивный остаток.

Граница не сужает поведение двери до номеров клеток: каждый рабочий item должен быть изолирован, сверка сдачи идёт с последним рабочим START, корень — из факта. Конкретное нарушение этих инвариантов в предъявленной реализации остаётся дефектом, даже если вход не включён в таблицу. Новая специально изобретённая мутация вне принятого конечного набора сама по себе не открывает очередной круг расширения.

Новая предметная операция модели требует новой строки и оформления изменения предмета; изменение семантики существующей операции требует обновления её строки, а не маскировки под старым именем. Это не разрешение implementer менять обязательства. Чистый перенос/рефакторинг той же операции сам по себе нового предмета не создаёт. После freeze изменение текста контракта — штатный v+1; усиление испытаний без ослабления нормы — по действующему порядку AGENTS.md.

## РЕШЕНИЕ 2. Строки «=», счёты и два совета критика

Совет о `t == START` по существу верен. В шапке батареи :97 неверна причина «иных t не пишет ни одна операция замка». Правильное основание: модель-дверь пишет только START; в рассмотренной реальной грамматике RELEASE не несёт `klass=rabochij` и отсекается сохранённым фильтром klass. Формулировка должна различать модель и реальный учёт, а не отрицать существование RELEASE. Если появится иной тип записи с рабочим klass, предпосылка эквивалентности пересматривается вместе с этим изменением грамматики; сейчас новая клетка для всех типов учёта не требуется.

«=» означает эквивалентность **указанного изменения в указанных условиях**, не разрешение удалять защиту в реализации. Аналогично частичное удаление NOSITEL не обязано краснеть, если тот же именованный отказ удержан другой ветвью. Полное исчезновение защиты — иной наблюдаемый случай; Crit199V3 описывает его поимку. Проверять все комбинации взаимно избыточных ветвей до freeze не требуется.

Счёт таблицы фиксируется здесь как 37/23, а не 39/22. Счёты батареи 44/18/5 согласованы. Расхождения сопроводительного счёта и суммы новых мутаций исправлять в дальнейших протоколах ссылкой на этот замер; чужой подписанный вердикт задним числом не переписывать. Они не являются новым дефектом поведения и не требуют платного круга критика.
