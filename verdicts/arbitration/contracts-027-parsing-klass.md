## Замеры арбитра (собственный клон, не пересказ)

1. **F8 подтверждён.** Кодовый контракт без раздела «## Док-приёмка» (игрушка
   по образцу `fixtures/freeze_contract/_repo.sh`):

   входе, который §Freeze обязывает замораживать («старые кодовые контракты

   `_doc_type_out="$(… --type … 2>&1)"` — под `set -e` rc≠0 подстановки
   завершает скрипт ДО `:274` и всего `case :277-293`. В
   `check_contract_ready.sh:114-116` тот же вызов безопасен — `set -e` там не
   включён (проверено прогоном: ready на тех же входах ведёт себя по ветвям).
2. **14/22 подтверждены.** Мера самого проекта в клоне:
   `bash scripts/verify_antiplacebo.sh --scope check_document render_document
   freeze_contract check_check_contract_ready` → rc=1, «барьеров: 4 · фикстур:
   22 · предъявлено красным повторным прогоном: 8 · расхождений: 14»; все 14 —
   `freeze_contract/case_*.sh` с диагнозом «нет положительного контроля».
   Независимо тот же регресс предъявил Rev020 CI-формой шарда ap2 на том же
   HEAD (58/72, красные — те же 14 фикстур).
3. **F9 подтверждён.** Раздел «## Док-приёмка» есть, единственный fenced
   json-блок `[]` либо `"ёж"`: `--type rc=1` (без сообщения, stderr пуст),
   `ready rc=0` с «OK» — doc-preflight пропущен. Грамматика замороженного

4. **Третий экземпляр того же класса, латентный.** Раздел есть, блок — валидный

   `doc_contract.ts:841` `return 1` для не-объекта и `:843`
   `s.type === 'documentation' ? 0 : 1` отображают «не узнал» в «не doc-контракт»
   (гейт пропущен), игнорируя присутствие раздела.
5. **Контроль:** конформный doc-контракт проходит `--type` rc=0 и доходит до
   doc-preflight с именованной причиной отказа — ветвь rc=0 жива; дефект F8
   виден только на rc≠0 из `--type`.

## Решение по вопросу 1 — класс или инцидент

**Два дефекта к3 — РАЗНЫЕ предметы; смешивать их в один «класс F5» неверно.**

- **F5 (к2) + F9 (к3) + латентная опечатка type (замер 4) — ОДИН класс**, и он
  системный, но не в parseSpecFromMarkdown (тот после `b4f40f3` считает разделы
  и блоки честно), а в решающем правиле `detectDocTypeFromFile`: отказ
  классификации по умолчанию отображается в rc=1 «не doc-контракт» = «гейт
  пропустить». Fail-open по построению: каждый неучтённый случай молча
  открывает ворота, и таких случаев уже три (первый блок без счёта; не-объект;
  опечатка type). Точечные фиксы по одному случаю этот класс не закрывают —
  двух кругов достаточно как доказательства.
- **F8 — отдельный инцидент другого слоя** (shell-интеграция, не разбор),
  внесён фиксом `b4f40f3` и пойман мерой самого проекта. Основанием для
  редизайна модуля он не является.

**Предписанный фикс класса — реструктуризация решающего правила, не редизайн
модуля.** Наличие раздела «## Док-приёмка» — ЕДИНСТВЕННЫЙ дискриминатор
doc-намерения. rc=1 («не doc-контракт, гейт неприменим») выводится ТОЛЬКО из
`hasSection === false`. При присутствующем разделе ЛЮБОЕ отклонение — rc=2 с
именованной причиной в stderr: ошибки parseSpecFromMarkdown (уже так),
не-объект/массив/null (`:841` — `return 2`; после успешного parse раздел
присутствует по построению — parseSpecFromMarkdown бросает «нет раздела»),
`type !== 'documentation'` (`:843` — `: 2`, с сообщением, называющим найденное
значение type). Замер 3 показал `--type rc=1` с ПУСТЫМ stderr — каждая ветвь
rc=2 обязана печатать именованную причину, как уже делают ветви исключений.
После этой правки новый экземпляр класса невозможен по построению: путь к
«пропустить гейт» один и охраняется тем же регексом, что и сами ветви case.

## Решение по вопросу 2 — канал для F8

**Канал — существующий паттерн ТОГО ЖЕ файла**, `freeze_contract.sh:280`:
`doc_rc=0; doc_out="$(…)" || doc_rc=$?`. Ровно так же для `--type`:

    _doc_type_rc=0
    _doc_type_out="$(cd "$ROOT" && node "$SELF_DIR/doc_contract.ts" --type "$_doc_type_tmp" 2>&1)" || _doc_type_rc=$?

Строка `_doc_type_rc="${_doc_type_rc:-0}"` мертва и удаляется. Предохранительный
комментарий прежней редакции («`set -e` трактует отказ команды в `$(...)` как
отказ присваивания и ВЫХОДИТ») восстанавливается у этой строки — фикс `b4f40f3`
убрал `|| true` вместе с комментарием и наступил ровно на описанные грабли.

Предложенные альтернативы ОТКЛОНЕНЫ: (а) отдельный helper без `set -e` — второй
механизм рядом с существующим паттерном `:280`, запрещён конвенцией; (б) вывод
во временный файл — второй tmp-канал без нужды, rc он не переносит; (в)
subprocess внутри TS — перенос ветвления из bash в TS двигает границу зон и
API ради дефекта одной строки. `check_contract_ready.sh` не трогать — измерен
безопасным (нет `set -e`, ветви живы).

Тот же фикс канала закрывает и побочное следствие F8: на мальформном
doc-контракте управление доходит до ветви `2) die …`, а `die` выходит rc=1
(`freeze_contract.sh:54`) — предписанный §Freeze «rc=2 — rc=1 (fail-closed)»
восстанавливается без отдельной правки.

## Решение по вопросу 3 — F9: gap или residual

**GAP. Блокер, править.** Residual — это именованный остаток, не нарушающий
замороженного инварианта (образец — арбитраж `contracts-027-izoljacija-probe.md`:
argv-флаги, регистр OID). F9 нарушает инвариант дословно: §Грамматика требует
именованный rc=1 за неверные типы полей, замер даёт `ready rc=0` и «OK», и
последствие — то самое, за которое остановлены к1 и к2: предмет заморозки
расходится с тем, что прочла машина. Носителя для residual-строки нет и быть не
может — текст контракта прямо требует противоположного поведения. Закрывается
фиксом класса из вопроса 1.

## Граница повторных споров

После реструктуризации rc=1 выводится единственно из отсутствия раздела.
Новая находка вида «мальформный doc-контракт минует гейт» с этого момента —
нарушение настоящего решения и законный FAIL без нового арбитража. Находки в
семантике самого doc-preflight (validateSpecSchema и далее) — другой класс и
судятся обычным порядком. Спор о цене третьей модели для арбитража
(`MiniMax-M3`) этим решением не затрагивается — вопрос владельца.
