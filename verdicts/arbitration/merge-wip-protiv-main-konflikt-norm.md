## Разбор вариантов

**(а) Узкий разрешённый sync-merge main→wip — ОТКЛОНЁН.** «Узость» двухродительского merge фиктивна. Merge, который берёт из main только конфликтующие файлы, при ленде молча откатывает остальные правки main (замер 4) — это хуже красного гейта. Честный полный merge тянет в diff с первым родителем все уставные правки main (замер 3). Тогда `check_charter` требует либо ручного копирования санкций владельца в чужой коммит (класс Рв97-20), либо нового маркера, который `check_charter`/`check_zones` научатся понимать. Маркер — это дверь «этот merge не судить» в уставном гейте, то есть ослабление контракта 019 И-7. Решать это не мне, и инженерно это не нужно: замер 2 показывает путь без него. Ещё один довод: merge не идемпотентен к движению main. Каждый следующий ленд соседа снова делает ветку CONFLICTING и требует нового merge (Н-291: три подряд; int-093: четыре, `25260760e…64bee4b5c`).

**(б) Конфликт только в land-коммите + PR-CI через временную ветку — ЧАСТИЧНО.**
- «Только в land-коммите» в буквальном смысле невозможен без смены механизма 016: `land_agent.sh:205-206` при конфликте отказывает («merge --no-ff … отказал — конфликт»), а разрешать он не умеет и не должен.
- Временная ветка слияния — это уже существующий санкционированный класс `wip/int-<NNN>/<автор>` (Н-256; `c62bc93ef`; ленды `c4bd709a1`, `ae280bb82`). Он ОТДЕЛЬНЫЙ от merge main→wip. Main — первый родитель, wip — второй. Сама wip не переписывается, frozen-тег — предок через второго родителя, preflight спрашивает CI по голове int-ветки, и её PR гоняется как обычный.
- Кто создаёт: автор ветки своей identity в одноразовом клоне (Н-256). Committer merge-коммита обязан быть в реестре ЗОНА-строк, author==committer (И-9).
- Два условия, оба из измеренной боли: (1) int-ветка строится ЗАНОВО от текущего main при каждом движении main, и main в неё НЕ сливается никогда — иначе это тот же класс (int-093 → Н-281, «Дополнение»: 295–318 коммитов в окне); (2) если wip правит уставные пути (M), merge-коммит int-ветки судится `check_charter` по diff с main и сам обязан нести их санкции.
- Дыра по чтению кода, не прогоном: `check_zones.sh:602-603` относит `land: wip/int-104/…` к ЧУЖИМ лендам (шаблон `land: wip/104/*` не совпадает) и исключает принесённые им коммиты из окна зон 104. Это `[INFERENCE]`-риск недосуда зон, адресат — implementer зоны `check_zones`.

**(в) Architect не пишет `NABLIUDENIA_ARCHITECT.md` в wip-ветках — ВЕРНО ИНЖЕНЕРНО.** Это единственная форма, которая убирает причину, а не лечит следствие.
