# Арбитраж: ротация токена, passthrough и коррелятор live-пробы (контракт 005)

Созыв судьёй по норме «два отказа по одной причине» (правило 15, согласия автора не требует;
автор — сторона): первый отказ — `verdicts/critic/contracts-005-v1.md` круг 1 (коммит
`01b4dc1`, судимый текст `7dbbd4e`), причины [К1-1], [К1-5], [К1-6]; второй — те же причины
против итерации 2 (круг 2, коммит `b67dd2f`, судимый текст `a23a6b1`), строка АРБИТР. Общий
класс причины: **декларация поведения в разделе «Предмет» без различающего исхода в
критерии готовности**.

Стороны: критик (правило без механизма не существует; по каждой из трёх причин нужен вход
с кодом возврата, который зашитая реализация не проходит) и автор конструкции (architect;
существо не оспаривает, спор — о минимальной форме каждого исхода).

Решение обязательно к исполнению обеими сторонами. Исполняет автор в итерации 3; новые
круги по причинам, решённым здесь, не открываются — несоответствие предъявляется ссылкой
на этот файл.

## Замеры

Все замеры — мои собственные, 2026-08-20. Первоисточники: судимый текст
`contracts/005-avtonomija-proksi.md` на `a23a6b1`, оба вердикта критика, референс
`/home/aka/Documents/content-factory/packages/metering-proxy/src/index.ts`.

1. **[К1-1] — разрыв предмета и критерия подтверждён.** Предмет `:27-29` требует строить
   карту токен→роль «ЧТЕНИЕМ конфигурации НА КАЖДЫЙ запрос (кэширование на старте
   запрещено): смена файла секретов отзывает/выдаёт токен без перезапуска». Ни selftest
   `:61-63`, ни одна из восьми ветвей `:64-77` не меняет файл секретов между двумя
   запросами к одному живому процессу; ветви (б), (в), (з) стартуют с готовой
   конфигурацией. Утверждение критика точно.

2. **Обход [К1-1] — не гипотеза, а устройство референса.** В референсе карта маршрутов
   строится один раз: `loadRoutes` (`index.ts:407`) возвращает `Map`, она передаётся в
   `createProxy` через `opts.routes` и замыкается обработчиком (`:253`, `:309`); внутри
   обработки запроса ни файл конфигурации, ни окружение не перечитываются. Реализация
   «по образцу референса» — то есть самая естественная — проходит всю текущую матрицу и
   нарушает предмет. Различающий исход обязателен не из осторожности, а потому что
   ближайший работающий образец и есть описанный обход.

3. **[К1-5] — состав «как есть» измерен по референсу.** Метод клиента доставляется до
   upstream дословно: не-GET/POST отсекается 405 (`:310`), дальше `method = req.method`
   (`:320`) → `forward(route, path, method, …)` (`:356`). Ответ возвращает `rawReply`
   (`:276-283`): статус как есть, тело `Buffer` байт-в-байт без пересборки, content-type
   как есть (запасной `application/octet-stream` при отсутствии). ПРОЧИЕ заголовки
   upstream референс сознательно НЕ пересылает. Предмет `:18-19` обещает ровно тройку
   «тело, статус, content-type» — состав сверки задан предметом и совпадает с референсом;
   требовать сверку прочих заголовков оснований нет.

4. **[К1-5] — матрица метод не различает.** Валидный вызов в матрице один — ветвь (в)
   `:66-67`; метод в ней не назван, отдельного GET-вызова нет. POST-only ретранслятор с
   пересборкой ответа в JSON проходит все восемь ветвей. Утверждение критика точно.

5. **[К1-6] — коррелятора в схеме нет, и в референсе его взять неоткуда.** Схема журнала
   `:30-32`: `ts, role, provider, model, path, tokens_in, tokens_out, usd, latency_ms,
   status` — ни uuid, ни request id, ни содержимого запроса. Live-критерий `:78-80`
   сверяет только роль и `ts` позже старта пробы; строку с той же ролью и свежим `ts`
   рождает ЛЮБОЙ вызов с токеном роли, в том числе вспомогательный вызов самой проверки —
   обход круга 2 воспроизводим по построению. Референсная строка (`CallRecord`,
   `:51-67`) коррелятора тоже не содержит — итерации 3 придётся расширять схему, а не
   заимствовать.

6. **Канал пер-вызовной метаинформации в референсе существует.** Роль и версия промпта
   приходят клиентскими заголовками `x-factory-*` (`:306-308`) — образец «клиент несёт
   метку, прокси пишет её в журнал» в семействе референса есть. Несёт ли порождённый
   заголовок ЖИВОЙ omp — не измерено; этот замер остаётся автору, если он выберет форму
   (б) ниже.

Фактических ошибок критика не найдено: 4 из 4 его проверяемых утверждений (замеры 1, 3, 4,
5) подтверждены. Позиция автора фактических утверждений не содержит — только вопросы формы.

## Вопрос 1 — достаточно ли декларации в «Предмете» без различающего исхода

**РЕШЕНИЕ: нет. Критик прав по существу по всем трём причинам.** Декларация поведения, не
имеющая входа с кодом возврата, который зашитая реализация не проходит, — не критерий:
`AGENTS.md:158-159` (правило без механизма не существует) и `:162-163` (проверка не готова,
пока не предъявлена красной). Для [К1-1] это усилено замером 2: обходная реализация — не
экзотика, а дословно референс. Согласие автора по существу спора не отменяет: созыв
правомерен, это второй FAIL по одним причинам, и правило 15 требует арбитра, не третьего
круга. Минимальная форма — предмет вопроса 2.

## Вопрос 2 — обязательный минимум итерации 3

Уровень требования; способ реализации — автору (граница — вопрос 3).

### А. Ротация [К1-1]

Отдельная ветвь барьера с собственным красным вызовом. ОДИН живой процесс прокси, без
перезапуска между шагами (тождество процесса утверждается проверкой — например, сверкой
pid до и после; способ не предрешаю):

1. фикстура порождает токен T1 в СВОЁМ файле секретов (путь через цепочку `--config`);
   вызов с T1 → принят, строка журнала с ролью;
2. файл секретов перезаписывается: T1 удалён, порождённый T2 приписан той же роли;
3. вызов с T2 → принят, строка с ролью;
4. вызов с T1 → 401, число строк журнала не выросло.

Красное предъявление ветви — реализация, строящая карту на старте (схема референса,
замер 2): она обязана падать на шаге 3 (T2 неизвестен → 401) либо на шаге 4 (T1 принят).

### Б. Passthrough [К1-5]

Два ОТДЕЛЬНЫХ вызова — GET и POST, каждый по своему порождённому пути, каждый со своим
красным предъявлением:

- подставной upstream фиксирует принятые метод и путь; проверка сверяет их с посланными —
  метод обязан дойти дословно;
- ответ подставного upstream порождается с нетривиальными свойствами: статус ≠ 200
  (порождённый), content-type ≠ `application/json` (порождённый), тело — порождённые
  байты, НЕ являющиеся валидным JSON (чтобы любая пересборка гарантированно исказила);
- клиентская сторона сверяет тройку предмета `:19`: статус равен, content-type равен,
  тело равно байт-в-байт (побайтовое сравнение или хеш).

Состав сверки — ровно тройка «тело, статус, content-type» (замер 3); прочие заголовки в
минимум НЕ входят. Красное: POST-only ретранслятор и ретранслятор с пересборкой ответа
обязаны падать.

### В. Коррелятор live-пробы [К1-6]

Схема журнала `:30-32` расширяется полем-коррелятором (имя поля — автору), и live-критерий
переписывается:

- положительная проба: uuid, порождённый пробой, обязан быть восстановим из НАЙДЕННОЙ
  строки сверкой равенства или подстроки по названному полю; роль и свежий `ts` остаются
  обязательными, но перестают быть достаточными;
- отрицательная проба (прямой маршрут): строки с ЭТИМ uuid нет → код 1.

Допустимые минимальные формы (выбор автора):

- (а) поле с ограниченным экстрактом пользовательского содержимого запроса (например,
  хвост последнего сообщения, фиксированное число байт) — uuid ищется подстрокой;
- (б) поле request-id из клиентского заголовка — ТОЛЬКО если автор замером докажет, что
  живой omp доносит порождённый заголовок до прокси (образец канала — замер 6);
- (в) иное поле, значение которого — детерминированная функция известного пробе uuid,
  вычислимая проверкой.

Что НЕ годится по построению: роль + `ts` (посторонний вызов той же роли рождает строку —
обход круга 2); хеш всего тела запроса (тело собирает живой omp, проба его байтов не знает
— ожидание невычислимо, сверка невозможна).

### Четыре неповторённые находки круга 2

Сужение grep до конфигов (блокер 2), тарификация с `usd = 0` (блокер 3), полнота строки
журнала и отсутствие строки у unpriced (блокер 6), холодный запуск `workshop` (блокер 7) —
предметом этого арбитража НЕ являются, но их закрытие в итерации 3 ОБЯЗАТЕЛЬНО: это
действительные блокеры вердикта FAIL, и оставленные без ответа они дадут третий отказ и
новый повтор причин. Форма закрытия — на усмотрение автора в рамках той же нормы
(различающий исход с кодом возврата), с двумя следствиями, вытекающими из самих находок,
а не из моего предписания:

- тарификация: закрытие по построению требует хотя бы одного исхода с известными usage и
  тарифом и ожидаемым НЕнулевым целым `usd` — иначе находка «ни один исход не доказывает
  вычисление стоимости» остаётся истинной дословно;
- workshop: норма `AGENTS.md:158-159` даёт два пути — механизм с кодом возврата ЛИБО явная
  пометка `cognitive-only` с записанным остаточным риском; ручная запись healthz в HANDOFF
  критерием не является ни по одному из них.

## Вопрос 3 — граница: реализация не предрешена

Не предрешаются: структура и язык прокси; способ чтения секретов — при соблюдении
наблюдаемого исхода А (текст `:27-29` «на каждый запрос» описывает намерение, судится
исход: отзыв и выдача без перезапуска); устройство подставного upstream и способ байтовой
сверки; множества порождаемых статусов и content-type; биллинговая семантика GET-путей;
имя и точная форма поля-коррелятора из допустимых; число попыток live-пробы; как печатается
причина отказа. Реализация барьера остаётся предметом обычного круга критика — этот файл
фиксирует только форму требования.

Воли владельца решение не требует: обязательность различающих исходов следует из нормы
«критерий не слабее предмета» и замеров, а не из вкуса сторон. Записанное «незаполненное
требование» о занятом порте (`:108-110`) не задето и остаётся владельцу.

## Счёт решений по сторонам

- Существо (достаточна ли декларация без исхода): **критику целиком, по всем трём
  причинам** — замеры 1–5.
- Форма минимума (вопрос 2): зафиксирована арбитром по фактам замеров; состав сверки
  passthrough ограничен тройкой предмета (в этой части позиция автора «что именно сверять»
  получила ответ ИЗ ЗАМЕРА, а не уступкой); реализация — за автором.

Асимметрия семейства записана в роли: арбитр — на модели семейства автора. Каждый спорный
пункт решён замером по судимому тексту и коду референса, у которых семейства нет.
