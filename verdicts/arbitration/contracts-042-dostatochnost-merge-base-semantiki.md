## Решение по существу

**Прав критик. Семантика «блоб пути равен блобу в одной merge-base + пусто у другого
родителя» НЕДОСТАТОЧНА, и недостаточна КАК КЛАСС, а не тремя дырами.** Три находки v2 —
два класса:

**Класс 1 (З1, З2) — ручная аппроксимация мерж-семантики git.** Контракт сам формулирует
правильный вопрос (:78): «бесконфликтный трёхсторонний мерж родителей дал бы то же самое
отсутствие пути БЕЗ единого ручного действия». Реализация отвечает на ДРУГОЙ вопрос:
«равен ли блоб одной из баз». Расхождения этих вопросов и есть обходы: state пути — это
(mode, oid), а не oid (З1: git предъявляет конфликт, предикат видит «молчание»); баз
бывает больше одной, и «merge-base вернул непустое» не доказывает однозначность (З2:
обещанный контрактом (:103, :120-121) fail-closed на неоднозначности НЕ реализуем формой
`git merge-base` без `--all` — команда не сообщает о множественности). Следующие члены
того же класса известны заранее: D/F-конфликты, rename-поведение, submodule-состояния
160000. Гоняться за ними по одному — та же бесконечная игра, что Б1 арбитража 040.

Доктрина самого барьера (шапка `check_protected.sh`): «Инвариант от РЕЗУЛЬТАТА, а не от
способа». Вопрос «что дал бы бесконфликтный мерж» имеет авторитетный вычислитель — сам
git. **РЕШЕНИЕ: `is_lagging_merge_artifact` переводится на оракул
`git merge-tree --write-tree`** (та самая команда, которой критик независимо проверял
криss-cross — теперь она становится мерой, а не только проверкой):

Мерж-коммит `c` с РОВНО двумя родителями `P1`,`P2` — артефакт по пути `p`, ЕСЛИ И ТОЛЬКО
ЕСЛИ все три условия сразу:
1. `git merge-tree --write-tree --no-messages -z P1 P2` завершился **rc=0 или rc=1**
   (0 — чисто; 1 — есть конфликты; rc>1 и любой сбой — fail-closed, НЕ артефакт);
2. `p` **НЕ входит** в секцию конфликтных путей вывода (`-z`-форма, побайтовое
   сравнение путей; при rc=0 секция пуста);
3. в результирующем дереве авто-мержа `p` **ОТСУТСТВУЕТ** (state снимается робастной
   формой из класса 2 ниже).

Тогда отсутствие `p` в дереве `c` унаследовано, `c` пропускается. Во всех прочих
случаях `c` — настоящий удаляющий кандидат и судится по собственному телу. Октопус
(3+ родителей) — fail-closed без изменений (риск 2 контракта). Структура `excuse_for`
(порядок обхода, остановка на первом не-артефакте) — байт-в-байт как в v2, здесь ничего
не ослабляется и не расширяется.

Измерено на всех четырёх деревьях: З1 → конфликт по `p` → не артефакт → rc=1
восстанавливается; З2 → авто-мерж СОДЕРЖИТ `p` (рекурсивная стратегия честно сливает обе
базы) → не артефакт → rc=1; З4 → чисто и `p` отсутствует → артефакт → легитимное
удаление остаётся зелёным. Существенно: на criss-cross оракул даёт ПРАВИЛЬНЫЙ ответ, а
не отказ — fail-closed-на-двух-базах (эпицикл через `merge-base --all`) на легитимной
criss-cross-истории дал бы ложное красное; обещание :103 выполняется не запретом
топологии, а корректным её вычислением.

**Класс 2 (З3) — лексика путей, независимый от семантики дефект разбора.** `blob_at`
режет `ls-tree` по пробельным полям — путь с пробелом превращается в «пути нет», и все
три сравнения предиката становятся вакуумно-пустыми. Домен путей с пробелами объявлен
самим барьером: грамматика ALLOW поддерживает кавычки. **РЕШЕНИЕ:** всякое снятие
состояния пути — только робастной формой: `git ls-tree --format='%(objectmode) %(objectname)'
<коммит> -- ':(literal)<путь>'` (state — ПАРА mode+oid, не голый oid) либо
`-z`-форма с NUL-разбором; всякий список путей, пересекающий конвейер, — `-z`.
Побайтовое сравнение, без полевого awk по пробелам. Это закрывает З3 при ЛЮБОЙ семантике
предиката и обязательно для чтения секции конфликтов merge-tree (пункт 2 выше).

**Отклонённая альтернатива, названная явно, чтобы к ней не возвращались:** ремонт
эпициклами — сравнение пары (mode,oid) вместо oid + `merge-base --all` с fail-closed на
>1 базе + починка разбора. Он закрывает ровно три ИЗМЕРЕННЫХ обхода, но оставляет
открытым класс 1 (следующее расхождение аппроксимации с git — новый круг), даёт ложное
красное на легитимном criss-cross и повторяет судьбу двух кругов этого контракта:
каждый круг закрывал точную предъявленную топологию и получал следующую. Класс
закрывается только сменой меры с аппроксимации на вычислитель.

## Цена решения, названная прямо (не молча)

1. **Версия git.** `merge-tree --write-tree` требует git ≥ 2.38 (2022). Барьер обязан
   пробовать команду на старте и при отсутствии отвечать **именным rc=2** — тот же
   класс, что существующий отказ «нет comm в доверенном PATH». Локально 2.55, CI
   ubuntu-latest — новее порога.
2. **Запись объектов.** `merge-tree --write-tree` пишет деревья в object DB. Барьер уже
   пишет в `$ROOT/tmp`; осиротевшие деревья собираются gc. Именованный остаток, не дыра.
3. **Дрейф мерж-семантики между версиями git.** Вердикт «артефакт/нет» теперь совпадает
   с тем, что сделал бы `git merge` ЭТОЙ версии. Это принимается сознательно: предмет
   барьера — «наследование против ручного действия», и авторитет здесь git, а не наша
   реконструкция. Именованный остаток.
4. **Стоимость.** Один `merge-tree` + одно-два робастных `ls-tree` на КАЖДОГО
   двухродительского diff-filter=D-кандидата пути — тот же порядок, что нынешние
   `merge-base` + 3×`ls-tree`. Класс Н-126 не активируется (кандидатов единицы на путь).
   Если честная реализация чуть превысит границу 30 в Р2 контракта 040 — действует
   §Риски-4 040 (пересчёт числа границы architect'ом с обоснованием), не ослабление.

## Граница третьего круга (что обязан предъявить контракт v3)

1. Семантика §«Семантика» переписывается на формулировку оракула (три условия выше);
   слова «блоб равен базе» и «merge-base вычисляется успешно и непусто» уходят.
2. Красная пачка пополняется ТРЕМЯ постоянными фикстурами — по одной на замер:
   mode-only modify/delete (З1), criss-cross через `commit-tree` (З2), путь с пробелом
   (З3). Каждая — с обеими полярностями там, где полярности две (З3: легитимная
   Н-127-топология с пробельным путём зелёная, повторное удаление красное). R2/R3/R6 и
   вся семья 22/22 остаются без правки текста.
3. Именной rc=2 на git без `merge-tree --write-tree` — пробой на старте, с фикстурной
   проверкой не обязательно (среда одна), но строка пробы в коде обязана быть.
4. Остатки 2 и 3 из «Цены решения» — в §Риски контракта дословно.
5. Круг v3 — ОБЫЧНЫЙ круг критика; предмет: соответствие внесённого этому вердикту +
   действительно новые дефекты. Решённое здесь не переоткрывается; несоответствие
   предъявляется ссылкой на этот файл. FAIL по решённой здесь причине — дефект
   исполнения, чинится правкой, не спором.
