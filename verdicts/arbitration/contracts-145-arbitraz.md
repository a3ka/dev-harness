### 2. «Тест упал без каталога» необходимо, но само по себе недостаточно

Тест может читать файлы/проверять пины, затем вообще не сравнивать ни одной позы. Добавление третьего/четвёртого regex или ещё нескольких произвольных мутантов этот класс ПО ПОСТРОЕНИЮ не закрывает.

Для движкового теста выбираю конечную строгую форму вместо распознавания семантики произвольного TypeScript:

**Обязательный продуктовый `faden-motion.test.ts` — побайтовая копия проверенного, запиннованного полного теста батареи. Проверяется файл, который затем действительно запускается и импортирует порт субъекта; не наличие PINY/комментария/хеша где-либо в продукте.** Пины эталонного файла уже есть в source.json; сейчас отсутствует именно равенство продуктового файла этому эталону. Канонический тест читает три оракула по предусмотренному пути, проверяет их SHA, реплеит каждую из 21 сцен и сравнивает каждую из 6680 строк по действующим допускам/тону. Числа 21/6680 не заменяют сам цикл сравнений. Сравнение выполняется с данными проверяющей стороны, не с результатом, переписанным субъектом.

Это ограничение формы ПРИЁМОЧНОГО артефакта, не пин реализации движка: реализацию продолжает судить поведение. Произвольные дополнительные тесты допустимы отдельно, но не заменяют обязательный файл. При изменении канонического теста architect заново предъявляет его код/пин/прогоны; одно обновление хеша не считается доказательством. Удаление реплея, перенос его в `if(false)`, замена assertions проверками `options()` теперь меняют обязательный исполняемый артефакт и отвергаются одним общим свойством, а не списком распознаваемых обманов.

Динамическое подтверждение этого фиксированного артефакта остаётся обязательным: честный прогон зелёный; отсутствующий каталог и отдельно порча каждого из трёх оракулов красные; живое искажение численного выхода порта краснит сравнение реплея. Нельзя засчитать падение импорта мутанта/синтаксиса/таймаут как пойманную численную ошибку.

### 3. Компонент: судить возвращённый рендер, а не исходник

Закрывающее свойство: **обязательный знаковый тест действительно монтирует поставленный FadenSign, получает SVG-узел/его `d` и наблюдаемые свойства из результата рендера, сравнивает их с независимым ожидаемым выходом проверенного порта при том же управляемом времени и входах; это делается во ВСЕХ 11 состояниях, с ОС-УД false и true, а также после обновления состояния/флага.** Null/отсутствующий SVG/другой путь — именованный отказ. Один вызов `pose()` в тесте, вызов мока настройки или проверка ненулевого числа узлов не являются достаточным assertion.

Множество состояний замкнуто по референсу OBJECT: idle, listening, understanding, speaking, working, waiting, needs_action, ready, done, uncertain, error. Перечень берётся из пиннованного референса проверяющей стороны, не из урезаемого субъектом списка. Продуктовый порт уже независимо судится P/S/D-осями; его можно использовать как численную ступень ожидаемого рендера, но не мокать FadenSign/его численное ядро так, чтобы мок сам выдавал ожидаемое дерево. Допустимы штатные jest-expo host-моки, управляемые AccessibilityInfo и часы.

**Важная поправка к предложению «только path по всем состояниям»: этого недостаточно для УД.** Собственный замер: у working при t=777 `path(false)==path(true)` и `dotXY(false)==dotXY(true)`, но `bead` меняется 0.8247986875→0.35. У listening путь тоже одинаков, меняется dotXY. Поэтому проверка ОС-привязки обязана включать заранее различающий наблюдаемый результат: например, геометрию idle при t=777 (путь И координаты точки различаются), сравненную в обеих полярностях и после смены флага. Нельзя доказывать УД только working-path или ожиданием, самостоятельно вычисленным вне рендера. Если тест судит bead — он обязан читать соответствующий реально возвращённый SVG-элемент, не отдельную позу теста.
