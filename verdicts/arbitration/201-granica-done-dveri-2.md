## РЕШЕНИЕ 1 — исправить способом канон/инструмент

**Адверсарий прав; согласие автора по fail-closed принимается.** Повреждённый ответ API входит в уже замороженное обязательство §2(б) «не JSON → не проверена». Ни редкость, ни отсутствие доказанного ущерба, ни конец бюджета не превращают доказанный false done в допустимый остаток.

Конечная инженерная граница:

- Свидетельство принимается только после успешного полного разбора входа: процесс-производитель и весь используемый конвейер завершились успешно; разобран **ровно один JSON-документ**; предметный предикат проверен именно на нём. Частичный stdout при любом ненулевом rc отбрасывается целиком.
- Для compare/check-runs корень — объект ответа API. Пустой ввод, синтаксическая ошибка в любом месте, второй документ (включая `{}` после успешного первого), ошибка jq/подачи данных — не доказательство. Разрешённые пробелы/переводы строк вокруг одного документа не являются вторым документом и не должны создавать ложный отказ.
- Использовать существующий канон jq, например полный slurp с проверкой мощности входа `length == 1` и предметного типа до извлечения поля; результат присваивания проверять явной веткой ошибки. Эквивалентный способ, гарантирующий полный разбор и единственность документа, допустим. `jq -e` само по себе не запрещает несколько документов; один `pipefail`, `set -e`, обрезка первой строки или добавление аварийного `0` также не заменяют эту границу. Самописный JSON-парсер и новый общий фреймворк не нужны.
- Проверять статус до использования результата в `case`, численном сравнении, выборе режима, адреса или пути. Если у разбора остаётся pipeline, ни один его ненулевой статус не маскировать. Не требуется отдельное семейство фраз для каждого системного rc: обязательны правдивый класс отказа и отсутствие тега.

Один валидный JSON с положительным значением, успешным транспортом и прочими честными свидетельствами по-прежнему открывает done. Семантика разрешённых status, имени arch, SHA, completed/success и прочих гейтов не меняется.

## РЕШЕНИЕ 3 — исправить способом клетка, не только прозой

**Батарея должна различать нарушенный механизм.** Architect усиливает существующую семью 201 и её модель; контракт frozen/201/1 задним числом не меняется.

Минимальные различающие входы в двух независимых API-маршрутах:

1. Compare: корректный положительный объект, затем повреждённый хвост; curl rc 0, настоящий jq. Ожидаются rc 1, причина «влитость … не проверена» и отсутствие done-тега.
2. Check-run: корректный положительный объект с успешным arch на точном HEAD, затем повреждённый хвост; curl rc 0, настоящий jq. Ожидаются rc 1, ARCH_CI и отсутствие тега. Это отрицательный контроль, даже если исходный код уже отказывает на этих байтах.
3. В обоих маршрутах отдельно предъявить два синтаксически полных JSON-документа после положительного префикса; второй может быть пустым объектом. Отказ должен быть по неединственному ответу, а не случайному побочному предикату. Так проверяется именно граница, которую rc jq в потоковом режиме не обеспечивает.
4. Сохранить/предъявить парные положительные одиночные ответы: compare behind и identical; arch, arch с пробелом/скобками на точном HEAD, completed/success. Хотя бы положительные API-контроли с допустимым внешним whitespace не должны ложно отказываться. Прежние curl rc≠0, ahead/недоступность, запрет arche и frozen/HEAD-класс риска остаются защищёнными.

Независимые клетки не объединять в один сценарий, который зачтётся по первому раннему отказу. Ожидание, тело ответа и факт ошибки должны согласовываться и в live, и в модели: нельзя оставить `compare_status=behind` как успешное доказательство при повреждённом теле, а затем объявить зелёный `--model` достаточным. Ожидания хранятся вне проверяемого мира; факты полного JSON-разбора получать каноническим инструментом, не особой обработкой строки `{broken`.

Для остальных перечисленных jq-callsite предъявить адресное доказательство отказа на ненулевой rc при содержательном stdout: путевые чтения, repoId и canonicalRemote не должны продолжать работу. Если реализация объединит их одним механизмом, допустимы общая проверка отказа механизма плюс проверяемая карта всех его вызовов и положительные профильные контроли; не требуется комбинаторная матрица произвольных профилей. Правдивый отказ и отсутствие тега проверяются, как и в API-клетках.

Стабы должны представлять возврат прежней ошибки — игнорирование rc/использование успешного префикса и допуск потока документов; наблюдаемое отличие проверяется против реального маршрута. Конкретные имена, число и привязки к клеткам задаёт **architect по коду**, не данный текст и не проза контракта. В SDACHA нужны также адресные мутации живой двери: одно модельное `--stabs` не доказывает, что живая дверь охвачена. Откат только явной rc-проверки может оставаться безопасным благодаря полному slurp; такой мутант нельзя ложно назвать пойманным по тому же хвосту — architect выбирает различающий вход/возврат прежней операции и показывает наблюдение.
