## С-1 (И-1): «merge исполняет сам скрипт» против «merge существует»

**Прав критик.** Наличие в first-parent журнале merge-коммита с committer=orchestrator не
доказывает, что его создал вызов `land_agent.sh`: замер 3 — идентичную запись журнала
создаёт любой актор через `-c user.name=orchestrator`. Смысл среза 3 — приземление ОДНОЙ
транзакцией (merge+push+снос ветки/worktree); скрипт-валидатор чужого merge эту
транзакцию не исполняет, а оба именованных case остаются зелёными.

**(а) Что наблюдаем.** Переход, а не состояние: вызов `land_agent.sh` на НЕслитой ветке
сам сдвигает main на новый merge-коммит. Результат-форма (не способ: как скрипт внутри
строит merge — `git merge` или иное — не судится; судится эффект вызова):
до вызова фикстура пинует `main_before=$(git rev-parse main)` и `tip=$(git rev-parse
<ветка>)`; заранее построенного merge в фикстуре НЕТ. После вызова с rc=0 обязаны
выполняться все четыре:
`git rev-parse main != main_before` (main сдвинут вызовом);
`git rev-parse main^1 == main_before` (сдвинут ровно одним first-parent шагом);
`git rev-parse main^2 == tip` (второй родитель — приземляемая ветка);
`git log -1 --format=%cn main == orchestrator`.

**(б) rc-носитель.** Зелёный case scoped `--scope land_agent` несёт пины и четыре сверки
выше; `case_merzh_ne_orkestrator` остаётся как есть (identity результата);
`case_kommit_mimo_merge` остаётся (прямой коммит на main).

**(в) Почему обход красный.** Валидатор заранее созданного merge попадает в вилку без
выхода: в фикстуре merge заранее не существует — валидатору нечего валидировать (rc≠0 на
зелёном case → красное), либо он «проходит», не сдвинув main (`git rev-parse main ==
main_before` → сверка красная). Создать merge может только сам вызов — что и требует :60.

**(г) Честная граница.** Живой журнал main не удостоверяет, КЕМ создан ИСТОРИЧЕСКИЙ
merge: committer подделываем `-c` (замер 3), и никакой критерий по журналу это не
различит. Фикстура доказывает поведение ИНСТРУМЕНТА; дисциплина «в живом репо приземляет
только инструмент» — cognitive-only остаток и называется в контракте прямо (ужесточение —
подписи/серверный контроль — отдельное слово владельца, класс уже записан в шапке
check_zones). Канарейка И-5 сторожит код в `scripts/`, не ad-hoc команды агента.

## С-2 (И-9): реестр судит committer, зоны судят author — расцепка

**Прав критик**, и это не теория: замер 2 — `author=implementer committer=critic` по пути
зоны implementer проходит настоящий `check_zones.sh` (rc=0) и одновременно проходит
реестр И-9 (critic — известное имя). Два судьи смотрят на РАЗНЫЕ поля одного коммита, и
зазор между полями — легальный вход `--author`.

**(а) Что наблюдаем.** Сцепку пары на приземлении: у КАЖДОГО коммита приземляемого
диапазона committer == author, И committer входит в реестр авторов замороженных
контрактов (существующая проверка И-9 остаётся). Тогда поле, которое судит check_zones
(author), тождественно полю, которое судит И-9 (committer), — расцепки нет по построению.
Вариант «реестр судит author» отвергнут: он дублирует check_zones и зазора не закрывает
(committer остаётся свободным). Вариант «check_zones судит committer» отвергнут: контракт
сам запрещает неэквивалентные правки check_zones, и замороженные ветви прошлых контрактов
менять нельзя.

**(б) rc-носитель.** Приземление отказывает rc 1 поимённо: «identity расщеплена: <sha>
author=<a> committer=<c>». Красный case scoped `--scope land_agent` —
`case_identity_rasscheplena`: диапазон с одним коммитом `--author='implementer <…>'` от
committer critic → rc 1 с этой причиной. `case_imja_vne_reestra` остаётся.

**(в) Почему обход красный.** Названный обход (`git -c user.name=critic … commit
--author='implementer <…>' --no-verify`) даёт committer≠author — приземление rc 1 ДО
merge; `--no-verify` не помогает: проверка живёт в land_agent, не в хуке. Merge-коммит
самого скрипта сцепку выполняет автоматически (обе identity — зашитый orchestrator).

**(г) Честная граница.** ИСТИННАЯ роль процесса не судится: identity самообъявлена, и
агент, назвавшийся чужой ролью ЦЕЛИКОМ (author=committer=critic), ловится только
пересечением путей с зонами (замер 1 — rc=1 на чужом пути; вне чужих путей — не ловится).
Это известный, уже записанный предел: ужесточение — подписанные коммиты со сверкой ключа
и имени — включается словом владельца (шапка `check_zones.sh:39-42`); здесь оно не
заводится и не требуется для закрытия механического зазора И-9↔check_zones.

## С-3 (И-6): refname жив ≠ checkpoint сохранён

**Прав критик.** Замер 4: `update-ref` на main оставляет имя в `for-each-ref`, а
checkpoint делает недостижимым из refs. «Вход с флагом силы отсутствует по построению» —
свойство интерфейса, не поведения: скрипту флаг не нужен, чтобы перевести ref.
`case_zavisshaja_snesena` наблюдает только пропажу имени и к подмене цели слеп.

**(а) Что наблюдаем.** Тождество цели: каждая несбитая ветка после прогона GC разрешается
в ТОТ ЖЕ OID, что до прогона. Это результат-форма и ровно анти-паттерн-safe: не
перечисляются способы исчезновения (delete / update-ref / reset / re-create) — любая
смена цели ref равносильна сносу и красна одной сверкой. Список владельцу и наличие имени
в `for-each-ref` остаются как были.

**(б) rc-носитель.** Фикстура gc_agent_branches пинует `oid_before=$(git rev-parse
refs/heads/wip/<NNN>/<автор>)` до вызова GC; после вызова зелёный case требует
`git rev-parse refs/heads/wip/<NNN>/<автор> == oid_before`. Красный case scoped
`--scope gc_agent_branches` — `case_zavisshaja_peredvinuta`: GC-обход печатает ветку в
СПИСКЕ и переводит ref на main → имя живо, OID сменился → rc 1 с повтором причины.
`case_zavisshaja_snesena` остаётся (пропажа имени — отдельная причина).

**(в) Почему обход красный.** Названный обход («напечатать в СПИСКЕ, затем перевести ref
на main») меняет OID — сверка тождества красная независимо от того, каким способом цель
сменена и что имя уцелело.

**(г) Честная граница.** Судится поведение `gc_agent_branches.sh` в фикстуре. Произвольный
`update-ref` МИМО GC в живом репо git'ом не запрещён и этим инвариантом не судится (как и
в С-1: живая дисциплина — не предмет фикстурного критерия). Прореживание объектов
`git gc`/`prune` — не предмет 016.
