## Решение по спорным пунктам

### Пункт 1 — критик прав по круг-2-обходу

ДА. Факт воспроизведён (замер 2), механизм подтверждён по коду (замер 3). Формулировка контракта
п.9 «состав производного (пары путь×метод, operationId, имена схем) равен проекции published»
слабее заявленного предмета «openapi.json несёт ВСЕ операции published»: операция — это связь
путь×метод→operationId→тело, а не три отдельных множества имён. Прямой вопрос критика («считать
ли проекцией три несвязанных множества достаточной границей R-2») — НЕТ, недостаточно.

### Пункт 2 — граница достаточной проверки (класс), что cognitive-only

Класс: «derived-документ, согласованно подделанный writer+checker при честной metadata и зелёных
lane». Для этого класса правило 7 AGENTS («открытые языки сверх-приближаются счётами/хэшами/
проекциями, не вычисляются») НЕ применимо: производный `app/schemas/openapi.json` по определению
боевого генератора (замер 7) есть тот же документ published в JSON — полная функция от published
с тривиально воспроизводимым определением. Там, где ожидаемое значение вычислимо независимо и
дёшево, приближать его проекциями — ошибка метода: каждая проекция оставляет следующий порядок
(круг 1 — `{}`; круг 2 — перестановка имён; круг 3 — перестановка тел при тех же именах, замер 4).

**Замкнутый критерий (обязателен):** оракул САМ строит ожидаемый документ из published
(`python3 -c 'yaml.safe_load → json.dumps'` — python3+PyYAML уже обязательная зависимость
батареи: их использует toy-двойник) и сравнивает канонические формы (`jq -S -c` ОБЕИХ сторон,
`cmp`). Сравнение каноническое, не побайтовое с `JSON.stringify`: порядок ключей JSON-объекта —
не семантика документа, а формат чисел/порядок у двух runtime воспроизводить незачем; замер 6
показывает, что на реальном документе каноны совпадают побайтово. Невалидный JSON, отсутствие
файла — та же причина. Три частичные сверки (operationId / путь×метод / имена схем) УДАЛЯЮТСЯ —
они подмножество полной и вторую истину не несут. Причина `schemas-proekcija` сохраняется
(алфавит 33 не меняется; смысл имени — «проекция published на производный» — теперь полная).
Файловые (`source_sha256`, `api_version`, `--check`) и поведенческие (stale → `gencontracts-noop`,
писатель восстанавливает → `gencontracts-ne-pishet`) пробы — без изменений: они ловят другие классы.

**Независимость:** оракул не вызывает ни писатель, ни его `--check`, ни его код; в продукте
парсеры к тому же разные (PyYAML vs npm `yaml`) — это сильнее, чем независимость только по коду.

**Что остаётся cognitive-only / остаточным (правило 7, стандарт-А):**
- R-7 (новый, записать в «Остаточные риски (v2)»): расхождение PyYAML 1.1-грамматики и npm
  `yaml` 1.2 на БУДУЩЕМ published после импорта в харнессе не измеримо (npm-дерева нет);
  направление риска — ложно-КРАСНЫЙ `schemas-proekcija` на честном импорте (виден на живом
  клоне п.7 и разбирается диффом канонов), не ложно-зелёный. Замер на базе 5.8.4 — равенство
  (замер 6); на published 3.15 — опасных скаляров сверх уже имеющихся в базе нет (замер 8).
  100%-эквивалентность парсеров НЕ требуется и не заявляется.
- Семантическая верность САМОГО published (не производного), генератор, распознающий пробы, и
  всё, что уже перечислено в НЕ ЗАЩИЩАЕТ, — без изменений.
- Дубликаты ключей в YAML (PyYAML берёт последний, npm `yaml` падает) — не ложно-зелёный:
  боевой `--check` в этом случае rc≠0 → `gencontracts-rashozhdenie` раньше проекции.
