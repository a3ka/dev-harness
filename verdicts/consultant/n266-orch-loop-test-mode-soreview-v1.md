## Техническая форма допустимого (Б)

Предложение — шов исполнения, не режим «без безопасности». Конкретная форма для обсуждения: точное значение ORCH_LOOP_TEST_MODE=1 выбирает фиксированные mock-исполнители sudo/getent/systemd-run из явно заданного тестового мира; пустая/отсутствующая переменная выбирает настоящие команды. Неизвестное значение или неполный тестовый мир дают именованный отказ до запуска, а не автоматический переход к прямому workshop. Команды передаются массивами аргументов, не строкой для eval.

Подмена сохраняет один общий алгоритм запуска: SCOPE с прежними --user --scope, MemoryMax и MemorySwapMax=0; внутри него тот же вектор sudo -nu с пользователем агента и HOME вне /home/harness; тот же свидетель RAN; отказ scope без свидетеля означает rc≠0 и отсутствие вызова сессии. Mock sudo моделирует исполнение без реального переключения uid только для безвредной toy-команды; mock getent, если нужен тесту, сообщает toy-учётную запись, а не меняет выбор пользователя в production. В текущем orch-loop getent непосредственно не вызывается. Mock systemd-run сохраняет протокол исполнения/отказа, а не пишет RAN при отказе. Логика маркера, счётчиков, остановки, зачистки потомков и обработки OOM не получает отдельных тестовых ветвей. Такой шов не должен восстанавливать запуск после отказа scope.

Контрольные границы применимости:

- ORCH_LOOP_TEST_MODE по умолчанию не установлена. На боевом входе доверенный установленный пускатель не принимает её и mock-пути из среды агента: среда очищается/задаётся доверенной конфигурацией, разрешение подмены не наследуется от кандидатного кода. Простое обещание «на станции никто не выставляет» НЕ доказывает недоступность переменной. Любой процесс может задать env для своего ребёнка; переменная — переключатель, не граница полномочий.
- Внешний тестовый раннер уже работает под непривилегированным uid, без доступа к /home/harness, ключам публикации и живому состоянию станции, с реальным внешним ресурсным пределом. Моки не создают эту изоляцию и не служат её доказательством. Это согласуется с И-8б 093: граница наследуется снаружи, а не строится самой фикстурой после старта.
- Производственный вход даже при подброшенных ORCH_LOOP_TEST_MODE=1 и mock-путях остаётся на настоящем sudo/systemd-run либо отказывает до запуска. Возможность запустить toy-копию под уже ограниченным агентским uid не должна превращаться в возможность получить uid владельца или привилегированный сервис. Проверка одного лишь пути /tmp или наличия флага этого не обеспечивает.
- Необходимы раздельные наблюдения: на toy-мире режим включается только явно; mock scope отказывает — команда не исполняется; production без флага и с попыткой его подбросить не исполняет mock; реальный ребёнок production имеет нужный uid/HOME, недоступные контрольные файлы и действующий cgroup-предел. Проверка argv моками не доказывает свойства ОС. Эти сценарии здесь предложены, не объявлены выполненными.

[INFERENCE] При выполнении этих условий (Б) может быть тестовым швом без ослабления реальной защиты. Но доказательства доверенной очистки боевого входа и доставки флага через существующую 085 в этом задании отсутствуют; более того, очищающий код 085 прямо мешает предложенному ORCH_LOOP_TEST_MODE. Не предлагаю обходить это новым не-ORCH именем или распознаванием CIKL085_* в production: это не устраняет семантическое противоречие м4/м6 и связывает защиту с конкретной батареей.
