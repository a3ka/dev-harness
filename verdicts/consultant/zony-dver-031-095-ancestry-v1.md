- Полный SHA судимого коммита: 8f1c25f011921721934d870914f562f9f3ff815c; его единственный parent — 41bc76874a5f792b7b1c96ee38953ab076f45eef, автор orchestrator.
- Дельта registry/contracts.tsv содержит ровно одну удалённую и одну добавленную содержательную строку:

  -095 → 9d6689de3efb3456e94ad61f69c434c47512d8e8
  +095 → 80a2e0df8f67f18fb51b3027ae3df805b97fde90

  Это REPLACE, не ADD. Перемещение строки в конец реестра не превращает замену в только-добавление. Старый SHA совпадает с tag-object id/CONTRACT/095, новый — с tag-object frozen/contracts/095/1.
- Аннотированный frozen/contracts/095/1 указывает на ae6ccc71fb6961ad06a7fbb5534a3f6d68e80ce8; parent последнего — e75ccdfa2462b59f6e7d3b94479a4217e3b097ee.
- **ae6ccc71 создан РАНЬШЕ, а не позже 8f1c25f0:** author-date и committer-date первого — 2026-10-09T22:38:07+00:00; второго — 2026-10-09T22:40:25+00:00. Разница 2 минуты 18 секунд. Формулировку «хронологически ПОСЛЕ» нельзя использовать как основание патча.
- Непредковость доказана разрешённой readonly-командой `git log --format=%H 8f1c25f0..ae6ccc71`: диапазон содержит ae6ccc71, e75ccdfa, 27f54d67. A..B означает достижимые из B коммиты за вычетом достижимых из A; наличие самого ae6ccc71 доказывает, что он не достижим по parent-рёбрам из 8f1c25f0.

Причина необратимости — **DAG, не часы**. Parent-указатели входят в содержимое commit object и его SHA. Будущий merge M может иметь обоих предков — 8f1c25f0 и ae6ccc71, но не добавляет parent старому 8f1c25f0. Проверка двери относится к C=8f1c25f0, не к M/HEAD. Изменение parent создаёт другой commit C' и меняет SHA всех переписанных потомков. Для опубликованного main это отдельная операция переписывания истории/force-push, а не обычный landing. Старый объект 8f1c25f0 при этом всё равно не меняется: лишь новая история перестаёт на него ссылаться. Git timestamps сами по себе не удостоверяют ancestry и допускают несогласованные часы.

Сообщённый FAIL общего check_zones/check_fork_route повторно не запускался: это известное наблюдение, а не основание для повторного глобального прогона. Здесь непосредственно исполнены git diff/log/show/cat-file/rev-parse и наблюдены их результаты.

## 2. Варианты и границы применимости

### (а) Узкий grandfather — самый дешёвый, прецедентно-согласованный вариант для прошлого

Ровно одна новая историческая пара полного SHA и пути, при сохранении внешнего условия автора orchestrator. У нового коммита будет другой SHA: он не совпадёт с исключением и пойдёт через прежнюю дверь со всеми проверками формы, first-parent-линии окна, ancestry, vmax и обоих tag-object SHA.

Это **сознательное исключение из исторического контроля**, а не доказательство того, что исходная заморозка удовлетворяла 049. В точке continue обходятся все последующие проверки данного пути, не только ancestry. Ограничение полным SHA делает исключение замкнутым: нельзя изменить содержимое/автора/parents этого коммита и сохранить тот же объект. Другие пути того же коммита исключение не получают.

Живая история уточняет прецеденты: исходные две registry-пары 079/090 введены d2ba198a (owner, явная РАЗРЕШИЛ-ВЛАДЕЛЕЦ); третья registry-пара 091 — 8675f9d7. db5d905b/3cd95d85/763d8dd7 относятся к исключению 81e6e252 с батареей 094, fab27940 — к contracts/092. Все поддерживают канал явного разрешения владельца, но не все являются введением трёх registry-пар.

### (б) Любой существующий frozen-тег без ancestry — не эквивалент будущему landing

Обещание, что тег «станет предком C после ленда», невыполнимо для фиксированного C. Замена условия на наличие тега где угодно — новая, более слабая норма, применимая в том числе к будущим коммитам.

[INFERENCE] При сохранении остальных проверок становится допустима REPLACE на tag-object frozen-тега из неслитой боковой ветки: реестр main заявляет заморозку текста, которого нет в истории main на момент C, и эта ветка может никогда не приземлиться. Утрачивается привязка freeze к истории публикующей ветки. Это окно подмены реестрового указателя без заморозки, интегрированной в main, а не возможность записать произвольный 40-hex при сохранённой проверке равенства tag-object.

Два разных ослабления нельзя смешивать:
- «Любая версия» дополнительно допускает откат к старой версии при наличии более новой достижимой заморозки — нарушает vmax и инвариант 049/1 (стаб С5).
- «Максимальная версия среди всех живых сейчас тегов, без ancestry» повторно красит корректную старую замену минт→v1 после появления v2 — ровно класс С6/Н-156 из контракта 049.

Даже если аннотированный тег настоящий, его существование не означает интеграцию commit в C. Граница процедуры создания доверенного тега остаётся отдельной от этой проверки. Не предлагаю менять дверь таким образом ради одного исторического коммита.

### (в) Revert/повторная заморозка — не ремонт опубликованной истории

Revert создаёт новый коммит R, но C остаётся предком R и продолжает судиться в исторических окнах. Обратная замена frozen→mint к тому же не является штатным REPLACE на frozen по 049; это может создать ещё одно нарушение. Исправление текущей строки и будущий правильный freeze не легализуют старый C.

Для будущих публикаций корректна последовательность: текст и необходимый вердикт включены в main → frozen-тег на достижимом состоянии → REPLACE-коммит на main. Существующий frozen/contracts/095/1 не следует перемещать ради обхода: tag-object SHA изменится, а историческая строка C останется прежней. Новая версия требует своей обычной процедуры и тоже не чинит C.

### (г) Структурная профилактика без ослабления двери

Класс предотвращается на **границе публикации реестра**, а не переписыванием исторического предиката:

1. К моменту создания REPLACE-коммита C tagged commit должен быть достижим из текущей целевой main, а C должен возникать на её требуемой линии истории. Проверяется конкретный новый tag-object строки, не обещание будущего мержа и не наличие произвольного frozen-тега.
2. Практический штатный вариант — freeze и регистрация на main после переноса туда текста и вердикта. Другой структурно допустимый порядок — создать frozen-тег на боковой ветке, затем сохранить именно tagged commit в ancestry при merge этой ветки, и лишь затем публиковать REPLACE на main. Таким образом, **freeze до landing не запрещён логически; registry REPLACE до landing — причина инцидента**. Squash/cherry-pick не сохраняют идентичность tagged commit и сами по себе нужного ancestry не дают.
3. Это отдельный предмет изменения процедуры/писателя, не реализуемый этим ответом и не повод расширять полномочия консультанта. Перед изменением механизма нужен соответствующий маршрут/контракт; готового нового guard-механизма данный анализ не вводит.

Важное уточнение к атрибуции причины: прочитанный freeze_contract.sh использует один ROOT для g tag (§7), registry/contracts.tsv (§8) и самокоммита (§9); прямого переноса строки в другой root этот код не содержит. Поэтому приписывать самому штатному скрипту автоматическое разделение «тег на branch / REPLACE на main» по одному симптому нельзя. Н-240 описывает дополнительный ручной перенос через plumbing. Наблюдаемые объекты доказывают нарушение порядка публикации; полный трассировочный разбор того переноса здесь не выполнялся.

**Итого:** структурная профилактика для новых C существует и оставляет дверь строгой. Структурного способа сделать уже существующий непредковый tag_commit предком неизменного C без изменения истории или нормы нет. Закрыть старое нарушение без SHA-исключения можно лишь ценой другой уступки: переписать main, изменить семантику аудитора либо вывести C из проверки. Сдвиг incr-кеша/окон или done-тегов ради зелёного CI — сокрытие нарушения, не исправление. Механизм общего реестра разрешённых исключений только переносит те же исключения из case в данные и добавляет новую границу доверия; выигрыша для этого случая не даёт.

## 4. Класс решения и процессуальная граница

Инженерный анализ DAG и минимального патча не требует владельца как передаточного звена. **Разрешить ли именно исключение из защищённого исторического guard** — иной акт: принятие остаточного риска, который существующая норма не делегирует консультанту. Это воля-владельца, признак риск, инв.2 контракта 029. Свидетельство класса отдельно: /tmp/dev-harness-verify/orch-fork-241/klass-v1.md. Оно не является разрешением патча.

Текущая запись не содержит КЛАСС и несёт МАРШРУТ: консультант: по классификатору она пока default-open инженерная. Самостоятельно маршрут не менял. Для предъявления решения владельцу запись должна быть оформлена её автором как КЛАСС: воля-владельца / ПРИЗНАК: риск / МАРШРУТ: батч; АВТОР должен содержать действительный полный id модели автора, а не нынешнее имя роли orchestrator. Конфиг назначает orchestrator тир default (основная anthropic/claude-sonnet-5, fallback zai/glm-5.3), отличающийся от моей модели, но конфиг не доказывает, какая модель фактически завела эту запись. Поэтому независимость от ФАКТИЧЕСКОГО автора ещё требует корректного поля; при совпадении модели автора с моей свидетельство непригодно и нужен другой свидетель. Совпадающих по предмету артефактов арбитража при поиске не найдено.
