### 3. Дизайн workflow

#### 3.1. Явные jobs сейчас; матрица — не условие масштабирования

Предлагаемый DAG:

```text
select-screens ───────────────┐
quality ── build-apk ─────────┼─ e2e-splash ──────────┐
                             ├─ e2e-first-run ───────┤
                             ├─ e2e-erstinformation ─┤
                             ├─ e2e-start ───────────┤─ android-e2e (агрегат PR)
                             ├─ e2e-mission* ────────┤
                             └─ e2e-pilot ───────────┘
* после появления исполняемой пачки в данном дереве
```

Каждый worker зависит только от выбора и сборки, **не от соседнего экрана**. Агрегат напрямую перечисляет selector, quality, build и все worker jobs в `needs`; выполняется с job-level `if: always()`. `quality` остаётся полным, без инкрементального урезания статических/поведенческих проверок. Сборку сначала оставить после quality: это сохраняет ресурсный профиль и не добавляет одновременно Gradle и тяжёлую батарею; отдельное распараллеливание build/quality не нужно для решения этой задачи. Существующая последовательность — `mob/.github/workflows/mobile.yml:250–262`.

Явные jobs позволяют сохранить тела разных шагов и видеть `needs.<job>.result` без реконструкции результатов матрицы. Цена — при добавлении экрана меняются manifest, один job и список зависимостей агрегата; inventory-проверка должна ловить пропуск любого из трёх. Матрица технически создаёт отдельные jobs и тоже годится, но потребует общего контракта исполнителя, `fail-fast: false`, `max-parallel: 2` и независимого учёта каждой ожидаемой строки, а не только общего matrix-result. Сейчас это лишняя одновременная переделка. Семантика матрицы: [GitHub Docs — Running variations of jobs](https://docs.github.com/en/actions/writing-workflows/choosing-what-your-workflow-does/running-variations-of-jobs-in-a-workflow).

#### 3.2. APK: одна сборка, один объект доказательства

Предлагается вынести существующий build в `build-apk`, сохранив release/mock/x86_64 и версии инструментов. После успешной сборки публиковать APK плюс manifest: проверяемый commit/tree, PR head/base/merge SHA, SHA-256 APK, build-env и версии toolchain. Каждый worker делает checkout **того же дерева**, получает **точный artifact-id** из build output и кладёт APK в прежний путь `mobile/android/app/build/outputs/apk/release/app-release.apk`. Самостоятельно APK не пересобирает. Имена артефактов включают run-id и build-identity; при повторе только worker нельзя вычислять имя build-артефакта из нового `github.run_attempt`: build мог остаться от первой попытки.

Проверять digest и provenance до установки; отсутствие/повреждение/истёкший artifact — красный, а не поиск «последнего APK». Передавать APK, не весь `android/` и не рабочую папку соседнего job. Зависимости npm/Python и H-checkout каждый worker подготавливает сам по своим нуждам; job workspace не является контрактом межзадачной передачи.

Прежние пути и команды уже зафиксированы: build — `mob/.github/workflows/mobile.yml:295–300`; APK-аргумент 995 — там же `325–329`; литералы 117/135/118 — `355,499,669`; публикация — `781–788`. Сохранять `EXPO_PUBLIC_API_MODE=mock`: это синтетическая продуктовая приёмка, не доказательство backend/runtime production (`mob/AGENTS.md:16–20`).

**Скрытые зависимости, которые надо перенести вместе с телом:**

- 995: свой H, Python requirements, приватный code-file и cleanup, redaction runner, rehearsal evidence и version gate; не отдавать секрет всем workers. Источники: `mob/.github/workflows/mobile.yml:279–342,770–796`; `harness/fixtures/workshop_project/pilot_995/maestro_probe.py:71–94,128–150`.
- 117: `.harness123`, сверка и свой upload после Maestro. Источник: `mob/.github/workflows/mobile.yml:448–475`.
- 135: `.harness135` **и** необходимая среда `.harness123`, валидатор → cmp → provenance, без изменения кадров между ними. Источник: `mob/.github/workflows/mobile.yml:476–495,563–589`.

Нельзя заменить отчёт 118 отчётом другой задачи только ради экономии: текущая проводка требует same-job порядка. Источник: `mob/.github/workflows/mobile.yml:647–665,733–761`.

#### 3.4. Повторы: один владелец, не произведение слоёв

Предлагаемая политика:

| Единица | Единственный автоматический механизм | Что не добавлять |
|---|---|---|
| 995 | owned restart внутри S, максимум две попытки его фиксированного набора | второй P, retry-action вокруг job, 139 поверх него |
| 117 | текущий ограниченный повтор темы при transport-signature | повтор всего job поверх повторов dark/light |

Текущая гранулярность важна: у 117 повтор **по теме**, а не один токен на всю задачу (`mob/.github/workflows/mobile.yml:407–446`); 135/118 повторяют validator (`574–589,746–761`); 995 — полный набор (`mob/mobile/scripts/ci-e2e.sh:24–25,174–185`). Это уже «свой повтор экрана» без повтора соседей. Если владелец требует строго один retry-token на job целиком, включая обе темы, это отдельная адресная дельта 117 v+1, а не побочный эффект split.

После исчерпания локального восстановления — красный job. Снимок не того момента, `NIZHE_POROGA`, assert/provenance/session-red не лечить повтором до зелени. Для ручного диагностического rerun адресовать конкретный job-id и сохранять историю попыток; это не новая автоматическая политика. GitHub API повторяет выбранную задачу **и её зависимые задачи**, поэтому повтор агрегата ожидаем и полезен, пересборка APK/повтор соседних workers не должны следовать из DAG: [Re-run a job](https://docs.github.com/en/rest/actions/workflow-runs#re-run-a-job-from-a-workflow-run).

Текущие 141/139 допускают смешанную сигнатуру из другого отказа; 139 прямо признаёт сигнатуру из уже успешного предыдущего шага (`harness/contracts/141-obryv-adb-diagnostika.md:179–185`; `harness/contracts/139-e2e-avtoperezapusk.md:102–103`). Новые workers должны классифицировать текущий упавший сценарий, а не весь архив workspace.

#### 3.5. Два раннера: общий пул, независимое состояние

Предложение: workers получают общую метку пула из двух KVM-раннеров; планировщик отдаёт job свободному, без жёсткой привязки экрана к `station-complior`/`station-complior-2`. Для явных jobs нет `strategy.max-parallel`; предел обеспечивается инвентарём **ровно двух** зарегистрированных runner slots данного пула. Перед поставкой проверить реальные GitHub labels/inventory: локальный YAML подтверждает требуемые labels, но не их фактическую регистрацию (`mob/.github/workflows/mobile.yml:261`). Не обещать порядок очереди или автоматический приоритет PR над nightly.

Сеть уже разделена у второго сервиса, Gradle-кэши различаются, но HOME/ANDROID_AVD_HOME/ANDROID_USER_HOME общие; оба процесса под одним uid. Источники: `/etc/systemd/system/gh-runner-complior.service:7–24`; `/etc/systemd/system/gh-runner-complior-2.service:7–26`. Cgroup-лимиты также различаются: 16G/20G/800% против 12G/16G/600% — те же файлы `38–40` и `40–42`. Это не две независимые физические машины.

До настоящего параллельного cutover — согласованное станционное окно для runner-specific HOME, Android user/AVD state, Maestro state; Gradle оставить раздельным. Не потерять установленные root-owned SDK/инструменты и adb-ключи. Альтернатива для AVD — job-private каталог с идентичностью `{run,attempt,screen,runner}` и чистка только собственного каталога; общий HOME всё равно остаётся отдельным риском. Netns не изолирует файлы и чужие процессы того же uid.

Существующие имена AVD уже различаются по 117/135/118 и run/attempt, порты 5562/5564/5566; у 995 — `ci-run-attempt`, 5560 (`mob/.github/workflows/mobile.yml:355–369,499–513,669–683`; `mob/mobile/scripts/ci-e2e.sh:19–22`). Это позволяет сохранить тела при разнесении существующих экранов, но для новых пользователей S нужен screen/runner namespace или строго приватный AVD_HOME. Нельзя масштабировать простым запуском двух копий одного S с общими AVD-файлами. Широкие `pkill` в старых 117/135/118 остаются конкретным риском одинаковых имён, не свойством owned-PID модели 995 (`mob/.github/workflows/mobile.yml:360–364,504–508,674–678`; `mob/mobile/scripts/ci-e2e.sh:40–53`).

### 4. Как выбирать затронутые экраны

#### 4.1. Один manifest в продукте

Предлагаемое место — `mob/mobile/ci-screens.json`, селектор — `mob/mobile/scripts/select-ci-screens.cjs`. Это новые файлы будущей реализации. В `STRUCTURE.md` описать назначение; в `mobile/structure-policy.json` разрешить ровно новый служебный manifest. Не добавлять поля в `ekran.json`: валидатор 132 требует точный набор 17 ключей (`harness/scripts/ekran_shablon.py:151–154,212–219`). Не класть продуктовую карту в harness fixtures: версия карты должна сопровождать продуктовый diff.

Поля: стабильный `screen_id`, ссылки на контракты, `approved|in-development`, владелец разбора, product-pack либо legacy entrypoint, собственные пути, общие dependency-группы, root/child flows, ссылки на существующие frame-manifest/validator, output namespace, CI job-id. Команды не брать произвольной строкой из PR: только известные исполнители/entrypoints. Не дублировать кадры из `kadry.json` и команды из пачки второй копией.

Карту правит автор экранной задачи **в том же PR**, что добавляет/перемещает файлы и зависимости. Общие слои и CI-policy — зона владельца CI; сужение карты и перевод статуса требуют отдельного review. Запись новой `in-development` пачки без исполняемого entrypoint — ошибка, а не разрешённый skip. `approved` подтверждается принятой продуктовой поставкой, не вычисляется по имени ветки или label PR.

#### 4.2. Алгоритм, который не превращает ошибку в пустую выборку

1. Зафиксировать base/head/merge-tree. Для PR получить полный diff merge-base→head, включая старое и новое имя rename, delete, изменение типа файла; исполнить merge-tree с базой. Учитывать также изменение базы после merge-base либо требовать актуальности PR к base: иначе выбранный по старой базе набор не соответствует собранному merge-tree. Если очередь merge используется, отдельно поддержать `merge_group` и весь её диапазон.
2. Читать принятую карту base и карту head. `selected = development(base ∪ head) ∪ affected(diff, map_base ∪ map_head)`. Удаление строки, сужение glob или снятие `in-development` самим PR не должны исключить прежний экран из проверки этого PR. Удалённый approved-экран требует явной принятой операции вывода, иначе красный inventory.
3. Shared-path, workflow/selector/map change, build/runtime config или неизвестный impact → **весь применимый набор**. Неизвестный путь одновременно выдаёт адресную ошибку карты; его нельзя скрыть одним успешным full-run. Неполный diff, отсутствующий base, malformed JSON, неизвестный screen/status — selector красный, не `[]`.
4. Пустой первичный результат не допускается в агрегат. Консервативная политика без исключений для docs-only: selector выбирает весь применимый набор с причиной `EMPTY_SELECTION_FALLBACK`; если реестр сам пуст/недоступен — отказ. Это явная безопасная надбавка к правилу «только затронутые», а не тайный skip. Оптимизацию docs-only без эмулятора вводить лишь отдельным решением с другим доказательством, не сейчас.
5. Публиковать полный `selection.json`: base/head/tree, версии/хеши карты и selector, изменённые пути, selected/excluded и причины, ожидаемые jobs. Не писать пользовательские имена файлов прямо в shell-source; использовать NUL-safe diff и JSON.

Полный Git diff предпочтительнее непроверенной первой страницы GitHub changed-files API. При API-варианте обязательны pagination, контроль полноты/лимитов и fail-closed на усечение. Встроенный workflow-`paths` не использовать как замену селектора: обязательный агрегат должен появляться на каждом PR, а не оставаться Pending из-за фильтра. Платформенное поведение: [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks).

#### 4.3. Что считать общим

Первоначально выбирать всё при изменении:

- `mobile/src/app/**`, `bootstrap/**`, `navigation/**`, `auth/**`, `api/**`, `theme/**`, `i18n/**`, общих `ui/**`;
- auth/onboarding-переходов и session admission, даже если они лежат в `features/`: они используются путями других экранов;
- shared mocks/fixtures, assets/fonts/tokens/copy, API-схем и runtime/build конфигурации, package/lockfile, Metro/Babel/Expo, общих e2e/lifecycle-скриптов, `.maestro/config.yaml`, CI и карты.

Это предложение консервативной классификации. Его основание — реальные composition-импорты `mob/mobile/src/bootstrap/pilot-app.tsx:14–40`, маршрут `mob/mobile/src/app/(tabs)/[section].tsx:44–52,78–109`, build-time mock/http alias `mob/mobile/metro.config.js:11–23`, путь First-Run→auth→disclosure→Start в `mob/mobile/.maestro/erstinformation.yaml:4–43`. Composer разделяется Start/Mission — `harness/contracts/116-cmp-mob-005-mission.md:43–50`. Карта «одна feature-папка = один экран» здесь недостаточна.

Для доказанно локального файла — union владельцев и зависимых экранов, включая сценарные зависимости перехода через соседний экран. Интеграционный `e2e-pilot` выбирать по собственным зависимостям, не автоматически на каждом PR как замаскированную полную регрессию. Общие изменения всё равно выбирают его вместе со всеми экранами.

`[ПРЕДПОЛОЖЕНИЕ]` На нынешней композиции существенная доля PR будет попадать в full-set из-за общих корней. Это цена корректности; уменьшать её надо отделением реальных зависимостей в продуктовой архитектуре, а не искусственным сужением glob. Частоту full-selection нужно измерить до обещаний экономии.

#### 4.4. Как ловить неправильную карту

Три независимые меры, а не проверка карты самой собой:

1. **Инвентарь файлов:** перечислить маршруты, `mobile/e2e-*/ekran.json`, root/child Maestro flows и известные legacy entrypoints независимо от карты; каждый обязан иметь владельца или явную роль helper. Новый pack без записи, запись без job/validator, неизвестный child или новый runtime-путь вне классификации — красный. Инвентаризатор работает до выноса пачек из дерева: сейчас quality переносит e2e-пачки перед lint (`mob/.github/workflows/mobile.yml:235–249`). Не считать это уже решённым структурным checker.
2. **Оракул зависимостей:** независимые от manifest контрольные изменения auth/navigation/theme/api/bootstrap, shared composer, локального screen-файла, удаления/rename и самого manifest. Ожидаемые наборы фиксирует судья по фактическому коду/сценариям, не функция `expected = select(map)`.
3. **Живое сравнение:** в окне приёмки полный shadow-run того же дерева сравнивается с выборочным; screen-red только в исключённом экране — ошибка карты/зависимости до доказанного разбора. После cutover nightly даёт отложенный сигнал о таких пропусках, но не доказывает, что конкретный PR ничего не пропустил.

Существующий 132 не является inventory gate продукта: discovery ищет `ekran.json` под `fixtures/workshop_project` и пропускает неподходящие формы; `mobile/e2e-*` этим обходом не перечисляется (`harness/scripts/ekran_shablon.py:496–518,534–545`). Существующая визуальная сверка судит объявленные кадры, не полноту карты влияния (`harness/scripts/sverka_maketa.py:280–378`). Ручной review остаётся ловцом семантической зависимости, которую статический импорт-граф не выражает; не объявлять это математически полным impact analysis.

### 5. Ночная и предрелизная регрессия

Предлагается один DAG исполнения в `mobile.yml` с режимом, вычисляемым из события, а не две расходящиеся копии экранных шагов:

- `pull_request`: development ∪ affected, обязательный PR-агрегат;
- `push main`: сохранить quality и выборочный post-merge контроль по полному before→after diff; при неизвестном диапазоне full-set;
- `schedule: '17 1 * * *'`: ежедневно 01:17 UTC, полный набор **всех approved на main**, без фильтра changed-files;
- `workflow_dispatch` для предрелизной проверки: полный набор approved на явно разрешённом immutable release-candidate SHA; определение workflow брать из доверенной принятой версии. SHA, config APK и head проверок явно записывать. Прогон после публикации релиза не заменяет проверку до неё.

01:17 UTC — предлагаемый слот, не измеренное свободное окно. У cron GitHub возможны задержки/пропуски; он действует только с default branch, по умолчанию UTC: [Events that trigger workflows — schedule](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule). На этой установке облако нельзя молча использовать как запасную мощность: в `mob/.github/workflows/mobile-cloud-e2e.yml:3–7` зафиксированы ручной режим и отключение расписания из-за бюджета; оно не даёт полного экранного контура, а запускает `.maestro` (`77–92`).

Развести concurrency groups по типу запуска: PR — `pr-<number>` с отменой устаревшего; nightly — отдельная группа без отмены новым push main; release — по candidate SHA, без отмены PR. Текущая группа только `mobile-${github.ref}` с `cancel-in-progress: true` иначе столкнёт nightly с push main (`mob/.github/workflows/mobile.yml:11–13`). Ни один экранный failure не отменяет соседний экран.

Ночной агрегат назвать `mobile-regression-signal`, а не required `android-e2e`. При красном workflow честно красный, без `continue-on-error`. **Не required ≠ скрыть failure.** Issue/уведомление делает отдельный trusted reporter с минимальными `issues:write`, не PR-код с привилегиями; ошибка уведомления не превращает e2e в success. Ночь не блокирует текущие PR и не меняет merge-policy; предрелизный отчёт — обязательный информационный вход решения владельца о выпуске, не неявный новый блок всех разработчиков.

Предлагаемая эксплуатационная норма:

- Одна открытая issue на `{screen, failure-class, signature}`; повторная ночь обновляет first/last seen, SHA/run/job, failed кадры, local attempts, owner, срок, не плодит одинаковые issues.
- Владелец разбора — дежурный мобильной линии; продуктовый red передаётся автору экрана/общей зависимости, infra — владельцу станции. Первичная классификация до 12:00 следующего рабочего дня; два подряд пропуска разбора или возраст >2 рабочих дней — эскалация владельцу. Это предлагаемое SLA.
- Показывать возраст последнего **полного** прогона, coverage `approved executed / approved expected`, количество открытых дефектов и первый/финальный исход. Не закрывать issue одним recovered или ручным rerun без разбора; закрытие — исправление и чистая полная проверка соответствующего SHA.
- Нет ночного отчёта к 06:00 UTC — отдельный `REGRESSION_NOT_RUN`, не «всё зелёное». Детектор свежести должен жить вне выключаемого workflow: независимый монитор станции/организации плюс предупреждение в PR selector. Именно внешний монитор ловит административное disable/delete; cron внутри отключённого workflow себя не проверит.
- Не исключать красный экран из approved-set для зелёного badge; карантин только явным решением с причиной/сроком, экран продолжает исполняться и оставаться видимым в сигнале. Неблокирующая полная регрессия не требует маскировки известных отказов.

### 6. Обязательные проверки и пустой набор

Сохранить стабильные required checks **`quality` и `android-e2e`**, но второе имя отдать настоящему PR-агрегату, а workers назвать по экранам. Нынешнее требование этих имён записано в `mob/AGENTS.md:25`; реальные настройки GitHub branch protection здесь не прочитаны. Их соответствие проверяет владелец при cutover, включая источник check-run и отсутствие другого одноимённого статуса. Не требовать каждый условный worker в branch protection.

Агрегат обязан проверять одновременно:

```text
selector.result == success
AND quality.result == success
AND build.result == success
AND selection валиден, соответствует base/head/tree и принятой политике
AND |selected| > 0
AND selected ⊆ registered_jobs
AND для каждого selected job: result == success
AND выполненные экранные jobs соответствуют ожидаемой выборке
AND evidence/APK identity принадлежит этому дереву и этой принятой попытке
```

`failure`, `cancelled`, `timed_out`, `skipped`, отсутствующий статус выбранного job — отказ. Невыбранный worker может быть skipped **только если** selector явно объяснил его исключение. Если selector или build упал, `always()` запускает агрегат и он краснеет; пустой `needs`/JSON не принимается как универсальное `all([])==true`. Если отменён весь workflow и агрегат не смог исполниться, это не зелёное доказательство — новую попытку оценивают отдельно.

Прямая проверка `needs` достаточна для статусов явных jobs; дополнительно проверять selection/evidence manifest, а не доверять одному JSON `success: true`, написанному тестом. При selective rerun использованная успешная сборка/selection могут быть из предыдущей попытки того же run: их идентичность должна оставаться явной; нельзя требовать одинаковый номер attempt всех артефактов либо брать произвольный последний.

GitHub считает conditional-skipped job успешным для required checks, а провал зависимости может пропустить агрегат без блокировки. Поэтому `needs` без `always()` недостаточно: [Troubleshooting required status checks](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/collaborating-on-repositories-with-code-quality-features/troubleshooting-required-status-checks). Политика required-агрегата должна проверяться доверенной базовой проверкой/защищённым review CI-файлов; если сам PR вправе заменить selector и агрегат на `exit 0`, ни JSON manifest, ни job-name не создают границу доверия. Не исполнять непроверенный PR-код через `pull_request_target` ради секретов; fork без необходимого доступа — явный непрогон/красный, не зелёный пропуск.

**Отдельный потребитель, который легко забыть:** harness `check_ci_gate.sh` смотрит все check-runs SHA, краснит failure и разрешает skipped только через собственный `legkij`/кодовый хеш (`harness/scripts/check_ci_gate.sh:192–205,223–250,260–268`); общая норма перед судьёй — `harness/AGENTS.md:160–163`. `[ПРЕДПОЛОЖЕНИЕ]` Если этот общий путь используется при сдаче mob, он будет конфликтовать и с разрешёнными selective skips, и с неблокирующим ночным red на том же SHA. До cutover проверить фактическую проводку мобильной сдачи; адресно научить потребителя доверенному PR-агрегату и отделению signal-прогонов. Не снимать глобально «все checks», не добавлять фиктивный `legkij`, не объявлять ночь неблокирующей только по branch protection.

### 10. Приёмка скорости: считать критический путь и стоимость, не число зелёных jobs

Пусть `Q` — quality, `B` — единственная сборка, `E_i` — полное время worker (setup/download/boot/test/upload), `A` — агрегат, `W` — ожидание раннеров. Тогда для сопоставимых успешных первых попыток:

```text
старое: T ≈ W_old + Q + B + сумма экранных шагов + публикация
новое:  T ≈ W_new + Q + B + makespan_2(выбранные E_i) + A
нижняя граница makespan_2 >= max(max(E_i), сумма(E_i)/2)
```

Это модель, не результат замера. Повторяется только упавший worker, не вся сумма экранов; однако setup/download и собственные H/npm/Python операции станут повторяться по jobs. Общий сервер, неравные cgroup-лимиты, quality и сборки других PR влияют на `W`/`E_i`; предел «две задачи» не означает линейного ускорения.

Единственная доступная численная историческая опора по полным удачным jobs в предыдущем отчёте — 901/976/875 с для run `40321887036`, jobs `121569641340`/`121577607948`/`121586043178`; это 15:01/16:16/14:35, **не** end-to-end PR, не свежая база v4 и не чистые одинаковые первые проходы (`harness/verdicts/consultant/obryv-emulyatora-mob-astra-v1.md:32–40`). По ним нельзя добросовестно обещать новые 7–8 минут. Длительности четырёх перечисленных свежих run здесь недоступны.

Предлагаемый измеримый gate:

- До внедрения по доступному GitHub API собрать baseline последних сопоставимых запусков: event, head/merge/tree, run/job/attempt, runner, selected/actual flows, queued/start/end, quality/build/setup/boot/Maestro/upload, local recovery и APK hash. Считать cancelled/incomplete отдельно, но не выкидывать их из пользовательского времени ожидания.
- После разрешения — парные штатные наблюдения на одинаковых tree/APK и близкой нагрузке: локальный набор, shared/full-set, полный nightly. Чередовать старый эталон/новую схему в окне проверки, не отбирать только успешные повторы. Отдельно первый проход и recovered/exhausted.
- Предлагаемый операционный порог для заявления «быстрее»: не менее 20 завершённых сопоставимых наблюдений в заявленном классе; p50 времени PR→required-result ниже базы минимум на 25% для локальных изменений, p95 не хуже базы; runner-minutes локального PR ниже минимум на 25%. Если выборок меньше — публиковать каждое значение и максимум, не выдавать неустойчивый p95 за доказанный SLO.
- Для полного split сравнить p50/p95 с полным старым набором при той же полноте покрытия; отсутствие ухудшения p95 и суммарной стоимости — минимальная цель. Если изоляция/setup съели выигрыш, показать это, не расширять конкурентность на одном сервере без ресурсного доказательства.
- Отдельно публиковать selection ratio, долю `COMMON_CHANGE`/fallback, first-attempt red, recovered, final red, queue time, total emulator-minutes. Растущая доля зелёных **jobs** после дробления не равна улучшению доли зелёных **PR**.

Предложенные 25% и 20 наблюдений — критерий для согласования до измерения, не статистическая гарантия и не поручение сейчас запустить серию. `[ПРЕДПОЛОЖЕНИЕ]` Основной выигрыш дадут уменьшение выбранного набора и отказ от повтора соседей; одна параллелизация полного набора ограничена общей сборкой/quality и двумя слотами.

### 12. Риски и что не делать

- **Не объявлять разделение лечением Splash.** В run `40434807469` один APK переносил влияние глобального Splash-env на 118; разные jobs этот факт не исправляют (`harness/HANDOFF.md:6`).
- **Не сохранять скрытый full-suite под именем 995.** Иначе выбранный экран запускает ещё и невыбранные. Но не вырезать интеграционные pilot/rehearsal assertions ради красивого времени (`mob/mobile/scripts/ci-e2e.sh:168–169`; `harness/contracts/995-cmp-mob-001-android-pilot.md:95–110`).
- **Не считать перенос run замкнутой миграцией.** Placement, cwd, env, same-job отчёт и H-checkout — часть исполнения; 141 специально защищает их (`harness/contracts/141-obryv-adb-diagnostika.md:47`; `harness/contracts/118-erstinformation.md:83`).
- **Не множить retry.** Текущий внешний 139 и локальные повторы — разные слои; механическое сохранение обоих не выполняет выбранную политику одного владельца (`mob/.github/workflows/mobile-e2e-retry.yml:65–67`; `mob/.github/workflows/mobile.yml:423–438,574–584,746–756`).
- **Не экономить за счёт ложной карты.** Неполные зависимости дают меньше минут ценой пропущенной регрессии; ночной сигнал — ловец с задержкой, а не оправдание такого пропуска.
- **Не выдавать один SHA карты за доверие.** Автор PR может менять и карту, и проверку; нужна защищённая policy/review граница. Не переносить PR-код в privileged `workflow_run`/`pull_request_target` ради удобного доступа к секретам.
- **Не расширять пул больше двух эмуляторов до измерения.** Общий сервер и общий файловый state не превращаются в независимые машины от числа jobs; подтверждённые ограничения — `/etc/systemd/system/gh-runner-complior.service:18–24,38–40`, `/etc/systemd/system/gh-runner-complior-2.service:20–26,40–42`.
- **Не добавлять облако как молчаливый fallback.** В текущем cloud workflow прямо записана бюджетная блокировка (`mob/.github/workflows/mobile-cloud-e2e.yml:3–7`).
- **Не превращать ночь в required через соседний инструмент.** Проверить harness gate и release/merge consumers, а не только убрать галочку branch protection (`harness/scripts/check_ci_gate.sh:204–250`).
- **Не делать ночь вечно красной путём исключения из внимания.** Нужны владелец, возраст issue, срок разбора, coverage и независимый missed-run signal; красный badge сам по себе эксплуатационным процессом не является.
- **Не менять одновременно API-level/GPU/Maestro/пороги/дизайн и топологию.** Тогда сравнение скорости и полноты потеряет причинность. В текущей схеме API36/x86_64 и version gate 2.11.0 явно заданы (`mob/mobile/scripts/ci-e2e.sh:22`; `mob/.github/workflows/mobile.yml:789–796`).
- **Не обещать доказанную полноту или ускорение до live acceptance.** Эта консультация доказала конкретные связи и ограничения чтением/разбором, но не запуск новой схемы. Недостающие сейчас эксплуатационные сведения: авторизованные свежие job-timings/логи, фактический GitHub runner inventory/required-policy и будущие smoke-результаты. Доступные альтернативы для журналов проверены; искать секреты в чужих каталогах ради их получения нельзя.

**Критерий завершения работы по split:** утверждённый DAG реально исполняет только выбранные экранные наборы плюс явно выбранную интеграцию; каждый имеет независимый emulator/recovery; никакой selected failure/skip/пустой выбор не даёт зелёный required aggregate; полный approved-набор действительно идёт по расписанию и перед релизом как видимый неблокирующий сигнал; все старые assertions/evidence имеют нового владельца; результаты времени опубликованы с исходным рядом и одинаковой мерой. Одного зелёного YAML-парсера, byte-copy тел или увеличения числа зелёных jobs для этого недостаточно.
