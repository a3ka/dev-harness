## 1. Рв-PP-1: неизвестность не равна отсутствию нарушения

В текущем файле `merges_main_into_wip` возвращает 1 и при отсутствии `LIVE_MAIN`, и при неуспешном `cat-file`, и при отрицательном ancestry. Вызывающая сторона знает только `if merges_main_into_wip`; код 1 означает разрешение. Ошибка доступа к графу теряет значение ещё до места, где можно напечатать отказ. Это не дефект вычисления диапазона: диапазон уже закрыт отдельно; здесь другой потребитель тех же отсутствующих объектов.

**Предпочтительный вариант:** три различимых исхода проверки — нарушение / доказанное отсутствие / проверить невозможно. На третьем исходе вызывающая сторона должна отклонять соответствующий push с именованной причиной, ref, SHA проверяемого merge, SHA снимка main и кодом неуспешной Git-команды. Предикат, возвращающий «ошибка», недостаточен без изменения обработки его результата. Для `merge-base --is-ancestor`: 0 — да, 1 — нет, прочие коды — ошибка, не «нет».

Отказ нужен там, где действительно требуется ancestry для merge в судимом wip-диапазоне; не стоит превращать недоступность main в глобальный запрет любого push, удаления ref или диапазона без merge. Отсутствующая ветка main в пустом origin и объявленный живой SHA main без локального объекта — разные состояния; нельзя смешивать их в одну ветку `return 1`. Пустой origin сохраняет существующую bootstrap-семантику.

**Почему не разрешающий fallback `origin/main` или `main`:** даже честно устаревший предок даёт только неполную информацию. Собственная проба ниже на одном графе даёт FLAG относительно живого M и PASS относительно старого B. Отсутствие нарушения относительно B ничего не доказывает относительно M. Более того, локальный tracking-ref сам по себе не доказывает, что он предок текущего live main (force-push, ручное перемещение). Проверенный старый предок может дать положительное свидетельство нарушения при дополнительных условиях, но не основание разрешить неизвестный случай.

Альтернатива: вне хука получить объекты актуального main, затем повторить push с новым живым снимком. Автоматический fetch внутри хука не предлагаю: это не нужно для узкого fail-closed исправления и добавляет сетевое изменение состояния. Проверку невозможности полного ancestry в shallow/неполном графе нельзя заменить одним `cat-file` вершины; без полного доказательства безопасный результат — именованная невозможность проверки.

## 2. Рв-PP-2: что проверять вместо имени второго родителя

Текущая проверка `is-ancestor p2 LIVE_MAIN` спрашивает, опубликован ли сам p2 на main. Это не вопрос о том, какую историю main он приносит в p1. Когда p2 — локальный main на один коммит впереди опубликованного, ответ закономерно отрицателен, хотя main уже включён в p2.

**Кандидат для простого графа с одной merge-base:** `b = merge-base(p2, LIVE_MAIN)`; нарушение — b не предок p1. Это эквивалент проверки, что через p2 привносится известная история main, ещё не достижимая из p1. Для каждого не-первого родителя требуется такая проверка, не только для второго. Ошибка вычисления b НЕ означает «не предок», пустой/ошибочный результат нельзя подавать дальше как SHA.

На моём графе кандидат ловит прямой merge и локальный-main-ahead, но пропускает int с текущим main первым родителем. Это собственный живой результат, а не ссылка на ожидаемое поведение. Дополнительная проба показывает необходимую семантическую границу: ветка-сосед, выросшая от нового main, классифицируется так же, как локальный main. Имя исходной ветки не записано в commit DAG; одинаковую ancestry невозможно различить по тому, называлась ли ветка main при создании коммита.

Условия применения предложения:

- Владелец подтверждает уже сформулированное в находке свойство «не приносить в wip отсутствующую у первого родителя историю main», а не требование угадывать имя ветки по DAG. Для синтаксического запрета любой команды `merge main`, включая избыточное слияние уже имеющейся истории, этот предикат неполон: случай `already-contained` намеренно PASS.
- Нельзя копировать отрицание shell-команды без раздельной проверки её rc: `!` превращает ошибку инструмента в логическое значение. Рв-PP-1 и Рв-PP-2 следует закрывать вместе.
- При нескольких лучших merge-base одна произвольно выбранная база недостаточна. Вариант — получить `merge-base --all` и проверить все базы против p1; нарушение, если хотя бы одна не достижима. Проба ниже использовала `--all`, но criss-cross и octopus отдельно НЕ упражнялись: это границы обязательной проверки при реализации, не заявление готовности кода.
- Независимая от хука неоднозначность PP-4/5 остаётся: этот предикат сам не меняет область `refs/heads/wip/*` и диапазон «новое для всех ref origin». Запушенный прежде через иной ref merge по-прежнему может не попасть в судимое множество.
