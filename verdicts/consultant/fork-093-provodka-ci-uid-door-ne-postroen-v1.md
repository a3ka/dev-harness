## 1. Конкретная дверь на GitHub-hosted ubuntu-latest

`jobs.ci` — матрица lane; `jobs.antiplacebo` — другая матрица на ДРУГИХ VM.
Пользователь, созданный в antiplacebo либо соседней lane, не существует в lane 093.
`ci` исполняет `bash scripts/run_ci_lane.sh ${{ matrix.keys }}` от runner-пользователя;
тот выполняет каждую команду реестра через `bash -c "$cmd"` и передаёт ненулевой rc.
Генератор создаёт только JOBS/SHARDS, а не отдельные shell setup-шаги.

Предлагаемый новый файл `scripts/run_ops093_ci.sh` вызывается именно этим workflow
шагом, от runner, ДО первого байта семьи. Его конкретное тело-кандидат:

```bash
#!/usr/bin/env bash
set -euo pipefail
[ "${GITHUB_ACTIONS:-}" = true ] || { printf 'CI-only door\n' >&2; exit 1; }
guard="$1"
sudo -n useradd --system --user-group --create-home --home-dir /var/lib/ci093-agent --shell /usr/sbin/nologin ci093-agent
chmod go-rwx "$HOME"
sudo -n install -d -o root -g root -m 1777 /tmp/dev-harness-verify
sudo -n install -d -o root -g root -m 700 /var/lib/orch-peak
scratch="$(mktemp -d /tmp/dev-harness-verify/ci093-XXXXXX)"
trap 'rm -rf "$scratch"' EXIT
mkdir "$scratch/repo"
git archive HEAD | tar -x -C "$scratch/repo"
chmod 755 "$scratch" "$scratch/repo"
chmod -R a+rX,go-w "$scratch/repo"
cd "$scratch/repo"
sudo -n -H -u ci093-agent -- /usr/bin/env -i PATH=/usr/bin:/bin HOME=/var/lib/ci093-agent LC_ALL=C.UTF-8 /bin/bash "$guard"
```

Это предложение к реализации, НЕ утверждение о проверенном полном выполнении
данного тела на GitHub. В эксперименте проверены резолв и отказ вне CI, не sudo-ветвь.
Условие GITHUB_ACTIONS — предохранитель от случайного локального запуска, не граница
безопасности и не средство авторизации; рецепт только для одноразовой hosted VM.
Не применять эти install/chmod к живой станции.

* `sudo -n useradd …` использует существующее passwordless sudo runner-пользователя.
  Новый системный пользователь получает отдельные uid/gid, закрытый пароль,
  собственный HOME и НЕ получает группу sudo/runner. Nologin не мешает явному
  `sudo -u … /bin/bash`. Конкретный номер uid выделяет useradd, жёсткий номер не нужен.
* **Новый sudoers НЕ нужен.** Нельзя выдавать `ci093-agent ALL=(ALL) NOPASSWD: ALL`:
  это вернёт процессу семьи доступ к владельцу/root. Существующая политика runner
  уже позволяет runner выполнить useradd и `sudo -u ci093-agent`; агенту права
  sudo не выдаются. `-n` делает отказ немедленным, а не интерактивным.
* Копия создаётся runner-пользователем, НЕ через sudo и НЕ с chown на агента.
  Поэтому `stat -c %u "$OPS093_ROOT"` остаётся uid runner, а euid семьи — иной.
  Chown корня на агента снова покрасит ступень 1. Архив HEAD исключает `.git`
  вместе с checkout credential-конфигурацией; node_modules семье не нужен.
  На PR workflow уже чекаутит реальный head_sha, не синтетический merge-ref.
* HOME runner закрывается, а код выносится в /tmp: простое закрытие /home/runner
  с последующим запуском из workspace лишило бы агента доступа и к коду.
  Scratch 0755 сохраняет чтение кода без права агенту менять его; корень копии
  остаётся владельцем станции. Среда очищена, HOME задан пользователю агента.
* Все клетки жёстко создают временные каталоги в `/tmp/dev-harness-verify`, а не
  только в TMPDIR. На свежей VM необходим доступ к этому каталогу у второго uid;
  sticky 1777 — отдельный CI scratch, НЕ список защищаемого состояния И-3/И-8.
* `/var/lib/orch-peak` создаётся root:root 0700 на одноразовой VM. Это реальный
  защищаемый путь, а не стаб результата чтения: клетка должна получить отказ ОС.
  Закрытый настоящий HOME runner защищает .ssh/.config/SESS. Половина-А проверяет
  также ближайших существующих предков и реальные touch-отказы, поэтому одного
  «разного числа id» для зелёного недостаточно.
* Семья и её клетки НЕ создают внешний uid. В клетках 3/4/7 sudo/systemd-run
  шимы относятся к тестируемому orch-loop и toy-сессиям; их нельзя использовать
  вместо внешнего sudo, запускающего САМУ семью. battery_stubs требует rc=1 от
  испорченного субъекта; rc=2 не засчитывается как поимка.
* Отдельное условие всей батареи: клетка 3 выполняет реальный `unshare --user --
  /bin/true`. Если политика конкретного ubuntu-latest образа это запрещает,
  она честно выдаст rc=2, а stub s7 не будет пойман. [INFERENCE] Готовность
  конкретного hosted образа надо измерить под ci093-agent; изменение uid само
  по себе НЕ доказывает зелёный rc всей батареи. Обходить эту проверку нельзя.

## 2. Точная строка реестра и зачем новый файл

TSV (между четырьмя полями — табуляции):

```tsv
step	check:ops-granica-093-family-selftest	120	bash scripts/run_ops093_ci.sh fixtures/_krasnye_093.sh
```

Вес 120 — [INFERENCE] начальная оценка для LPT, НЕ измеренные секунды; заменить
результатом привилегированного прогона перед поставкой. Затем
`bash scripts/gen_ci_steps.sh --write`. Изменяется generated JOBS в ci.yml;
SHARDS antiplacebo не меняется. Отдельная строка package.json для такого bash-step
не требуется существующим резолвером. Имя guard оставлено настоящим аргументом
обёртки, которую она действительно исполняет, а не комментарием для обхода проводки.

Реестр не принимает `sudo …` как ведущую команду, а `bash -c 'sudo …'` пытается
резолвить как файл `-c`. Поэтому прямой sudo-step или встроенный bash -c не являются
маршрутом без нового файла. Два независимых step «setup»/«run» тоже не задают
зависимость: LPT может распределить их по разным VM. Вся последовательность должна
находиться в одной двери либо setup должен стоять перед Lane в той же job.

Альтернатива — вынести useradd/install/chmod/подготовку копии в явный условный
`run: |` перед Lane в `jobs.ci`, с условием
`contains(format(' {0} ', matrix.keys), ' check:ops-granica-093-family-selftest ')`,
и оставить в bash-обёртке переход uid/вызов семьи. Это те же конкретные команды
выше, НЕ `jobs.antiplacebo`. Но `verify_ci_parity.sh` требует дословной оплаты новых
вспомогательных workflow-команд в `config/ci_parity_exceptions.txt`; генератор эти
команды не добавляет. Поэтому единая дверь за bash-step проще и не расширяет
грамматику/исключения паритета. Все прочие lane-команды остаются под runner.
