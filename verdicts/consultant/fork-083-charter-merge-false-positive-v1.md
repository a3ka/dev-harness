## 1. Диагноз: отказ предусмотрен нормой, название форка — гипотеза

Основание — дерево bcefbfd29fb0e8f9122098290b392cc5520c8a85 и объект

существующего маршрута, не СОревью новой конструкции и не пересмотр текста 083.

В scripts/check_charter.sh:174–183 charter_diff_paths сравнивает коммит с
ЕГО ПЕРВЫМ родителем: diff-tree -r --no-commit-id --name-only --no-renames
--diff-filter=MD <c>^1 <c>. Для корневого коммита предусмотрена отдельная ветвь.
В :321–345 история берётся rev-list "$since..HEAD" — БЕЗ --first-parent и БЕЗ
--no-merges. То есть обходятся обе стороны DAG, но дельта каждого merge — к ^1.

razreshil() ищет строку разрешения в теле САМОГО проверяемого коммита; разрешение
в другом предке автоматически не наследуется. Отдельное исключение — закрытый
список точных grandfather-пар SHA/путь.

27500886a87be054e034e97bdd1870853472ae6e. Сообщение действительно только

## 3. Ось (а): чистый путь без переписывания чужого merge

Вариант новой линии от зафиксированного origin/main=d1cbcf771494c3a803b8be5819b64ef746304529
допустим при сохранении текущего локального main/wip как архивной линии и при
явном отборе переносимых изменений. 2c01b1e не предок d1cbcf7: собственный
merge-base --is-ancestor дал rc 1. Ни amend/rebase/reset чужой истории, ни force-push
не нужны. Публикуемый результат может быть обычным потомком remote main в отдельном
клоне/ветке; старый локальный main при этом остаётся нетронутым.

Существенная поправка к предложенному примеру: git cat-file -s
 d1cbcf7:contracts/083-ci-a-parallelnye-dzhoby-generator-shagov.md дал rc 128,
«exists on disk, but not in 'd1cbcf7'». Diff d1cbcf7..bcefbfd для этого пути —
добавление ВСЕГО файла, 468 строк. На d1cbcf7 есть вердикт критика, но это не означает,
что туда уже попал предмет критики. Cherry-pick только будущей правки строки
не создаёт самодостаточный контракт и может дать modify/delete-конфликт.
Кроме того, в переданном задании SHA успешно созданного zone-expansion-коммита
нет: попытка его создания как раз была заблокирована.

Рабочие условия варианта для роли-владельца:

1. Новая интеграционная линия не должна иметь 2c01b1e среди предков. Нельзя после
   переноса слить её обратно в загрязнённый локальный main и считать историю очищенной:
   rev-list всё равно найдёт старый merge. Revert его содержимого также не удаляет
   исторический отказ. Перенос вердикта консультанта — отдельным коммитом, не merge
   всей текущей ветки ответа, которая тоже наследует исходный локальный main.
2. До правки строки требуется чистое основание 083: явно отобранные исходные коммиты
   создания/утверждённых изменений контракта и необходимые артефакты его приёмки,
   без blanket cherry-pick всего диапазона wip. Исходное создание — 1e91ef4;
   до проблемного merge существовал 91789c7 с контрактом и утверждёнными правками.
   91789c7 — полезный источник/альтернативная рабочая база, но НЕ потомок d1cbcf7
   (собственный is-ancestor rc 1), поэтому это не готовая замена remote main.
   Список зависимостей заморозки/приёмки должен собираться по содержимому и проверяться,
   а не выводиться из одного имени ветки. Этот ответ не объявляет непроверенный список
   полным и не санкционирует перенос несвязанных 084/085/ночных изменений.
3. Уже утверждённая владельцем замена СПАСЕНО → zone-expansion переносится без
   изменения предмета/критериев и с данной владельцем строкой разрешения. На чистом
   основании architect может создать этот узкий коммит непосредственно; если он уже
   создан отдельно — cherry-pick сохраняет его сообщение и реальную авторскую санкцию.
   Самовольная вставка всего текущего рабочего дерева под видом «одной строки» не годится.
4. При необходимости нового merge импортирующая сторона переносит существующие
   строки разрешения в его тело по правилу 065; совпадение содержимого с родителем
   не заменяет этого. Новые/изменённые разрешения не синтезируются.
5. Перед публикацией условия готовности — штатные preflight/критик по разрешённой
   строке, заморозка фактического текста, полный check_charter и check_zones на
   РЕЗУЛЬТАТЕ интеграции, а затем штатные push/CI-ворота. Полный суд нужен именно
   на новой линии, не только на веточном патче. Frozen/id-реестры нельзя молча
   отбрасывать ради зелёного результата; старые теги и их провенанс сохраняются.

[INFERENCE] Такая пересборка устраняет зависимость от конкретного плохого merge,
не меняя уставную норму и не расширяя уже данное разрешение на строку 083.
Это условная инженерная рекомендация, не заявление об уже выполненном переносе:
ни clean-интеграция, ни заморозка, ни полный CI этой рекомендацией не исполнены.

Если требуется продолжать публиковать ИМЕННО старую линию с 2c01b1e в предках,
без её переписывания, существующий механизм — точечный grandfather по SHA/пути.
Он требует отдельного прямого слова владельца и правки разрешённым исполнителем;
нынешнее разрешение на zone-expansion в contracts/083 не является таким словом.
Предпочтительный чистый вариант этого дополнительного решения не требует.

## 4. Ось (б): что адресовать исполнителю, а не менять здесь

Условие «если это действительно false positive» НЕ выполнено. Для check_charter
нет совместимого с текущими 019/065 механического исправления, которое сделает
этот merge зелёным просто за равенство файла второму родителю. Исключение всех
merge, переход на --first-parent/--no-merges, сужение делегирования только до staged
пути или приём чужой санкции из другого коммита нарушат явно записанные требования.
Не рекомендуется также добавлять новый SHA в grandfather без отдельного разрешения.

Механическая профилактика находится у ПРОИЗВОДИТЕЛЯ будущего sync-merge:
дословный перенос уже существующих строк по прецеденту 065 и проверка результата
перед интеграцией. Это адресная работа уполномоченного исполнителя в своей зоне,
не поручение консультанту править scripts/. Для старого 2c01b1e профилактика
задним числом не работает. Если будет выбран иной общий контракт суда merge,
потребуется отдельное изменение нормы 019/065 и их различающих примеров;
это не обход в рамках санкции на одну строку 083 и здесь не проектируется.
