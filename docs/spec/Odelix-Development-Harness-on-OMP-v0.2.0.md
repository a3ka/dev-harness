# Универсальный dev-harness поверх OMP

Спецификация архитектуры и доработки

Репозиторий: [a3ka/dev-harness](https://github.com/a3ka/dev-harness).  
Версия спецификации: **0.2.0**.  
Назначение: требования к реализации и приёмке возможностей харнесса-разработчика поверх OMP.

## 1. Назначение и целевой результат

`dev-harness` — универсальная агентная система для выполнения проектной работы поверх OMP. Она должна подключаться к разным новым и существующим проектам: понимать их устройство, находить существующие решения, планировать задачи, запускать исполнителей, проверять результат и поддерживать знания. Разработка кода, архитектура, документация, исследования и операционные задачи используют подходящие им процессы.

**Главный архитектурный принцип: новое подключение проекта не должно требовать изменения ядра харнесса.** Ядро реализует общие механизмы; адаптеры соединяют их с инструментами; пакеты добавляют повторно используемые процессы и проверки; профиль проекта задаёт его цели, устройство, правила и полномочия. Odelix — один из потребителей этой системы. Пример его подключения приведён в разделе 19.

Универсальность означает расширяемую архитектуру с явным перечнем поддерживаемых возможностей. Она не означает, что любая интеграция уже реализована. Первый рабочий набор использует существующий OMP runtime и Git-проекты; дополнительные инструменты и режимы подключаются по конкретной потребности.

**Ответственный за целостность каждого подключённого проекта — его Orchestrator.** Он обеспечивает актуальность плана и знаний, распределяет работу и проверяет полноту поставки. Программные компоненты обеспечивают состояние, ограничения, поиск и проверки. Architect, Implementer и проверяющие роли выполняют содержательную работу в своих границах.

Спецификация описывает целевое поведение. Наличие требования в этом документе не означает наличие реализации. Готовность каждой возможности подтверждается кодом и соответствующей проверкой. Состояние реализации ведётся в задачах и автоматически собираемых фактах проекта.

Целевые результаты:

1. Новый или существующий проект подключается без копирования всего харнесса в его репозиторий.
2. Каждая задача получает подходящий процесс и проверяемый результат.
3. До написания кода определены владелец изменения, существующая реализация и границы модулей.
4. Каждый агент получает достаточный, актуальный и ограниченный по размеру контекст.
5. Сбой процесса или исчерпание окна не теряет задачу, полномочия и сведения о внешних действиях.
6. Независимые задачи выполняются параллельно с контролем общих файлов, контрактов, бюджета и интеграции.
7. Roadmap, описание модулей и фактический статус обновляются вместе с результатами работы.
8. Владелец проекта видит очередь, блокеры, результаты и решения через выбранный интерфейс: локальный CLI, GitHub или другой поддерживаемый адаптер.
9. Два проекта с разными языками, архитектурой и workflow используют одну установку харнесса и изолированное состояние.
10. Подключение проекта меняет профиль и набор разрешённых расширений, сохраняя исходники ядра.

## 2. Существующая основа и точки расширения

Основа для интеграции — дерево `a3ka/dev-harness` на commit `fd6c7bc1465ce32895dc61849993fb58f5dbe6fa`. Перед изменением конкретного компонента исполнитель проверяет его актуальный код и незавершённые задачи.

| Существующий механизм | Назначение | Требуемое расширение |
|---|---|---|
| `workshop` | Запуск OMP для самого харнесса или внешнего Git-проекта | Bootstrap профиля, привязка запуска к задаче и проверка среды |
| `config/harness_pin.json` | Фиксация совместимости с OMP | Проверка необходимых возможностей runtime и понятная диагностика несовместимости |
| `roles/*.md` | Инструкции восьми ролей | Ответственность за контекст, архитектуру, знания и разные типы задач |
| `scripts/gen-harness.ts` | Генерация инструкций агентов | Сборка применимого профиля без второго редактируемого комплекта правил |
| `contracts/` | Критерии приёмки задач разработки | Связь с Issue, Run, workflow и результатами проверки |
| `scripts/spawn_agent.sh` | Ветка и worktree исполнителя | Управляемый запуск процесса, идентификация попытки и восстановление |
| `scripts/land_agent.sh` | Локальное слияние и уборка | Явное разделение локального результата, публикации и интеграции внешнего проекта |
| `scripts/check_ci_gate.sh` | Проверка CI в действующем процессе | Отдельная проверка кандидата PR до слияния для внешних проектов |
| Проверки зон, frozen-критериев и CI | Ограничение изменений и контроль результата | Использование в выбранном workflow, привязка к точному кандидату |
| `.omp/extensions/startup-digest.ts` | Начальный дайджест сессии | Получение ограниченного ContextPack из актуального состояния |
| `scripts/check_ceilings.sh` | Ограничение размеров файлов инструкций | Сохранить отдельно от контроля токенов конкретного запроса |
| `scripts/proxy/metering_proxy.ts` | Учёт вызовов и затрат | Корреляция с Run, резервирование бюджета и контроль параллельных вызовов |

Создание worktree и запуск агента — отдельные операции. Успешное локальное слияние и публикация результата — отдельные операции. Каждый переход должен иметь свой результат в состоянии Run.

Сам `dev-harness` использует профиль `self`, сохраняющий его действующий процесс до принятия изменений. Внешний проект выбирает профиль поставки: проверенный локальный результат, patch или PR с интеграцией. Для PR кандидат проходит необходимые проверки до merge. Устав самого харнесса не становится обязательным уставом всех подключённых проектов. Общие проверки выделяются из существующего процесса, а специфические соглашения self остаются в его профиле.

Существующий генератор остаётся единственным механизмом сборки инструкций. Редактируются исходники ролей и проектные правила; сгенерированные файлы воспроизводимы и проверяются на расхождение.

## 3. Архитектура универсальности

### 3.1. Пять уровней и границы владения

| Уровень | Содержимое | Где поддерживается | Меняется при подключении проекта |
|---|---|---|---|
| **Core** | Состояние Run, переходы, контекст, ссылки на evidence, лимиты, планирование зависимостей | Исходники `dev-harness` | Нет |
| **Adapters** | OMP, Git, tracker, CI, хранилище, модельный gateway и среда выполнения | Версионируемые расширения харнесса | Выбирается реализация и её параметры |
| **Reusable Packs** | Процессы, инструкции ролей, языковые проверки, шаблоны архитектурных правил | Библиотека пакетов харнесса или явно подключённый доверенный пакет | Выбирается набор; существующий пакет может быть переиспользован |
| **Project Profile** | Цели, репозитории, домены, владельцы, принятые правила, проверки, tracker mapping, лимиты | Сам проект или указанный владельцем каталог управления | Да |
| **Local Binding и Run** | Пути машины, ссылки на credentials, capabilities, конкретная задача, snapshot настроек | Локальное изолированное состояние | Да, без изменения общей конфигурации проекта |

Правило выбора места: механизм жизненного цикла относится к Core; протокол внешней системы — к адаптеру; применимая к разным проектам методика — к пакету; предметный смысл и решение владельца — к Project Profile. Новая способность ядра оправдана общим инвариантом или проверенной потребностью разных подключений.

Примеры: ограничение токенов — Core; вызовы OMP — runtime adapter; проверка Rust imports — language pack; запрет конкретному модулю импортировать хранилище — правило проекта; путь к его репозиторию на ноутбуке — local binding.

В Core отсутствуют имена продуктов, доменов и репозиториев, стадии продуктового roadmap, URL tracker и конкретные названия колонок. Проверяемое условие: в основном коде нет маршрутизации по идентификатору конкретного проекта.

### 3.2. Компоненты ядра

| Компонент | Ответственность | Результат |
|---|---|---|
| Profile Resolver | Проверка и сборка профиля, пакетов и binding | ResolvedProjectProfile с provenance |
| Project Bootstrap | Онбординг и достаточность входов для следующей работы | Baseline и список значимых пробелов |
| Inventory & Retrieval | Координация поиска через языковые и источниковые адаптеры | Факты с версиями источников |
| Task Router | Выбор процесса по задаче, эффекту и принятой политике | WorkflowPolicy |
| Planner | Покрытие требований, зависимости и готовность работы | Следующая задача или блокер |
| Run Controller | Переходы, попытки, восстановление и синхронизация | Устойчивое состояние Run |
| Context Manager | Бюджет и сборка контекста каждой роли | ContextPack и checkpoint |
| Knowledge Manager | Согласование требований, фактов и описаний | Knowledge delta и gaps |
| Scheduler | Ресурсы и независимые запуски | Lease и очередь |
| Capability & Budget Control | Проверка разрешений и совокупных лимитов | Разрешение или отказ операции |

Компоненты — модули программы, а не отдельные обязательные сервисы или LLM-агенты. На старте они работают в одном контроллере с одним writer состояния. Разделение процессов вводится при реальной необходимости.

### 3.3. Порты и первые адаптеры

| Порт | Контракт, который использует ядро | Первая реализация |
|---|---|---|
| RuntimePort | Возможности runtime, start, observe, cancel, checkpoint/resume либо новый запуск | Существующий OMP через контролируемый Runner |
| WorkspacePort | Snapshot, рабочая зона, diff, publish/reconcile | Git и worktree; ограниченный файловый workspace для задач без репозитория |
| TaskStorePort | Найти/получить/обновить задачу, связи и результат с защитой от дублей | Локальное хранилище; GitHub Issues как внешний адаптер |
| ChecksPort | Запустить/получить проверки для определённого входа | Локальные команды и GitHub CI |
| DeliveryPort | Подготовить, применить разрешённую поставку, проверить внешний результат | Локальный артефакт/patch; GitHub PR |
| KnowledgeSourcePort | Получить источник и его версию, извлечь факты | Файлы проекта, Git, tracker и результаты проверок |
| UsagePort | Получить расход, резерв и степень достоверности | Существующий metering proxy |
| CredentialPort | Получить ограниченный доступ к ресурсу без помещения секрета в prompt | Локальный credential broker |

Адаптер объявляет capabilities, версию протокола, ограничения, timeouts и семантику повторов. Например, runtime может поддерживать сохранение сессии, но не безопасный resume операции. Resolver проверяет необходимые возможности до запуска и выбирает предусмотренный fallback; обязательная отсутствующая возможность даёт точную ошибку.

Граница универсальности не требует заранее писать адаптеры ко всем провайдерам. OMP остаётся рабочим runtime. Новый адаптер принимается через контрактные сценарии порта, а не через изменения предметной логики Core.

### 3.4. Общие модели данных

- `ProjectId`, `WorkspaceId`, `TaskId`, `RunId`, `AttemptId`: внутренние идентификаторы, не GitHub ID.
- `ExternalRef`: adapter, connection, object type, external ID; необязательная ссылка на Issue, PR или другой объект.
- `SourceVersion`: тип версии и значение — commit SHA, hash файла, revision внешнего объекта; для изменяемого workspace учитывается overlay.
- `EvidenceRef`: источник, версия входа, средство проверки, время, результат и предел применимости.
- `ResolvedProjectProfile`: зафиксированные настройки, версии пакетов, происхождение правил и hash.
- `Run`: задача, snapshot профиля, состояние, полномочия, версии входов и операции.

Кодовый Git-run использует SHA и worktree. Задача исследования может использовать hash набора источников и артефакта. Отсутствие Issue или Git не заставляет создавать фиктивные идентификаторы.

Результаты различают `passed`, `failed`, `unknown`, `unavailable` и `not_applicable`. Последнее допустимо только по выбранному профилю с основанием, а не как способ обойти требуемую проверку.

### 3.5. Пакеты и проектные расширения

Поддерживаются небольшие явные типы пакетов:

| Тип | Что добавляет | Что не решает за проект |
|---|---|---|
| Workflow pack | Шаблон этапов, входов, результатов и возвратов | Продуктовые приоритеты и доступ к production |
| Language pack | Inventory, проверки, правила модульности языка | Бизнес-границы и имена модулей |
| Architecture pack | DDD/layers/ports-and-adapters как выбираемый набор проверок и вопросов | Обязательное переписывание существующей архитектуры |
| Role/skill pack | Специализированные инструкции и методы работы | Полномочия, бюджеты и итоговый вердикт вместо проверок |
| Domain pack | Переиспользуемые предметные методики, если они действительно нужны нескольким проектам | Автоматическое принятие этих методик новым проектом |

Manifest пакета содержит ID, версию, совместимость, зависимости, доступные contributions и необходимые capabilities. Зависимости закреплены lock-файлом. Код проверки выполняется только как разрешённая команда через Runner, с ограничением среды и времени. Markdown-skill не получает права исполнить произвольный hook только из-за обнаружения в репозитории.

Первый формат — локальные версионируемые модули и manifests. Отдельный marketplace, удалённая установка и универсальный язык workflow не нужны для первого подключения. Проект может начать с локального правила или skill; вынос в общий пакет выполняется после подтверждения переиспользования.

### 3.6. Инварианты ядра и настраиваемые правила

Ядро обеспечивает: изоляцию проекта, идентичность входов, сохранение состояния, соблюдение выданных capabilities и бюджета, честный результат операции и привязку evidence к версии. Профиль не может объявить неизвестный результат успешным или выдать себе новые права.

Проект выбирает: архитектуру, используемые роли, необходимые проверки по риску, формат документов, tracker, способ поставки, лимиты и источники истины. Восемь существующих ролей доступны как базовый набор; полный круг нужен только workflow, который его требует.

Программный код контролирует инварианты. LLM предлагает решения внутри действующих правил. Генератор собирает инструкции из исходников выбранных ролей, пакетов и проектных дополнений, сохраняя происхождение каждого фрагмента.

### 3.7. Границы в исходниках харнесса

Предлагаемое размещение новых модулей уточняется по текущему дереву, сохраняя существующие entrypoints и скрипты:

| Область исходников | Содержимое | Допустимые зависимости |
|---|---|---|
| `core/` | Run, policy, context, knowledge, planning, scheduler и модели данных | На общие типы и объявления портов |
| `ports/` | Интерфейсы внешних операций и типизированные результаты | На небольшие независимые типы |
| `adapters/` | OMP, Git, GitHub, local store, metering | На реализуемые порты; зависимости от внешних систем остаются здесь |
| `profiles/` | Общие presets и self-профиль | На schema конфигурации и ID доступных пакетов |
| `packs/` | Workflow, language и architecture contributions | На extension contract; без импорта внутренних модулей Core |
| Composition/launcher | Загрузка закреплённых расширений и связывание объектов | На Core и выбранные адаптеры |

Core не импортирует GitHub SDK, правила конкретного языка или проектные файлы напрямую. Их читает адаптер либо Resolver и передаёт нормализованные данные. Пакет описывает contribution через публичный контракт; он не изменяет частные поля Run Controller и не перехватывает переходы произвольным monkey patch.

Минимальный набор extension points: источник inventory, набор checks, инструкция роли, шаблон workflow, TaskStore и Delivery adapter. Расширять набор следует только под конкретный сценарий. Такие границы не требуют заранее дробить инструмент на npm packages или микросервисы.

## 4. Профиль, настройка и онбординг проекта

### 4.1. Минимальное подключение

Нужны идентификатор проекта, рабочая область и выбранный базовый процесс. GitHub, DDD, отдельный roadmap-файл и несколько репозиториев не являются обязательными.

Ниже целевой формат конфигурации, который требуется реализовать и валидировать; это не заявление о существующем CLI/API:

```json
{
  "schemaVersion": 1,
  "project": { "id": "notes-tool" },
  "workspaces": [{ "id": "main", "binding": "main" }],
  "extends": ["local-development"],
  "packs": ["language-typescript"],
  "taskStore": { "adapter": "local" },
  "delivery": { "adapter": "local-patch" },
  "knowledge": { "instructions": ["AGENTS.md"], "root": "docs" },
  "limits": { "maxActiveRuns": 1 }
}
```

Resolver раскрывает закреплённые defaults: runtime OMP, стандартные роли выбранного процесса и безопасные лимиты. Локальный binding связывает `main` с путём машины. Подключение обнаруженных package scripts, внешнего API и credentials оформляется как конкретная конфигурация; сканирование проекта само не запускает найденные команды.

Для первого пользовательского сценария достаточно одного файла `harness.project.json` в корне проекта или выбранном каталоге управления. Он генерируется при онбординге и редактируется как обычная конфигурация. Названия путей являются предлагаемой конвенцией; существующие документы перемещать не требуется.

В профиле различаются обязательные и необязательные источники. Отсутствие необязательного `AGENTS.md` у нового проекта не блокирует подключение; отсутствие документа, который определяет полномочия или критерии выбранной задачи, требует выяснения до зависимого действия. Краткая диагностика показывает эффективные настройки и источник каждого решения.

### 4.2. Полный профиль по мере необходимости

| Часть | Что задаёт |
|---|---|
| Identity и workspaces | Один/несколько репозиториев или рабочих областей, владельцы, связи |
| Sources | Где находятся принятые правила, архитектура, план и описания модулей |
| Architecture | Принятый стиль, границы и разрешённые зависимости |
| Toolchain | Языковые пакеты, команды и версии инструментов |
| Workflows | Процесс по типу задачи, риску, review и способу поставки |
| Integrations | Tracker, CI, mappings полей, доступные окружения |
| Policy | Утверждённые ограничения автономности и ссылки на выданные полномочия |
| Limits | Run/role/project concurrency, время, расходы и размер контекста |
| Knowledge | Первичные источники, freshness, документы, правила обновления |

Цели, roadmap, словарь домена и модули остаются в документации проекта. Профиль ссылается на них и связывает с процессом, не копируя всё содержание в JSON.

### 4.3. Размещение настроек и состояния

| Место | Содержимое | Разделение |
|---|---|---|
| Установка `dev-harness` | Core, адаптеры, базовые роли и пакеты | Общий исполняемый инструмент |
| `harness.project.json` | Принятые настройки конкретного проекта | Версионируется вместе с проектом |
| `harness.lock.json` | Закреплённые версии профилей, пакетов и адаптеров | Генерируется; воспроизводимость |
| Опциональный каталог `.harness/` проекта | Собственные workflows, rules, skills и mappings | Только специфичные дополнения |
| Локальный binding | Пути, connection refs, настройки машины | Не содержит общих проектных секретов в Git |
| Локальное состояние по ProjectId | Run, leases, журнал, cache, context, логи | Изолировано от других проектов |

Секреты доступны через CredentialPort и не попадают в профиль, lock или prompt. Штатные статусы собираются автоматически. От владельца не требуется вручную синхронизировать эти файлы после каждой задачи.

Для monorepo профиль лежит в его корне и задаёт зоны/пакеты. Для multi-repo выбирается один корень управления со ссылками на репозитории. Для проекта без Git используются выбранные источники и версии артефактов; текущий Git-only launcher требует отдельного файлового адаптера для такого режима. До его реализации режим явно не поддерживается, а не маскируется фиктивным repo.

### 4.4. Как разрешаются настройки

1. Валидируются schemaVersion, закреплённые зависимости, adapter capabilities и разрешённые источники правил.
2. Разворачиваются defaults и выбранный reusable preset.
3. Применяются явные проектные настройки и scoped-правила workspace, модуля и workflow.
4. Привязываются локальные пути и connection refs.
5. Формируется TaskPacket, который сужает scope и ресурсы в пределах разрешённого профиля.
6. Получается ResolvedProjectProfile: итоговые значения, источники, версии, hash и понятный diff от базового preset.

Для скалярных обычных настроек допускается явное override. Коллекции ролей, checks и tool permissions сливаются по ID с определёнными операциями, а не произвольным deep merge. При конфликте пакетов с одинаковой областью правило выбирается явной настройкой проекта. Неизвестные поля и циклы наследования отклоняются. Диагностика показывает конкретное поле и источники конфликта.

Полномочия и лимиты не используют правило «последний файл победил». Эффективные capabilities ограничены политикой среды, выданным пользователем разрешением, доверенной политикой проекта и scope задачи. Пользователь может явно расширить разрешение в своих пределах; агент или прочитанный файл не могут сделать это самостоятельно. Требования обязательной проверки не удаляются случайным overlay.

Существующие `AGENTS.md`, standards и ADR подключаются по их области действия. Обнаруженная инструкция из кода или внешнего документа не становится автоматически доверенной политикой. Неоднозначность, влияющая на конкретное действие, разрешается до этого действия; несвязанный конфликт не останавливает всю работу проекта.

### 4.5. Snapshot и обновления

Run закрепляет resolved profile, lock, применимые документы и capabilities. Изменение общего профиля не переписывает незаметно активный запуск. Совместимое обновление применяется на checkpoint после проверки влияния; изменение критериев или полномочий требует явного перехода и новых проверок.

Отзыв доступа, аварийная остановка и снижение обязательного лимита действуют сразу через контроллер полномочий. Snapshot не даёт права продолжать отозванное действие.

Обновление версии пакета показывает изменения правил, проходит совместимость и имеет возможность отката. Миграция схемы профиля является явной операцией с проверяемым результатом. Генератор может обновить производные файлы, сохраняя авторские разделы.

### 4.6. Последовательность онбординга

1. **Определить проект и режим.** Новый или существующий; код, документация, исследование либо смешанная работа; один workspace или несколько.
2. **Проверить среду.** Пути, доступ, runtime, инструменты; для Git — root, branch, HEAD, remote и незакоммиченные изменения. Не сбрасывать чужую работу.
3. **Обнаружить источники.** Действующие инструкции, архитектуру, задачи, тесты и точки входа. Прочитать только нужную часть; различить принятое решение и гипотезу.
4. **Собрать минимальный inventory.** Реализованное поведение, владельцы, проверки и поставка; для нового проекта — требования и ближайший проверяемый сценарий.
5. **Предложить профиль.** Выбрать подходящие пакеты и адаптеры, связать существующие документы, объяснить значимые конфликты. Сохранить минимальную обратимую конфигурацию в пределах поручения.
6. **Проверить очередь и gaps.** Найти незавершённую работу и зависимости; не создавать дубликаты и не превращать все будущие возможности в блокеры старта.
7. **Выбрать одну готовую задачу.** Входы, владелец, scope, критерии, проверка и полномочия определены.
8. **Начать выполнение.** Сохранить baseline и Run, собрать ContextPack. Расширять inventory и документы по мере затрагивания областей.

Онбординг не требует заморозки всей архитектуры до первого изменения. Работающий проект адаптируется к харнессу через описание существующего процесса. Харнесс не навязывает ему свой собственный layout, полный набор ролей или миграцию tracker.

### 4.7. Выход онбординга

Достаточный результат: эффективный профиль, факты с версиями источников, список влияющих на работу неопределённостей, выбранная задача и способ её приёмки. Владелец получает краткое объяснение, что обнаружено, что настроено и какая следующая работа возможна. Расширение стратегии, расходов или внешних действий требует соответствующего поручения; обычная настройка внутри уже принятого scope выполняется без повторных подтверждений.

## 5. Роли и ответственность

Восемь существующих ролей образуют базовый role pack. Для каждой задачи workflow выбирает необходимый состав: вопрос может выполнить один агент, а критическое изменение — полный круг с независимой проверкой. Проект может добавить специализированную роль через versioned contribution, указав входы, результат, capabilities и проверки; ей не выдаются новые права только из-за названия. Программные менеджеры состояния, контекста и знаний не требуют дополнительных постоянных LLM-агентов.

| Роль | Обязанность | Что передаёт дальше |
|---|---|---|
| **Orchestrator** | Вести план, выявлять пробелы, выбирать workflow, распределять работу, обеспечивать актуальность знаний и завершение поставки | TaskPacket, назначения, состояние задачи, следующая работа |
| **Architect** | Определять границы, владельца, переиспользование, интерфейсы, зависимости и критерии | Решение по размещению изменения и приёмочный контракт |
| **Critic** | Проверять достаточность постановки, критериев, рисков и архитектурных предположений | Замечания до реализации или принятие постановки |
| **Implementer** | Реализовывать в выделенной зоне, проверять поведение, обновлять затронутую документацию | Код, проверки, объяснение изменений, documentation delta |
| **Adversary** | Искать контрпримеры и нарушения инвариантов независимо от автора | Воспроизводимый отказ или результат проверки |
| **Reviewer** | Проверять итог по требованиям, архитектуре, смыслу документации и evidence | Вердикт, привязанный к кандидату |
| **Arbiter** | Разрешать содержательный спор в пределах полномочий | Решение с основанием; эскалация изменения scope при необходимости |
| **Steward** | Находить применимые решения и прецеденты | Ссылки и краткое объяснение применимости |

Steward остаётся ролью чтения прецедентов. Ответственность за ведение roadmap и запись знаний закреплена за Orchestrator; он поручает авторские изменения подходящей роли и обеспечивает проверку.

Владелец проекта определяет цели, приоритеты между продуктами, бюджет и границы автономности. Orchestrator принимает рабочие решения внутри уже выданного поручения. Повторное подтверждение того же разрешения не требуется. Новый внешний эффект за пределами поручения, изменение стратегии или повышение бюджета выносится владельцу проекта с конкретным подготовленным решением.

CI выполняет автоматические проверки. Отдельная постоянная роль Tester не требуется. Независимость проверки обеспечивается отдельной сессией, входами и полномочиями проверяющего, а не только названием роли.

## 6. Маршрутизация задач и цикл выполнения

### 6.1. Тип задачи определяется её эффектом

| Тип | Минимальный процесс | Приёмка |
|---|---|---|
| Вопрос или обзор | Ограниченное чтение, проверка источников, ответ | Ответ соответствует вопросу и источникам |
| Диагностика | Гипотеза, наблюдение, проверка, вывод | Воспроизводимые факты; неизвестное обозначено |
| Редакционная правка | Изменение текста, проверка diff и ссылок | Смысл сохранён, требуемая правка выполнена |
| Архитектурное решение | Architect, Critic, проверка влияния, уполномоченное принятие | Ясные границы, альтернативы при существенном выборе, проверяемые последствия |
| Изменение кода | Постановка, архитектурный preflight, реализация, CI, независимая проверка, интеграция | Поведение и критерии подтверждены для кандидата |
| Миграция | Анализ совместимости, план перехода, проверка восстановления, исполнение | Данные и потребители совместимы либо явно переведены |
| Операционная задача | Проверка цели и прав, действие, независимая проверка постусловия | Подтверждён внешний результат |

Изменение документа с нормативными правилами, рисками или полномочиями проходит содержательную проверку соответствующего уровня. Расширение `.md` не делает задачу безопасной автоматически. Читающий диагностический скрипт и команда изменения production имеют разные полномочия.

Task Router сохраняет причину выбора, обязательные проверки и условия эскалации. Если фактический diff или действие расширяет риск, workflow пересчитывается до продолжения. Упрощённый процесс применяется только там, где он предусмотрен принятым профилем. Лимит времени или токенов не отменяет обязательную проверку.

### 6.2. Цикл задачи разработки с независимой проверкой

Этот workflow — базовый пакет для изменений кода, требующих независимой проверки. Обязательные этапы выбираются политикой проекта и риском задачи; упрощённые процессы сохраняют инварианты Core.

1. Orchestrator получает запрос, находит существующую задачу через TaskStorePort и уточняет проверяемый результат. При локальном режиме задача получает внутренний TaskId без обязательной Issue.
2. Planner проверяет зависимости, scope и отсутствие дублирующей работы.
3. Architect выполняет reuse preflight и решает, куда вносить изменение.
4. Critic проверяет постановку и приёмочные критерии. Требования фиксируются до реализации.
5. Run Controller создаёт запуск; Scheduler выделяет ресурсы; Runner готовит worktree и запускает исполнителя.
6. Implementer получает ContextPack, реализует изменение и выполняет авторские проверки.
7. Для external PR публикуется кандидат. CI и проверяющие роли работают с определённым SHA. Adversary проверяет контрпримеры, Reviewer — итоговую поставку.
8. Замечания возвращаются автору. Изменение кандидата инвалидирует зависящие от него результаты; применимые проверки повторяются.
9. Интеграция выполняется последовательно для репозитория. Если итоговый кандидат отличается от проверенного, применяется политика повторной проверки или merge queue.
10. Knowledge Manager принимает фактические изменения, Orchestrator обновляет задачу и зависимые работы.

Отказ проверяющего не превращается в успех после нескольких попыток. Повторяющийся спор передаётся Arbiter; исчерпание бюджета оставляет задачу незавершённой с объяснением.

### 6.3. TaskPacket

Каждая исполняемая задача содержит: цель, ProjectId/WorkspaceId/TaskId, владельца результата, тип работы, scope и запреты, критерии, зависимости, версии входов, разрешённые зоны, применимые проверки, полномочия, бюджет и ожидаемый результат. Для Git добавляются repo/branch; для внешнего tracker — ExternalRef. Команды сборки не обязательны у задачи, которая не изменяет код.

TaskPacket ссылается на источники. В него включается только необходимый для исполнения текст. Запрос владельца проекта и его последующие уточнения сохраняются как авторитетные входы; резюме агента не может незаметно изменить их смысл.

## 7. Архитектурный workflow и модульность

### 7.1. Определение модуля

**Модуль — единица реализации с одной связной ответственностью, владельцем, явным интерфейсом, инвариантами и разрешёнными зависимостями.** Он скрывает внутреннее устройство и допускает самостоятельную проверку своего поведения.

Доменная область задаёт язык и смысловые границы. Модуль реализует часть её поведения. Репозиторий задаёт границу управления исходниками и поставкой. Процесс задаёт границу исполнения. Эти границы могут совпадать, но не обязаны.

Отдельный бизнес-модуль обычно оформляется как crate/package или внутренний модуль языка в owner repository. Выделение репозитория обосновывается самостоятельным runtime, языковым стеком, правами или жизненным циклом выпуска. Создание папки само по себе не доказывает модульность.

### 7.2. Решения до первого изменения кода

Architect обязан определить:

1. Какое поведение меняется и какие инварианты должны сохраниться.
2. Какой домен и модуль владеют этим поведением.
3. Что уже существует в коде, тестах и незавершённых PR.
4. Какие публичные интерфейсы и потребители затронуты.
5. Как проверить результат и совместимость, включая отрицательные сценарии.

Для простого изменения достаточно короткого решения в задаче. ADR нужен для существенного выбора границ, протокола, хранения, совместимости или другого дорогого в изменении решения.

### 7.3. Reuse preflight

Inventory & Retrieval выполняет поиск по смыслу и реализации: доменные термины, символы, публичные экспорты, вызовы, тесты, зависимости, действующие решения и открытые PR. Поиск учитывает HEAD и рабочие изменения. Устаревший индекс не используется как доказательство отсутствия кода.

Architect выбирает один из исходов:

| Решение | Основание |
|---|---|
| Использовать существующее | Поведение уже соответствует требованию |
| Расширить модуль | Ответственность та же, интерфейс можно совместимо дополнить |
| Выделить часть | Внутри модуля сформировалась самостоятельная ответственность |
| Создать модуль | Есть отдельная обязанность, интерфейс и правила владения |
| Отложить | Не хватает значимого требования или необходимой зависимости |

Результат содержит исследованные места, выбранного владельца и причину. Формулировка «ничего не нашёл» без области поиска недостаточна. Поиск снижает риск дублирования, но не даёт математической гарантии; Reviewer повторно проверяет существенные новые абстракции.

Сходный код разных доменов не объединяется автоматически. Общая библиотека оправдана общей семантикой и согласованным жизненным циклом, а не только похожими строками.

### 7.4. Слои и зависимости

Таблица задаёт проверяемый профиль слоистой архитектуры для проектов, которые его выбрали. Core умеет проверять описанный граф зависимостей, но не требует DDD и одинаковых слоёв от любого проекта. Для библиотеки, плагина, исследовательского notebook или существующего приложения выбираются соответствующие границы. Миграция архитектуры — отдельная задача.

| Слой | Содержимое | Разрешённое направление зависимостей |
|---|---|---|
| Domain | Типы, инварианты и предметные вычисления | На минимальные общие примитивы; без UI, БД и сетевых клиентов |
| Application | Use cases, координация, порты внешних операций | На Domain и объявленные порты |
| Adapters | Хранилища, API-клиенты, транспорт и интеграции | На интерфейсы, которые адаптер реализует |
| Entrypoints | CLI, HTTP, MCP, события | На прикладные сценарии |
| Composition | Создание и связывание реализаций | На собираемые компоненты |

Направление импортов проверяется отдельно от порядка вызовов во время выполнения. Domain не должен импортировать адаптер потому, что прикладной сценарий вызывает внешний сервис.

Небольшой чистой библиотеке не нужны пять пустых каталогов. Структура должна выражать реальные границы. Составной атомарный сценарий может затрагивать несколько объектов: правило границ определяется инвариантом и транзакцией, а не механическим запретом на число сущностей.

### 7.5. Паспорт модуля

Для значимого модуля поддерживается краткое описание рядом с кодом, например `MODULE.md`:

- идентификатор, ответственность и что находится за его границей;
- владелец, доменный язык и основные инварианты;
- публичный интерфейс и разрешённые зависимости;
- принадлежащие модулю данные и правила изменения состояния;
- ошибки, отказные сценарии и требования совместимости;
- ссылки на проверки, решения и незавершённые работы.

Смысловые разделы пишет Architect или Implementer и проверяет Reviewer. Список экспортов, зависимостей, тестов и версия исходников собираются инструментами. Генератор обновляет обозначенные фактические разделы и сохраняет авторский текст.

Описание не дублирует каждую функцию. Сложность документа соответствует сложности границы. Утверждение «модуль готов» требует критериев и evidence, а не наличия паспорта.

### 7.6. Модульность по языкам

| Язык | Механизм | Что проверять |
|---|---|---|
| Rust | `mod`, visibility, crate, Cargo workspace, features | Публичную поверхность, запрещённые зависимости, циклы между пакетами, утечку инфраструктурных типов |
| TypeScript/JavaScript | Modules, package exports, entrypoints | Deep imports, runtime/type-only зависимости, циклы и импорт внутренних файлов потребителем |
| Python | Packages, публичные интерфейсы и направленные зависимости | Импорты, побочные эффекты загрузки, смешение предметной логики с инфраструктурой |
| Solidity, когда потребуется проекту | Contracts, libraries, interfaces | Границы storage, внешние вызовы, полномочия, upgrade layout и межконтрактные инварианты |

Граница Python-пакета или TypeScript-модуля не является границей безопасности. Отдельный crate не нужен для каждой функции. Выбор языка и проверок задаётся профилем репозитория.

Для `dev-harness` первым реализуется пакет его существующего Node/TypeScript-стека. Пакет Rust добавляется как независимо подключаемая реализация языковых проверок. Новые зависимости и инструменты вводятся по конкретной потребности с учётом принятой политики репозитория.

### 7.7. Проверяемое качество

Architecture Checks проверяет запрещённые связи, импорт внутренних интерфейсов и применимые циклы. Проверка имеет отрицательный fixture: намеренное нарушение должно обнаруживаться. Непокрытые динамические зависимости явно обозначаются.

Reviewer оценивает понятность ответственности, явность ошибок, ограниченность побочных эффектов, отсутствие дублирования поведения и достаточность тестов. Метрики размера и покрытия служат сигналами, а не универсальными критериями качества.

Ожидаемый результат теста берётся из требования, независимого расчёта или инварианта. Тест, который повторяет алгоритм реализации, не является достаточным доказательством. Проверки внутренних алгоритмических инвариантов допустимы там, где они помогают обнаружить реальный дефект.

Оптимизация требует измерения. Архитектурная задача не даёт разрешения массово переписать стиль, переименовать несвязанные модули или заменить инфраструктуру без связи с её целью.

### 7.8. Контракты и межрепозиторные изменения

| Вид контракта | Назначение | Место владения |
|---|---|---|
| Приёмочный контракт разработки | Что требуется сделать и как принять задачу | В self-профиле — существующий `contracts/`; во внешнем — выбранный TaskStore или документ задачи |
| Программный контракт | API, schema, события, типы, совместимость | Репозиторий владельца интерфейса |
| Смарт-контракт | Исполняемые правила onchain-системы | Репозиторий соответствующего runtime при его появлении |

Проект сам выбирает место общего каталога интерфейсов. Каноническая схема имеет одного владельца; каталог содержит ссылки, а SDK и производные типы генерируются с версией. Core хранит отношения и версии, не определяя предметное содержимое схем. Самостоятельный репозиторий общих типов не является обязательным.

Изменение общего интерфейса требует карты потребителей, правил совместимости и последовательности поставки. Пока интерфейс меняется, конфликтующие задачи сериализуются. Независимая реализация потребителей возможна после фиксации согласованной версии интерфейса.

## 8. Управление контекстным окном каждого агента

### 8.1. Ответственность и виды памяти

**Context Manager — программный компонент Run Controller.** Он измеряет, собирает и обновляет контекст. Orchestrator отвечает за достаточность входов и выбор следующего действия. Агент может запросить дополнительный материал или checkpoint, но не должен быть единственным механизмом обнаружения переполнения.

| Уровень | Содержимое | Время жизни |
|---|---|---|
| Окно агента | Инструкции, текущая задача, выбранные факты, последние результаты | Один ограниченный диалог |
| Состояние Run | Фаза, права, входные версии, попытки, внешние операции, результат | До завершения и в период хранения аудита |
| Знания проекта | Архитектура, модули, решения, фактические возможности, план | Между задачами и запусками |

Сохранённая история OMP не заменяет структурированное состояние Run. Дайджест помогает навигации; критические сведения о полномочиях и незавершённых действиях восстанавливаются из состояния контроллера.

### 8.2. ContextPack

Перед запуском роли формируется пакет:

- версия пакета, project/workspace/task/run/attempt/role IDs и snapshot профиля;
- цель, актуальные уточнения пользователя, критерии и scope;
- применимые инструкции и ссылки на принятые решения;
- разрешённые действия, зоны и лимиты;
- SourceVersion входов и версия приёмочного контракта; для Git — HEAD, branch/worktree;
- нужные модули, интерфейсы, инварианты и результат reuse preflight;
- результаты предыдущего этапа с версиями и ссылками на evidence;
- блокеры, неопределённости и ожидаемый следующий результат.

Обязательные поля проверяются до старта. Недоступный вспомогательный дайджест допускает ограниченный режим с явной диагностикой. Отсутствие критического scope или сведений о незавершённой внешней операции не допускает изменяющих действий.

### 8.3. Контекст по ролям

| Роль | Приоритетное содержимое |
|---|---|
| Orchestrator | Цели, зависимости, активные Run, блокеры, бюджет и решения |
| Architect | Требование, карта владельцев, существующий код, интерфейсы, ограничения |
| Critic | Постановка, критерии и основания архитектурного решения |
| Implementer | Контракт задачи, изменяемая зона, используемые интерфейсы и команды проверок |
| Adversary | Требования, инварианты, кандидат и возможность независимо проверить поведение |
| Reviewer | Критерии, diff, результаты CI и независимых проверок, documentation delta |
| Arbiter | Предмет спора, позиции сторон, evidence и границы полномочий |
| Steward | Точный вопрос и ограниченный набор источников решений |

Полный архив проекта и история всех агентов не передаются каждому исполнителю. Дочерняя задача получает достаточные входы для своей ответственности. Reviewer не получает авторский вердикт как готовый ответ: критерии и доказательства должны позволять собственную проверку.

### 8.4. Бюджет перед каждым запросом

Контроллер определяет эффективный предел окна по фактическому маршруту модели, runtime и возможностям провайдера. Единый фиксированный размер для всех моделей не задаётся.

Условие отправки:

`input_tokens + output_reserve + tool_result_reserve + safety_margin <= effective_context_limit`

В `input_tokens` входят системные инструкции, роль, schemas инструментов, сообщения, skills и вложения. Кэшированные токены продолжают занимать окно. При отсутствии точного измерителя используется консервативная оценка с зафиксированной погрешностью.

Резервы и пороги настраиваются по профилю и уточняются измерениями. Ограничение байтов файла инструкций сохраняется как отдельная проверка; оно не измеряет весь запрос модели.

### 8.5. Действия Context Manager

| Ситуация | Действие |
|---|---|
| Данных достаточно, бюджет соблюдён | Продолжить |
| Нужен конкретный факт | Выполнить ограниченный поиск и добавить выбранный фрагмент |
| Большой результат инструмента | Сохранить полный результат вне окна, передать сводку и ссылку |
| Много завершённой истории | Сохранить checkpoint и пересобрать пакет |
| Задача содержит независимые части | Предложить разделение с отдельными входами и результатами |
| Следующий запрос не помещается | Остановиться в безопасной точке и начать новую сессию с checkpoint |
| Сменились модель или маршрут | Пересчитать размер окна и резервы |
| Изменились SourceVersion, контракт или scope | Инвалидировать зависящие сведения и загрузить актуальные |

Checkpoint допускается внутри этапа, если иначе следующий запрос небезопасен. Контроллер сначала фиксирует текущую операцию и состояние; незавершённое внешнее действие нельзя потерять при смене сессии.

### 8.6. Что обязано пережить сжатие

Без потери сохраняются:

- исходная цель и последние действующие уточнения;
- scope, запреты, полномочия и оставшийся бюджет;
- идентификаторы и версии контракта и workspace; для Git — branch и SHA, для файлового результата — snapshot/hash;
- выполненные действия и ссылки на результаты;
- активные leases и общие ресурсы;
- незавершённые внешние операции и их идентификаторы;
- замечания проверяющих, блокеры и следующий шаг.

Эти поля хранит контроллер в структурированном виде. LLM может сжать объяснения и ход анализа, но не переписывает авторитетные поля. Новая сессия сверяет состояние через подключённые workspace и внешние адаптеры до повторного действия.

### 8.7. Актуальность и безопасность извлечения

Каждый найденный факт имеет источник и SourceVersion. Для Git индекс отражает commit и overlay незакоммиченных изменений; сведения другой ветки помечаются отдельно. Для файлового workspace используется snapshot/hash. Изменение версии приводит к обновлению затронутого индекса.

Текст из документа, issue, лога или внешнего источника является данными, пока ему не назначена соответствующая нормативная роль. Он не может расширять полномочия агента. Секреты и полный вывод чувствительных команд не включаются в общие дайджесты.

Интеграция с OMP использует подтверждённые возможности закреплённого runtime. Если необходимый перехват или безопасное восстановление не поддерживается, применяется контролируемая новая сессия. Не следует проектировать обязательное поведение на непроверенном имени hook.

## 9. Знания проекта, документация и планирование

### 9.1. Кто ведёт всё состояние проекта

**Orchestrator отвечает за то, чтобы существенная работа была замечена, описана, поставлена в очередь и доведена до подтверждённого результата.** Knowledge Manager и Planner обеспечивают ему проверяемые данные и обнаружение пробелов.

| Объект | Кто создаёт и обновляет | Кто проверяет |
|---|---|---|
| Цели и продуктовые приоритеты | Владелец проекта; Orchestrator фиксирует принятые изменения | Владелец проекта при изменении стратегии |
| Roadmap и зависимости задач | Orchestrator через Planner | Автоматическая проверка связности; Владелец проекта для стратегического изменения |
| Архитектура и границы модулей | Architect; Implementer обновляет затронутые части | Critic/Reviewer по типу изменения |
| Фактический inventory | Инструменты по коду, CI и поставке | Проверки актуальности и источников |
| Статус возможностей | Knowledge Manager собирает факты; Orchestrator разрешает расхождения | Проверяемые критерии и evidence |
| Задача и результат работы | Orchestrator, данные от исполнителя | Reviewer и профиль приёмки |
| Прецеденты | Steward находит; уполномоченная роль записывает принятое решение | Проверка источника и применимости |

Опциональная функция Scribe может готовить текст по фактам. Она не становится самостоятельным владельцем архитектуры и не объявляет работу принятой.

### 9.2. Где хранятся знания

| Источник | Что хранит |
|---|---|
| Owner repository | Код, схемы, тесты, описания модулей и решения этой области |
| Выбранный корень знаний проекта | Общие решения, roadmap, каталог доменов и ссылки на владельцев интерфейсов |
| Выбранный TaskStore и система поставки | Очередь, обсуждение конкретного изменения, критерии и результат |
| Выбранное представление очереди | Рабочий статус и обзор задач; например CLI или GitHub Project |
| Локальное хранилище Run | Checkpoints, попытки, операции, логи и диагностические артефакты |
| Генерируемый индекс | Производные факты и быстрый поиск с указанием источников |

Для каждого факта существует первичный источник. Каталог ссылок не должен превращаться в конкурирующее описание той же реализации. Обычное завершение задачи не требует от владельца проекта вручную переписывать несколько статусных файлов.

### 9.3. Требования, факты и гипотезы

Знания разделяются на три категории:

- **Принятое требование:** каким должно быть поведение; имеет источник решения.
- **Наблюдаемый факт:** что реализовано, проверено или запущено; имеет SourceVersion, применимую среду, время и evidence.
- **Гипотеза:** предположение или предложение; имеет способ проверки и не выдаётся за принятую норму.

Наличие кода, противоречащего требованию, создаёт расхождение. Код не отменяет правило автоматически. Отсутствие найденного evidence означает «не подтверждено», а не доказанное отсутствие реализации.

### 9.4. Статус возможности

Готовность описывается несколькими независимыми признаками:

| Признак | Примеры значений |
|---|---|
| Намерение | Предложено / принято / отложено |
| Реализация | Нет / schema-only / частично / реализовано |
| Проверка | Не проверено / passed для SourceVersion / failed / unavailable |
| Интеграция | Не соединено / подтверждено для набора версий |
| Эксплуатация | Не развёрнуто / развёрнуто в среде / наблюдается работа |
| Актуальность | Актуально / устарело / неизвестно |

Endpoint, интерфейс или заглушка не доказывают законченный сценарий. Зелёный CI не доказывает deployment. Документированный Run не доказывает, что процесс действительно запускался.

Для результата документации или исследования используются применимые признаки: принятие, версия артефакта, проверка содержания и доставка. Неприменимые поля эксплуатации не требуется заполнять вымышленными значениями. Конкретный формат статуса знания задаётся проектом в пределах общей модели фактов.

### 9.5. Как выявляется забытая работа

Planner поддерживает покрытие:

`принятое требование → возможность → модуль/интерфейс → задача или обоснованное исключение → evidence`

Это форма покрытия программного проекта. Для работы без кода вместо модуля указывается владелец документа, исследовательского результата или операции. Отсутствие программного модуля не создаёт gap само по себе.

В покрытие входят нефункциональные требования: восстановление, безопасность, стоимость, наблюдаемость, совместимость и эксплуатация.

Поводы для сверки: онбординг, новый запрос, принятое решение, начало задачи, merge, отказ проверки, инцидент и завершение операции. Периодическая автономная сверка требует реально работающего scheduler или внешнего запуска. Без него проверка выполняется при следующем активном запуске харнесса.

Для каждого gap Planner:

1. Проверяет через TaskStore и систему поставки, существует ли задача, кандидат или активный Run по той же обязанности.
2. Определяет владельца, зависимость, влияние и минимальный проверяемый результат.
3. Связывает найденную задачу либо создаёт новую в пределах выданного поручения.
4. Указывает, блокирует ли gap текущую работу или относится к будущему этапу.
5. Выбирает следующую готовую задачу с учётом приоритета и доступных ресурсов.

Используется устойчивый ключ обязанности для дедупликации. Planner выявляет циклы зависимостей, задачи без владельца и принятые требования без покрытия. Он не придумывает обязательства из каждого случайного комментария.

### 9.6. Обновление при поставке

Implementer передаёт documentation delta: какие интерфейсы, инварианты, правила использования и ограничения изменились. Reviewer проверяет смысл и соответствие коду. Генераторы обновляют только производные факты.

После принятой поставки Knowledge Manager обновляет затронутый индекс и статусы для итоговой SourceVersion; для Git — итогового SHA. Общий каталог обновляется через одного writer или compare-and-swap; параллельные задачи не перезаписывают изменения друг друга.

Если код интегрирован, а синхронизация знаний не завершилась, Run получает `knowledge_sync_pending`. Контроллер повторяет синхронизацию и сохраняет видимый блокер завершения. Он не выполняет повторно уже успешную миграцию или deployment.

Документы создаются там, где помогают принимать решения, использовать модуль или проверять результат. Полная расшифровка всех рассуждений агентов не является документацией проекта.

## 10. Устойчивое состояние и восстановление запуска

### 10.1. Состояние Run

Run содержит:

- project/workspace/task/run/attempt IDs и необязательные ExternalRef;
- WorkflowPolicy и текущую фазу;
- версии входов, критериев, полномочий и контекста;
- версии входов и результата; для Git — worktree, branch, base SHA и candidate SHA;
- назначения ролей, процессы, leases и ресурсы;
- бюджет, расход и неопределённые списания;
- результаты команд, CI и проверяющих ролей;
- внешние операции, PR и сведения об интеграции;
- блокер, следующий шаг и состояние синхронизации знаний.

Каждый переход имеет причину, время и ссылку на результат. Пример состояний: `prepared`, `running`, `waiting`, `reviewing`, `integrating`, `reconciling`, `completed`, `failed`, `cancelled`. Конкретная реализация может использовать более подробные фазы, сохраняя однозначную семантику.

### 10.2. Хранение

Для первого однопроцессного контроллера достаточно одного writer, append-only журнала и атомарного snapshot. Повреждённая последняя запись должна обнаруживаться. При нескольких writers необходимы транзакции или compare-and-swap с проверкой версии.

Полные логи хранятся отдельно от компактного состояния. Путь к артефакту и его контрольная сумма позволяют проверить целостность. Срок хранения и редактирование чувствительных данных задаются профилем.

### 10.3. Внешние операции

Перед действием фиксируются намерение, целевой ресурс и идентификатор идемпотентности, если API его поддерживает. После действия фиксируются результат и внешний ID.

Если процесс завершился между отправкой запроса и записью ответа, состояние операции — `unknown`. После восстановления сначала проверяется внешний результат. Создание Issue/PR, merge, deployment или миграция не повторяются вслепую.

Exactly-once не обещается поверх API, который его не обеспечивает. Для каждого изменяющего адаптера определяется способ reconcile: запрос состояния, поиск по устойчивому ключу или ручное разрешение неоднозначности.

## 11. Agent Runner и проверяемая поставка

### 11.1. Запуск

Runner принимает структурированный argv, WorkspaceRef, cwd, environment allowlist, Run ID, role, timeout и предел вывода. Workspace adapter проверяет идентичность рабочей области и версию источников; для Git дополнительно проверяются root, branch, SHA и принадлежность worktree.

Runner обязан:

- действительно запустить OMP в назначенном каталоге;
- привязать процесс и попытку к Run;
- сохранить stdout/stderr и настоящий exit code;
- отличить ненулевой выход от timeout, отмены и недоступности инструмента;
- завершать принадлежащую ему группу процессов, не затрагивая чужие;
- сохранить результаты до уборки worktree;
- восстанавливать состояние после сбоя без доверия одному старому PID.

Конвейер логирования не должен подменять exit code команды успешным кодом `tee`. Текст агента «готово» не заменяет результат процесса и проверки.

### 11.2. CI и вердикты

Для external PR проверяется кандидат до merge. Gate учитывает источник CI, применимый набор required checks, SHA, незавершённые и повторные попытки, pagination API и состояние проверок. Пустой набор не трактуется как успех.

Вердикт Reviewer и Adversary содержит SourceVersion кандидата и версию критериев; для Git-кода — SHA. Изменение кандидата требует проверки влияния и повторного выполнения затронутых проверок. Проверка старого main не подтверждает новый diff.

Интеграция сериализуется для репозитория. Успех означает подтверждённое изменение целевой ветки или другой явно заданный результат поставки. Локальный merge, push, CI и принятие PR представлены отдельными фактами.

В workflow без удалённого CI ChecksPort выполняет выбранные локальные проверки. Для документа это могут быть проверка ссылок и содержательный review, для исследования — проверка источников и воспроизводимости расчёта. Отсутствие remote CI допустимо, когда выбранный процесс его не требует; это отличается от недоступности обязательного CI.

## 12. Параллельные задачи

### 12.1. Условия независимости

Scheduler проверяет не только разные репозитории или папки. Общими ресурсами считаются:

- изменяемые файлы, lockfiles и результаты code generation;
- schemas, API и приёмочные критерии;
- общая БД, тестовая среда, deployment target и production-ресурс;
- интеграционная ветка и обновляемый каталог знаний;
- доступный бюджет, provider rate limits и вычислительные ресурсы.

Два агента, обсуждающих одну задачу, не являются двумя независимо поставляемыми работами. Параллельные роли внутри проверки и параллельные задачи планируются отдельно.

### 12.2. Lease и интеграция

Задача получает lease на ресурсы с владельцем, сроком, heartbeat и fencing token. Проверка актуальности выполняется в момент изменяющей операции через контролируемый инструмент. Просроченный исполнитель не может продолжить запись только потому, что ещё работает.

Если исполнитель имеет прямые общие credentials и может обойти проверку, lease обеспечивает координацию, но не строгую изоляцию. Профиль должен честно обозначать такой режим. Для строгого режима используются ограниченные credentials, sandbox и broker операций.

Конфликтующая работа ожидает ресурс. Интеграция в один репозиторий проходит последовательно. Cross-repo задача имеет parent и отдельные поставки с правилами совместимости; общего атомарного Git merge для нескольких репозиториев нет.

### 12.3. Рост параллельности

Порядок включения:

1. Один полный Run с публикацией, проверкой, восстановлением и обновлением знаний.
2. Два действительно независимых Run с проверкой конфликтов, общего бюджета и интеграции.
3. Увеличение до принятого проектного и общего лимита после подтверждения выигрыша по завершённым результатам.

В Core нет постоянного числа Agent Build или founder-integration слотов. Профиль задаёт ограничения по проекту, роли, среде и ресурсу; локальная установка задаёт общий предел. Фоновая работа — управляемый job с ресурсами и правами, а не исключение из учёта.

Ожидание проверки не освобождает ресурсы автоматически. Явно припаркованная задача может освободить lease после сохранения состояния и оценки последствий. После возобновления входы и независимость проверяются заново.

Эффективность измеряется поставленными задачами, временем проверки, конфликтами, расходом и вниманием владельца проекта. Число запущенных окон не является показателем пропускной способности.


### 12.4. Несколько проектов в одной установке

Каждый проект имеет отдельные Run, очередь, knowledge index, context cache, credentials bindings, worktrees и namespace артефактов. Orchestrator проекта A не получает документы, секреты и незавершённые решения проекта B. Retrieval всегда выполняется с явным ProjectId и разрешёнными источниками.

Общий Scheduler видит минимальные метаданные ресурсов и лимитов, необходимые для распределения мощности. Он учитывает общий provider budget и rate limit поверх проектных лимитов. Приоритеты между проектами задаёт владелец; планировщик не выводит их из текста чужих задач.

Если два профиля ссылаются на одну физическую БД, repository или deployment target, ресурс получает единый канонический ключ. Разные ProjectId не делают этот ресурс независимым. Защита от starvation и управление очередью задаются простой явной политикой.

Передача знания между проектами — явное действие с разрешённым содержимым: например вынести обезличенное архитектурное правило в reusable pack. Полный журнал разговора или код приватного проекта не становится общей памятью автоматически.

## 13. Полномочия и границы автономности

Роль определяет ответственность; capability определяет разрешённое действие. Выдача capability привязана к проекту, репозиторию, ресурсу, типу операции, сроку и Run.

Implementer получает запись в рабочую зону и возможность необходимых проверок. Проверяющие роли получают чтение кандидата и разрешённую среду проверки, но не право незаметно изменить проверяемый код. Интеграционные credentials выдаются компоненту поставки.

Git worktree и инструкция о cwd не являются sandbox. Строгое ограничение доступа требует механизмов среды исполнения. В доверенном локальном режиме ограничения, которые остаются процедурными, обозначаются явно.

Уже выданные разрешения сохраняются в состоянии задачи. Обычное чтение, обратимая подготовка и реализация внутри scope продолжаются автономно. Для действия за пределами полномочий Orchestrator сначала готовит конкретный результат, diff или план операции, затем запрашивает решение по этому действию.

Внешние документы, логи и ответы инструментов не могут выдавать новые capabilities. Production-ключи и продуктовые пользовательские данные не попадают в общие контексты разработки. Политика ретраев не расширяет разрешённый объём действий.

## 14. Бюджет и наблюдаемость

Существующий metering proxy используется как основа. Корреляция Run/attempt/role/project с запросом модели добавляется совместимо с действующим форматом учёта, например отдельным отображением request ID. Нельзя молча изменить зафиксированную схему записи.

Перед вызовом контроллер резервирует расход с учётом маршрута, максимального ответа и допустимых повторов. После ответа выполняется settlement по фактическому usage, неиспользованный резерв освобождается. Проверка и резервирование общего лимита атомарны для параллельных запросов.

Если usage неизвестен после ошибки или соединение оборвалось, запись не считается бесплатным вызовом. Неопределённая сумма сохраняется до сверки либо учитывается консервативно. Провайдеры с подпиской или неполным usage имеют явно обозначенное покрытие учёта.

Денежный жёсткий предел гарантируется только при известной верхней границе тарификации и контроле всех оплачиваемых маршрутов. Во всех остальных случаях различаются измеренный расход, оценка и недоступные данные.

Минимальные метрики:

- Run и время по этапам, число попыток и причины остановки;
- контекст: размер, резерв, ошибки оценки, compaction и восстановление;
- затраты и неизвестный usage по роли, Run и провайдеру;
- качество: отказы CI, Adversary, Reviewer и повторные дефекты;
- знания: stale facts, открытые gaps, задержка синхронизации;
- параллельность: ожидание ресурсов, конфликты и время интеграции;
- участие владельца проекта: запросы решений и время ожидания.

Достижение лимита останавливает или паркует задачу с checkpoint. Оно не разрешает пропустить обязательную независимую проверку.

## 15. Интерфейс владельца и интеграция с tracker

### 15.1. Задача не обязана быть GitHub Issue

Ядро использует TaskStorePort и внутренний TaskId. Минимальный режим — локальная очередь и CLI. Внешний tracker выбирается проектом; GitHub Issues/Projects — первый адаптер. Интеграция с другой системой добавляется при необходимости через тот же порт.

Профиль определяет первичный источник задачи. При внешнем tracker локальное Run-state является журналом исполнения и очередью синхронизации, а не вторым редактируемым roadmap. При локальном режиме хранилище харнесса само является источником задач.

При временной недоступности настроенного внешнего tracker контроллер хранит подготовленный результат и повторяет синхронизацию. Он не переключает источник истины на локальный молча. Новая изменяющая работа выполняется только при достаточных актуальных входах и полномочиях.

### 15.2. Внешние статусы и внутренние фазы

Project Profile задаёт mapping между фазами Run и существующими значениями tracker. Не требуется создавать колонку на каждую роль, review или ожидание ресурса. Все незавершённые фазы могут отображаться в одном статусе с понятной сводкой.

Mapping определяет направление синхронизации и конфликт: ручное изменение задачи должно быть замечено. Перенос карточки в Done не создаёт отсутствующее evidence и не доказывает выполнение операции. Намеренное закрытие владельцем может иметь исход `cancelled` или `accepted-with-exception`, отличимый от verified completion, согласно полномочиям и правилам проекта.

При адаптере GitHub используются реальные IDs полей, repo и Project. `Status`, `Domain`, `Priority` — допустимая конфигурация конкретного проекта, а не фиксированная схема Core. Отсутствие необязательного поля не блокирует задачу.

### 15.3. Результат и evidence

Задача содержит цель, критерии, зависимости и ссылки на результат. При завершении Orchestrator сообщает: что сделано, чем проверено, версию артефакта или commit/PR, внешний результат и оставшиеся ограничения.

Evidence может быть локальным результатом проверки, CI run, комментарием, PR или приложенным файлом. Объём соответствует задаче. Одна содержательная запись достаточна, если из неё проверяемо следуют все критерии.

Для multi-repo проектов TaskStore хранит parent/child связи либо эквивалентные ссылки. Число досок, представлений и репозиториев выбирает проект; Core оперирует зависимостями и владельцами независимо от их UI.

Адаптер обязан поддерживать дедупликацию, внешние версии/условные обновления, reconcile после timeout и понятный результат частичной синхронизации. Merge или deployment не повторяются из-за ошибки публикации итогового комментария.

## 16. Проверки приёмки харнесса

Проверки выполняются по мере реализации соответствующих компонентов. Для адаптеров нужны контрактные тесты и хотя бы одна проверка полного сценария в разрешённой среде. Для недетерминированных решений роли используются фиксированные сценарии с проверяемым результатом, а не совпадение текста ответа.

| Сценарий | Ожидаемый результат |
|---|---|
| В проекте уже есть нужная функция | Preflight находит её; задача не создаёт второй независимый вариант без обоснования |
| Похожий код имеет другую доменную семантику | Architect не объединяет его автоматически |
| Индекс относится к другому SHA | Факт помечается stale и перепроверяется до использования |
| Изменяется запрещённая зависимость | Языковая проверка обнаруживает отрицательный fixture |
| Документ меняет полномочия | Router выбирает содержательную проверку, а не редакционный shortcut |
| Простая редакционная задача | Выполняется краткий применимый workflow без полного кодового цикла |
| Дочернему агенту выдана задача | Пакет содержит его scope и критерии, без полного архива родителя |
| В запросе много tool schemas или вложений | Они учтены в бюджете окна |
| Требуется compaction | Сохраняются полномочия, версии, блокеры и pending operation |
| Модель переключена на меньшее окно | Пакет пересобран до следующего запроса |
| Восстановление после внешнего действия | Контроллер сверяет результат, не создаёт второй PR и не повторяет операцию вслепую |
| Команда завершилась с ошибкой через pipeline | Runner сохраняет действительный ненулевой код |
| Кандидат изменился после review | Старый вердикт не принимается за проверку нового SHA |
| CI пуст, недоступен или содержит незавершённые checks | Gate не сообщает успех |
| Две задачи меняют общий lockfile или schema | Scheduler обнаруживает конфликт до записи |
| Lease истёк | Контролируемая изменяющая операция со старым fencing token отклонена |
| Два вызова одновременно расходуют остаток бюджета | Атомарное резервирование не выдаёт оба сверх лимита |
| Usage ответа неизвестен | Расход не записывается как достоверный ноль |
| Merge прошёл, обновление знаний упало | Повторяется только синхронизация; поставка не дублируется |
| Генерация фактов модуля | Авторская семантика MODULE.md сохранена |
| Принятое требование не покрыто задачей | Planner находит gap и связывает или создаёт ровно одну задачу |
| Две задачи обновляют общий каталог | Нет потери одной из записей |
| Tracker содержит только согласованные поля проекта | Адаптер использует mapping; необязательные поля не требуются |
| Две независимые задачи завершены | Есть два проверенных результата, актуальные знания и измеренный общий расход |

Дополнительные критерии универсальности:

| Сценарий | Ожидаемый результат |
|---|---|
| Подключены TypeScript-библиотека и Rust-проект с разными процессами | Одна версия Core; различия выражены профилями и пакетами |
| Нет GitHub и удалённого CI | Локальная задача получает TaskId, проверки и результат без фиктивной Issue |
| Проект использует существующие документы и свою структуру | Онбординг связывает их без обязательного переезда в шаблон харнесса |
| Задача не связана с кодом | Не требуются вымышленные SHA, компиляция и полный круг кодовых ролей |
| Два пакета задают конфликтующее правило | Resolver указывает источники и требует явного разрешения этого конфликта |
| Project Profile пытается расширить выданные capabilities | Действие отклонено; конфигурация не выдаёт полномочия сама себе |
| Профиль изменён во время Run | Snapshot сохранён; обновление применяется контролируемо, отзыв прав — немедленно |
| Запрос retrieval из проекта A совпадает с секретным фактом проекта B | Данные B не возвращаются |
| Два проекта используют один физический ресурс | Scheduler видит конфликт через общий ключ |
| Пакет обновлён и затем откачен | Разрешённый lock восстанавливается; поведение воспроизводимо |
| Адаптер не умеет необходимый resume/reconcile | Выбран предусмотренный fallback или честный блокер до операции |
| Новый проект содержит своё имя, Domain и tracker statuses | Для подключения не изменяются исходники Core |

Критические свойства проверяются негативными сценариями: ошибка должна действительно блокировать неверное действие. Наличие happy-path теста не доказывает устойчивость к сбою, конкуренции или stale state.

## 17. Единая последовательность реализации

Работа ведётся в `dev-harness` по ограниченным принимаемым задачам. На каждом этапе проверяется актуальное дерево и используется готовый механизм. Универсальные границы вводятся вокруг существующих точек расширения без большого переписывания OMP и работающего self-процесса.

### Этап 1. Выделить границу self и Project Profile

**Добавить:** минимальные ProjectId/WorkspaceId/TaskId/SourceVersion, schema профиля, local binding и resolver с происхождением правил. Вынести соглашения разработки самого харнесса в self-профиль. Обозначить существующие OMP/Git/GitHub механизмы как первые адаптеры.

**Готово, когда:** прежний self-сценарий работает, а второй тестовый проект разрешается в профиль без изменений Core и копирования харнесса. Ошибочный профиль даёт точную диагностику.

### Этап 2. Надёжный одиночный Run и локальное выполнение

**Добавить:** минимальное устойчивое состояние, TaskStore local, настоящий Runner, проверку workspace, exit status, timeout и логи. Подключить OMP через RuntimePort. Определить доступные режимы поставки локального результата.

**Зависит от:** этапа 1.

**Готово, когда:** одна задача внешнего Git-проекта выполняется без GitHub Project; ошибка команды не теряется; после остановки известны попытка, workspace и результат. Для задач без Git файловый workspace включается после отдельной проверки адаптера.

### Этап 3. Онбординг, reuse и ContextPack

**Добавить:** подключение существующих документов, начальный inventory, поиск реализации и текущей работы, пакеты по ролям, решение Architect о размещении изменения. Первым — language pack Node/TypeScript; затем Rust как независимый пакет.

**Зависит от:** этапов 1–2.

**Готово, когда:** два разных проекта обнаруживают собственные модули и правила; агент переиспользует найденный код; profile одного проекта не попадает в контекст другого.

### Этап 4. Внешний tracker и поставка через PR

**Добавить:** GitHub TaskStore/Checks/Delivery adapters, явный mapping, идемпотентную публикацию, gate для candidate SHA и вердикты до merge. Формат TaskPacket и Run не зависит от GitHub ID.

**Зависит от:** этапов 1–3.

**Готово, когда:** один проект поставляет через PR, другой продолжает использовать локальный режим. Новый tracker mapping задаётся конфигурацией. Изменение кандидата инвалидирует старую проверку.

### Этап 5. Восстановление и жизненный цикл профиля

**Добавить:** полный журнал переходов, pending operations, reconcile для подключённых изменяющих адаптеров, snapshot профиля и lock, управляемую миграцию настроек и отзыв capabilities.

**Зависит от:** этапов 1–4.

**Готово, когда:** сбой до/после публикации не дублирует действие; повторный запуск восстанавливает правильный профиль; его изменение не подменяет активные критерии, а отзыв доступа действует сразу.

### Этап 6. Знания и планирование по проектам

**Добавить:** фактический статус возможностей, documentation delta, coverage map, gaps, дедупликацию и синхронизацию. Корень знаний и источник задач выбираются профилем.

**Зависит от:** этапов 3–5.

**Готово, когда:** пропущенная обязанность обнаружена ровно в нужном проекте; после поставки обновлены его описания и очередь. Локальный и внешний tracker не создают два источника истины.

### Этап 7. Полное управление контекстом

**Добавить:** измерение всего запроса, model/runtime capabilities, резервы, ограниченное извлечение, checkpoint/compaction и контролируемую смену сессии.

**Зависит от:** этапов 3, 5 и 6.

**Готово, когда:** длинная задача и смена модели сохраняют scope, версии и pending operations; контекст изолирован между проектами и не зависит от одного фиксированного размера окна.

### Этап 8. Пакеты workflow, архитектуры и ролей

**Добавить:** manifest и versioned contributions, проверку конфликтов, блокировку неподдерживаемых capabilities, генерацию инструкций. Вынести выбранные языковые и архитектурные правила из проектных исключений в подключаемые пакеты. Реализовать короткие процессы документов/диагностики и нужные ops-профили.

**Зависит от:** этапов 1, 3 и 6; согласуется с гарантиями этапа 5.

**Готово, когда:** слоистый DDD-проект использует соответствующие проверки, небольшая библиотека — свой пакет границ, а текстовая задача — краткий процесс. Ни один пакет не расширяет полномочия самостоятельно. Отрицательные fixtures ловят нарушение выбранной архитектуры.

### Этап 9. Параллельность и общие ресурсы

**Добавить:** reservations бюджета, leases/fencing, общую очередь ресурсов, канонические ключи shared resources и последовательную интеграцию. Сначала два Run внутри проекта, затем по Run в двух проектах.

**Зависит от:** этапов 4–8.

**Готово, когда:** независимые задачи доставлены; конфликтующая пара заблокирована; суммарный расход учитывается атомарно, а данные проектов изолированы.

### Этап 10. Эксплуатация и проверка переносимости

**Добавить:** регулярный запуск сверки при реально работающем scheduler, сводку состояния, обновление pins/пакетов с проверками и откатом, контроль stale knowledge и метрики полезной параллельности.

**Зависит от:** этапов 6–9.

**Готово, когда:** владелец подключает новый поддерживаемый проект через онбординг и профиль, выполняет первую полезную задачу и получает проверенный результат. Для подключения не редактируются Core, базовые роли и код уже существующих адаптеров.

Первая полезная локальная работа возможна с этапов 2–3; поставка через GitHub PR — с этапа 4. Полный набор функций не является условием начала проекта. Для контроля универсальности используются минимум два различающихся проекта и сценарий работы с документом; Odelix может быть одним из них.

## 18. Рабочий режим и сопровождение

В начале активной работы Orchestrator разрешает профиль выбранного проекта, сверяет источники через адаптеры, очередь, незавершённые Run и состояние ресурсов. Затем сообщает владельцу проекта: текущую цель, готовую следующую задачу, блокеры и решения, требующие участия. Если полномочий и входов достаточно, запускает работу.

Во время исполнения он поддерживает актуальное состояние, реагирует на отказы, обновляет план зависимостей и обеспечивает checkpoint перед остановкой. По завершении предоставляет результат со ссылкой на проверку и следующую разрешённую работу.

Изменения OMP, моделей, role generator и профиля проекта вводятся через pin и проверку совместимости. Регрессии должны покрывать запуск внешнего репозитория, сборку инструкций, контекст, восстановление, metering и поставку. Обновление upstream не должно незаметно менять полномочия или обязательные проверки.

Целевой patch surface ядра OMP — ноль. Расширения реализуются через поддерживаемые поверхности, обёртку и собственные модули. Необходимый core patch имеет техническое основание, учёт расхождения и план удаления или передачи upstream.

Документ хранится в документации `dev-harness` как общая спецификация. Каждый проект хранит свой профиль, принятые правила и ссылки на применимые пакеты. Копия универсальной спецификации в каждом проекте не нужна. Задачи реализации ссылаются на конкретные требования и содержат собственные критерии; статус выполнения живёт в задачах и evidence.

Изменение этой спецификации проходит содержательную проверку по влиянию на архитектуру и полномочия. Правки текста не объявляют новые возможности реализованными. Приёмка производится по работающему поведению и проверкам из раздела 16.

## 19. Odelix как проектный профиль

Этот раздел — пример применения универсального харнесса. Он содержит настройки Odelix и не определяет обязательный процесс других проектов.

| Возможность | Универсальная часть | Настройка Odelix |
|---|---|---|
| Multi-repo | Workspaces, владельцы, зависимости и связанные Run | Корень управления `odelix-stack`; подключаются существующие репозитории по мере работы |
| Архитектура | Inventory, reuse preflight, dependency checks | Доменные области, модули, контракты и принятые правила из архитектуры Odelix |
| Языки | Подключаемые language packs | Rust для соответствующих backend-областей, TS для применимых приложений и инструментов |
| Планирование | Coverage map, readiness и dependency graph | Принятый roadmap, gates и конкретные критерии Odelix |
| Tracker | TaskStorePort и mapping | GitHub Organization Project `Odelix Delivery`, поля Status/Domain/Priority |
| Поставка | Проверка кандидата, CI, review и merge | PR в owner repository; межрепозиторные задачи связаны через parent |
| Знания | Knowledge Manager, versions и freshness | Общий каталог в `odelix-stack`, первичные схемы и описания у владельцев |
| Параллельность | Scheduler, leases и бюджеты | До трёх независимых Agent Build после обкатки; одна founder-integration и один разрешённый фон при достаточных ресурсах |
| Предметные проверки | Check provider и evidence | Только применимые требования market data, воспроизводимости, расчётов и безопасности Odelix |

Число репозиториев, имена модулей, gates и их готовность читаются из текущего профиля и проектных источников. Они не зашиваются в Core и не объявляются выполненными по факту создания Issues.

В `odelix-stack` размещаются `harness.project.json`, lock и ссылки на правила Odelix. Repo-level документы остаются у владельцев кода. Профиль выбирает принятые требования и пакеты; специализированные skills Odelix хранятся как проектные дополнения, пока не появится основание для переиспользуемого domain pack.

Продуктовый `odelix-harness` — создаваемая система Odelix для его пользователей. Универсальный `dev-harness` помогает разрабатывать её как любой другой проектный компонент. Runtime-state, credentials, знания разработчика и данные продуктовых пользователей разделяются.

Само подключение профиля не переносит репозитории, не закрывает операционные gates и не запускает production-команды. Такие действия выполняются соответствующими задачами с уже выданными полномочиями и проверкой результата.

## 20. Как подключать следующий проект

Практический пользовательский сценарий, который должен поддержать bootstrap:

1. Владелец указывает путь или набор рабочих областей, цель и желаемый режим работы.
2. Харнесс определяет языки, существующие инструкции, тесты и tracker; показывает только значимые неизвестные сведения.
3. Собирает минимальный профиль из готовых пакетов, связывает существующие документы и локальные пути.
4. Проверяет совместимость инструментов и показывает, какие действия уже разрешены и что требует отдельного доступа.
5. Находит ближайшую готовую задачу и выполняет её выбранным workflow.
6. По мере появления реальных потребностей добавляет проектные правила или поддерживаемый адаптер; перед переносом общего решения в Core обосновывает его универсальность.

| Пример | Конфигурация | Что остаётся общим |
|---|---|---|
| Небольшая TypeScript-библиотека | Один Git repo, локальные задачи, пакет языка, tests и patch/PR | Run, контекст, knowledge, права, evidence |
| Существующий Rust backend | Свой layout и стандарты, Rust pack, CI и tracker | Те же механизмы без требования перестроить проект под self-профиль |
| Документация или исследование | Файловые источники, редакционный/исследовательский workflow, версия результата | Состояние, контекст, проверка источников и доставка артефакта; без вымышленных кодовых checks |
| Несколько репозиториев и команд | Корень управления, repo overlays, владельцы и отдельные способы поставки | Зависимости, изоляция, Scheduler и единый формат Run |

Критерий хорошего подключения: владелец задаёт особенности своего проекта, а харнесс выполняет общую работу управления. Наличие нового языка или tracker может потребовать нового адаптера; само имя и бизнес-модель проекта не должны требовать изменения ядра.
