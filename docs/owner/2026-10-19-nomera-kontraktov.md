# Решение владельца 2026-10-19: номера контрактов после 999

Слово владельца 2026-10-19 ~09:55 UTC: «по всем 3 вопросам согласен с твоими рекомендациями». Передал консультант.

## Проблема

`scripts/next_id.sh` выдаёт max+1. Номер 999 выдан (`id/CONTRACT/999`, CMP-MOB-002). На 1000 скрипт отказывает (`next_id.sh:470`): формат — ровно три цифры. Без нового номера не стартуют следующая задача mob, `ci-proekta` и бэкенд.

## Решение

Формат номера не меняется: три цифры. `next_id.sh` для класса CONTRACT выдаёт **наименьший свободный номер в диапазоне 106–989**. Свободный — номер, который не занят ни одним источником, которые уже сверяет скрипт: тег `id/CONTRACT/<NNN>`, строка `registry/contracts.tsv`, файл `contracts/<NNN>-*`, ветка. Атомарность прежняя: тег создаётся до печати номера.

Отвергнуто: формат в 4 цифры. Это правка всех проверок имён (`check_ids`, «ровно три цифры»), сортировки и сверки — дорого и с риском.

## Как вводится

Контракт в слоте харнесса, кодовый, с красными тестами. Красные тесты: на текущем коде выдача после 999 — отказ; на новом коде выдаётся наименьший свободный ≥106; занятый номер из любого источника не выдаётся повторно; два параллельных вызова получают разные номера.

Номер для самого этого контракта — **106**. Это разовая выдача вручную тем же механизмом: тег `id/CONTRACT/106` и строка `registry/contracts.tsv` на origin, по этому слову владельца. Скрипт выдать его пока не может. Только для этого контракта.

В плане — символический id `nomera-kontraktov`; после ручной выдачи 106 он заменяется номером (как 995–999).

Приоритет: слот харнесса берёт контракт **106 сразу после текущей работы по 996**, раньше `ci-proekta`. Слот mob после 999 и бэкенд ждут 106.
