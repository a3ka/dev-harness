# Решение владельца 2026-10-17 ~20:30 UTC: режим проекта для бэкенда Complior-back

Слово владельца «да, давай» на предложение консультанта. Передал консультант.

## 1. Топология

- Харнесс один: `a3ka/dev-harness`. Отдельный форк для бэкенда не заводится.
- Сервер ведёт два слота: харнесс и Complior-mob.
- Основная фаза бэкенда `a3ka/Complior-back` переходит на ноутбук владельца. Там отдельная сессия `./workshop <путь к Complior-back>` в режиме проекта. Её работа (контракты, вердикты, состояние) живёт в `.harness/` самого Complior-back. Ноутбук держит клон `a3ka/dev-harness` и только подтягивает обновления харнесса, в него не пишет.
- Ноутбук стартует ПОСЛЕ доводки режима проекта (§2).

## 2. Следующий предмет слота харнесса — после закрытия 991 и 993

Доводка режима проекта до полного цикла на внешнем репозитории:

1. **Обмен.** `scripts/gitw` берёт канонический origin из профиля проекта (`harness.project.json`), а не только из `GIT_EXCHANGE_GUARD_CANONICAL` или зашитого `a3ka/dev-harness`.
2. **Судьи.** Вердикты критика, адверсария, ревьюера и арбитра пишутся в `workflowPaths.verdicts` профиля, то есть в `.harness/` проекта. `done_contract.sh` и `freeze_contract.sh` читают их оттуда.
3. **Вторая станция.** Норма и механизм: станция проекта не пишет в `HANDOFF.md`, `NABLIUDENIA*.md`, `registry/` и `forks/` харнесса, у неё свои в `.harness/` проекта. Номер контракта резервируется на origin проекта. Детектор утечек сервера не видит работы станции проекта.
4. **Приёмка — сквозной прогон полного цикла на Complior-back в режиме проекта:** контракт → критик → заморозка → implementer → CI проекта → адверсарий → ревьюер → done. Предмет прогона — первый бэкенд-контракт, «гейт сверки с источниками» (§3). Ручные шаги прогона записываются болями с ценой.

Frontier и обоснование болью (Н-NN) — у architect. Кап кругов прежний.

## 3. Обязательное требование к бэкенду: перепроверка по документам

Всё, что делается по бэкенду, перепроверяется по md-документам бэкенда, перенятым у первоисточника и доработанным с Astra:

- нормативные: `Complior_Backend_Architecture_v3_14_RU.md`, `contracts/BrokerOS_Unified_OpenAPI_v3.yaml`, `db/001–013`;
- документы бэкенда: `AGENTS.md`, `STRUCTURE.md`, `docs/ARCHITECTURE.md`, `docs/CODING-STANDARDS.md`, `docs/DATABASE.md`, `docs/RUNBOOK.md`, `docs/backend/PORT-PLAN.md`, `DONOR-INVENTORY.md`, `AUTH-AND-DB-DECISIONS.md`, `backend/structure-policy.json`;
- раздел `## Источники` каждой задачи CMP-BCK.

Механизм — в Complior-back, без второго раннера CI:

- карта задачи `docs/backend/trace/CMP-BCK-NNN.json`: источник@sha256 + раздел → требование → реализация → проверка → заключение ревьюера на SHA;
- `tools/check_source_trace.py` в lane `checks` `tools/run_backend_ci.py` и в `required`. Он даёт отказ, если:
  - хэш источника устарел;
  - раздела нет;
  - источник issue отсутствует в карте;
  - изменённый путь не покрыт картой;
  - проверка упала или NOT_RUN;
  - заключение ревьюера относится к старому SHA;
  - команда вне контролируемого набора.
- Остаточный риск (cognitive-only): полнота и верность толкования требований. Отвечают роли: architect — карта, критик — её полнота, адверсарий — пропущенное требование, ревьюер — diff против разделов.
