# Решение архитектора бэкенда Complior-back по 57 отказам валидатора и спецификации 5.8.4 (2026-10-18)

Передал владелец 2026-10-18; владелец поручил встроить решение в роадмап (`ROADMAP.md` §12). Задача — Complior-back issue #148 [CMP-BCK-133]. Исходный разбор консультанта: 57 отказов `tests/validate_contract_v3_9.py` на PR #146 (CMP-BCK-121, контракт 993): 6 отказов CAS в 5 операциях и 51 операция без подтверждённого потребителя.

## Итог

Это реальные пробелы спецификации, их закрывает отдельная поставка 5.8.4. Фиктивные привязки ради зелёного валидатора не добавляются. 57 отказов — не 57 сломанных функций: в них смешаны противоречия CAS и неподтверждённые связи с потребителями.

## Порядок

1. Merge #146 — при условии проверки PR. Валидатор запускается в CI и честно показывает `FAIL_STATIC`.
2. До исправления — временный неблокирующий режим. Известные отказы зафиксированы, новые незаметно не добавляются.
3. Отдельная задача — 5.8.4 (CMP-BCK-133): CAS, потребители, генерация производных, согласование с mobile и web.
4. После устранения отказов проверка становится обязательной (`required`).
5. Статическая успешность — не доказательство работы обработчиков; HTTP и SQL проверяются отдельно.

## CAS — выпускаем 5.8.4, решения по смыслу операций

- **acknowledgeDisclosure** — подтверждение относится к точной версии раскрытого документа. Если используется ETag Disclosure — `If-Match` обязателен; описать, откуда клиент получает ETag.
- **revokeApproval** — версионная защита сохраняется. Описать гонку с исполнением: отзыв ещё неисполненного согласования и отмена уже отправленного действия — разные операции.
- **revokePermission** — без механического ужесточения, пока не проверен сценарий отзыва. Отзыв не требует действующего допуска HEALTH. Нужна явная повторяемая операция отзыва конкретного разрешения с серверной перепроверкой ресурса и scope. Допустимы обязательный CAS с корректной обработкой устаревшей версии или отдельная семантика идемпотентного отзыва. Выбор — после проверки контракта, а не переименованием в `CREATE_OR_APPEND`: запись события в append-only журнал не означает, что операция не меняет существующее разрешение.
- **requestAction** — если команда меняет версионное состояние Mission, обязательный `If-Match` оправдан. Уточнить, какие изменения Mission делают команду устаревшей, чтобы фоновые события не создавали бессмысленных конфликтов.
- **revokePartnerGrant** — проверка версии гранта и актуальных полномочий вызывающего. Условный профиль — проверяемая структура вместо строки. Один `If-Match` не заменяет проверку полномочий.
- Для всех пяти: источник ETag или версии, повтор запроса, устаревшая версия, уже завершённое действие, конкурентное исполнение.
- Номер 5.8.4 сам по себе совместимости не даёт. В поставке — список изменённых требований к запросам и проверка всех вызывающих сторон, включая web и workers; «мобильное приложение пока не вызывает» — недостаточно.

## Потребители

- `BACKEND_ADOPTION_PENDING` — статус ожидания принятия, а не нормативный источник. Целиком файл не принимается.
- createPartnerInvitation, getPartnerOverview, listPartnerClients, listPartnerEarnings сохраняются как функции партнёрского направления. Принимаются конкретные привязки к подтверждённым сценариям; волны и статус доступности сохраняются: принятый контракт ≠ работающий интерфейс.
- getVoiceTranscript привязывается к W29 после проверки, что виджет читает этот ответ; при необходимости — плюс голосовой workflow.
- 46 операций: назначение сохраняется, потребители подтверждаются.

| группа | где искать и фиксировать потребителя |
|---|---|
| logoutSession, registerDevice, streamMissionEvents, completeUpload | жизненный цикл мобильного клиента: сессия, устройство, подписка на события, завершение загрузки |
| createVoiceSession, getVoiceTranscript | голосовой сценарий и компоненты клиента |
| updateInsuredAsset, acknowledgeDisclosure, revokeApproval, getDataRightsRequest, getMemoryChange | конкретные пользовательские сценарии, действия и чтения |
| почтовые операции и mailbox grants | почтовый workflow, provisioning, отправка, управление доступом; не обязательно прямые вызовы mob |
| getManualLetterDelivery, recordManualLetterDelivery | ручная доставка с точным указанием исполнителя |
| партнёрские операции | Partner Portal и подтверждённые партнёрские процессы с ограниченными правами |
| комиссии, расчёты, импорт | финансовые и импортные workflows, workers, операторы |
| getInternalCaseQueue, getInternalAgentRun, recordOutcomeEvidence | Internal Workbench и процессы исполнения |
| getAgentProfile, updateAgentProfile | уточнить, чей профиль и кто его меняет |
| createActionPlan, requestApplicationSubmission | оркестрация и workflow подачи заявления |
| getProviderInvocation, reconcileProviderInvocation | наблюдение и сверка внешних вызовов |
| getGroupMetrics | будущий внутренний управленческий раздел; вне текущего запуска |
| getInbox | отдельно проверить назначение; **не** назначать источником Post (для Post согласован listPostItems) |

- Правило валидатора дополняется типизированным потребителем `mobile lifecycle/service` (например, подписка SSE без экрана). Иначе разработчик будет вынужден придумывать фиктивные экраны.
- Связь содержит конкретный сценарий, роль потребителя, источник, волну и статус принятия. Запись «используется backend» недостаточна.
- `deferred` ≠ `deprecated`: отложенная функция остаётся в плане, устаревшая выводится из использования. Удалять операции ради зелёной проверки нельзя.

## Один реестр

`frontend-consumer-bindings.json` вручную не редактировать, если он производный: правка нормативных источников, затем `tools/generate_derived.py`. По каждой из 51 операции — подтверждённый потребитель либо обоснованный статус отложения или вывода, в существующих реестрах и evidence, без нового параллельного слоя документов.

## Ограничения для исполнителя

Не принимать pending-файл целиком; не менять семантику отзыва разрешений ради валидатора; не скрывать неподтверждённые операции массовым `deprecated`.
