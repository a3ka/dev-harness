# Дополнение владельца 2026-10-17 ~23:30 UTC к решению 2030: сверка с документами проекта — часть регламента

Слово владельца: работа по бэкенду обязана идти по md-документам проекта (архитектура, стандарты кода и др.), и это должно быть встроено в воркфлоу, а не только в отдельный инструмент проекта. Передал консультант.

В предмет слота харнесса «доводка режима проекта» (`docs/owner/2026-10-17-resheniya-2030.md` §2) добавляется ПЯТЫЙ пункт, равный по весу первым трём:

5. **Канон источников проекта — в регламент.**
   - Профиль проекта (`harness.project.json`, контракт 054) объявляет:
     - канон источников: пути md-документов и нормативных файлов с приоритетом;
     - команду гейта сверки проекта.
   - Если канон объявлен, роли харнесса ОБЯЗАНЫ работать по нему:
     - **architect** читает канон до контракта и кладёт в контракт карту «источник@хэш + раздел → требование → проверка»;
     - **критик** судит полноту карты против канона и `## Источники` задачи;
     - **implementer** не отступает от канона без строки в карте;
     - **адверсарий** ищет требование канона, которое карта пропустила;
     - **ревьюер** сверяет итоговый diff с исходными разделами и требует зелёный гейт сверки на текущем HEAD.
   - Проводка: role-канал (норма-строки в `roles/*.md`) плюс guard-канал. Это команда гейта проекта, её зовут `pre_critic`/`done_contract` для проектов с объявленным каноном.
   - Для проекта без канона поведение не меняется. Так это «включается только для нашего бэкенда».
   - Приёмка — тот же сквозной прогон на Complior-back (§2 п.4): первый бэкенд-контракт «гейт сверки с источниками» (§3) проходит регламент, где роли уже обязаны сверяться с каноном.

Канон Complior-back перечислен в решении 2030 §3.
