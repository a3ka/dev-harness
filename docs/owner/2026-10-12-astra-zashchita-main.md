# Astra — защита main на GitHub как переходный маршрут до части В 094, 2026-10-12

Ответ gpt-6-astra (консультация владельца через консультанта, только чтение). Решение владельца 2026-10-12: оформить контрактом и поставить первым в поток А, до доделки 098.

**Включать с условием: как защищённый переходный маршрут до части В 094, а не как замену `accept_publish`.** Серверный отказ закрывает измеренную дыру, которую локальные хуки не закрывают. Но простое включение двух настроек сейчас оставит обход через изменённые проверки и может сломать ленд.

### 1. Совместимость с путём Г и 094

Совместимо с правилами 1–2: есть конкретный ущерб и отсутствующая серверная граница полномочий. §1.5 требует дополнительно **доверенного происхождения проверок**: кандидат не должен получить зелёный статус, переписав workflow или проверяющий скрипт. Выбор источника статуса GitHub Actions сам по себе этого не обеспечивает. Код кандидата исполняется без credential публикации; административные полномочия — вне агентского доступа.

Это именно «отдельно согласованный защищённый переходный путь», предусмотренный последним абзацем нарезки 094. **PR не доказывает семь требований 094**, подлинность identity или принятие точного объекта судьёй. В части В единственным инициатором публикации становится установленный `accept_publish`; серверная защита остаётся. Его транспорт нужно согласовать заранее: обычный GitHub merge создаёт свой коммит, не обещанный подготовленный **M**. Нельзя молча заменить точность объекта совпадением дерева.

### 2. Что менять

| Узел | Необходимое изменение |
|---|---|
| `land_agent.sh` | Сейчас делает **локальный** merge и удаляет рабочую ветку; push — отдельный шаг. Перенести подготовку в интеграционную ветку, не двигать локальный main и не удалять исходную ветку до принятия PR. Сохранить авторство, `land:`-семантику и дословные санкции. Не включать squash/rebase-merge без миграции исторических барьеров. |
| `gitw` / предполёт 071 | Гард канонического remote оставить. Предполёт публикации main при GitHub API merge **не вызывается**: его содержательные проверки перенести перед серверным слиянием. Удалить заменённую проверку «хотя бы один зелёный PR-workflow», не потерять контроль тегов и дерева. |
| CI / `check_ci_gate.sh` | PR workflow уже есть, но checkout берёт **head PR**, не результат слияния. Проверять интегрируемый результат, включая сообщение и identity финального merge: `check_charter` судит его дельту к первому родителю. Убрать требование `sha ∈ origin/main` из предсудейского CI-гейта; требовать конкретный обязательный набор для проверяемого объекта. `push: main` оставить как постконтроль, не условие допуска. |

| Служебные коммиты | Коммитить вне main, публиковать пакетными PR. Обновить роли и потребителей, предполагающих немедленное попадание записи в main. |

Ограничить их создание доверенным писателем, запретить изменение/удаление серверными правилами тегов. `freeze_contract` уже создаёт тег и отдельный коммит реестра: последовательность должна обеспечивать наличие тегов для PR-CI и целостность реестра. Опубликованный frozen-коммит нельзя считать свободно переписываемой частью PR. |

### 3. Красный main: не строить лишний механизм заранее

**Красный main сам по себе не блокирует исправляющий PR:** обязательные checks оценивают PR, а не прежний запуск main.

Предпочтительно подготовить исправляющий PR для названных l7/ap2 и включить **все 12** обязательных проверок. Если переход действительно требует промежуточного ленда, временно обязательны l1–l6 и ap1/ap3–ap5, **но этого недостаточно**: l7/ap2 содержат много других проверок.

Для такого промежутка нужен обязательный доверенный гейт, допускающий только **точно перечисленные существующие дефекты**; остальные проверки l7/ap2 остаются обязательными по существу. Не сравнивать количество или текст красных строк: одинаковое число может скрывать новую поломку. Неизвестный отказ, отсутствие результата, сбой раннера — блокировка. Базу исключений кандидат менять не может. После исправления — все 12 обязательны, временный гейт удаляется. Если исправляющий PR достижим сразу, этот механизм **не нужен**.

Имена checks лучше стабилизировать, исключив список ключей из имени. Учесть: GitHub допускает также `skipped`/`neutral`; обязательная проверка должна удостоверять фактическое выполнение, не просто наличие зелёной оболочки.

### 4. Служебные записи

**Сейчас — пакетные PR в том же репозитории.** `process` создаст второй источник состояния: нынешние читатели ищут HANDOFF, вердикты и форки в checkout/HEAD. Отдельный репозиторий добавит ещё транспорт и синхронизацию. Локальный checkpoint и восстановление не должны ждать слияния пакета — это граница §1.12.

### 5. Включение, проверка, откат

1. Одним решением владельца зафиксировать переходный маршрут, полномочия и окончание перехода в части В; сохранить текущую конфигурацию защиты.
2. Подготовить изменения выше и исправляющий PR. На отдельном проверочном репозитории с той же защитой провести **живой** цикл: прямой push отвергнут; плохой PR не сливается; исправленный проходит; сообщение, identity, теги и реестр приняты барьерами. Отдельно проверить подмену workflow и движение базы.
3. Включить PR-only, обязательные checks и актуальность базы; сохранить `enforce_admins`, запрет force/delete. Не добавлять обязательное человеческое approval без независимого аккаунта: общий SSH-ключ не создаёт независимых рецензентов.
4. Провести первый настоящий PR и проверить post-merge CI. Откат кода — revert-PR; при неисправности допуска — остановка публикации и восстановление настроек только владельцем. Не автоматический возврат к прямым push.
