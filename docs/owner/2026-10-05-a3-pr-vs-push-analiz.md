Путь файла ВНЕ ЗОНА-строки контракта 083 (зона architect: contracts/083-*,

## Диагноз

Формулировка подозрения оркестратора подтверждена живыми замерами этой сессии — это
РЕАЛЬНЫЙ пробел frozen-текста (конфликт двух абзацев по эффекту), а не недочитанный
механизм. Цепочка, каждый узел проверен живьём:

1. Триггеры workflow (живое чтение `origin/wip/083/integration:.github/workflows/ci.yml`):
   `on: push: branches: [main]` + `pull_request:` — push-событие на `wip/083/integration`
   не существует и существовать не может.
2. Живое окно ветки: `gh run list --branch wip/083/integration --limit 30` → 3 завершённых
   прогона, все `event: pull_request` (37314773712, 37316476429, 37319679314).
3. Этикет зон (frozen, §Зоны дословно): «restore всегда, save только на push-событиях».
   Реализация (90716b0, ветка wip/083/implementer-gen): save-шаги `if: github.event_name
   == 'push'`. Значит на ветке предмета save не срабатывает НИ РАЗУ.
4. Прогреть кеш «из main» до лендинга невозможно физически: записи с префиксом
   `ci-incr-*` создаёт только save-шаг НОВОГО workflow, а workflow на main ещё не
   запускался (083 не в main). Живой замер: `gh cache list -L 30` → 0 кешей репозитория
   вообще, в т.ч. 0 с префиксом `ci-incr-` (команда вернулась пусто, rc 0 — пустая
   выборка списка кешей, не ошибка).
5. Следствие: каждый прогон ветки — cache-miss полный режим для самого тяжёлого чека.
   Живой прогон А3 этой сессией из worktree архитектора:
   `bash fixtures/ci_gen_083/timing_083.sh wip/083/integration` →
   «timing_083 НАРУШЕНИЕ: самая долгая lane-джоба ci = 642 с (> 360): ci (l1,
   check:charter)», rc 1. Full-режим с `--incr` физически не быстрее полного без
   `--incr` (тот же код-путь, инв. И-6б: «нет кеша — явный полный прогон»).
6. А3 (frozen, §Приёмка дословно): «rc 0 — самая долгая lane-джоба семейства ci ≤ 360 с
   по ВСЕМУ окну и отмен джоб ci в окне — 0 … Лендинг блокируется rc≠0; порог числом в
   скрипте, локальная интерпретация после прогона не предусмотрена». Окно названо
   буквально: «по окну ЗАКОНЧЕННЫХ прогонов ветки (`wip/083/…`, до 20 —
   `gh run list --limit 20`), до слияния».

Тупик структурный: rc 0 достижим только после лендинга (первый push в main сохраняет
кеш), а лендинг требует rc 0. Никакой фикс incr_finish() (пачка implementer-incr, в
работе) это не снимает: он делает холодный прогон зелёным, но не быстрым.

## Вопрос 1: противоречие текста или недочитанный механизм?

Противоречие текста. Два frozen-абзаца конфликтуют по эффекту для переходной ветки:

- §Остаточный риск (дословно): «PR-прогоны кеш не сохраняют (save только push): первый
  инкр-прогон PR чаще полного на словах „кеш отсутствует“ — принятая цена (CI-Б снимет
  класс целиком)» — объявляет холодные PR-прогоны ПРИНЯТОЙ ЦЕНОЙ.
- §Приёмка А3 судит ту же популяцию прогонов красным без исключения: на PR-only ветке
  100 % окна — холодные, max lane = 642 с > 360 с ⇒ вечный rc 1 ⇒ «Лендинг блокируется».

«Первый инкр-прогон PR» из остаточного риска предполагает, что последующие PR-прогоны
тёплые — но на переходной ветке тёплых не будет НИКОГДА (нечем греть: ни своего save, ни
main-кеша). Фраза описывает steady-state ПОСЛЕ лендинга 083 (будущие контракты греются
от main-pushes), а А3 судит переходное состояние ДО лендинга.

Проверенные и закрытые альтернативные прочтения (легитимной интерпретации НЕТ):

1. «Читать окно по другой ветке/событию» — текст называет ветку предмета буквально
   (`wip/083/…`, `gh run list --branch`); push-прогонов на ней не существует (замер 2).
   timing_083.sh фильтра по событию не имеет — но и фильтровать нечего.
2. «Порог — steady-state после ленда, предмет закрывается без живого rc 0» — текст А3
   буквально «до слияния … Лендинг блокируется rc≠0»; rc 2 («НЕ зелёное, приёмка не
   проходит „по умолчанию“») тоже блокирует. Пост-лендинговой интерпретации в тексте нет.
3. «Аргумент 2 скрипта (порог) — легитимный рычаг» — нет: «порог числом в скрипте,
   локальная интерпретация после прогона не предусмотрена»; поднять порог под факт
   (360 → 642+) — ровно запрещённая локальная интерпретация.
4. «Кеш мог бы быть откуда-то ещё» — закрыт замером 4 (0 кешей в репо).
5. «Арбитраж 083-krug2 что-то предписывает про события» — нет: мандат П2 (цитата
   РЕШЕНИЯ из e1a84dc) — «`|| continue` в timing_083.sh:37 → именованный rc 2», т.е.
   только полнота чтения gh-окна; об источнике кеша и событиях вердикт молчит.

## Вопрос 2: решение в рамках текущего текста?

## Варианты решения (оба — v+1)

### Вариант 1 (минимальный): save и на pull_request, окно А3 не трогаем

Замена предложения этикета в §Зоны (дословный текст новой строки):

> обёртка `actions/cache` (кладёт генераторная пачка): по restore-шагу на каждый чек,
> path `tmp/ci-incr/<check>.sha`, key `ci-incr-<check>-<sha>`, restore-keys
> `ci-incr-<check>-`, restore всегда; save — на push И pull_request событиях: на push с
> key `ci-incr-<check>-<sha>`, на pull_request с PR-scoped key
> `ci-incr-<check>-pr-<N>-<sha>` (N = github.event.pull_request.number; кеш, сохранённый
> в PR, изолирован GitHub по PR и виден только этому PR — push-путь main не
> затрагивается; PR-раны выбирают по restore-keys префиксу самую свежую видимую запись:
> свою предыдущую зелёную, иначе последнюю push-запись); инкрементальная пачка своего в
> `ci.yml`/реестр не пишет.

Механика: первый PR-прогон после врезки — холодный, сеет PR-кеш; второй и далее —
тёплые, l1 падает под порог.

Цена: А3 «по ВСЕМУ окну» остаётся красным, пока холодные прогоны (3 текущих + 1 сеющий)
не вытолкнутся из последних-20: нужно 20 завершённых БЕЗ отмен прогонов с интервалом
больше длительности прогона (concurrency `ci-${{ github.ref }}` cancel-in-progress
отменяет спешащие синхронизации, а отменённая джоба ci — сама нарушение окна А3).
≈ 3+ часа ожидания и ~20 коммитов-синхронизаций в ветку предмета. Работает, но дорого и
хрупко: любая отмена обнуляет старение.

### Вариант 2 (рекомендованный): этикет Варианта 1 + граница окна А3

(а) строка этикета — та же, что в Варианте 1;

(б) дополнение к §Приёмка А3 (дословный текст вставки; окно судит только прогоны,
которые МОГЛИ быть тёплыми):

> окно А3 — завершённые прогоны ветки, созданные ПОСЛЕ граничного прогона; граничный
> прогон — аргумент 3 вызова `timing_083.sh <ветка> <порог-с> <граничный-run-id>`,
> фиксируется оркестратором ДО приёмочного прогона как последний завершённый холодный
> прогон ветки (для переходной ветки — первый зелёный прогон после врезки этикета v+1:
> он сеет PR-кеш, тёплым быть не мог); прогоны до границы включительно — переходные, не
> судятся (принятая цена в смысле §Остаточный риск); в окне после границы — не менее 2
> завершённых прогонов, иначе rc 2 «мало данных» (НЕ зелёное); порог, ноль отмен и
> полнота чтения gh-окна (арбитраж 083-krug2 П2) — без изменений.

Механика перехода: фикс incr_finish() (в работе, implementer-incr) → v+1 врезан в
ветку → сеющий зелёный прогон → граница := его run-id (число-аргумент, зафиксирован ДО
приёмочного прогона — тот же статус, что порог: локальной интерпретации ПОСЛЕ прогона
по-прежнему нет) → 2–3 тёплых прогона → А3 rc 0 → лендинг. Суммарно ~3–4 прогона.

Сопутствующая работа (зона architect, следующая пачка после слова владельца):
timing_083.sh получает аргумент 3 + фильтр `createdAt` строго позже границы; батарея —
красная А3-клетка на обход «исключённый граничный прогон больше порога не краснит
окно» + сценарий «окно после границы < 2 прогонов → rc 2».

### Почему Вариант 2

Вариант 1 оставляет текст А3 судящим заведомо-холодную популяцию и платит ~3 часа и
~20 мусорных пушей за механическое выкатывание окна. Вариант 2 приводит окно А3 в
соответствие с УЖЕ принятой остаточным риском ценой («холодные PR-прогоны — принято»)
за один сеющий прогон, сохраняя предикат механическим rc-командой без локальной
интерпретации после прогона. Риск Варианта 2 — граница становится новым местом
злоупотребления (подвинуть границу «поудобнее») — закрыт тем, что граница фиксируется
ДО прогона и видна в журнале приёмки командой с литеральным run-id, а минимум 2
тёплых прогонов запрещает зелёность на одном прогоне-счастливчике.
