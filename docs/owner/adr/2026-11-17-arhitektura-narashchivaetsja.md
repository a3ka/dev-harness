# Архитектура наращивается по ходу работы; разбиение identity/auth не перекраиваем; пробелы инструментов — находкой

дата: 2026-11-17
вопрос: после упоров бэкенда 177 (компенсация удаляет append-only аудит) и 183 (модель revokeSession ≠ код, нет ребра identity→auth) — улучшать ли саму архитектуру CompliorOS
решение:
  1. Архитектура не статична: модель наращивается по ходу работы («скелет обрастает мясом») штатным путём пакета — находка → правка → новый снимок с утверждением владельца; L2 пачкой на срез, блокирующее — хранителю сразу.
  2. Разбиение identity/auth не перекраивается: auth владеет входом и техническими сессиями, identity — сторонами, Principal и правами (решение 2026-11-11, `CompliorOS-architecture/governance/findings/001-auth-owner-transition.md:11,27`).
  3. 177 — ошибка реализации, не модели: append-only аудит и INSERT-only права мигратора уже в модели (`system/resources.js:927–944, 220–231`), широкий суперпользователь отклонён (`governance/findings/003-resource-registry-authority.md:43`); лечится в коде — атомарная регистрация внутри процедуры 152, без DELETE (слова №30/№31).
  4. 183 — недостающая конструкция модели: identity-owned required interface + binding в compose без прямого ребра identity→auth; кандидат снимка 6 — CompliorOS-architecture#8 (слово по diff — 2026-11-17 ~20:00 UTC).
  5. Пробелы инструментов проверки (native schema не выражает XOR/oneOf; нет first-class adapterBinding; conformance не доказывает required/provided binding) — оформить находкой в `CompliorOS-architecture/governance/findings/`; отдельный предмет — при повторении таких остатков.
  6. Архитектурные решения владельца записываются ADR: в модели — `CompliorOS-architecture/DECISIONS.md` (ADR-EXEC-011 — хранитель в PR снимка 6), в процессе — здесь.
кто решил: владелец, 2026-11-17 (~20:40 по часам консультанта): «1) да, я с этим согласен, 2) надо подобные решения оформлять на сервере в АДР, чтобы потом не думать почему именно так, 3) архитектура не статическое явление. мы по ходу ее можем развивать, как скелет наращиваться мясом» — на рекомендацию консультанта «модель не перекраивать; пробелы инструментов — находкой».

рассмотренные варианты:
  - перекроить владение identity/auth — отвергнуто: разделение выбрано сознательно 11.11, сегодняшние случаи укладываются в предусмотренный порядок пересмотра;
  - широкий замер всех упоров бэкенда до решения — отвергнуто: переписка уже отвечает; «12 boundary-арбитражей» — в основном границы предмета контракта, не модуля;

условие пересмотра: соблюдение границ identity/auth систематически требует циклов или непрозрачных адаптеров (повторяющиеся находки одного класса) — тогда предмет пересмотра границ.
