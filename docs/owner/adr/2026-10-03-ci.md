# CI: скорость, независимость, ноль выброшенных прогонов

дата: 2026-10-03
вопрос: как сократить ожидание CI и прекратить выбрасывать прогоны
решение: четыре этапа.
  А (первая пара): задание ci разбивается на 6–8 параллельных заданий, шаги и шарды
  генерируются из реестра барьеров; проверки истории (check_charter, check_zones,
  check_ids, check_protected) — инкрементально от последнего проверенного sha. Приёмка:
  полный прогон ≤ 6 мин, таймаутов PR — ноль.
  Б (вторая пара): классы изменений — push в main без кода (verdicts/, HANDOFF,
  NABLIUDENIA*, docs/, строки registry/) → лёгкое задание ≤ 2 мин; код в main — только
  через PR; зелёный результат принимается по хешу кодового дерева (дерево без учётных
  путей) — приземление, вердикт, чекпойнт тяжёлый CI не перезапускают. Приёмка:
  отменённых тяжёлых прогонов ≈ 0 в неделю.
  В (параллельно с V-2): граф модулей из кода; PR — по затронутому; полный прогон по
  расписанию, при закрытии фазы и правке ядра; герметичность фикстур; промах графа →
  Н-запись + исправление графа.
  Г (в «done проекта»): профиль проекта объявляет источник графа и команды «затронутое»
  и «полное»; CI проекта генерируется тем же генератором (gen_ci_workflow, 063).
  До done CI-Б — временная норма 9.6: учётные коммиты пушить пачкой раз в 30–60 мин; код
  только через PR; работа не лежит локально дольше часа.
основание: слово владельца 2026-10-03; снимок §9 (9606609).
  Замер за 7 дней: 405 прогонов — 199 cancelled / 104 failure / 100 success; 192 отмены —
  push в main (из них 110 успели отработать 5–29 мин); причина — полный CI (~23 мин) на
  каждый push в main и concurrency по ref main. Задание ci — 1371 с, ~50 последовательных
  шагов; check_charter 445 с. Окно «судья → done» у 071–074: 33% — ожидание CI.
  2026-10-03 после 13:45 из 8 прогонов 5 отменены новыми пушами.
область: .github/workflows/**, package.json, scripts/check_ci_gate.sh,
  scripts/gen_ci_workflow.sh, scripts/check_charter.sh, scripts/check_zones.sh,
  scripts/check_ids.sh, scripts/check_protected.sh, scripts/verify_antiplacebo.sh,
  роль:orchestrator
рассмотренные варианты:
  - поднять таймауты / докупить раннер — отвергнуто: последовательность и отмены остаются;
  - отключить проверки на учётных push — отвергнуто: устав и зоны проверяются всегда, но
    лёгким заданием.
условие пересмотра: после этапа А полный прогон > 6 мин, или после Б отмен > 10 в неделю
статус: принято (слово владельца 2026-10-03); А и Б — первые пары, В — с V-2, Г — «done
  проекта»
