Решение владельца 2026-10-11: принять нарезку А → Б → В; временный путь ленда — прежний land_agent до части В.

**094 нужно разделить на три последовательно приземляемых результата: доверенная основа → реальные доказательства → переключение публикации. Старые ленды удалять только в третьей части, после доказанного производственного прохода первых двух.** Не делить на «дверь сейчас, писатели потом»: именно это создаёт остановку поставки.

**Граница обещания:** семь отказов сохраняются как обязательная сквозная приёмка. Обещать, что неизменённый `land_agent` уже обеспечивает их между частями, нельзя: исходный аудит установил обратное. Переходный маршрут нужно явно разрешить и ограничить завершением миграции, не объявлять его соответствующим 094.

### А. Доверенная основа и подготовка объекта

**Входит:** базовые поля существующего профиля, включая `targetBranches`; чтение политики и определений проверок из принятой версии; `prepare/object` для харнеса и проекта. Объект фиксирует репозиторий, задачу, target, B/C/M и версию политики/профиля. Подготовка сохраняет identity и дословный перенос санкций.

**Не входит:** запись результатов CI/судей, публикация, изменения `done_contract`, удаление старых лендов. Никакой зависимости от ленда 087.

**Закрывает:** основу §1.5, И-1/И-5; сценарии **6** — кандидат не выбирает собственную политику — и **7** на этапе подготовки. Полноценный отказ публикации пока не заявляется.

**После ленда:** живы прежние `land_agent`/`land_project`; их проверки не выключаются. Новая подготовка уже используется для реальных кандидатов, но не двигает целевую ветку. Этот ленд заранее помещает необходимые поля политики в принятую базу — устраняет bootstrap-цикл.

**Готовность:** на производственном профиле подготовлен M, target не изменился; изменение каждого компонента объекта различается. Кандидат, удаляющий обязательную проверку или расширяющий allowlist, не получает новую политику для собственного принятия. Красная подмена — чтение профиля кандидата вместо принятой версии. Пробы нужны для обоих профилей, не только `harness/policy`.

**Переиспользование:** подготовка и идентификация из `accept_publish.sh`, профильный резолвер, проверки identity/санкций и соответствующие клетки 094. Исправления из веток переносить обычными коммитами, без подставного носителя.

### Б. Производственные доказательства до публикации

**Входит:** полный применимый CI подготовленного **M**, независимый суд этого объекта, реальные писатели `check/verdict/policy` и чтение доказательств дверью. M передаётся CI через нецелевую ссылку; требование «уже на `origin/main`» здесь недопустимо.

Доверенная обвязка запускает принятые определения проверок на дереве M, без credential публикации. Результат каждого обязательного ключа связывается структурно с конкретным запуском, определением и исполненным деревом — не извлекается подстрокой из display-имени job. Судейский писатель получает событие решения, а не превращает зелёный CI в `accept`.

Журнал сохраняется **вне проверяемой ветки**; запись доказательства не меняет B/C/M. Разрешение перехода политики выдаёт доверенный канал, не кандидат и не ленд.

**Не входит:** переключение производственной публикации, удаление старых путей, кеш CI, расширение `done`.

**Закрывает:** сценарии **1–4**, происхождение доказательств §1.5 и санкционирование **6**. Проверка движения B/C остаётся обязательной непосредственно перед публикацией.

**После ленда:** прежние ленды продолжают работать. Новый контур собирает настоящие доказательства до изменения target; публикацию новой дверью проверяют в изолированной копии с этими доказательствами, без ручного сочинения строк.

**Готовность:** для реального кандидата, ещё отсутствующего в main, штатные вызовы создают полный применимый журнал; дверь публикует ровно M в изолированной копии. Затем по отдельности: чужой accept, поздний fail, находка только в кандидате, отсутствующая обязательная проверка при постороннем зелёном workflow, чужое дерево/определение — именованный отказ, target неизменен. Отключение любого писателя обязано краснить сквозную пробу.

**Переиспользование:** грамматика журнала, проверяющая часть двери, существующие клетки отказов. `--verdict-row`/`--check-row` — материал для исправления, **не готовые поставщики** по свидетельству Р4-3.

### В. Единственная публикация и миграция потребителей

**Входит:** установленная доверенная дверь; повторная сверка B/C, перенос именно M, восстановление после частичного успеха; миграция всех вызовов, роли, npm/CI и тестов. Старые скрипты удаляются одновременно с переключением, без обходного fallback. Существующее обязательство `done_contract` читать `published` выполняется здесь вместе с объявленной `ПОТРЕБИТЕЛЬ`-пробой для `check_spec_ready`, без расширения до всего продуктового `done`.

**Закрывает:** все **семь сценариев**, И-8/И-9 и единственность двери. Код с полномочиями публикации берётся из установленной принятой версии, не из checkout кандидата.

**После ленда:** только `accept_publish`; push остаётся через gitw. Сам переход приземляется последним использованием принятого `land_agent`; затем устанавливается принятая версия и старый маршрут отключается. Операция переключения и её полномочия фиксируются заранее.

**Готовность:** сначала репетиция полного перехода на копии реального репозитория; затем первый настоящий ленд новой дверью. До отключения старого пути должны быть подтверждены доступность писателей и установки. Приёмка включает семь отдельных негативных сценариев, движение B/C перед publish и сбой после переноса ref, но до `published`: повтор не создаёт второй merge. Зоны и потребители проверяются на обычной истории, без merge-сокрытия. Старые поведенческие гарантии переносятся в новые тесты до удаления прежних семей.

**Переиспользование:** CAS-публикация, идемпотентность и батарея 094; проверки 016/022/063/065 — по сохраняемому поведению, не по старым именам скриптов.
