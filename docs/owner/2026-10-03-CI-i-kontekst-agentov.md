### 1.4 Временная норма 9.6 (до done CI-Б)
Учётные коммиты (вердикты, HANDOFF, наблюдения, строки реестра) — пачкой раз в 30–60 мин;
код — только через PR; работа не лежит локально дольше часа. 📝 Соблюдается плохо

### 1.5 Уроки дня по CI
- **Вердикт CI — только по `gh run list/view --json conclusion,jobs`**, success у каждого
  задания. Текстовый `gh run view` показывает задание `ci` звёздочкой без ✓/✗ — красный
  `ci` дважды прочитан как зелёный (Н-194).
- **`check_charter` берёт якорь всегда `frozen/…/1`** и судит `v1..HEAD` включая merge
  (по diff с первым родителем). Перезаморозка v2 якорь не сдвигает; лечение — grandfather-
  пары (Н-192, 080).
- **PR-CI видит только то, что в ветке.** Фикс барьера, сделанный на main, на ветку не
  попадает → cherry-pick фикса наверх ветки (не merge main в ветку: merge судится по
  первому родителю и тащит уставную дельту, Н-191).
- **Не ребейзить ветку с grandfather-парами** — пары привязаны к sha.

## Часть 2. Контекстное окно

### 2.1 Почему не «широкое окно у оркестратора»
- **Цена:** каждый запрос перечитывает весь контекст; кэш у z.ai дешевле некэшированного
  в ~4 раза (формула: input×6,9 + cached×1,7 + output×24).
- **Качество:** Chroma «Context Rot» — деградация у всех 18 моделей с ростом длины, у окна
  1M уже на 50K; отвлекают тематически близкие, но нерелевантные куски. Рекомендация —
  рабочий контекст 25–30% окна.
- **Роль:** оркестратор раздаёт и держит порядок; глубина нужна архитектору задачи.
Вывод: **широко и мелко — у оркестратора; глубоко и свежо — у субагента на одну задачу.**

### 3.6 Два уровня пакетов для внешнего проекта
**Уровень 1 — брифинг проекта для оркестратора** (генерируется, ~25–40K): правила
(AGENTS.md пакета и репо целиком); карта проекта — модули по строке (ответственность,
владелец, статус) из оглавления PROJECT.md; текущая волна из ROADMAP проекта; индекс
решений (ADR по строке); задачи волны (заголовок, статус, blocked-by, модуль) из
issue-map.json и проекта «Odelix Delivery»; здоровье репо (CI, PR, `.review/`).

**Уровень 2 — пакет модуля для архитектора/исполнителя/судей** (под задачу): MODULE.md;
разделы спеки с идентификатором модуля; ADR, чья ОБЛАСТЬ пересекается с модулем; задача
целиком (issue, критерии, результаты закрытых blocked-by); интерфейсы соседей; нужные
разделы DEVELOPMENT / RUNBOOK / INTEGRATIONS. **Вклейка 10–20K обязательного + манифест
ссылок; потолок вклейки 40K** (уточнение §13 к §12.4).

Требования к документам проекта (разово, в II-3): разделы спеки и PROJECT.md помечены
идентификатором модуля; у ADR поле ОБЛАСТЬ; связь задача → модуль в issue-map.json;
профиль `.harness/` объявляет карту. Тексты не переписываются — только разметка.

## Часть 4. Статус «done»: харнес и внешний проект; роль метапрограммирования

### 4.1 Принцип: что делает код, а что модель
Код делает то, что повторяется с известным ответом; модель — суждение, конструкцию,
развилку, судейство. Класс нормы определяет канал ПРОВОДКИ:

| класс нормы | канал | пример |
|---|---|---|
| процедура | **tool** — `scripts/<инструмент>` + role-строка вызова (инструмент делает вместо агента) | `orch_status`, `ci_wait`, `pr_land`, `mint_line`, `make_task` |
| отказ | **guard** — `scripts/<барьер>` | `done_contract`, `check_charter`, `pre_critic`, `path-guard` (081) |
| суждение / поведение | **role** — `roles/<роль>.md` | «правки по FAIL — implementer», батч владельцу |
| устав | **charter** — `AGENTS.md` | правила 1–16 |
| два артефакта обязаны совпадать | **генератор** — один генерируется из другого | роли → `.omp/agents`, реестр барьеров → шаги CI |

Норма-процедура, проведённая только role-каналом, — отказ pre_critic «процедура без
инструмента». Инструмент обязан иметь красную клетку «делает заявленное». Кандидаты в
инструменты — по замеру: действия, повторённые > N раз за неделю (из 2129 bash ведущей
сессии ~1300 — снятие состояния).

### 4.5 Роль метапрограммирования
Метапрограммирование здесь — **код, который пишет или проверяет другие артефакты из
одного источника**: генераторы и декларативные профили. Его роль в done — сделать так,
чтобы «сделано» нельзя было подделать расхождением копий и чтобы проверки не писались
руками каждый раз.

| механизм | источник → артефакт | что даёт для done | статус |
|---|---|---|---|
| `gen-harness.ts` | `config/agent_models.json` + `roles/*.md` → `.omp/agents/*.md`, `modelRoles`, fallback-цепочки | `gen:harness --check` в CI: роль, правленная без генерации, — красный CI (сегодня: «Генератор ролей под чек») | ✅ |
| `gen_ci_workflow.sh` (063) | профиль проекта → CI-файл проекта | done(А) п.2 опирается на сгенерированный CI, а не рукописный | ✅ |
| генератор шагов CI | реестр барьеров → задания/шарды CI + `package.json` | снимает ci-parity и ручные таймауты; база CI-А | 📋 |
| `make_task` = ContextPack v0 | frozen-блоб + профиль + ADR + уроки → задание + манифест | done(А) п.10, отказ `spawn_agent` без манифеста | 📋 II-3 |
| `new_contract.sh` | грамматика → скелет контракта; ПЕРЕСЕЧЕНИЕ из пересечения зон frozen-блобов | меньше ошибок зон (Н-71) | 📋 |
| заготовка красной батареи | инварианты И-N → клетки с меткой `# ИНВ: И-N` | покрытие по построению (база 079) | 📋 |
| стандартные мутанты | код барьера → инверсия условия, ранний `exit 0`, пропуск проверки | анти-плацебо без ручного сочинения стабов | 📋 |
| норма-строки ролей | реестр норм с каналами → строки ролей | снимает ручную правку ролей и потолки (сегодня: потолок роли 52 342 / 51 200 байт) | 📋 |
| `decisions_for` / `lessons_for` | ОБЛАСТЬ ADR/уроков (глобы) → выдача по зоне | архитектор не может «не знать» решение в своей зоне; pre_critic «не учтено ADR-NNN» | 📋 II-3 |
| реестр плана `registry/plan.tsv` | строка плана → блок ROADMAP, «Следующая сессия», todo; `check_plan` | freeze отказывает контракту «вне плана»; нет двух «Итоговых порядков» | 📋 первая пара |
| `handoff_rotate.sh` | HANDOFF → архив | HANDOFF всегда один «ГДЕ МЫ», ≤ 30 КБ | 📋 |
| инвентарь ARCHITECTURE.md | шапки скриптов + ПРОВОДКА → раздел «инвентарь механизмов» | done отказывает, если механизм изменён, а инвентарь не перегенерирован | 📋 |
| генерация ADR из вердикта арбитра | РЕШЕНИЕ арбитра → ADR (вопрос/решение/основание = sha вердикта) | решения не теряются в переписке | 📋 |

**Правило:** если два артефакта обязаны совпадать — один генерируется из другого, а CI
проверяет `--check`. Ручная синхронизация — источник «зелёного на пустом предмете»,
расхождения документов и потерянных решений (сегодняшние примеры: два «Итоговых порядка»,
роль без генерации, решения владельца только в контексте сессии).

**Граница:** генераторы и инструменты не судят смысл. «Предмет реализован», «решение
правильное», «находка блокирующая» — суждение судей. Метапрограммирование делает так,
чтобы судьи судили одинаковые, полные и свежие артефакты, а не копии.
