**Вывод: автономность сохранять; сокращать нужно не полномочия харнеса в обычной задаче, а число конкурирующих механизмов поставки. Рекомендую довести один маршрут: изолированный агент → восстановимое состояние → независимая приёмка конкретного результата → единственный доверенный писатель → повторяемое завершение задачи. GitHub использовать как серверную границу, а не строить рядом второй GitHub.**

Моя прежняя рамка была недостаточной: пилот с владельцем в роли постоянного интегратора действительно ускоряет первый PR, но не доказывает автономную разработку. Уже написанный код — материал для сокращения оставшейся работы, **не основание заканчивать каждый начатый механизм целиком**.

*Граница сверки:* прочитаны контракты, вердикты, текущие скрипты, ссылки `wip/*` и теги заморозки. `git show` заблокирован политикой инструмента, поэтому содержимое последних веток целиком не проверено; GitHub-настройки и станция не проверялись. Прогонов здесь не было. Ниже — рекомендация, не новый accept.

## 2. Как разорвать тупик лендов

**Выбор — исправляющий интеграционный PR плюс однократное согласование перехода, не постоянный режим разрешённых красных проверок.**

Собрать исправления причин красного main из существующих веток: маркер семьи 098, ap2 из 095, остальные установленные причины. Исторические нарушения разобрать одним конечным списком: точные коммиты/пути и решение по каждому. Не выдавать разрешение на будущие нарушения и не переписывать историю заморозок.

Одновременно убрать логический цикл: `scripts/check_ci_gate.sh` сейчас требует достижимость проверяемого SHA из `origin/main`. **Предпубликационный гейт должен проверять кандидата на нецелевой ссылке, а не требовать его предварительной публикации.** Красный старый main не обязан означать красный исправленный кандидат.

Целевая конструкция:

- серверные правила запрещают агентским credentials запись в main, force/delete и произвольную запись служебных тегов;
- единственный доверенный писатель публикует после CI и независимого accept;
- определения проверок берутся с принятой стороны; кандидат исполняется без полномочий публикации и изменения доказательств;
- все служебные изменения идут вне main; обычная задача внутри заранее выданных полномочий не требует новой owner-подписи;
- изменение политики, полномочий, бюджета и принятие риска остаются исключениями владельца.

**Не спрятать ещё одну развилку:** обычный GitHub merge не гарантирует публикацию буквально подготовленного SHA **M**. Для сохранения требований 094 я выбираю публикацию подготовленного M доверенным писателем с отказом при изменившейся базе. Права писателя и серверные правила надо проверить вместе; общий bypass всех проверок недопустим. Если выбрать нативный merge вместо этого — потребуется явное изменение контракта идентичности результата.

При зелёной базе **не нужны** реестр разрешённых дефектов 100, обмен исключениями и переходная логика красных lanes в 099. Сам 100 сейчас не готов заменить восстановление CI: по вашему сегодняшнему наблюдению производитель отчёта отсутствует; читаемый `run_ci_lane.sh` действительно прекращает выполнение на первом отказе.

## 3. Порядок: два потока, шесть контрольных точек

Это последовательность работ, **не предложение завести шесть новых контрактов**. Сужение замороженных предметов оформляется явно; существующие accept не переносятся на изменённый предмет.

| Шаг | Поток | «Готово» — наблюдаемый результат |
|---|---|---|
| **1. Один переходный регламент** | Общий | Зафиксированы конечный исторический долг, обычные полномочия и единственный маршрут публикации. Прогон предполёта на исправляющем кандидате не требует новой подписи для каждого старого коммита. |
| **2. Зелёная база и серверная граница** | А | Исправляющий кандидат проходит полный применимый CI; выполнен первый ленд и post-merge CI. Живые попытки агентского push и публикации плохого кандидата отвергнуты. |
| **3. Исполнение и восстановление** | Б, параллельно шагу 2 | 093 проверен на настоящем uid/systemd-контуре, не только shim-ами. Затем 092/095: реальный запуск внешнего проекта получает его контекст; остановка и рестарт во время CI сохраняют задачу и следующий шаг без ручного HANDOFF. |
| **4. Единая приёмка и публикация** | А после шага 2 | Реальный кандидат проходит подготовку, CI, суд и публикацию ровно M. Чужой accept, поздний отказ, подмена проверки и сдвиг базы запрещают публикацию. Заменённые пути удалены. |
| **5. Завершение 096** | Б после шага 3; интеграция после 4 | После сбоя между публикацией и закрытием issue повтор завершает остаток без нового merge; отказ отправки тега не объявляется полным done. |
| **6. Автономный продуктовый опыт** | Оба потока сходятся | Реальная задача завершена без вмешательства владельца после постановки; затем три последовательные задачи, включая восстановление после прерывания. Проверены опубликованный пользовательский результат и завершение учёта. |

Суды — по действующему регламенту. Четвёртый–шестой круг не превращать в нормальный план: триггер арбитража должен срабатывать.

## 4. Пилот: что делать сейчас

**При цели «автономность» выбираю сначала минимальный автономный маршрут, затем пилот как его приёмку.** Сейчас допустим диагностический запуск без публикационных полномочий — после доказанной изоляции либо в отдельной безопасной среде. Он может проверить вход агента и продуктовую приёмку, но не считается автономной поставкой.

Не открывать параллельный поток «владелец вручную доводит продукт»: он займёт один из двух потоков и замаскирует разрывы маршрута. Надзор в итоговом пилоте наблюдает; любое ручное восстановление состояния или разрешение обычного ленда считается дефектом автономности.

## 5. Срок и точка повторного сужения

**[INFERENCE] При сохранении темпа 4–6 кругов — ориентир 2–4 календарные недели, не 2–3 дня.** Шесть контрольных точек частично параллельны, но критический путь проходит через восстановление CI, доверенную публикацию и сквозной опыт. Оптимистичные 7–10 дней возможны только при переиспользовании готового и прекращении расширения предметов.

Предлагаю два рубежа:

- **Через два рабочих дня нет первого честного ленда исправляющего пакета** — не достраивать 100 по инерции; разбирать конкретный неразрешённый переход.
- **Через пять рабочих дней нет сквозной репетиции внешней задачи до публикации** — снова сужать: один проект, один target, один способ публикации; исключить из критического пути автономное изменение харнесом собственной политики.

Автономная поставка внешнего продукта и автономная перестройка собственной системы управления — разные цели. Вторую сейчас не делать условием первой.
