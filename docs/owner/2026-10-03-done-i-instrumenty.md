# Слово владельца 2026-10-03: каналы норм, инструменты, генераторы, done

## 1. Принцип
Код делает то, что повторяется с известным ответом; модель — суждение, конструкцию,
развилку, судейство. Класс нормы определяет канал ПРОВОДКИ:
- процедура → tool (scripts/<инструмент> + role-строка вызова): инструмент выполняет вместо агента;
- отказ → guard (scripts/<барьер>);
- суждение/поведение → role (roles/<роль>.md);
- устав → charter (AGENTS.md);
- два артефакта обязаны совпадать → один генерируется из другого (генератор).
Норма класса «процедура», проведённая только role-каналом, — отказ pre_critic
«процедура без инструмента». Инструмент обязан иметь красную клетку «делает заявленное».
Источник кандидатов — замер: шаблоны действий агентов, повторённые > N раз за неделю
(замер 2026-09-30..10-03: из 2129 bash ведущей сессии ~1300 — снятие состояния:
git 441, детектор 318, gh CI 239, fetch 169; субагенты Mint/Obs/Fix* — механика).

## 8. Архитектурные документы и решения (слово владельца 2026-10-03)

### 8.1 Набор (без оверинжиниринга)
Основные: AGENTS.md (как работаем); ARCHITECTURE.md (как устроено сейчас: компоненты,
границы, потоки, инварианты; раздел «инвентарь механизмов» ГЕНЕРИРУЕТСЯ из шапок скриптов
и ПРОВОДКИ); ADR — decisions/ADR-NNN-*.md (почему решили; одно решение — один файл);
RFC = контракт (contracts/) или plans/ для многоконтрактной инициативы — нового типа нет;
ROADMAP.md (порядок).
Служебные: HANDOFF.md — только «где мы и что дальше» (без истории и решений);
NABLIUDENIA — уроки и инциденты; RUNBOOK (вырастает из ops/server/README.md).

### 8.2 ADR
Поля: дата, вопрос, решение, основание, ОБЛАСТЬ (пути/глобы: scripts/gitw*,
roles/orchestrator.md, ops/server/** …), рассмотренные варианты, условие пересмотра,
статус (предложено → принято → заменено ADR-NNN). Номер — next_id (класс ADR).
check_decisions: снять «ровно семь»; грамматика полей, область — непустые пути,
ссылки «заменено/заменяет» взаимны.
Когда пишется: слово владельца, меняющее политику; РЕШЕНИЕ арбитра (ADR генерируется из
вердикта: вопрос/решение/основание = sha вердикта); принятый остаточный риск (условие
пересмотра — «живой укус»); существенный выбор в контракте (границы, протокол, хранение,
совместимость — спека §7.2).
Инструмент: new_adr.sh (канал tool); оркестратор — вместо записи решения в HANDOFF.

### 8.3 Кто и когда читает (решения приходят к агенту, а не ждут памяти)
- decisions_for <пути|NNN>: действующие ADR, чья ОБЛАСТЬ пересекается с путями; по каждому
  1–2 строки: решение, почему, условие пересмотра.
- Старт сессии: оркестратор — сгенерированный индекс действующих ADR + краткое ARCHITECTURE.md.
- Черновик контракта: архитектор — обязательный раздел «§Действующие решения» (вывод
  decisions_for по зоне + как контракт их соблюдает) и поле «Решения: ADR-NNN | нет
  существенного выбора — причина». pre_critic: пересекающийся ADR не упомянут → отказ
  «не учтено ADR-NNN»; противоречие без явного «заменяет ADR-NNN» (черновик нового ADR
  с причиной) → отказ.
- Задание исполнителю: make_task вклеивает ADR его зоны (решение + почему).
- Файлы на границах: в шапке «см. ADR-NNN»; инвентарь ARCHITECTURE.md собирается из шапок.
- Критик: полнота и честность «§Действующие решения».
- Ревьюер: класс находки «противоречит ADR-NNN» (с меткой масштаба); decisions_for по диффу.
- add_observation.sh печатает ADR, чьё условие пересмотра совпадает с областью нового Н;
  пересмотр — вопросом владельцу батчем.
- close_contract: ADR, заменённые фазой, → «заменено».
- done_contract: контракт добавил/изменил механизм → инвентарь ARCHITECTURE.md
  перегенерирован, ADR пачки → «принято»; иначе отказ.

- check_plan (CI + pre-commit): блок ROADMAP == генерация из plan.tsv (ручная правка внутри
  блока — красное); у каждого пункта есть источник; номер контракта в плане существует в
  реестре; done-пункт не стоит «следующим»; зависимости ссылаются на существующие id.
- freeze_contract: контракт не из текущей/следующей пары plan.tsv — отказ «контракт вне
  плана» (вместе с лимитом активных 078 закрывает «взял лишнее»).
- Сторож здоровья (параллельно с V-2): HANDOFF «Следующая сессия» старше последней правки
  plan.tsv — сигнал.

### 10.5 Порядок исполнения
Контракт «реестр плана» (кодовый, красные тесты): plan.tsv с текущим порядком (первым
действием — перенос действующего пункта ROADMAP), генератор блока ROADMAP, генерация
«Следующей сессии», check_plan, отказ freeze_contract. Пара — первая после закрытия, с CI-А.
Внешние проекты: профиль указывает свой plan.tsv — тот же механизм.

### 10.6 Уточнение decisions_for (к §8.3)
ОБЛАСТЬ ADR = метки трёх видов: пути (глобы), роль:<роль>, класс:<кодовый|doc|смешанный>;
ADR попадает в выдачу, если пересекается хотя бы одна метка; «заменено»/«предложено» не
выдаются; запрет области «**» и корня (широкое решение — кандидат в устав); потолок выдачи
8 ADR — превышение → отказ «зона слишком широкая, режь задание»; вход по номеру контракта —
его ЗОНА-строки + метки роли. Красные тесты: пересечение → в выдаче; нет → нет; заменённый
→ нет; роль:architect → архитектору да, implementer — нет; превышение потолка → отказ.

## 11. Стартовый брифинг оркестратора (слово владельца 2026-10-03)
Принцип: оркестратор видит проект ЦЕЛИКОМ, но с низким разрешением — каждая часть одной-двумя
строками; детали подгружаются по месту. Замер: стартап сессии #9 — ~60K токенов чтения
(6.6K → 70K за 11 запросов), при этом наблюдения читаются целиком, а устройства системы,
действующих решений и здоровья в стартапе нет.
Брифинг — один ГЕНЕРИРУЕМЫЙ файл (orch_brief, часть orch_status, инструменты-1), бюджет
~15–20K:
- цель и фаза: где в ROADMAP (сделано по фазам, текущая пара, что до V-2) — из блока порядка
  (затем plan.tsv) + тегов;
- устройство системы: семейства механизмов по строке (гарды, инструменты, генераторы, роли,
  двери, серверная обвязка) — из ARCHITECTURE.md (до него — из шапок scripts/);
- активная работа: по контракту — предмет одной строкой, стадия, круг судьи, последний
  вердикт, кто работает — из тегов, вердиктов, журналов субагентов;
- действующие решения: индекс ADR и слов владельца, по строке — из decisions/, docs/owner/;
- открытые проблемы: только открытые наблюдения и принятые риски, по строке с адресом —
  scripts/nabludenia_digest.sh;
- здоровье: CI, детектор, неотправленное, worktree, контекст, расход — orch_status;
- ждёт владельца: вопросы на его слово — из HANDOFF.
НЕ входит (по месту): полные тексты контрактов, вердикты, история HANDOFF, NABLIUDENIA целиком.
До готовности генератора — норма стартап-протокола роли: верхний раздел HANDOFF «ГДЕ МЫ»
(до следующего «## ГДЕ МЫ»), вывод nabludenia_digest.sh, действующий блок порядка ROADMAP,
активные контракты (Предмет/Инварианты/Зоны); остальное — по месту.

## 12. Контекст на внешнем проекте: два уровня пакетов (слово владельца 2026-10-03)

### 12.1 Замер (Odelix r15.11, токены ≈ символы/3)
ISSUES.md ~332 000; INTEGRATIONS.md ~52 000; PROJECT.md ~44 000; RUNBOOK.md ~27 000;
ROADMAP.md проекта ~23 000; odelix-workstation (WORKSTATION-SPEC, DEVELOPMENT,
FOUNDATION-DECISION, AGENTS, модуль) ~45 000; 8 ADR odelix-stack/adr ~8 400; AGENTS.md
пакета ~600. Всё нужное для workstation без задач ~200K, с задачами — больше 500K.

### 12.2 Принцип
Широкое окно нужно тому, кто работает глубоко в модуле, а не долгоживущему оркестратору:
оркестратор проекта видит ВЕСЬ проект с низким разрешением; архитектор/исполнитель задачи
получает ПОЛНУЮ глубину своего модуля в СВЕЖЕМ контексте на одну задачу — без обрезки и
без перезапусков. Причины: цена (каждый запрос оркестратора перечитывает весь контекст),
качество (детали модуля тонут в документации всех модулей), роль (оркестратор раздаёт,
глубоко работает архитектор задачи).

### 12.3 Уровень 1 — брифинг проекта для оркестратора (генерируется, ~25–40K)
- правила: AGENTS.md пакета и репо — целиком;
- карта проекта: модули по строке (ответственность, владелец, статус) — оглавление и карта
  модулей из PROJECT.md, не документ целиком;
- текущая волна: блок волны из ROADMAP проекта;
- индекс решений: ADR по строке «что решено»;
- задачи волны: заголовок, статус, blocked-by, модуль — из issue-map.json и проекта
  «Odelix Delivery», НЕ из ISSUES.md;
- здоровье репо: CI, PR, .review/.
Генератор — режим проекта orch_brief (брифинг харнеса, §11) по карте из профиля.

### 12.4 Уровень 2 — пакет модуля для архитектора/исполнителя/судей (генерируется под задачу,
~30–80K)
- modules/<модуль>/MODULE.md;
- разделы спеки (WORKSTATION-SPEC.md и др.) с идентификатором модуля;
- ADR полностью, если ОБЛАСТЬ пересекается с модулем (decisions_for, §8.3, §10.6);
- задача целиком: текст issue, критерии приёмки, результаты закрытых blocked-by;
- соседи: интерфейсы связанных модулей (что экспортируют);
- соглашения: нужные разделы DEVELOPMENT.md, RUNBOOK, INTEGRATIONS (по меткам модуля).
Собирает make_task (режим проекта) по карте из профиля; судьи получают пакет + контракт + дифф.
Числа уточнены §13 (вклейка 10–20K + ссылки, пороги 150K/250K).

### 12.5 Окна по ролям
- оркестратор харнеса: старт ≤15–20K; мягкий 300K, жёсткий 500K → перезапуск на чистой точке;
- оркестратор проекта: старт ≤25–40K; те же 300/500K;
- архитектор задачи проекта: старт 30–80K; предел — окно модели, без перезапусков; пакет
  больше ~150K → задача слишком крупная: резать задачу, не документы;
- исполнитель, судьи: пакет модуля + контракт + дифф; то же правило.
Числа уточнены §13 (вклейка 10–20K + ссылки, пороги 150K/250K).

### 12.6 Требования к документам проекта (разово, при подключении в II-3)
Генераторы режут по СТРУКТУРЕ, не по смыслу:
- разделы WORKSTATION-SPEC.md и PROJECT.md помечены идентификатором модуля (якорь или
  заголовок с id);
- у ADR поле ОБЛАСТЬ — пути и модули (разово дописать в ADR-001…013);
- связь задача → модуль — в issue-map.json (дополнить, где нет);
- профиль .harness/ объявляет карту: модули, спека, ADR, задачи, RUNBOOK, INTEGRATIONS.
Тексты не переписываются — только разметка.

### 12.7 Где в плане
