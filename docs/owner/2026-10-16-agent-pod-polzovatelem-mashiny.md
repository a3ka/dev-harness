# Агент работает под пользователем машины — решение владельца 2026-10-16

**Решение.** На любой машине харнесса (станция, ноутбук, другая) сессии агентов по умолчанию запускаются под тем же пользователем Linux, что и цикл оркестратора (`orch-loop`), и **с токеном владельца** (GitHub и прочие ключи этого пользователя доступны агенту). Отдельный пользователь агента из контракта 093 (`orchagent`: нет доступа к ключам и токенам владельца, запуск через `sudo -nu`) остаётся **выключенной опцией**: `OPS_SERVER_AGENT_USER=<uid>` при установке / `ORCH_AGENT_USER=<uid>` у цикла.

**Что это отменяет.** Умолчание «отдельный uid агента, публикационных креденшл в среде сессии нет» (контракт 093, И-3/И-4) перестаёт быть умолчанием; клетки 093-3/4/7 судят режим отдельного uid явно (`ORCH_AGENT_USER=orchagent`). Текст контракта 093 (done) не переписывается — действует это решение.

**Почему.** Агентам нужен токен владельца для работы с GitHub (PR в `a3ka/Complior-mob`, чтение `a3ka/Complior-back`); раздельный uid этого не даёт. Решение «агенты под `harness`, orchagent не включается» владелец принял ранее; 2026-10-16 — «у меня должен быть единый харнесс везде», реализовано пакетом «один харнесс» (`6799dc5b5`…`139de1364`, ревью `verdicts/review/odin-harness-ops-v3.md` — accept).

**Принятый риск.** Агент с токеном владельца технически способен на всё, на что способен токен. Ограничения держатся нормой и механизмами харнесса: агентам запрещено мержить PR в Complior-mob и менять настройки GitHub; ruleset на `main` (`a3ka/Complior-mob` 25121366, `a3ka/dev-harness` 25119829); pre-push и pre-commit стражи dev-harness.
