# Решение владельца 2026-10-18: CI-предполёт — ошибки CI ловятся до PR, а не прогонами

Слово владельца 2026-10-18 ~14:30 UTC: «сделай так, чтобы таких проблем с CI больше не было». Передал консультант.

## Измеренная боль (контракт 995, CMP-MOB-001)

После первой сдачи кода implementer прошёл 4 круга исправлений (Impl995Fix1–4), и все 4 касались `.github/workflows/mobile.yml`, а не кода продукта:
1. `defaults.run.working-directory: mobile` ломал пути к `.harness/` и `mobile/` в шагах проб;
2. одноразовая копия R лежала вне `/tmp/dev-harness-verify/`;
3. `npm run lint` видел выгруженный `.harness/` в дереве;
4. секрет `PILOT_DEMO_CODE` не был заведён в репозитории.

Пять прогонов CI шли последовательно, 13:26→14:24 UTC, около часа. После этого e2e стоял до тех пор, пока владелец не завёл секрет. Каждая ошибка была видна до PR: workflow ни разу не прогоняли до PR, а предпосылки не проверили до заморозки. Модель implementer не виновата: узкие задания выполнены быстро и точно.

## Что делаем

**1. Норма — действует сразу, cognitive до механизма:**
- **Architect** в каждом контракте, который меняет CI-workflow проекта или требует секретов, variables, environments или настроек репозитория, пишет поле `ПРЕДПОСЫЛКИ:` с их полным списком.
- **Оркестратор до заморозки** проверяет, что предпосылки существуют, по GitHub API (`gh secret list`, `gh variable list`). Чего нет — приносит консультанту владельца: агентам менять настройки репозитория запрещено.
- **Implementer** перед сдачей прогоняет изменённый workflow локально в одноразовой копии: все шаги, кроме требующих железа или облака, с заглушками секретов из `ПРЕДПОСЫЛКИ`. Зелёный предполёт — часть его acceptance. Оркестратор не пушит PR без предъявленного предполёта.
- **Оркестратор**, если CI всё же упал, сначала прогоняет весь workflow локально и даёт implementer ОДНО задание на все найденные ошибки, а не по одной за прогон.

**2. Механизм — контракт слота харнесса, очередь: после 997 (Н-304), до 996:**
- `scripts/ci_preflight.sh --repo <одноразовый клон> --workflow <файл> [--job …]` прогоняет jobs workflow локально, например через `act` в docker (docker на станции есть). Секреты — заглушки из поля `ПРЕДПОСЫЛКИ`. Jobs, требующие эмулятора или облака, помечаются явно и идут отдельным станционным прогоном (эмулятор на станции есть).
- `pre_critic` / `freeze_contract` отказывают, если в контракте с CI-изменениями нет поля `ПРЕДПОСЫЛКИ:`, а `freeze_contract` — ещё и если объявленный секрет или переменная отсутствуют в репозитории проекта.
- Норма-строки в `roles/architect.md`, `roles/implementer.md`, `roles/orchestrator.md` (role-канал ПРОВОДКИ).
- Красные тесты:
  - сломанный `working-directory` в фикстурном workflow → предполёт rc 1;
  - отсутствующий секрет → заморозка rc 1;
  - контракт с правкой workflow без `ПРЕДПОСЫЛКИ:` → `pre_critic` rc 1;
  - честный случай → rc 0.

Режим проекта (996) дополнительно убирает межрепозиторную обвязку (выгрузку харнесса в CI продукта), которая была источником ошибок 1–3.

## Порядок (уточнение владельца 2026-10-18 ~15:10 UTC)

Сверка с ADR `docs/owner/adr/2026-10-03-ci.md` (этапы CI-А…Г):
- **CI-А** сделан (079/082/083), но цель «полный прогон ≤ 6 мин» не достигнута: медиана успешного прогона 13 мин.
- **CI-Б** (087) заморожен, не сделан. За ~24 ч 17–18.10 из 60 прогонов CI харнесса — 33 отменены, 16 упали, 11 успешны. Условие пересмотра ADR — «отмен > 10 в неделю».
- **CI-Г** (CI проекта генерируется из профиля тем же генератором) не сделан.

Решение:
1. **087 (CI-Б) поднят** — слот харнесса берёт его сразу после 997 (Н-304), раньше 996.
2. **Механизм предполёта не отдельным контрактом:** он объединяется с CI-Г в один предмет **«CI проекта»** (id плана `ci-proekta`) — генерация workflow проекта из профиля + локальный предполёт + проверка `ПРЕДПОСЫЛКИ:`. Предмет идёт после 996, потому что CI-Г опирается на профиль проекта.
3. Норма из раздела «Что делаем», п. 1, действует до механизма без изменений.

Порядок слота харнесса: 994 → 997 → 087 → 996 → ci-proekta.
