# Контракт 058 — шаринг agent.db omp между зонами проекта: симлинк лаунчера на дев-зону (боль пилота №1)

Статус: черновик. Минт: тег `id/CONTRACT/058` (резерв 058 исполнен, mint `42f6ec1`).
Заморозка — после круга критика (оркестратор). Работа ведётся в worktree
`/tmp/dev-harness-worktrees/775e24e1/wip-058-architect`, ветка `wip/058/architect`.

## Предмет

Боль пилота №1 (замер консультанта на копии, владелец согласен): в режиме
проекта workshop поднимает пер-проектный дом (`$PSTATE/home`, контракт 055)
с ПУСТЫМ `.omp/profiles/dev/agent/agent.db` — на первом запуске odelix-stack
владелец попал в мастер настройки и заново входил в anthropic и openai-codex.
Проверено консультантом на копии: со ссылкой на agent.db дев-зоны anthropic
даёт 20 моделей, codex 7; без неё 0/0. Цена: сорванный старт пилота, ручной
обход. «Один сетап — работает везде».

Решение (консультант + владелец): **agent.db проекта = симлинк на agent.db
дев-зоны мастерской.** Шарить базу omp разрешает сам omp (есть
auth_credential_refresh_leases), а копия разошлась бы при ротации токенов.
Лаунчер в режиме проекта делает этот симлинк сам, но ТОЛЬКО agent.db —
остальное в `$PSTATE/home` остаётся изолированным (контракт 055). Повторный
запуск не ломает существующую ссылку, а проверяет цель.

Вход — frozen/contracts/054/1 (профиль два слоя + лаунчер) и
frozen/contracts/055/1 (изоляция по ProjectId: `$PSTATE`, экспорты HOME/
HARNESS_SCRATCH/XDG_STATE_HOME, PID-лок, метеринг-баннер — всё живое и
зелёное, батареи 054/055 зелёные на HEAD). 058 НЕ правит семантик 054/055;
дельта — один новый блок в проектной ветви workshop + батарея в семье
fixtures/workshop_project/.

Один механизм:

- **М шаринг**: после экспортов М1 055 и ДО PID-лока М2 workshop (режим
  проекта, probe и живой — один код, 054 Граница-3) выводит путь дев-базы
  из СТАРТОВОГО `$ZONE` (формула 028, вычислена ДО подмены HOME) и профиля
  запуска `$PROFILE`, приводит `$PSTATE/home/.omp/profiles/$PROFILE/agent/
  agent.db` к симлинку на неё — по дереву ветвей §Инварианты.

## Frontier: границы и отвергнутые варианты

- **Граница-1 (симлинк, НЕ копия).** Ротация токенов omp пишет в agent.db;
  копия разошлась бы при первом же refresh (консультант: leases в базе).
  Отвергнуто: копия файлом — рассинхрон немедленно; отвергнуто: HARNESS_-
  env-проброс пути базы в omp — omp держит базу в `$HOME/.omp`, канал
  переназначения НЕВЕРИФИЦИРОВАН («не предъявляй меру, которую не прогнал»).
- **Граница-2 (ТОЛЬКО agent.db).** Ссылка — ровно на файл базы, не на каталог
  `agent/`, не на `.omp/`: всё прочее состояние сессии (промпт, агенты,
  конфиги) остаётся пер-проектным по слову 055. Отвергнуто: шаринг каталога —
  утечка изоляции 055 одним движением (журналы/кэш проектов смешались бы).
- **Граница-3 (цель — стартовый ZONE, второй формулы нет).** Дев-база =
  `$ZONE/.omp/profiles/$PROFILE/agent/agent.db`, где `$ZONE` — переменная,
  вычисленная формулой 028 на старте (workshop:97, ДО подмены HOME — та же
  болезнь «разрешившийся внутрь» закрыта в 028/055), `$PROFILE` — литерал
  запуска workshop:99 (`dev`). Dev-режим мастерской использует ТОТ ЖЕ старт
  → та же зона: где владелец логинился, туда проект и ссылается. Второй
  копии формулы не заводим (единый источник, §Единый источник семантик).
- **Граница-4 (шаг в probe и живом — один код; probe судит без exec omp).**
  Проба проектного режима проходит блок М и материализует ссылку так же,
  как живой старт (прецедент 054 Граница-3: STATE/METERING в обоих).
  Отвергнуто: шаг только в живом — батарея обязана судить механизм пробой,
  без стаб-omp (Н-39: вход, где дефект наблюдаем).
- **Граница-5 (существующий непустой файл НЕ трогаем — W8; пустой
  замещаем).** Регулярный файл по пути PROJDB с данными — собственность
  владельца проекта (входы, сделанные в проектной сессии до 058):
  затирание = потеря данных. Отказ тоже отвергнут: не блокирует пилот.
  Итог: непустой файл → предупреждение W8, продолжаем rc 0. ПУСТОЙ
  (size 0) регулярный файл замещается ссылкой: это ровно измеренная боль
  («пустой agent.db → мастер настройки»), данных в нём нет.
- **Граница-6 (dev-режим не меняется ни на байт).** Шаг живёт только в
  проектной ветви, между экспортом `XDG_STATE_HOME` (055 М1) и блоком
  М2/PID-лока; формула дев-зоны (:75-80) потребляется, не правится.
- **Граница-7 (объём).** НЕ входит: шаринг других артефактов omp (агенты,
  конфиги, кэш), миграция/слияние непустых локальных баз (решение владельца
  по W8-предупреждению), конкурентный доступ sqlite из двух зон (лочит сам
  sqlite; «шарить базу разрешает сам omp»), правка .omp/* (005/002 frozen),
  metering (055 Граница-5), ci.yml (раннер подхватывает семью сам).

## Инварианты

Обозначения (формулы — одна точка сборки в workshop, §Единый источник):

```
DEVDB  = $ZONE/.omp/profiles/$PROFILE/agent/agent.db        (Граница-3)
PROJDB = $PSTATE/home/.omp/profiles/$PROFILE/agent/agent.db
```

- **И-1 (дерево ветвей шага; порядок — единственная точка правды).** В
  проектном режиме (probe и живой) workshop исполняет РОВНО одну ветвь:

  | # | условие на PROJDB до шага | условие на DEVDB | действие | баннер |
  |---|---|---|---|---|
  | C1 | отсутствует | существует | `mkdir -p` родителя, `ln -s DEVDB PROJDB` | `AGENTDB: <DEVDB>` |
  | C2 | отсутствует | отсутствует | ничего не создавать (ни ссылки, ни каталогов шага) | `AGENTDB: изолирована` |
  | L1 | симлинк, readlink == DEVDB, цель жива | — | ничего (идемпотентно) | `AGENTDB: <DEVDB>` |
  | L2 | симлинк, readlink ≠ DEVDB ИЛИ цель мертва | существует | `ln -sfn DEVDB PROJDB` (чинит цель) | `AGENTDB: <DEVDB>` |
  | L3a | симлинк, readlink ≠ DEVDB, цель жива | отсутствует | не трогать (working setup не ломаем) | `AGENTDB: <readlink>` |
  | L3b | симлинк dangling (цель мертва) | отсутствует | `rm PROJDB` (проект получает свою пустую) | `AGENTDB: изолирована` |
  | R0 | регулярный файл size 0 | существует | заместить ссылкой (`ln -sf`-класс) | `AGENTDB: <DEVDB>` |
  | R1 | регулярный файл/каталог непустой | — | не трогать, W8 в stderr | `AGENTDB: изолирована` + W8 |

  Все ветви продолжают запуск (rc 0); W8 — предупреждение, не отказ
  (Граница-5). Шаг стоит ПОСЛЕ строки `METERING:` (workshop:746) и ДО
  блока М2 PID-лока — строка `AGENTDB:` печатается сразу после `METERING:`
  в том же потоке, что `STATE:`/`METERING:` (workshop:740/746).
- **И-2 (только agent.db).** После шага (любая ветвь) в дереве
  `$PSTATE/home` находится НЕ БОЛЕЕ ОДНОЙ симлинки, и её путь — PROJDB.
  Файлы дев-зоны, лежащие рядом с DEVDB (каталог `agent/`, `profiles/`,
  любое другое содержимое `$ZONE`), НЕ наблюдаемы в дереве `$PSTATE/home`.
- **И-3 (идемпотентность и цель).** Повторный запуск при валидной ссылке
  (L1) не пересоздаёт её: readlink байт-в-байт тот же, inode самой ссылки
  (stat -c %i) тот же. Устаревшая ссылка (L2) чинится на ТЕКУЩИЙ DEVDB;
  подмена цели НЕ молчит (баннер несёт фактическую цель ветви).
- **И-4 (транзитивность — боль и ротация).** Сквозная запись/чтение:
  (а) байты, дописанные в DEVDB до запуска, читаются через PROJDB после
  шага (боль: входы видны проекту); (б) байты, записанные в PROJDB после
  шага, наблюдаются в DEVDB (ротация: refresh токена уходит в дев-зону);
  (в) живой субъект (стаб-omp в PATH) пишет маркер в
  `$HOME/.omp/profiles/dev/agent/agent.db` СВОЕЙ сессии — маркер наблюдается
  в DEVDB; inode цели за симлинкой совпадает с inode DEVDB.
- **И-5 (изоляция 055 и 054 не ломаются).** Экспорты М1 055, STATE/
  METERING-строки, PID-лок М2, probe/промпт/bootstrap 054 — без дельт;
  батареи 054 и 055 (`fixtures/_krasnye_054.sh`, `_krasnye_055.sh`)
  остаются зелёными; ни один из четырёх путей 055 И-2 не приобретает
  компонент `dev-harness-sessions` (ссылка ЦЕЛИ в дев-зону — не компонент
  пути PROJDB).
- **И-6 (dev-режим).** Dev-ветка workshop не содержит ни строки `AGENTDB`,
  ни W8, ни шага (структурный якорь: весь блок — в проектной ветви после
  экспорта `XDG_STATE_HOME`).

## Модель угроз (по свойству, норма 041 формы)

ЗАЩИЩАЕТ:
- потерю входов/токенов при первом запуске проекта (боль №1): дев-база
  с входами доступна проекту через ссылку с первого старта;
- рассинхрон токенов при ротации: запись одна, точка одна (И-4б/в);
- тихое состояние шаринга: баннер `AGENTDB:` несёт фактическую ветвь
  (создан/валиден/чинен/изолирована/W8) — молчание невозможно;
- потерю данных владельца: непустой регулярный файл не трогается (R1/W8),
  валидная ссылка не пересоздаётся (L1), working setup с другой живой целью
  не ломается (L3a).

НЕ ЗАЩИЩАЕТ:
- ЗЛОНАМЕРЕННЫЙ проект, получивший право записи в общую базу владельца:
  это АРХИТЕКТУРНОЕ решение (шаринг разрешает сам omp, слово владельца);
  изоляция секретов от проекта — отдельный предмет, если боль измерена;
- конкурентный доступ sqlite из двух зон одновременно (лочит sqlite);
- TOCTOU между проверкой и `ln` (одно окно, класс 055 «гонка стартов»);
  цена — редкая гонка двух запусков одного проекта, лок М2 055 её уже
  сужает до живой сессии;
- унаследованный `HARNESS_SESSION_HOME`/`HARNESS_SCRATCH`, искажающий
  стартовую формулу `$ZONE` (класс 028: формула на старте, не 058; в
  чистом окружении запускающего формула даёт зону мастерской);
- подделку слоя проекта/дев-зоны владельцем машины (TCB-класс 040).
