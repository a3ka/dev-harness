## Предмет

Харнес поднимает **свой** прокси учёта трафика моделей: OpenAI-совместимый
ретранслятор с потолком расхода и журналом вызовов, без внешних зависимостей
(`node:` builtins только), со своей базой на файловой системе. Дом секретов уже
развязан с фабрикой (6a8480b); этот контракт закрывает вторую половину автономии —
учёт. Решения кругов 1 (01b4dc1) и 2 (b67dd2f) закрыты в тексте и помечены [К1-N]/
[К2-N]; повторённые причины — по арбитражу `proksi-rotaciya-passthrough-live.md`
(4c03aa7, обязательный минимум исполнен дословно).

1. **Прокси-ретранслятор** `scripts/proxy/metering_proxy.ts` (запуск
   `node scripts/proxy/metering_proxy.ts`): OpenAI-совместимый; ЛЮБЫЕ пути
   провайдера методами GET и POST [К1-5]; запрос клиента доходит до upstream
   ДОСЛОВНО: метод, путь, ТЕЛО байт-в-байт, content-type, x-request-id
   [К4-6]; ответ upstream возвращается клиенту КАК ЕСТЬ: статус, тело
   байт-в-байт, `content-type` (сверяются именно эти три; прочие заголовки
   в минимум не входят — арбитраж). Конфиг — путь аргументом
   `--config <файл>`; фикстуры пишут свой конфиг с ПОРОЖДЁННЫМИ при каждом
   прогоне значениями (токены, provider id, model id, upstream-пути) [К1-5].
2. **Приписывание роли токеном** [К1-1, К2-1]: токены живут ТОЛЬКО в доме
   секретов (`~/.config/dev-harness/secrets.env`, строки `METERING_TOKEN_<ROLE>=…`);
   в репозитории буквальных токенов НЕТ НИГДЕ — барьер ветви (з) грепает
   ЛЮБЫЕ файлы репозитория на шаблон значения секрета, не только конфиги [К2-2].
   `.omp/models.yml` ссылается `${METERING_TOKEN_<ROLE>}`. Прокси строит карту
   токен→роль чтением конфигурации НА КАЖДЫЙ запрос; кэш на старте запрещён и
   ДОКАЗЫВАЕТСЯ ветвью ротации (арбитраж): один живой процесс (тождество pid
   утверждается) — T1 принят → секрет перезаписан (T1 удалён, T2 порождён) →
   T2 принят → T1 даёт 401 без новой строки журнала; реализация со стартовым
   кэшем падает на шаге T2. Неизвестный токен — 401, строки нет.
3. **Журнал** `data/metering/calls.jsonl` — append-only, строка на вызов, ВСЯ
   схема обязательна и сверяется [К2-6]: `ts, role, provider, model, path,
   tokens_in, tokens_out, usd, latency_ms, status, request_id` (коррелятор —
   арбитраж [К1-6]: значение заголовка `x-request-id` вызова, порождённое
   вызывающим; прокси доносит его в строку). Деньги — ЦЕЛЫЕ микро-доллары
   (int64 minor units). Пишется и для неуспешного вызова (обрыв: usage нет →
   tokens 0, usd 0 — записанная граница). НЕ пишется для unpriced-модели и
   неизвестного токена — ветви требуют ОТСУТСТВИЕ строки [К2-6]. Направление
   производности доказывается: `--rebuild-budget` пересобирает `budget.json`
   из журнала; барьер удаляет budget.json, запускает пересборку и сверяет.
   `data/metering/` — локальное состояние, в `.gitignore` [К1-С3].
4. **Тарификация** [К2-3]: цены в `config/metering.json` per provider+model:
   `per_m_tokens: { in: <int микро-USD>, out: <int> }`; формула закреплена:
   `usd = (tokens_in*in + tokens_out*out) / 1_000_000` в целых микро-USD
   (округление вниз — консервативно для бюджета? НЕТ — вверх: списываем не
   меньше начисленного провайдером; выбор закреплён: ОКРУГЛЕНИЕ ВВЕРХ).
   Барьер предъявляет вызов с ИЗВЕСТНЫМИ порождёнными usage и тарифом и
   сверяет вычисленный ненулевой ЦЕЛЫЙ usd с формулой. Модель без цены —
   503 `model_unpriced` ДО запроса, upstream не вызван, строки нет [К1-2, К2-6].
5. **Потолок ДО запроса, списание ПОСЛЕ** [К1-8]: `ceilings: { "<provider>":
   { "usd_per_month": <int микро-USD> } }`; период — КАЛЕНДАРНЫЙ МЕСЯЦ UTC,
   `periodAt(ts)` чистая функция UTC `YYYY-MM`, вызывается НА КАЖДОМ запросе
   (selftest на стыке месяцев фиксированным временем). Исчерпан — 402 с
   состоянием бюджета ДО запроса; перерасход на один вызов — записанная граница.
6. **Запуск лаунчером — ВЫНЕСЕН v2** (решение владельца 2026-08-20) в отдельный
   будущий контракт режимов прокси: healthz-переход `workshop --check-metering`,
   окна `W_healthz`/`W_probe`, все исходы cold-start и команда
   `check_metering.sh --cold-start`. Недоступный upstream НЕ повод гибнуть —
   остаётся предметом ЭТОГО контракта ветвью (д): пер-запросный 502 со строкой
   журнала (арбитраж proksi-cold-start, замер референса).
7. **Живой маршрут omp — ВЫНЕСЕН v2** (решение владельца 2026-08-20) в тот же
   будущий контракт режимов: `check_metering.sh --live` с порождённым uuid и
   коррелятором через ЖИВОЙ omp, замер канала заголовков omp. Коррелятор
   `request_id` в схеме журнала и его дословная доставка клиентским каналом —
   предмет ЭТОГО контракта ветвью (м).

## Критерий готовности

1. `node scripts/proxy/metering_proxy.ts --selftest` → 0: `periodAt` на стыке
   месяцев; приписывание токена; свёртка журнала в бюджет (int64 микро-USD);
   append-only запись; формула тарификации с округлением вверх.
2. `bash scripts/check_metering.sh` → 0 с подставным upstream. ПЯТНАДЦАТЬ
   ветвей — (а), (б), (в), (в2), (г), (г2), (д), (е), (ж), (з), (и), (к1),
   (к2), (л), (м) — каждая отдельным красным вызовом собственной фикстуры
   [К1-4], все порождаемые значения порождаются при каждом прогоне [К1-5]:
   - (а) прокси не поднят → код 2;
   - (б) неизвестный ПОРОЖДЁННЫЙ токен → 401, строки нет;
   - (в) составной POST [арбитраж, К4-1, К4-6, К5-1, К5-2]: порождённые
     provider/model/путь ≠ chat/completions, порождённые ТЕЛО запроса (не-JSON,
     порождённые байты), request content-type ≠ application/json и заголовок
     x-request-id; upstream-счётчик фиксирует метод POST, путь, ТЕЛО байт-в-байт,
     REQUEST content-type и request_id — все пять дословно; upstream отвечает
     порождёнными статусом ≠200, response content-type ≠ application/json,
     телом-не-JSON → клиент получил байт-в-байт тело+статус+content-type; строка
     ПОЛНОЙ схемы (одиннадцать полей): роль по токену, usage из ответа,
     ненулевой ЦЕЛЫЙ usd по формуле. ОБМАННОЕ ПРЕДЪЯВЛЕНИЕ [арбитраж, К5-2,
     К8-1]: стаб с пересборкой ответа из usage — краснеет на ЭТОЙ ветви
     (наблюдаем на POST: тройка ответа искажена);
   - (в2) составной GET [арбитраж, К4-1, К5-1, К6-2]: порождённый путь,
     порождённое тело (GET может нести тело — HTTP это позволяет), request
     content-type и x-request-id; upstream-счётчик фиксирует ДОСЛОВНО все
     пять полей, как и POST; нетривиальная тройка ответа байт-в-байт; строка
     полной схемы; ОБМАННОЕ ПРЕДЪЯВЛЕНИЕ [К8-1]: стаб POST-only ретранслятора
     (GET превращает в POST) — краснеет ИМЕННО ЗДЕСЬ (его дефект наблюдаем
     только на GET-входе); стаб пересборки (в) краснеет и здесь.
   - (г) составной переход потолка [К6-4]: бюджет ниже потолка, но вызов
     известной порождённой стоимостью его ПЕРЕСЕКАЕТ → запрос upstream
     ПРОХОДИТ (счётчик вырос), ответ возвращается клиенту КАК ЕСТЬ, строка
     пишется с полной стоимостью, budget.json после — СВЫШЕ потолка.
     Красное: стаб, подменяющий ответ на 402 и не пишущий стоимость,
     валится сверкой ответа и суммой бюджета;
   - (г2) исчерпанный потолок → 402 ДО запроса (счётчик upstream не вырос);
     ТЕЛО 402 несёт состояние бюджета {period, provider, spent_usd, limit_usd}
     ДО запроса [К7-6]; этот отказ ПИШЕТСЯ строкой полной схемы с usd=0
     [К7-6]. Красное: стаб с пустым 402 и без строки — валится;
   - (д) обрыв upstream → клиенту 502 [К7-7]; строка ПОЛНОЙ схемы (все
     одиннадцать полей, включая role, provider, model, path, latency_ms,
     request_id), status=502, tokens/usd = 0;
   - (е) маркер append-only жив после прогона; удалённый budget.json
     пересобран `--rebuild-budget` и равен свёртке;
   - (ж) модель без цены → 503 ДО запроса, upstream не вызван, СТРОКИ НЕТ;
   - (з) в РЕПОЗИТОРИИ нет буквальных значений секретов: grep шаблона
     значения секрета по ВСЕМ файлам репозитория — пуст [К2-2];
   - (и) РОТАЦИЯ [арбитраж, К4-2]: собственный файл секретов фикстуры,
     доступный прокси через цепочку `--config` (реальный дом секретов НЕ
     трогается); один живой процесс (тождество pid утверждается); T1 приписан
     роли R → строка с R сверена; файл секретов перезаписан: T1 удалён, T2
     приписан ТОЙ ЖЕ роли R; T2 принят → строка с R сверена; T1 даёт 401 и
     НОВОЙ строки нет. Красное: реализация со стартовым кэшем падает на T2.
   - (к1) builtins-only, импорты [К6-1, К7-1]: grep импортов исходника вне
     `node:` — пуст; СОБСТВЕННОЕ красное: копия ТОЛЬКО с vendor-импортом
     (без внешних процессов) — ветвь красная;
   - (к2) builtins-only, процессы [К6-1, К7-1]: grep exec/spawn внешних путей
     — пуст; СОБСТВЕННОЕ красное: копия ТОЛЬКО с внешним `curl` (без
     сторонних импортов) — ветвь красная;
   - (л) границы периода и конфигурации [К7-3, К7-4, К7-5]:
     - период на каждом запросе: времЕна запросов контролируемы фикстурой
       (инъекция времени — свойство, реализация свободна); ОДИН живой процесс
       делает два вызова по РАЗНЫЕ стороны границы UTC-месяца → строки в
       РАЗНЫХ периодах; потолок первого периода исчерпан → вызов во втором
       ПРОХОДИТ [К7-3]; красное: кэш периода на старте — второй вызов
       записывается в первый период и/или 402 — ветвь красная;
     - оси тарифа: ДВА provider с ОДНОЙ model, цены/потолки РАЗНЫЕ и
       порождённые [К7-4]: вызов P1 списывает по цене P1 и видит потолок P1,
       вызов P2 — по P2; красное: прокси, ищущий цену/потолок только по
       model, валится расхождением сумм;
     - int64: тариф и usage порождены так, что usd в микро-USD ПРЕВЫШАЕТ 2^53
       [К7-5]; строка несёт ТОЧНОЕ целое (сверка строки, не числа с плавающей
       точкой); красное: число IEEE-754 теряет единицы — ветвь красная.
   - (м) заголовок-коррелятор [v2: живой канал omp вынесен]: `x-request-id` от
     клиента доходит до upstream ДОСЛОВНО и в строку журнала ДОСЛОВНО — тем же
     каналом, которым ходит живой omp (Bearer + x-metering-model +
     x-request-id); красное: копия прокси, теряющая коррелятор в журнале.
3. `npm run check:antiplacebo` → 0; `check:ci-parity`: в CI — только
