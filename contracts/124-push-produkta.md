## Предмет

Одна дверь `scripts/push_product.sh` (bash, офлайн-судимая батареей):

    bash scripts/push_product.sh --repo <клон> --branch <ветка> --sha <sha40> --title <заголовок> [--body-file <файл>]

Порядок суждения, побеждает ПЕРВАЯ красная (rc 1 — `push_product ОТКАЗ: <причина>`,
rc 2 — `push_product NEEDS_ENV: <причина>`, одной строкой stderr):

1. г1 форма argv: только пять флагов выше, каждый не более раза, у каждого
   значение; иное — «аргумент вне грамматики: …»; нет любого из четырёх
   обязательных — «нет аргумента: <флаг>».
2. г2 значения (замкнутые алфавиты, сравнение литеральное):
   ветка `^[A-Za-z0-9][A-Za-z0-9._-]*(/[A-Za-z0-9][A-Za-z0-9._-]*)*$`, ≤200 байт,
   без `..`, без хвоста `.`/`.lock` у сегмента, не `refs/…` — иначе «ветка вне
   грамматики: …» (алфавит не содержит `+`, `:`, пробела — refspec из значения
   не собирается); ветка ∈ {main, master, HEAD} — «ветка защищена: <ветка>»;
   sha `^[0-9a-f]{40}$` — иначе «sha вне грамматики: …»; заголовок непуст и без
   байтов 0x01–0x1F, 0x7F — иначе «заголовок вне грамматики: …»; файл тела, если
   задан, — читаемый обычный файл.
3. г3 среда: нет git/jq/gh в PATH — rc 2 «нет <инструмент>»; `gh auth status
   --hostname github.com` не rc 0 — rc 2 «gh не авторизован (gh auth status)».
4. г4 канон — ТОЛЬКО эффективный `.git.value.canonicalRemote` профиля клона
   через `HARNESS_PROJECT_LAYER_ROOT=<корень клона> bash <корень двери>/scripts/profile_resolver.sh --repo <корень клона>`
   (тот же источник и то же окружение, что у gitw 996 К17, `scripts/gitw:164`;
   fallback на origin клона или константу нет): нет
   `harness.project.json` — «профиль проекта отсутствует: …»; отказ резолвера —
   «профиль битый: …»; канон, JSON-представление которого не равно
   `"https://github.com/<владелец>/<имя>.git"` (владелец `[A-Za-z0-9-]+`, имя
   `[A-Za-z0-9._-]+`; управляющие байты в JSON-форме экранированы и в класс не
   входят), — «канон вне грамматики двери: …». Произвольный URL двери не
   передаётся (флага нет).
5. г5 харнесс — не продукт: `<владелец>/<имя>` канона равен (ASCII без учёта
   регистра) слагу канона самого харнесса — «репозиторий харнесса — не продукт:
   … (обмены харнесса — scripts/gitw)». Корень двери — каталог над `scripts/`,
   где лежит дверь (не cwd, не константа); канон харнесса — тот же резолвер:
   `HARNESS_PROJECT_LAYER_ROOT=<корень двери> … --repo <корень двери>`; слаг —
   из JSON-формы `"ssh://git@github.com/<владелец>/<имя>.git"` (форма харнесса на
   HEAD) либо `"https://github.com/<владелец>/<имя>.git"`, классы как в г4. Отказ
   резолвера на корне двери или иная форма — rc 2 «профиль харнесса не
   резолвится: …» / «канон харнесса вне грамматики: …».
6. г6 `git rev-parse HEAD^{commit}` клона == `--sha`, иначе «HEAD клона ≠ --sha: …».
7. г7 push — refspec несёт sha-литерал, не HEAD и не имя ветки клона:
   `git -C <клон> -c credential.helper= -c 'credential.helper=!gh auth git-credential' push <канон> <sha>:refs/heads/<ветка>`;
   без `--force`, `+`, удаления, `--all/--mirror/--tags`. Отказ удалённого
   (не fast-forward и пр.) — «push отказан: …» (вывод git санирован).
8. г8 PR: `gh pr list --repo <владелец>/<имя> --head <ветка> --base main --state open --json url --jq …`
   — открытый есть → он; нет → `gh pr create --repo … --base main --head <ветка>
   --title <заголовок> (--body-file <файл> | --body "")`. Отказ gh — «PR не создан: …».

Успех — rc 0 и stdout РОВНО одна строка:
`push_product ОК: <владелец>/<имя> <ветка> <sha> PR <url> создан|существует`.
Токен gh дверь не читает и не передаёт: ни в argv, ни в окружение, ни в вывод,
ни в конфиг клона — git берёт его у хелпера `gh auth git-credential`.

## Инварианты

1. Цель push и PR — только канон профиля клона в грамматике г4; не харнесс (г5).
2. Только ветка вне {main, master, HEAD}; никогда force, `+`, удаление; из всех
   ref'ов всех удалённых репозиториев меняется ровно `refs/heads/<ветка>` канона.
3. Запушенный объект = `--sha` = HEAD клона в момент проверки.
4. PR идемпотентен: открытый PR пары `<ветка>→main` переиспользуется, base = main.
5. Токен gh не виден в выводе, argv и окружении вызовов, файлах клона.
6. Нет gh / нет входа gh — rc 2 без push; rc 0 только при запушенной ветке и PR.
7. Порядок г1→г8 фиксирован; каждый отказ — одна строка с префиксом причины.

## Модель угроз

ЗАЩИЩАЕТ:
- от пуша в чужой репозиторий: цель берётся только из профиля клона, origin клона и произвольный URL игнорируются
- от пуша в харнесс через продуктовую дверь: слаг канона сверяется со слагом харнесса без учёта регистра
- от перезаписи и удаления истории: refspec собирается дверью из sha-литерала, force, плюс и удаление невыразимы
- от пуша в main и master: защищённые имена и refspec-синтаксис в ветке отвергаются до любого обращения к сети
- от пуша непроверенного кода: запушен ровно заявленный sha, равный HEAD клона в момент проверки
- от дубля PR: открытый PR той же ветки в main переиспользуется, повтор вызова идемпотентен
- от утечки токена: дверь не читает токен, git получает его у хелпера gh, канарейка проверяется в выводе и следах
- от тихого зелёного без пуша: отсутствие gh или входа даёт rc 2, успех требует запушенной ветки и PR
- от подлога строк вывода: управляющие байты заголовка и значений отвергаются или гасятся при печати

НЕ ЗАЩИЩАЕТ:
- от вызова двери изолированным субагентом: тот же пользователь ОС и gh-credential, различение cognitive-only, ущерб ограничен новой веткой и PR без merge
- от профиля клона, переписанного автором клона: канон берётся из дерева, которое пушится, ловец — судьи по зоне и табло PR оркестратора
- от веток, защищённых только правилами GitHub кроме main и master: их охраняет правило репозитория
- от отличия двойников от настоящего GitHub: живой транспорт судится первым живым пушем приёмки, не батареей
- от продуктовых клонов без профиля 112: дверь отказывает именованно до доставки профиля в клон

ПРОВОДКА-ЭНФОРСМЕНТ: дверь — механизм (guard-канал: батарея судит её на
двойниках); «кто вызывает дверь» механически не различим (Рассмотренные варианты,
г) — поведенческая норма role-каналом оркестратора. Подключение батареи в CI —
интеграционный коммит оркестратора; абзац, принимающий красный provodka до него,
не вводится.

## Приёмочный критерий

- `bash fixtures/workshop_project/push_produkta_124/red_124.sh --cell t01` → красная: предмет отсутствует

- Дано: база (двери нет). Когда: `bash fixtures/workshop_project/push_produkta_124/red_124.sh`.
  Тогда: rc 1; клеток 57, красных 27 (Д1, т01–т26 «предмет отсутствует»),
  зелёных 30 (С01–С30 «ПОЙМАН»).
- Дано: честная модель. Когда: `bash fixtures/workshop_project/push_produkta_124/red_124.sh --model`.
  Тогда: rc 0, клеток 57, зелёных 57.
- Дано: реализация `scripts/push_product.sh`. Когда: `bash fixtures/workshop_project/push_produkta_124/red_124.sh`.
  Тогда: rc 0, клеток 57, зелёных 57. Негативная пара — в том же прогоне:
  С01–С30 судят модель с одной подменённой строкой на привязанной т-клетке,
  каждая такая т-клетка красна (rc прогона 0 только при «ПОЙМАН» у всех 30).
- Дано: реализация и роль. Когда: `bash scripts/check_provodka.sh . contracts/124-push-produkta.md`.
  Тогда: rc 0 после интеграционного коммита проводки; до него rc 1 «guard не подключён».
- Дано: авторская пачка. Когда: `bash scripts/pre_critic.sh contracts/124-push-produkta.md`.
  Тогда: rc 0.
- Живая приёмка (после реализации, вне батареи; сеть): клон продукта с профилем
  112 в HEAD. Когда: оркестратор `bash scripts/push_product.sh --repo <клон>
  --branch <ветка> --sha <HEAD> --title <…>`. Тогда: rc 0, строка ОК с URL PR;
  `gh pr view <url> --json baseRefName,headRefOid` → base main, head = sha;
  повтор той же команды — rc 0 «существует». Негативная пара: `--branch main` —
  rc 1 «ветка защищена: main», ref main продукта не изменился.

## Остаточные риски

- cognitive-only: «дверь вызывает только оркестратор» — механизма нет (тот же
  пользователь ОС и gh-credential); ловец — табло PR оркестратора
  (`ops/server/user/orch-tablo` перечисляет PR Complior-*) и merge-гейт
  консультанта/владельца; ущерб ограничен инвариантами 1–6.
- До доставки профилей 112 в клон продукта дверь отказывает «профиль проекта
  отсутствует» — ветки, рождённые до профиля, пушит прежний маршрут; ветка
  доставки профиля сама несёт профиль и пушится дверью.
- Пересборка ветки (rebase) требует новой ветки и нового PR: force дверь не делает.
