# 997 — orch-loop: факт запуска переживает удаление метки

## Предмет

Н-304: после удаления `orch-restart.scoped` уже отработавшая в scope сессия была названа запуском без потолка; цикл остановился, станция простаивала ~10 ч (17.10 23:43 → 18.10 09:56). Результат 997: факт запуска в scope хранится вне удаляемого файлового имени, маркерный рестарт действительно запускает следующую сессию, отсутствие подтверждения не разрешает запуск без потолка, одновременно живёт один цикл. Чистый кодовый cutover, не новая политика рестартов.

КОНТЕКСТ: `docs/owner/2026-10-18-tri-slota.md` §1 — Н-304 первая задача слота харнесса; три слота разрешаются консультантом только после исправления в main и штатного рестарта станции.
КОНТЕКСТ: `docs/owner/2026-10-18-tri-slota.md` §3 — кап 3 круга; первый список блокеров полный, поздние новые требования — советы, нарушение принятого требования блокирует.
КОНТЕКСТ: `NABLIUDENIA.md` Н-304 — журнал scope доказал исполнение (1h23m CPU), удаливший метку не установлен; это не расследование виновника.

## Frontier и выбор

Н-304 (~10 ч простоя):

- `systemctl show/is-active SESSION_UNIT` после возврата — отклонён: завершённый transient scope мог уже исчезнуть.
- Перенос `.scoped` в state-dir — отклонён: меняет вероятность уборки, не зависимость от unlink.
- Файл + systemd + история — отклонён: добавляет ретенцию/гонку GC.
- **Выбран анонимный pipe → память родителя**: подтверждение внутри scope до exec, отдельно от stdout; unlink и GC не отзывают байты.
- Singleton: **flock**, не pgrep/PID-файл/check-then-start (гонка, stale PID). Требование владельца — без второго экземпляра; lock-inode вне verify, без unlink.
- Retry отказа scope — отклонён: **ноль повторов**, И-5. Н-189 (потеря сессии #11, ручное восстановление): сохранить общий EARLY_MAX=3, не бесконечный цикл.

Н-266 (~45 мин разбора 085/093): только частные PATH-подмены, без production test-mode. Н-211 (8 ч простоя): нормы слотов/кругов и другие двери вне предмета.

## Инварианты реализации

1. Каждый запуск по-прежнему проходит `systemd-run --user --scope` с `MemoryMax=$ORCH_MEM_MAX` и `MemorySwapMax=0`; ни одна ветка не запускает AGENT_CMD напрямую после отказа. Без подтверждения именно ЭТОГО запуска — rc 1 немедленно, без повторов. Значение по умолчанию 32G, нормализация user-bus, выбор uid, снятие credentials в опциональном режиме и reaping сохраняются.
2. Вместо RAN — отдельный одноразовый канал текущего запуска. Команда внутри scope пишет фиксированное `SCOPED\n` до exec агента; родитель получает подтверждение в память. Сравнение буквальное, токен не берётся из stdout агента, файла, rc агента или истории предыдущего запуска. Перед exec агента канал записи и lock-fd закрываются. Ошибка подготовки/чтения канала — отказ, не fallback. Результат команды хранится отдельно от подтверждения; выход агента rc 1/137 не объявляется отказом создания scope. `.scoped` больше не создаётся/читается production-кодом; legacy alias не оставляется.
3. Stdout/stderr и stdin агента остаются исходными (TUI не направляется в receipt). Запуск через shell command-substitution допустим только с отдельным fd подтверждения и возвратом stdout на исходный терминал. Сигналы наблюдателя и reaping по-прежнему достигают агента; следующая сессия начинается после завершения предыдущей. `model.sh` демонстрирует канал, но не заменяет production-обвязку.
4. Подтверждённая сессия пишет payload `scope подтверждён (канал запуска); файловая метка не используется` с обычным префиксом номера сессии/времени. При отсутствии подтверждения payload `запуск в scope не подтверждён — запуск без потолка запрещён (И-5, контракт 093)`. Второй диагноз намеренно не утверждает, что юнит точно никогда не создавался: таких сведений нет. Удаление старой метки при живом/отработавшем scope не даёт ложного «ресурсный предел не создан». Последняя фраза удаляется как production-диагноз, соответствующие потребители 085/093 мигрируются.
5. Singleton — один цикл на HOME пользователя: `flock -n` на `$HOME/.local/state/dev-harness/orch-loop.lock`, до изменения состояния рестарта/наблюдателя/сессии. Отказ второго экземпляра: rc 1, payload `ОТКАЗ: orch-loop уже запущен`, без запуска второго агента и без гашения первого. Lock держится во время живой сессии и штатного перехода; собственный exec не должен приниматься за конкурента. Швы MARK/LOG не меняют ключ блокировки. Не доверять env-флагу «lock уже взят». Открытие/взятие lock, если невозможно, — именованный отказ до сессии. После выхода самостоятельный новый запуск снова разрешён.
6. Перезапуск по MARK/GO и отсутствие файла-свидетеля — независимые события. Само исчезновение `.scoped` не является приказом перезапуска: штатный `/exit` без MARK всё ещё останавливает цикл. Ранний маркер и падение используют прежний общий счёт; смена причин его не обнуляет. После трёх ранних нештатных исходов (EARLY_MAX=3) нет четвёртого запуска; штатные долгие сессии сохраняют прежний сброс счёта.

## Приёмочный критерий

Команды из корня принятого дерева. `probe.sh` возвращает 0 при совпадении ожиданий, 1 при нарушении поведения, 2 при недоступном входе; печатает каждый выполненный сценарий, реальные rc/число запусков и итог непустой выборки. Все процессы — настоящие bash/игрушечный omp в одноразовой копии со своей `.git`; systemd-run и systemctl всегда подменены. Станция не участвует.

- `bash fixtures/ops_server/orch_loop_997/probe.sh --cases` → красная: RESTART_COUNT

Дано до-997 субъект; когда указанная команда; тогда rc 1: потерянная метка не даёт второй сессии и второй процесс не защищён lock. Это красное предъявление до реализации, не обещание зелёного старого кода.

- Дано реализованный субъект; когда та же команда; тогда rc 0: `marker_removed` реально удаляет существовавшую `.scoped` во время живого агента, ставит MARK, ждёт сигнал от наблюдателя, наблюдает завершение первого и старт второго; итог loop rc 0, запусков 2, ложного отказа нет. `removed_crash` — тот же unlink и rc 7 без MARK, затем новая сессия; не используется exit-code как свидетель scope.
- Дано scope-отказ до команды; когда `probe.sh --case scope_refused`; тогда проба rc 0, loop rc 1 с указанным честным payload, вызов scope ровно один, запусков агента ноль. Парный положительный контроль — `probe.sh --case clean_exit`: проба rc 0, loop rc 0, один scoped-агент, без рестарта. В полном `--cases` маркерная проба и отказ предъявляются также опциональному пути другого uid через shim sudo; это проверка проводки, не доказательство ОС-изоляции uid.
- Дано завершившийся первый scope и отказ второго; когда `probe.sh --case second_refused`; тогда проба rc 0, loop rc 1, создан ровно один агент и сделаны две попытки scope. Свидетель первого запуска не разрешает второй; отсутствие подтверждения не запускает retry.
- Дано первый живой цикл; когда `probe.sh --case duplicate`; тогда проба rc 0, второй loop rc 1 с singleton-payload, первый остаётся жив до release, всего один агент. Эта же проба в новой одноразовой среде допускает первый запуск (положительный контроль); `marker_removed` проверяет переход между сессиями владельца lock без самоблокировки.
- Дано чередование ранний MARK / crash / ранний MARK; когда `probe.sh --case bounded`; тогда проба rc 0, loop rc 3, попыток scope и агентов ровно 3, четвёртого нет. Положительная пара — `marker_removed`: один ранний рестарт допускается. Проверяется число реально исполненных процессов, не только слово «предел»; timeout не считается успешной поимкой.
- Правило различимости: `bash fixtures/ops_server/orch_loop_997/probe.sh --matrix` → rc 0. Честная исполняемая модель зелена на каждом сценарии; обманные формы отвергнуты только по назначенной наблюдаемой причине. Привязки и измеренный census — код `probe.py`, не таблица прогнозов в контракте. Синтаксическая авария/timeout/невалидный вызов инструмента не засчитывается как поимка.
- Правило неизменности соседних контрактов: после миграции субъекта и его потребителей `bash fixtures/_krasnye_072.sh`, `bash fixtures/_krasnye_080.sh`, `bash fixtures/ops_server/red_cikl_perezapuska_085.sh` → rc 0 в одноразовой копии по их штатным швам. Для 093 — существующий CI-ключ `check:granica-ispolneniya-093-family-selftest` через CI-only дверь второго uid → rc 0. Локально на станции root-дверь 093 НЕ запускать. Изменение тех тестов допускается только для новой диагностики/мутации удалённого RAN, а не удаления отказа без потолка или его отрицательного контроля.
- Дано собранная ветка; когда `bash scripts/run_ci_lane.sh check:orch-loop-997`, `bash scripts/gen_ci_steps.sh --check`, `bash scripts/check_provodka.sh "$PWD" contracts/997-orch-loop-metka-perezapuska.md`; тогда каждая rc 0. Lane выполняет новую пробу целиком, включая модели. Отсутствие lane — именованный отказ штатного runner; одной декларации guard недостаточно.

## Модель угроз

ЗАЩИЩАЕТ:
- От потери факта исполненного scoped-запуска при unlink старого имени, от смешения exit-code агента с отказом launcher и повторного использования свидетельства предыдущей сессии.
- От второго обычного запуска цикла с тем же HOME при живом первом; от бесконечного повтора отказа scope и сброса общего предела при смене ранних причин.

НЕ ЗАЩИЩАЕТ:
- От намеренно враждебного процесса того же uid, удаляющего сам lock-inode, подменяющего systemd-run/код цикла или атакующего fd через procfs; от гибели всего host/tmux/user-manager. Каталог lock — операционное состояние, не граница между одинаковыми uid.
- От удаления самих MARK/GO/PGID: это другие свидетели и другой класс отказа. Не меняет условия двери 072/080 и не делает удаление `.scoped` самостоятельным restart-триггером.
- От недостаточности реального kernel MemoryMax или регрессии интерактивного терминала, которую PATH-модель не воспроизводит. CI-пробы доказывают вектор и поведение процессов; фактический cgroup и TUI проверяет консультант при поставке ниже.

Конформный вход: Linux/bash, доступные flock/pgrep, штатная грамматика ORCH_* (абсолютные частные пути, положительный целый EARLY_MAX, числовые задержки), доверенный systemd-run, который исполняет команду только после успешного создания scope с переданными свойствами. Валидный контрпример = расхождение на таком входе, сохраняющееся при замене значений путей/номеров сессии; подмена протокола systemd-run, произвольный shell-код в конфиге и общий злонамеренный uid не являются моделью Н-304. Оракул ожиданий снимается в память до субъекта; журналы процессов — наблюдения, не перепрочитанная спецификация. Payload журнала сравнивается отдельным полем целиком. Новый production-парсер чужих структурных полей не вводится: receipt — единственный фиксированный литерал доверенной команды, не JSON/TSV/regex-парсер.

Это объявленный операционный шаг, не право архитектора/исполнителя менять живую станцию. До него код может быть done в репо, но условие этапа 2 решения владельца НЕ выполнено.

1. Консультант фиксирует принятый main SHA и штатно завершает старый цикл без второго ведущего экземпляра; не запускает тестовую модель на станции. Из принятого чекаута под пользователем станции выполняет `HOME=/home/harness bash ops/server/install.sh user`. Root-часть в 997 не меняется; если verify обнаружит её дрейф — отдельный root-вызов `sudo bash ops/server/install.sh root` по процедуре README, не самовольная правка установленного файла.
2. `HOME=/home/harness bash ops/server/install.sh verify` → rc 0, «сверка: 9/9». Дополнительно `sha256sum ops/server/user/orch-loop /home/harness/bin/orch-loop` даёт одинаковые хеши. Расхождение — отказ поставки, не green с оговоркой. Для иной машины подставляется настоящий HOME установки, не перенаправленный HOME omp-зоны.

Консультант запускает установленный цикл один раз в существующей tmux-панели; наблюдает рабочий TUI (ввод/вывод), один PID ведущего агента, его cgroup с конечным MemoryMax (по умолчанию 34359738368) и MemorySwapMax=0.
