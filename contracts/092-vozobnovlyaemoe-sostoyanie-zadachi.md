## Диагноз по коду

- **Д1. Носителя состояния нет.** Состояние рассыпано по прозе HANDOFF, контексту модели и git-фактам; «продолжает тот же предмет» после рестарта зависит от того, что оркестратор успел записать прозой ДО краха; следующий шаг и ожидание теряются (Н-211).
- **Д2. Ожидание CI = повторные вызовы модели** (ci_diag rc 3 → модель спрашивает снова); ожидание не зафиксировано нигде, кроме прозы, и не переживает рестарт.
- **Д3. Круги судьи считаются файлами вердиктов и прозой контрактов.** «Повторный FAIL — новый круг; редактура файла — не обязательно новый круг» (докс 1.8) не механировано; после рестарта счёт восстанавливается глазами.
- **Д4. «Опубликовано» и «закрытие не завершено» неотличимы одной лампой**; повторная операция публикации после рестарта не имеет идемпотентного ключа (докс 1.12: «done повторяет уже выполненный merge после частичного сбоя» — названный риск).
- **Д5. Недоступный GitHub = отказ утилит (rc 2) и недоказуемость HEAD==origin/main** — локальное восстановление связано с транспортом (докс 1.12: «orch_status недоступен без GitHub → восстановление опять зависит от транспорта»).
- **Д6. Ротация HANDOFF ручная** (Н-209); предмет 091 спроектирован и round2-accept, но не в main; «HANDOFF — производная orch_status» (строка 091 сопоставления докса) не чем собирать.

## Решения

- **Р1 Носитель — один файл вне дерева.** Шов `ORCH_STATE_DIR` (умолчание `/tmp/dev-harness-verify/orch-state/`): state.tsv + events.tsv. Не коммитится, не мутирует стерегомое дерево (porcelain остаётся пустым; Н-85, правило 8). Отвергнуто: состояние в репо — каждая мутация коммитом, гонки с check_staged и гейтом «porcelain пуст» двери рестарта. Выживание рестарта СТАНЦИИ не заявляется (см. Модель угроз): «Выход» требует перезапуска сессии, не станции; git-факты переживают всё.
- **Р2 Семь полей состояния** (грамматика И-2): task, stage, candidate, last_proven, waiting, next_step, pub_state. Закрытые алфавиты значений; поле «задача» — стабильный id из столбца id plan.tsv ЛЮБОГО поколения либо NNN контракта (реестр меняется — состояние нет; «техническая связь плана из 1.5» без власти текущей/следующей пары).
- **Р3 Круги — события.** Журнал events.tsv append-only; круг = round-fail-событие с ref = `<путь вердикта>@<blob-sha>`: РЕДАКТУРА файла меняет блоб только при новой записи вердикта, рестартный повтор той же записи — тот же блоб → no-op. Три разных FAIL (разные блобы) = три круга; файл вердикта, дополненный вторым FAIL, = второй блоб = второй круг (докс 1.8 дословно).
- **Р4 Долг публикации отдельно.** pub_state НЕ выводится из локальной сохранности: checkpoint успешен при любом pub_state; «опубликовано» подтверждается ТОЛЬКО git-фактом достижимости кандидата из origin/main; при неизвестном удалённом состоянии pub_state остаётся прежним (не повышается и не понижается) со строкой «удалённое состояние: неизвестно».
- **Р5 Идемпотентность операций.** Ключ публикации = (candidate sha, target ref); pub-done с тем же ключом → повторный pub-start = именованный отказ «уже опубликовано: <sha>» БЕЗ второй записи. Аналогично task-init и события — дедуп по полной тройке (kind, subject, ref).
- **Р6 ci_wait — один вызов.** Внутренний поллинг с ненулевым интервалом (шовы интервала/попыток/таймаута), rc-грамматика ci_diag: 0 зелёный / 1 красный (упавший шаг + причина) / 2 нечем проверить / 3 таймаут. Ставит события wait-start/wait-done. Транспорт — curl+jq GitHub API, только `-r`, без eval, литеральные якоря полей.
- **Р7 Ротация 091 вбирается дословно.** Инварианты черновика round2-accept переносятся без пересуда: CLI `[--root <dir>] [--date <YYYY-MM-DD>]`; секция = литеральный префикс `## ГДЕ МЫ`; span до первой из (BEGIN-маркер 084 целой строкой | следующая `^## ` | конец файла); архив байт-в-байт БЕЗ шапки; отказы: HANDOFF отсутствует / --date вне грамматики (fullmatch) / секций нет / >1 секции / архив существует / итоговый >30720 байт; все проверки до первой записи; архив пишется ПЕРВЫМ; маркеры — литеральные константы субъекта. Батарея fixtures/handoff_rotate/ + fixtures/_krasnye_091.sh переносится байт-в-байт с wip/091/architect. Маршрут ветки 091 (поглотить лендом 092 или закрыть mint отдельным решением) — ВОЛЯ оркестратора, предмет один; 092 не сужается до 091 и не зависит от его заморозки.
- **Р8 Оракул клеток — модель мира в памяти** (правило 8): ожидания снимаются в память ДО вызова субъекта; диск проверяемого как истина не перечитывается; сверка структурная (строка-поле, grep -Fx-класс, не подстрока-где-угодно).
- **Р9 Сверка зон — живым union заморозок** (Н-144/Н-150): до заморозки grep по замороженным ЗОНА-строкам; заявленные ниже пересечения сверены по main (061: HANDOFF.md orchestrator; 083/084: ci-steps.tsv, ci.yml implementer; 011/015: ci.yml исторические architect). При появлении параллельного Контракта 1 — сверка его ЗОН на пересечение по ops/server/** и scripts/, конфликт объявляется, не замалчивается (арбитр по 033-union).

## Инварианты

- **И-1 Состояние.** ЕДИНСТВЕННЫЙ писатель — orch_checkpoint.sh. Каталог — шов ORCH_STATE_DIR; при переопределённом шве субъект НЕ читает и НЕ пишет умолчание того же шва (прецедент orch_restart И-6). Запись атомарна (tmp+rename в том же каталоге, fsync не заявляется); при любом отказе прежние файлы байт-в-байт. Составные операции (init = state + task-init-событие; pub-done = событие + state) атомарны КАК ЦЕЛОЕ: все проверки доступа и вся подготовка (tmp-файл состояния в каталоге шва, открытие журнала на дозапись) выполняются ДО первого необратимого шага; отказ любого шага → rc 1 «запись состояния не удалась», И state.tsv, И events.tsv байт-в-байт прежние. Состояние ВНЕ дерева: полная серия put/event/status на чистом дереве оставляет `git status --porcelain` пустым.
- **И-2 Грамматика state.tsv.** Строки `ключ<TAB>значение`; ключи — литерально: task, stage, candidate, last_proven, waiting, next_step, pub_state (каждый ровно один). Алфавиты: stage ∈ {draft, spec, frozen, implement, judge, publish, close, done}; waiting ∈ {none, ci:<40-hex>, owner, judge:[0-9]{3}, external}; pub_state ∈ {unknown, nothing, pushed, merged, published, close_incomplete}; task = [0-9]{3} | печатный токен без TAB/управляемых (id plan.tsv); candidate = 40-hex | `-`; last_proven = `<kind>@<порядковый номер события>` | `-`; next_step — одна строка ≤200 байт печатных без управляющих. Неизвестный ключ, значение вне алфавита, дубль ключа,_control-символ → rc 1 «состояние вне грамматики: <ключ>», файл байт-в-байт (037: литеральные сравнения, никакого regex/glob из значения).
- **И-3 События.** events.tsv: `ts ISO-8601 <TAB> kind <TAB> subject <TAB> ref`; kind ∈ {task-init, stage, round-fail, round-accept, pub-start, pub-done, wait-start, wait-done}; subject = task-id; ref для round-* = `<путь>@<blob-sha>`, для pub-* = `<candidate>@<target>`, для wait-* = sha. Append-only; запись существующей тройки (kind, subject, ref) — no-op rc 0 «уже записано». Счёт кругов предмета = число round-fail с различными ref. При трёх round-fail orch_status печатает «кругов: 3» и строку «предел: арбитр» (действующая норма роли — 3 → арбитр; 092 счётчик и строка, не политика).
- **И-4 orch_status.** `bash scripts/orch_status.sh [--next]`; rc 0 — сводка собрана. Вывод: локальные семь полей ВСЕГДА; отдельной строкой «удалённое состояние: неизвестно» при недоступном GitHub либо сводка CI кандидата при доступном. Различение (И-4а): «опубликовано: да|нет» и «закрытие: завершено|не завершено» — ДВЕ отдельные строки (не одна лампа). `--next` — ровно значение next_step. НИКАКОЙ выход orch_status не является запретом локального восстановления (недоступность сети — не отказ команды; rc 1 у orch_status — только грамматика состояния/отсутствие состояния, с именованной причиной).
- **И-5 ci_wait.** `bash scripts/ci_wait.sh [--sha <sha>] [--timeout <сек>] [--interval <сек>] [--attempts <n>]` — один вызов; при незавершённом CI опрашивает повторно (≥2 запросов суммарно) с ненулевым интервалом до таймаута; rc 0/1/2/3 (1 печатает упавший шаг + причину, формат ci_diag). Два терминальных исхода различены rc: транспорт недоступен (класс connection refused) → rc 2 «нечем проверить», немедленно, без поллинга; таймаут после ≥1 валидных in_progress-ответов → rc 3 — исходы НЕ взаимозаменяемы. Каждый wait ставит wait-start и (по завершению) wait-done события.
- **И-6 Производность HANDOFF и todo.** Субъекты 092 не пишут НИ ОДНОЙ строки прозы HANDOFF (первая секция — оркестратор, 061); единственное касание HANDOFF — перенос ротацией байт-в-байт (предмет 091). Блок «Следующая сессия» остаётся за gen_plan.sh (084). Наполнение todo роли («обрыв через N мин») — строкой `orch_status --next` (проводка роли, см. ПРОВОДКА).
- **И-7 Ротация — дословно инварианты 091 round2** (Р7): перечень отказов и порядок (HANDOFF отсутствует → --date → секций нет → >1 → архив существует → размер), атомарность отказа (ни один байт дерева), архив-первый, префикс-грамматика секции, fullmatch --date, 30720 строго больше — успех при равенстве.
- **И-8 Долг публикации.** Локальная сохранность успешна независимо от pub_state; изменение pub_state на published — только при git-факте (кандидат достижим из origin/main) или событии pub-done; при «удалённое состояние: неизвестно» pub_state не меняется. `orch_checkpoint.sh put pub_state published` принимается ТОЛЬКО если выполнено хотя бы одно: (а) журнал содержит `pub-done <task> <candidate>@<target>` с candidate, равным текущему полю candidate; (б) candidate ≠ `-` и кандидат достижим из `refs/remotes/origin/main` репозитория (`git -C <repo> merge-base --is-ancestor`, локальный ref, сеть не нужна — та же мера, что «опубликовано: да» И-4а). Иначе rc 1 «публикация не доказана: <candidate|->», файлы байт-в-байт. Прочие значения pub_state — по алфавиту И-2 как сейчас. `event pub-done` остаётся санкционированным путём повышения.
- **И-9 Гигиена.** Никакой субъект 092 не мутирует стерегомое дерево и не читает/не печатает секреты; GITHUB_TOKEN — из окружения или .env по прецеденту ci_diag, не печатается. Все git-вызовы с `-C` и снятыми GIT_DIR/GIT_WORK_TREE/GIT_CONFIG* (Н-85).
