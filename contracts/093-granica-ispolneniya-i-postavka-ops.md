## Диагноз-по-коду

1. **Root исполняет код из harness-записываемого чекаута** — `orch-peak:166–168` (bootstrap из `${REPO}`). Отказ наблюдаем: файл `${REPO}/scripts/lib_session.sh` принадлежит uid harness; установленный `/usr/local/sbin/orch-peak` — root:root 755 (074, И-4). Почин: корневой bootstrap — только из установленного root-owned источника (копия библиотеки ставится `install.sh root` рядом с orch-peak как root:root); источник из `${REPO}` в root-контексте — именованный отказ. Инварианты 090 (посев `ORCH_SESS_GLOB`, `ORCH_UHOME`) сохраняются побайтово в поведении.
2. **Сессия агента живёт под uid harness** — `orch-loop:10–11,47`: полный доступ к `/home/harness` (ключи, сессии, состояние) и до публикационного ключа. Почин по уточнению консультанта: отдельный uid агента; орch-loop (автономный пускатель) запускает сессию под ним с cgroup-потолком; контрольные файлы станции для этого uid недоступны.
3. **Фолбэк без потолка** — `orch-loop:48–53`: отказ `systemd-run` → запуск `"$WORKSHOP" --yolo` без лимита. Почин: удаление ветки фолбэка, именованный отказ, автономный процесс НЕ стартует.
4. **Установщик не проверяет жизнь юнита и не имеет отката** — `install.sh` usage `user|root|verify`. Почин: новые подкоманды (грамматика CLI — implementer; контракт пинует входы/отказы/сценарии): проверка старта поставленного юнита и откат к предыдущей установленной версии, оба — с живой проверкой запуском службы.
5. **Credential публикации в среде агента** — среда сессии = наследие uid harness (Н-196). Почин: uid-разделение + HOME агента вне `/home/harness`; публикация — только доверенной установленной дверью под другим пользователем (семантика сверки базы — Контракт 3 пути Г, не здесь).
