## Frontier

- **Носитель доказательства.** (а) git notes на merge-коммите: мутируемо, вне истории, невидимо для судей реестров — отвергнуто. (б) Аннотированные теги `cand/<id>`: второй смысловой namespace рядом с done/frozen, движет refs, конфликтует с «номер артефакта выдаёт механизм» — отвергнуто. (в) **Выбрано:** append-only журнал `registry/candidates.tsv` (харнес) / `<workflowPaths.registry>/candidates.tsv` (проект, 054): строка реестра — прецедент культуры registry/*.tsv, судится grep -Fxq, версионируется самой историей git, объект не меняет сам себя фактом записи (§1.4).
- **Подготовленный merge.** (а) Слияние в боковой ветке/worktree с движением refs, затем перенос: два движения refs = окно расхождения; топология «первый родитель не main» уже ломала судей (Н-191/Н-127) — отвергнуто. (б) **Выбрано:** `git merge-tree --write-tree` + `git commit-tree -p base -p candidate` БЕЗ движения refs: merge-коммит — неизменяемый объект с момента проверки; дверь в момент публикации переносит ЦЕЛЕВУЮ ветку на ИМЕННО этот sha (`update-ref` с ожиданием старого значения = base, CAS). Повтор публикации физически не может создать второй merge (И-9 по построению). Дерево merge дверью НЕ пересчитывается (живой `git merge-tree --write-tree base candidate`): различимость подготовленного merge несёт id объекта (И-1б: merge при неизменной базе, Замер 3 арбитража 094); пересчёт двери — альтернативный путь П6 того арбитража, не выбран.
- **Происхождение доверенной политики.** (а) Файл политики в рабочем дереве кандидата: проверяемый сам определяет, чем его проверять (§1.5 дословно) — отвергнуто. (б) Отдельный внепоисный конфиг двери: второй профиль, Astra 1.2 запрещает — отвергнуто. (в) **Выбрано:** политика читается из ПРИНЯТОЙ версии: для харнес-репо — дерево по base SHA (`git show <base>:…`; base уже принят), для внешнего проекта — пин слоя проекта (054 И-5) вне кандидатного репозитория; версия политики в объекте = sha256 байтов политики. Доверенные ОПРЕДЕЛЕНИЯ обязательных проверок — та же доверенная версия (для харнеса — CI-шаги/workflow по base SHA; toy-носитель `harness/checks/<имя>.cmd`), wfsha проверки = sha256 их байтов. Правка политики — отдельный явно разрешённый переход: строка `policy` журнала (санкция судейского канала, Б4); к собственному принятию кандидата НЕ применяется.
- **Доказательство дерева исполнения (Б3-остаток, арбитраж 094 П5).** (а) **Выбрано:** строка `check` несёт СЕДЬМОЕ поле — tree sha (40 hex) ИСПОЛНЕННОГО дерева; дверь сверяет его литерально с `MERGE^{tree}` (класс H семантики 087 — не ослабляется): ошибочный поставщик, честно записавший дерево кандидата C, отказывается именованно «проверка не того дерева: <имя>». Дыра закрывается У САМОЙ ДВЕРИ — нулевое расширение зон и нулевое исполнение кандидатного кода (Решение 4: дверь читает git-объекты по sha и ничего не запускает); критерий различает «проверено M» и «проверено C, записано для M» уже сейчас, до landing 087. (б) toy-поставщик в семье (исполняет `harness/checks/<имя>.cmd` на дереве M в отдельном worktree и пишет строку): отвергнуто — требует сначала решить, чья зона `check_merge_gate` (совет критика круга 2, арбитражом НЕ судён), исполняет кандидатный код в среде батареи и расширяет семью исполнителем; живой поставщик строк остаётся зависимостью landing 087 (ПЕРЕСЕЧЕНИЕ 063/087). Лгущий поставщик (записал дерево M, ничего не исполняя) — доверенная сторона, НЕ ЗАЩИЩАЕТ.

## Решения

1. Субъект — ОДНА дверь `scripts/accept_publish.sh` с глаголами `object` (выдать id объекта), `prepare` (подготовить merge-коммит без движения refs), `publish` (повторная сверка и перенос). Грамматика CLI закреплена честной моделью `fixtures/accept_publish_094/model/dover.sh`: субъект обязан принимать её CLI и фразы дословно (детали реализации — implementer); `publish` принимает `--candidate-ref` ОБЯЗАТЕЛЬНО (Б5: вызов без него — именованный отказ, сверка движения кандидата не выключается молчанием CLI).
2. Id объекта = sha256 канонической TAB-строки (repoId, задача, целевая ветка, base, candidate, merge, policyVersion) — «номер артефакта выдаёт механизм»; никто не изобретает id руками, судьи и клетки получают его от `object`. Различимость ВСЕГО состава — КАЖДАЯ составляющая ОТДЕЛЬНО (арбитраж 094 Б1): та же задача+кандидат при другой целевой ветке / другой базе / другом merge (в т.ч. merge при НЕИЗМЕННОЙ базе: иное дерево объединения при тех же родителях, Замер 3) / другой версии политики ⇒ ДРУГОЙ id; предъявлена клеткой И-1б.
3. Журнал `registry/candidates.tsv`: строки `verdict|check|policy|published` (грамматика И-0). `verdict` пишет судейский канал (судья/оркестратор — доверенная сторона; judge_gate поставляет СОБЫТИЕ решения судьи — вердикт-файл круга, не CI success), `check` — CI-обвязка по завершении обязательной проверки (vorota 087 / check_merge_gate 063 для харнеса и проекта) с wfsha ИСПОЛНЕННОЙ версии определения И tree sha ИСПОЛНЕННОГО дерева (обвязка судит подготовленный merge по ДЕРЕВУ объекта, не checkout main; дверь сверяет поле дерева литерально с `MERGE^{tree}` — «проверили C, записали для M» отказывается, Б3 арбитража 094), `policy` — санкция перехода политики (судейский канал, Б4), `published` — только дверь. Дверь журнал читает и пишет ИСКЛЮЧИТЕЛЬНО свою строку `published`. rc нормы дерева доказательства: `bash fixtures/accept_publish_094/red_proverka_ne_togo_dereva.sh`
4. Дверь переносит ЛОКАЛЬНУЮ целевую ветку; push остаётся в канале gitw (045) — «посажено локально», прецедент 022/063; кандидатный код не исполняется (дверь читает git-объекты по sha, не запуская ничего из репо).
5. Дверь наследует обязательства лендов: identity merge-коммита `orchestrator` (016), перенос строк-санкций диапазона кандидата в тело merge ДОСЛОВНО (065 И-10), первый родитель — base (Н-191-класс), отказ не трогает ветку (022).
6. Миграция (Пять правил §2 — замена, не наслоение): `land_agent.sh` и `land_project.sh` удаляются либо становятся тонкими вызовами двери (без собственной merge-логики); семантика «все check-runs» `check_ci_gate.sh` заменена перечнем обязательных из политики; предполёт gitw чек 5 (vorota) поставляет строки `check` в журнал; батареи и строки реестра CI мигрированных дверей обновляются той же пачкой (перечень — ЗОНА implementer).

## Демаркация контрпримеров

Конформные входы (грамматика И-0): sha 40 hex; object_id/wfsha/версии политики 64 hex; задачи/имена/ветки/repoId в замкнутых алфавитах; строки журнала TAB-поля; политика — три ключа в алфавите; определения проверок `harness/checks/<имя>.cmd` на доверенной версии; находки — `.review/<имя>.md` со строкой `status: <слово алфавита>`. Валидный контрпример против клетки = инвариантность к ЗНАЧЕНИЯМ конформных полей (имена задач/проверок/веток, длины, порядок байтов значений, путь находки) ∧ расхождение честной реализации и контрпримера на КОНФОРМНОМ входе клетки. Неконформные входы (битый sha, TAB в имени, запятая в имени проверки, пустой CSV-компонент перечня — ведущая/хвостая/двойная запятая, неизвестный kind строки, ключ политики вне трёх, wfsha не 64 hex) — предмет И-0-отказов, НЕ контрпримеры против И-1…И-9: клетка, краснеющая только на неконформном входе, не доказывает свой инвариант.

## Модель угроз

ЗАЩИЩАЕТ:
- принятие результата по доказательству ДРУГОГО результата (иная задача/объект/ветка/база/кандидат/политика) — И-1, И-2, И-3;
- коллапс идентичности объекта (та же задача+кандидат, другой base/merge/ветка/политика: доказательства старого состава годятся новому) — И-1б;
- подмену проверяемого после проверки (amend базы/кандидата, пересборка merge на месте; выключение сверки кандидата отсутствием CLI-опции) — И-5 и подготовленный merge (§1.4);
- «зелёность» посторонним workflow, умолчание отсутствующей обязательной проверки, одноимённый ПОДМЕНЁННЫЙ workflow (имя зелёное, происхождение чужое) и приписывание результата прогона другого дерева объекту M («проверили C, записали для M») — И-4, И-4б (wfsha И дерево строки check);
- открытую находку, живущую только в ДЕРЕВЕ публикуемого кандидата (журнал чист, main чист) — И-3в;
- самоназначение перечня проверки проверяемым (правка политики/workflow кандидатом) и НЕавторизованный переход доверенной политики (обычный accept ≠ санкция) — И-6, И-6б, Frontier-3;
- тихий перенос непроверенного; повторный merge после частичного сбоя; преждевременное движение ветки при отказе — И-8, И-9;
- публикацию в непущенную ветку — И-7;
- расхождение «что судили» и «что опубликовано» на merge-топологии — подготовленный merge (Н-191/Н-127-класс).

НЕ ЗАЩИЩАЕТ:
- подмену доверенной стороны ВНЕ кандидата (компрометация судьи/оркестратора, пишущего строки `verdict`; компрометация реестра/слоя проекта) — Astra 1.5: «уточнение существующей границы доверия, не новая платформа»;
- содержательную силу обязательной проверки (зелёная, но слабая) — происхождение определения защищено (И-4б), сила самого предиката — предмет проверок и Контракта 6 (ключ предиката);
- гонку ДВУХ публикаций на одной базе (проигравший получает честный «база изменилась» по факту, не по блокировке);
- push в origin и его секреты — канал gitw (045) и uid-граница 093; дверь переносит только локальную ветку;
- исполнение кандидатного кода средой ПРОВЕРОК (CI) — дверь читает git-объекты и ничего не исполняет, но прогон проверок — среда CI, не дверь.
