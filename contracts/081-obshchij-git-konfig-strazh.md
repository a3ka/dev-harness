**И-1 (запирание ядром).** `ops/server/install.sh root`, ПОСЛЕ копирования обвязки и

«не основной чекаут» rc 1, ДО вызова chattr); отказ chattr → именованный отказ rc 1

## Модель угроз

ЗАЩИЩАЕТ:
- запись `user.*` / `remote.*` / `branch.*`-upstream в РАЗДЕЛЯЕМЫЙ `.git/config` ЛЮБЫМ
  процессом (JS/bash-страж не участвует: omp-сессия, субагент, скрипт-файл, терминал,
  PATH-подменённый git, python-subprocess) на машине с root и установленным атрибутом —
  ядро отказывает EPERM на open-на-запись/rename/unlink ДО записи (формы R1-R4
  батареи: основной чекаут, worktree `-C`, `GIT_DIR`, из скрипта; R5/R6: remote/upstream);
- форма `git config --worktree` в одиноком репо (тихо пишет в ОБЩИЙ config, замер
  2026-10-04) — под замком отказывает ядром (R7); в репо с linked worktrees git сам
  отказывает rc 128;
- включение `extensions.worktreeConfig` — само есть запись в общий config → ядро
  отказывает; если уже включён (до блокировки / в окне обслуживания) — детектор красен
  (б) (D3); остаточный `config.worktree`-файл — форензика, детектор красен (б2) (D4);
- снятие атрибута без возврата — детектор красен (а) (D2): сеть возврата для процедуры
  обслуживания и для «разморозил и забыл».

НЕ ЗАЩИЩАЕТ:
- **машины без root / без установленной root-части** (сандбоксы субагентов, dev-ноутбуки,
  CI-runner): атрибут не ставится (chattr EPERM, замер uid 1004), защита отсутствует
  ЦЕЛИКОМ — это заявленный более слабый режим, НЕ равнозначное закрытие класса; детектор
  на такой машине честно красен (а) всегда;
- **процесс с достаточными правами (root/sudo)**: `chattr -i` доступен всегда — ядро
  защищает от не-root процессов; окно «снял → правка → не вернул» закрывается только
  детектором ПОСЛЕ факта (частота обнаружения = частота прогона детектора), не
  предотвращением;
- **правка в окне процедуры обслуживания** между `chattr -i` и `chattr +i` (И-5) —
  физически открытая дверь, длительность окна — решение оператора;
- **ФС без поддержки chattr** (overlayfs-раннеры, ряд tmpfs): `+i` не ставится —
  установщик даёт именованный отказ «chattr +i», станция обязана стоять на ФС с
  поддержкой immutable-атрибута;
- **запись в worktree-собственный config.worktree**: файл существует ТОЛЬКО при
  включённом extension (замер: без extension файла нет и канал закрыт), а включение
  закрыто ядром (запись в общий config) и детектором (б) — но если станция СОЗНАТЕЛЬНО
  включит extension и пройдёт мимо детектора, per-worktree identity пишет мимо `+i`;
  потому И-2/И-4 держат состояние extension=false fail-closed (любое true — красное).

## Frontier: отвергнутые варианты

- **Страж текста команды в path-guard.ts (прежний предмет 081, круги 1-6).** Грамматика
  форм записи бесконечна: К1 `--file`, К2 приоритет файла, К3 `--git-dir`-формы, К4
  цепочки `-C`, К5 cwd/cd-формы — каждая закрытая форма открывала новую (6 кругов,
  131 клетка, всё ещё два живых обхода). Ядро закрывает класс ЦЕЛИКОМ и для ЛЮБОГО
  процесса (включая скрипты и терминал, куда страж вызова не видит вовсе). Снято словом
  владельца 2026-10-04.
- **`extensions.worktreeConfig` как «решение».** Обычный `git config` всё равно пишет в
  общий файл; сама запись включения — в общий config. Не решение ни в какой роли.
- **chmod 0444 как замена +i.** git пишет через `config.lock` + `rename(2)`; chmod
  rename не мешает — все формы записи прошли rc 0 (замер 2026-10-04). Только `chattr +i`
  закрывает open/rename/unlink. Мок-режим батареи поэтому несёт LD_PRELOAD-шим, не chmod.
- **Обёртка на PATH (прецедент 045 gitw).** Норма-строка на каждый git-вызов сессии,
  не ловит скрипты/терминал, второй экземпляр грамматики (дрейф). Отвергнута ранее,
  остаётся отвергнутой; 045 остаётся сетью обменов.
