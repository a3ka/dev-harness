## Предмет и последовательность

Хранитель `architecture-steward` — именованный постоянный субагент, вызванный оркестратором после `done` ПОСЛЕДНЕГО предмета КАЖДОГО Э-этапа и немедленно при блокирующей архитектурной находке. Повторяющийся timer станции только страховочный: сообщение не выдаёт себя за слово владельца и не становится первичным триггером. Оркестратор сохраняет ожидающий вызов при занятом слоте. Строки оркестратора/агентов о вызове и подаче findings — предмет 188; 186 обеспечивает принимающую роль и событийный интерфейс станции. Ни один freeze/done не ждёт подписи хранителя.

1. **Непрерывный приём и статусы.** Любая роль или человек может внести файл в `CompliorOS-architecture/governance/findings/`; грамматика шести полей §8.3: `Компонент/ресурс`, `Наблюдение` с доказательством, `Ожидание модели`, `Предлагаемый уровень`, `Автор`, `Статус`. Предварительный уровень проверяется `check --base`, окончательный не выбирается именем автора. Допустимые состояния: `принята L1` / `принята L2` / `принята L3` / `отклонена: <непустая причина>` / `вопрос владельцу`. `python3 scripts/findings_status.py <корень-CompliorOS-architecture> <git-ref-предыдущего-среза>` читает через Git файлы предыдущего среза: незакрытый файл без допустимого статуса печатает `ПРОСРОЧЕНО: governance/findings/<имя>`, rc 1; именованные строки включаются в отчёт обзора. Свежие файлы не становятся просроченными. Исходный ref задаётся предыдущим срезом, а не временем модификации файла.
2. **Обзор среза и контроль.** После `done` коммит обзора в `CompliorOS-architecture/governance/review/<YYYY-MM-DD>-<Э>.md` обязателен даже при нуле находок: diff модели, `arch:conform` на main, закрытые/отклонённые находки, L2-пачка на снимок, актуальный DRAFT-реестр. Срочный блокирующий сигнал не ждёт `done`/понедельника. `python3 scripts/architecture_review.py <корень-CompliorOS-architecture> <YYYY-MM-DD> <Э>` проверяет наличие непустого файла В HEAD проекта (не незакоммиченную запись), отсутствие → `НЕТ ОБЗОРА: governance/review/<дата>-<Э>.md`, rc 1; это находка оркестратору, а не молчаливое отсутствие отчёта. Проверка вызывается ПОСЛЕ сессии обзора, не до возможности создать файл. Сверка Word/3.17/4.1 с моделью при архитектурном слове владельца записывается в DECISIONS.md и дельту.
3. **Реестр и CI проектного checker.** Из `check --base` → `contractReadiness.unresolved` строится `governance/REGISTER.md`: для каждой операции/компонента — приоритет по проектному ROADMAP, нужный Э-этап, закрывающий предмет и срок `до контракта X`; недостающие контракты также показаны. Данные `check` генерируются, не переписываются вручную; устаревший реестр относительно текущего `check` → rc 1 в CI `CompliorOS-architecture`. Маршрут выбран по разрешённой альтернативе владельца: **поручение Астре** реализовать генератор и `--check` в `CompliorOS-architecture/tooling/checks/` и подключить к CI ЭТОГО репозитория; хранитель передаёт поручение проектному оркестратору как задачу Астре с приёмкой «актуальный реестр → rc 0; изменить conformant unresolved/удалить запись реестра без пересборки → rc 1 на том же проектном CI; исправить реестр → rc 0». Роль харнесса не содержит проектный checker: он зависит от схемы вывода проектного `check` и должен исполняться без установленного харнесса. Проектный CI и PR Астры — необходимый результат поручения, но 186 не выдаёт непостроенный проектный checker за зелёный в своей батарее. В7 схемы операций впрок — L1 до контракта, которому они необходимы; DRAFT не выдают за готовую схему.
4. **Маршрут решений и дверь слияния.** L1 хранитель вне предмета либо architect своего предмета пишет PR в `CompliorOS-architecture` с АДРЕСНОЙ дельтой модели отдельным коммитом `arch(L1)` и diff (код не узаконивает отклонение от модели; модель не узаконивает себя), `check --base` PASS, `--strict-new-ops`, шестой вопрос critic. **Слово владельца 2026-11-10 ~20:26 UTC:** мейнтейнер L1 = оркестратор станции, не автор PR. `bash scripts/merge_architecture_pr.sh <корень-CompliorOS-architecture> <номер-PR>` — дверь, запускаемая ТОЛЬКО оркестратором: получает с GitHub title, author, head SHA и accept критика на этот ЖЕ SHA с фактической моделью семейства GLM (в отличие от Sol хранителя) и автором вердикта, отличным от автора PR; требует зелёных check-runs на head; запускает в корне проекта `npm run check -- --base governance/baseline/approved.json --report` и механически выводит L1 из `baseline PASS` (защищённые секции не задеты). Заголовок PR несёт `COMPLIOR-<NNN>`; identity автора PR не равна сливающему; при всех выполненных условиях вызывается `gh pr merge <номер> -R a3ka/CompliorOS-architecture --merge --match-head-commit <head>`; на любой ошибке до вызова merge — именованный отказ без слияния. L2 (например `BASELINE_MISMATCH: moduleBoundaries`) хранитель собирает к концу среза: `arch/l2-<Э>`, отдельный diff-коммит, вердикт critic, одна страница предложения снимка владельцу; без записи `РАЗРЕШИЛ-ВЛАДЕЛЕЦ:`/акта снимка дверь отказывает `L2_OWNER_APPROVAL_REQUIRED`, слияние по отдельному маршруту владельца. L3 (`BASELINE_MISMATCH: resources` и др. защищённые секции) — один вопрос с рекомендацией; без записи владельца отказ `L3_OWNER_APPROVAL_REQUIRED`; решение и снимок публикует владелец. Ни L2, ни L3 автор не сливает. Спор инженерный L1/L2 — арбитр, по воле/L3 — владелец. Независимость суда здесь — отдельный GLM-critic, не автор PR; совпадение моделей само по себе не запрещает вызов судьи других предметов (frozen 166), но подмена назначения `roles.critic` на Sol хранителя запрещена инвариантом 186. После слияния продуктовый PR закрепляет ТОЧНЫЙ commit слияния в `architecture.lock.json` с тем же `COMPLIOR-<NNN>`. Внешняя зависимость: консультант owner-PR обновляет архитектурный `MIGRATION.md` («designated human maintainer») на станционного оркестратора; до этого реальный merge не заявляется доступным. Режим merge-commit и правила архитектурного репозитория сверяются по его `MIGRATION.md`, не угадываются из toy.
5. **Выход в код.** Если находка требует кода или долг предмета, хранитель передаёт её проектному оркестратору как предмет/B-DEBT с доказательством и приоритетом; код и вердикты за хранителем не закреплены. Артефакты идут в проектный workflow (`governance/findings/`, `governance/review/`), не в `fixtures/` и не в `architecture/` как каталог находок. Хранитель не правит L2/L3 под видом L1.
6. **Маршрут модели.** `config/agent_models.json`: новый `tiers.steward-arch.model="@gpt-sol"`, `fallback="@gpt-astra"`, `roles["architecture-steward"]="steward-arch"`; `routing.rules` связывает именно `приём находок и обзор архитектуры после done этапа и блокирующей находки` с этой ролью. `npm run gen:harness` генерирует `.omp/agents/architecture-steward.md` (`model: ["@steward-arch"]`) и `.omp/config.yml`; `npm run gen:harness -- --check` rc 0. `tiers.plan` и назначения остальных ролей неизменны: critic остаётся `roles.critic=apex-sol` → `tiers.apex-sol.model=@glm`; не менять распределение моделей под видом добавления хранителя. Timer `orch-architecture.timer` диспатчит `Unit=orch-peak@architecture.service`, а не другое action.

Конформная проба: независимый Git toy с настоящими parser/generator и station action, неизменным `ORCH_PEAK_TEST`, шестипольными findings и парой срезов. Для двери: отдельный Git toy со своим `.git`, локальный `governance/baseline/approved.json` и сравнение живого toy-моделя с ним, сетевые `gh`/GitHub заменены fake-CLI, `npm check` в toy воспроизводит только baseline-сигнал; реальный `CompliorOS-architecture` не мутируется. Контрпример валиден при документированных полях GitHub PR/reviews/check-runs, sha40 и одинаковых значениях модели при смене temp-корня/OID; ожидания сняты до запуска субъекта в память проверяющего. После субъекта сверяются rc, структурные поля и фактический аргумент merge; несетевые ошибки окружения не засчитываются красным. Внешний проектный CI реестра судится по приёмке поручения Астре в самом `CompliorOS-architecture`, а не фиктивным CI toy харнесса.
