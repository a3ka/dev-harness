     разбор вывода по SHA-заголовкам.

2. **Критерий приёмки — ДИФФЕРЕНЦИАЛЬНЫЙ, не абсолютный (РЕШЕНИЕ арбитража,
   §Б1).** Круг 1 и круг 2 критика показали дважды подряд: ЛЮБАЯ абсолютная
   граница вида `a·(K+M)+b` на toy с НЕРАВНОМЕРНОЙ нагрузкой имеет зазор,
   который честный батчинг во всех окнах, кроме одного, всегда может занять —
   это КЛАСС обхода, не свойство конкретной константы. Решающее утверждение
   §Приёмка Р1 (check_zones) и Р2 (check_protected) — **`C_high − C_low <= S`**
   на паре toy-деревьев с ОДИНАКОВОЙ структурой, отличающихся ТОЛЬКО ОДНОЙ
   величиной нагрузки (`L` для check_zones — числом коммитов ОБЪЯВЛЕННОГО
   автора ОКНА в СВОЮ зону, добавляемых в КАЖДОЕ из K окон ОДИНАКОВО; `M` для
   check_protected — числом фоновых коммитов), при обязательном **`Δ >= 2·S`**
   (`Δ` — разница уровня нагрузки HIGH−LOW). Абсолютная граница `a·(K+M)+b`
   (check_zones) и `BOUND` (check_protected) СОХРАНЯЮТСЯ как ВТОРОЕ, ГРУБОЕ
   утверждение того же файла (внятный диагноз для случая «батчинга нет
   вовсе»), но РЕШАЮЩИМ является п.3 §Приёмка. Негативный контроль (Н-39,
   agent03 → чужая зона для check_zones; `-s ours`-пропажа для
   check_protected) обязан ловиться на ОБОИХ деревьях независимо — иначе rc=1
   с причиной «поймана потеря проверки, не производительность».
   Право architect на правку ЧИСЛА (§Риски-4) распространяется на `a`, `b`,
   `BOUND` — **НЕ распространяется на `S` и `Δ`**: они связаны соотношением
   `Δ >= 2·S`, и ослабление `S` без соответствующего роста `Δ` — ослабление
   предмета, а не щедрая константа. Один и тот же `S` действует для
   check_zones И check_protected (единая калибровка, вердикт: «тот же S»).
   Калибровка-отправная-точка (замер арбитра З4, прожита заново architect'ом
   в этом круге — см. живые прогоны §Приёмка): check_zones K=12, M=60,
   L_low=5, L_high=35 (Δ=30 на окно); check_protected M_low=60, M_high=360
   (Δ=300); `S=15` для обоих (Δ>=2S держится с запасом в обоих случаях).
   Почему это закрывает КЛАСС, а не очередной мутант: добавочная нагрузка `Δ`
   попадает в КАЖДОЕ окно/во ВСЮ историю одновременно, поэтому реализация,
   оставившая по-коммитный источник хоть в ОДНОМ месте, платит НЕ МЕНЕЕ `Δ`
   доп. вызовов либо НЕ МЕНЕЕ `K·Δ` — оба случая больше `S` по построению
   `Δ>=2·S`; неравенство не зависит от того, КАКИЕ окна/участки остались
   по-коммитными, только от того, что таковые есть.

5. **check_protected.sh — конвейер `git rev-list HEAD | git diff-tree -r
   --root -m --no-renames {--name-only|--raw} --stdin` вместо двух
   per-commit-циклов (РЕШЕНИЕ арбитража, §Б4).** `rev-list HEAD --objects`
   (форма v1/v2) признан арбитражем НЕПРАВИЛЬНЫМ КЛАССОМ техники и УДАЛЁН
   ЦЕЛИКОМ, не дополнен: он перечисляет УНИКАЛЬНЫЕ ОБЪЕКТЫ с ОДНИМ
   представительным именем на объект, а барьеру нужно множество ПАР «путь в
   дереве достижимого коммита» — при двух путях с ИДЕНТИЧНЫМИ байтами (один
   блоб) он МОЛЧА теряет имя второго (замер арбитра З1/критик Б4 круга 2,
   независимо подтверждено architect'ом в этом круге). Оба места (`roleblobs`
   `:130-132`, `existed.raw` `:172-177`) заменяются ОДНИМ конвейером каждое:
   `git rev-list HEAD | git diff-tree -r --root -m --no-renames --raw --stdin
   -- ':(literal)roles/'` (roleblobs — нужны и путь, и блоб, отсюда `--raw`) и
   `git rev-list HEAD | git diff-tree -r --root -m --no-renames --name-only
   --stdin -- "${prefixes[@]}"` (existed.raw — нужен только путь). Флаги
   **`--root`, `-m`, `--no-renames` — ОБЯЗАТЕЛЬНЫ ЛИТЕРАЛЬНО**:
   - `--root` обязателен: без него `diff-tree` пропускает root-коммиты
     целиком, и путь, живущий с корневого коммита и никогда не менявшийся,
     теряется (замер арбитра З2; воспроизведено architect'ом живьём — риск 2
     §Приёмка Р2);
   - `-m` обязателен: без него merge-коммиты не диффятся вовсе, и путь,
     СОЗДАННЫЙ в самом merge-коммите, теряется (замер арбитра З2;
     воспроизведено — риск 3 §Приёмка Р2);
   - `--no-renames` обязателен: иначе результат зависит от `diff.renames`
     конфига машины читателя — та же причина, что уже действует в
     `check_protected.sh` для `excuse_for`/`moved_for`.
   Полнота техники доказана арбитром структурно (не по счастью): всякая пара
   (путь, блоб) в дереве достижимого коммита либо отличается от
   соответствующего родителя — тогда она есть в выводе `diff-tree` для ЭТОГО
   коммита, — либо совпадает со всеми родителями и введена раньше по тому же
   рассуждению; индукция упирается в корневые коммиты, которые покрывает
   `--root`. Цена — два git-процесса НА УПОТРЕБЛЕНИЕ (было ≈3888 на реальном
   дереве); `cat-file --batch-check` НЕ нужен — `--raw` сразу отдаёт режим и
   dst-блоб, а режим прямо нужен для уже существующего условия «жив КАК
   регулярный файл». `excuse_for`, `moved_for`, `head`/`head_blobs` (`git
   ls-tree -r HEAD` — уже ОДИН вызов, не трогается), `comm`-based diff,
   PATH-hardening (`:81`), env-гигиена, отказ на shallow (`:96-100`), коды
   0/1/2 — ВСЁ остальное байт-в-байт.

   > workflow, срабатывающего на `push` в `main` и на `pull_request`; команда
   > шага — ровно `npm run <ключ>` (допускается хвост `-- <аргументы>`) без
   > операторов оболочки; у шага НЕТ ключа `if:` и нет
   > `continue-on-error: true`; у джобы, несущей шаг, нет `if:`, и ни одна
   > джоба её транзитивного `needs:`-замыкания не несёт `if:`. Это — всё, что
   > проверяется деревом; утверждение «исполнится каждым прогоном» деревом не
   > проверяется и здесь НЕ утверждается.

   Обе пробы (`red_predel_git_vyzovov.sh`, `red_predel_git_vyzovov_ours.sh`)
   ОБЯЗАНЫ жить именно ТАКИМ отдельным прямым шагом (НЕ через shard `keys:`
   matrix — это ИЗМЕНЕНИЕ относительно v1/v2, где матричная форма допускалась
   как альтернатива; см. §Зоны). Механическая проверка — §Приёмка Р9
   (fail-closed структурный предикат, §Инварианты п.9). Разрыв между
   «подключено безусловно» и «фактически исполнилось хоть раз» закрывается НЕ
   фикстурой, а одноразовым живым наблюдением — см. «Условие done» в конце
   этого контракта.
9. **Р9 — fail-closed СТРУКТУРНЫЙ предикат, не построчное регулярное
   выражение (РЕШЕНИЕ арбитража, §Б3, часть 2).** Прежняя редакция (critic
   contracts-040-v2, Б3) засчитывала `if: false`, `run: npm run <key> ||
   true`, `run: npm run <key>; true` — текстовое присутствие ключа, не
   гарантию исполнения (замер арбитра З6: все три формы дают True тем же
   регулярным выражением). Новый предикат, реализован
   `fixtures/check_zones/probe_ci_dostizhimost_predelov.sh`:
   1. Разбор — СТРУКТУРНЫЙ, по объявленному подмножеству формы: блочный YAML,
      шаг — элемент `- ` списка `steps:` на общем отступе. Любая иная форма
      (flow-стиль, якоря/алиасы/теги, `steps:` не блочный список) → **rc=1
      «форма шага вне объявленного подмножества»**, не молчаливый пропуск —
      доктрина `verdicts/arbitration/oblast-i-porog.md` (вопрос 1).
   2. Найдя шаг с нужной командой, проба **ОТКАЗЫВАЕТ при наличии `if:`** на
      шаге, на его джобе или в её `needs:`-замыкании — БЕЗ вычисления
      выражения (направление ОБРАТНОЕ прецеденту `verify_ci_parity.sh`, но не
      противоречащее ему: тот запрещает МЕХАНИЗМУ решать, какой шаг
      исполнится — для ПАРИТЕТА корректно сверх-приближение вверх; здесь
      предмет обратный — `if:` просто ЗАПРЕЩЁН на этих двух шагах, не
      толкуется. `verify_ci_parity.sh` не правится ни на байт).
   3. `continue-on-error: true` на шаге или джобе → rc=1.
   4. Команда шага сверяется на РАВЕНСТВО канонической форме
      (`^npm run(-script)? <ключ>( -- .+)?$`), не на вхождение подстроки;
      наличие `|`, `&&`, `;`, `>`, `` ` ``, `$(` в строке `run` → rc=1 (замер
      арбитра З6 — иначе `|| true`/`; true` проходят).
   5. Существующие проверки (rc через npm == rc напрямую для ОБЕИХ проб,
      зелёный `verify_ci_parity.sh`) сохраняются без изменений.
   6. Разбор ПИШЕТСЯ В САМОЙ ПРОБЕ — дублирование разборщика с
      `verify_ci_parity.sh` ПРИНЯТАЯ ЦЕНА (РЕШЕНИЕ арбитража): тот барьер
      принадлежит замороженному контракту 020, вынесение разбора в общий
      модуль означало бы правку чужого замороженного предмета.
   Живьём проверено architect'ом в этом круге на 9 синтетических CI-сценариях
   (канон; `if: false`; `continue-on-error: true`; `|| true`; `; true`;
   flow-стиль `steps:`; YAML-якорь; `if:` на джобе; `if:` в `needs`-замыкании)
   — все 8 обходов ловятся именованной причиной, канон проходит (см. §Приёмка
   Р9, живой прогон).
10. **Стабы к обманным веткам — по коду, не по прозе (Н-39 дословно).**
    `red_predel_git_vyzovov.sh` привязывает свою красноту к ЖИВОМУ
    дифференциальному git-подпроцессному счёту на паре toy LOW/HIGH (не к
    тексту контракта); `red_predel_git_vyzovov_ours.sh` — аналогично на паре
    toy `M_low`/`M_high`, И ДОПОЛНИТЕЛЬНО несёт ТРИ отдельных, тоже живых,
    стаба конкретных рисков разрешённой техники diff-tree--stdin (дубликат-
    блоб — старая техника теряет/новая держит; без `--root` — теряет
    корневой путь; без `-m` — теряет путь мерж-коммита), все три — на РЕАЛЬНОМ
    toy этого же файла, измерены architect'ом живьём в этом круге. Р2
    ДОПОЛНИТЕЛЬНО несёт НОВЫЙ ПОСТОЯННЫЙ красный вход в п.Б: история с двумя
    путями одного блоба, где один удалён БЕЗ `ALLOW` и без переноса —
    сегодняшний (по-коммитный, per-commit `ls-tree`) `check_protected.sh` уже

    сохранением этой корректности НОВОЙ техникой (см. РЕШЕНИЕ Б4 п.4 ниже,
    §Приёмка Р2).
11. **Пин ПРОСТРАНСТВА ИМЁН для приёмочных артефактов, не список файлов

    - **Соглашение об именах — НОРМА, не привычка:** каждый исполняемый
      артефакт приёмки, принадлежащий architect байт-в-байт, живёт в
      `fixtures/<семья>/` (`check_zones` либо `check_protected`) и носит

      контракта (`red_predel_git_vyzovov.sh`, `red_predel_git_vyzovov_ours.sh`,
      `probe_ci_dostizhimost_predelov.sh`) уже следуют этому соглашению.
    - **Механическая проверка — §Приёмка Р8**, ОДНОЙ командой на
      GLOB-ПРОСТРАНСТВАХ (8 паттернов, РЕШЕНИЕ арбитража дословно), не на

      файла в него: будущие, ещё не написанные architect-оракулы покрыты

      architect-кругом, обновляющим пин), и ни один новый оракул своего

    - **Целостность самого пина обеспечена уже существующим барьером, а не

      версии/заморозки красит этот барьер. Без этой ссылки пин выглядел бы
      самоподтверждающимся, хотя таковым не является.
    - **Правило замыкания (РЕШЕНИЕ арбитража):** каждая команда §Приёмка
      этого контракта обязана вызывать ЛИБО исполняемый файл из запиненного
      пространства имён (Р1, Р2, Р9 — `red_*`/`probe_*`), ЛИБО барьер

      Приёмочный оракул вне обоих множеств — ЗАПРЕЩЁН. Остаток, названный
      арбитром прямо: пункт проверяется чтением §Приёмка критиком, а не

## §A1-эскалация (зафиксировать письменно, НЕ реализовывать)

Триггер: смоук-тест implementer'а (после A2, живой прогон `time bash
scripts/check_zones.sh .` на реальном дереве) показывает **>40 секунд**. Только

числом, только классом риска):
- DAG reachability на графе такого размера в чистом bash/awk рискует упереться

  python3-двойника — по прецеденту `check_staged.sh:240-265` (канонический

  триггер сработает;
- риск тихо разойтись с семантикой: шапка `check_zones.sh:261-269` — упрощённый

## Риски (named residual)

1. **`user.name` — не удостоверение** (существующий cognitive-only остаток
   шапки `check_zones.sh`, этим контрактом не меняется и не ухудшается).
2. **Байт-в-байт «решающая логика неизменна» (§Инварианты п.1) проверяется
   РЕГРЕССОМ (§Приёмка Р3/Р4), не построчным диффом implementer'а.** Если
   батчинг тихо меняет поведение в углу, НЕ покрытом 21+20 существующими
   фикстурами, регресс его не поймает — ловец: adversary, дополнительное
   зондирование на своём круге (прецедент `probe_slabye_realizacii.sh`:
   каждая известная слабая форма уже привязана к конкретному case-файлу; НОВАЯ
   слабая форма батчинга — новый adversary-зонд, не предугадан здесь).
3. **Единый порог Р2 не различает вклад roleblobs/existed.raw по
   отдельности** (§Инварианты п.6) — приемлемо, потому что дифференциал мал
   и недостижим без батчинга ОБОИХ конвейеров; если implementer формально
   «батчит» только ОДИН конвейер и как-то всё равно укладывается (например
   резко сократив M-подобную нагрузку другим путём) — это уже нарушение
   §Инварианты п.5/6 самих по себе, ловец — critic по тексту диффа, не только
   по числу.
4. **Границы `a,b,BOUND` (грубые) — щедрые константы architect'а, не
   пересчитаны под КОНКРЕТНУЮ реализацию implementer'а; `S,Δ` (дифференциал) —
   НЕ входят в эту свободу (РЕШЕНИЕ арбитража, §Инварианты п.2).** Если
   честная batched-реализация (не наивная, соблюдающая §Инварианты п.1/5) по
   какой-то ЗАКОННОЙ причине (например реальные редкие ветви draft/минт/
   СПАСЕНО на toy оказываются не такими уж редкими) даёт грубое число
   НЕЗНАЧИТЕЛЬНО выше `a·(K+M)+b`/`BOUND` — правка ЧИСЛА этих ДВУХ/ТРЁХ
   констант ЗОНА architect (не implementer, не критик) по его же правилу
   «порог не ослабляется ради собственного результата»: новая граница — с
   обоснованием и фикстурой/числом, которое старая граница пропускала бы как
   ложно-красное. Правка `S`/`Δ` той же свободой НЕ покрывается: они связаны
   `Δ>=2·S`, и любое изменение обязано СОХРАНЯТЬ это соотношение, иначе это
   ослабление решающего предмета, а не щедрая константа. Обычная (не
   наивная O(нагрузка)) регрессия продолжает краснить и на пересчитанной
   границе/дифференциале.
5. **A1-эскалация (§A1-эскалация) без сегодняшнего числа для триггера.**

   реализован); если A2 даёт, например, 39с, триггер формально не сработал,
   хотя запас до 60с-хардкода мал — residual, решает критик/владелец по факту
   смоук-теста, не эта фраза.
6. **Остаток, названный арбитром прямо (§Б1):** ни дифференциальный критерий,

## Условие done — ОДНОРАЗОВОЕ живое наблюдение CI (РЕШЕНИЕ арбитража, §Б3 часть 3; НЕ фикстура, НЕ постоянный страж)

То, что §Инварианты п.8 честно называет статически недоказуемым (workflow
может быть выключен в настройках репозитория, сужен `paths:`-фильтром,

«подключено безусловно» и «исполнилось». Оно НЕ механизируется постоянным
стражем: попытка сделать Р9 стражем, ходящим в GitHub API за списком шагов
прогона, ОТКЛОНЕНА арбитражем именно потому, что в этом дереве отсутствие
внешнего ресурса даёт rc=2 (NOT_IMPLEMENTED), и офлайн такой страж стал бы
МОЛЧА зелёным — постоянный страж, зеленеющий от недоступности сети, хуже
отсутствующего.

**Перед объявлением этого контракта `done`, ДОПОЛНИТЕЛЬНО к зелёной таблице
§Приёмка, ОРКЕСТРАТОР обязан**, после того как implementer-пачка запушена и
реальный CI-прогон на `origin` завершился зелёным:

1. Открыть лог этого прогона на GitHub Actions и глазами убедиться, что ОБА
   новых прямых шага (`npm run check:zones-call-budget` и
   `npm run check:protected-call-budget` — точные имена по факту implementer-
   пачки) присутствуют в списке исполненных шагов джобы `ci` И оба зелёные
   (не пропущены, не отменены, не помечены skipped).
2. Записать в `HANDOFF.md` (раздел «ГДЕ МЫ» текущего чекпойнта) дословно: SHA
   коммита этого прогона И прямую ссылку на сам прогон (`https://github.com/
   .../actions/runs/<ID>`), с пометкой «040: оба call-budget шага зелены на

3. Это делается ОДИН РАЗ на ФИНАЛЬНОЙ implementer-пачке перед `done`, не на
