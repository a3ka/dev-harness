ПРОВОДКА-ЭНФОРСМЕНТ: норма — инвариант производительности/корректности двух
существующих барьеров (call-count граница check_zones; -s ours-корректность и
call-count граница check_protected); судится прогоном фикстур этого контракта
(§Приёмка Р1/Р2), которые становятся постоянными CI-стражами (§Инварианты
п.8) — поведение РОЛЕЙ предмет не несёт (это не «как агент должен работать», а
«что обязан пройти артефакт scripts/»), потому guard-канал без role-строки.
Проверено: `roles/implementer.md` несёт только ОБЩУЮ норму «красная проверка
первична… нет красной проверки — не реализуй» — применима к КАЖДОМУ контракту
одинаково, не специфична для 040; цитировать её здесь означало бы пин общей
нормы под видом предметной (обход В1, не честный role-канал) — потому role= не
выбран. `AGENTS.md` не несёт секции о call-count-бюджетах барьеров — charter=
неприменим (нет секции для пина).

## Риски (named residual)

1. **`user.name` — не удостоверение** (существующий cognitive-only остаток
   шапки `check_zones.sh`, этим контрактом не меняется и не ухудшается).
2. **Байт-в-байт «решающая логика неизменна» (§Инварианты п.1) проверяется
   РЕГРЕССОМ (§Приёмка Р3/Р4), не построчным диффом implementer'а.** Если
   батчинг тихо меняет поведение в углу, НЕ покрытом 33+20 существующими
   фикстурами, регресс его не поймает — ловец: adversary, дополнительное
   зондирование на своём круге (прецедент `probe_slabye_realizacii.sh`:
   каждая известная слабая форма уже привязана к конкретному case-файлу; НОВАЯ
   слабая форма батчинга — новый adversary-зонд, не предугадан здесь).
3. **Единый порог Р2 (30) не различает вклад roleblobs/existed.raw по
   отдельности** (§Инварианты п.5) — приемлемо, потому что порог мал и
   недостижим без батчинга ОБОИХ циклов; если implementer формально
   «батчит» только ОДИН цикл и как-то всё равно укладывается в 30 (например
   резко сократив M-подобную нагрузку другим путём) — это уже нарушение
   §Инварианты п.4/5 самих по себе, ловец — critic по тексту диффа, не только
   по числу.
4. **Границы 452 (Р1) и 30 (Р2) — щедрые константы architect'а, не пересчитаны
   под КОНКРЕТНУЮ реализацию implementer'а.** Если честная batched-реализация
   (не наивная, соблюдающая §Инварианты п.1/п.6) по какой-то ЗАКОННОЙ причине
   (например реальные редкие ветви draft/минт/СПАСЕНО на toy оказываются не
   такими уж редкими) даёт число НЕЗНАЧИТЕЛЬНО выше границы — правка ЧИСЛА
   границы в этих ДВУХ файлах ЗОНА architect (не implementer, не критик) по
   его же правилу «порог не ослабляется ради собственного результата»: новая
   граница — с обоснованием и фикстурой/числом, которое старая граница
   пропускала бы как ложно-красное. Обычная (не наивная O(M)) регрессия
   продолжает краснить и на пересчитанной границе.
5. **A1-эскалация (§A1-эскалация) без сегодняшнего числа для триггера.**
   Триггер «>40с» — число владельца, не измерено на A2 (A2 ещё не
   реализован); если A2 даёт, например, 39с, триггер формально не сработал,
   хотя запас до 60с-хардкода мал — residual, решает критик/владелец по факту
   смоук-теста, не эта фраза.
