# Контракт 002 — режим подтверждений и роль steward (майлстоун плана 006)

Номер выдан механизмом: `bash scripts/next_id.sh CONTRACT` → `002`, тег `id/CONTRACT/002`.

Это первый майлстоун, исполняемый ПО новому регламенту: настоящий контракт, настоящий круг
критика, настоящая заморозка, настоящая раздача по зонам. Черновик предмета —
`plans/006-approval-mode-and-steward.md`; всё живое из черновика перенесено сюда, черновик после
заморозки этого контракта к жизни не возвращается.

## Предмет

Два дефекта сегодняшнего входа в систему:

1. **Режим — инвентарь, а не политика.** `workshop` делит входы на `--talk` (чтение) и `--work`
   (полный инвентарь), и обещание «в разговоре править нельзя» держится ОТСУТСТВИЕМ инструментов.
   Измеренный дефект этой конструкции: переключение режима требует перезапуска сессии, а слово
   владельца «работай» теряется вместе с контекстом перезапуска. У omp есть штатная политика
   подтверждений — `tools.approvalMode: always-ask`: каждый инструмент спрашивает разрешения, и
   режим становится свойством сессии, а не её инвентаря.
2. **Решения владельца живут в прозе.** Семь решений уже записано в переписке и планах; каждое из
   них — прецедент, на который должен опираться ответ «можно ли». В прозе их находит только тот,
   кто помнит; прецедент, который не находится, не существует.

## Критерий готовности

Четыре условия, каждое доказывается КОМАНДОЙ с кодом возврата:

1. **Режим — политика подтверждений.** `.omp/config.yml` несёт `tools.approvalMode: always-ask`
   (проектный слой). Один вход в `workshop`, без `--work`/`--talk` и требования `--plan`;
   `--plan` остаётся опциональным указанием предмета работы, а не ключом замка. Проверка:
   `bash workshop <проект>` поднимает сессию с полным инвентарём И always-ask; правка без
   подтверждения не проходит (фикстура).
2. **Реестр решений.** `decisions/` с записями в объявленной грамматике: дата, вопрос, решение,
   основание, область, условие пересмотра. Семь уже записанных решений извлечены из прозы.
   Проверка: `scripts/check_decisions.sh` → 0 — грамматика, полнота полей И разрешимость ссылки:
   поле «основание» обязано называть существующий в истории коммит (`git cat-file -e`), запись с
   неразрешимой ссылкой — код 1. Именной состав реестра сверяется списком: ровно файлы
   `decisions/001-…md` … `decisions/007-…md` из перечня в теле ЭТОГО контракта (ниже), перечень
   составлен архитектором по прозе и представлен кругу критика — счёт не проверяется «на глаз»
   исполнителем.
3. **Роль steward.** `roles/steward.md`: модель `@plan`, вердикт `decisions/proxy/`, отвечает
   ТОЛЬКО ссылкой на прецедент из `decisions/`; нет применимого прецедента — отказ с названным
   местом, а не мнение. Применимость — не вкусовщина: запись применима, когда её поле «область»
   покрывает предмет вопроса; конфликт двух применимых записей решает ДАТА — действует позднейшая,
   если у ранней не сработало «условие пересмотра». Проверка тремя отрицательными фиксtuрами:
   ссылка на несуществующую запись → код 1; ответ без основания → код 1; ссылка на запись, чья
   «область» предмета НЕ покрывает → код 1 (ловит «ответ любой существующей ссылкой»). Границы
   роли: объём, порядок, приоритет — то, что владелец уже решил; воля и деньги — владельцу.
4. **Норма и арбитр.** `AGENTS.md` и `roles/arbiter.md` несут поправку о делегировании воли
   (steward решает по прецеденту, владелец — новое; дата 2026-08-17). Проверка: правки уставных
   файлов несут строку `РАЗРЕШИЛ-ВЛАДЕЛЕЦ:` в том же коммите — держит `check_charter.sh`.

Чего этот критерий НЕ обещает, названо прямо: always-ask проверяется конфигом и фикстурой
поведения лаунчера, а не перехватом живого диалога — перехват чужой сессии не строится. Помечено
`cognitive-only`, ловец — круг адверсария.

## Исполнители и зоны

Работа ДЕЛИТСЯ — впервые под новым регламентом, и зоны объявлены построчно:

ЗОНА implementer: .omp/config.yml workshop scripts/check_decisions.sh fixtures/check_decisions/ decisions/ roles/steward.md .omp/agents/ package.json config/ .github/workflows/ci.yml
ЗОНА architect: AGENTS.md roles/arbiter.md scripts/roles.ts plans/006-approval-mode-and-steward.md contracts/002-approval-mode-steward.md NABLIUDENIA.md
Разделение по предмету, не по удобству: исполнитель строит МЕХАНИЗМ — политику входа, реестр,
барьер, роль steward и ПРОВОДКУ новых команд в приёмку и CI (правило 6: барьер вне CI не
барьер); архитектор несёт НОРМУ — `AGENTS.md` и `roles/arbiter.md` уставные, правки требуют
строки владельца, которую исполнитель писать не вправе (правило 11), и замысла, который не
разменивается на исполнение.

Пересечений зон нет: списки путей не имеют общих элементов, проверено до предъявления.

Правка v2: `scripts/roles.ts` добавлен в зону architect по заявке исполнителя — роль
порождается ТОЛЬКО парой «файл роли + запись в таблице», и зона v1 разрезала эту связку.
Тот же дефект, другие связки, найден кругом по v2: сам КОНТРАКТ (его правит архитектор
по процедуре vN) и NABLIUDENIA.md (его ведёт архитектор по прямому слову владельца) —
оба были вне зоны, и заморозка v2 краснела на собственных коммитах архитектора. Урок Н-22
подтверждён дважды за один майлстоун: зона обязана покрывать ВСЁ, что её автор правит
в диапазоне, включая процедурные правки самого контракта.

Реестр обязан содержать РОВНО эти записи первыми; каждая — с полем «основание», разрешающимся в
названный коммит. Позднейшие решения владельца добавляются тем же порядком и этим же барьером —
реестр открыт, но эти семь составляют извлекаемое из прозы ядро:

| 002 | Раскладка моделей: дорогое семейство — точечно, массовая работа на дешёвом; `implementer` на MiniMax | `.omp/config.yml`, шапка «решение владельца 2026-08-16» |

| 004 | План и контракт не утверждаются без вердикта критика; устав — только словом владельца | `plans/007-reglament-vorkflou.md`, раздел «Причина» (требования дословно) |

Барьер `check_decisions.sh` сверяет: файлов ровно семь с этими номерами, каждый с разрешимым
основанием; лишний файл без основания — код 1; отсутствие любого из семи — код 1. Состав ПО
СМЫСЛУ каждой записи не механируется: сверка «решение в записи равно решению в источнике» —
чтение круга критика, записано здесь, чтобы не оставлять исполнителю.

## Приёмка

Команды с кодами возврата, каждая обязана иметь пункт в CI (правило 6):

- `npm run check:gen` → 0 (роль steward порождена, таблица ролей пополнена);
- `npm run check:antiplacebo` → 0 (фикстуры трёх новых барьеров предъявлены красными);
- `npm run check:ci-parity` → 0;
- `npm run check:charter` → 0 (уставные правки несут строку владельца);
- `npm run check:decisions` → 0 — НОВАЯ команда приёмки, обязана получить шаг в CI (правило 6).

Живой прогон — ВНЕ списка CI-команд, отдельным пунктом: `bash workshop <проект>` поднимает
сессию с полным инвентарём и активным always-ask; интерактивный вход в CI не гоняют
(записанное исключение паритета), потому он здесь и не обещает кода возврата — предмет
живого прогона проверяется человеком и фикстурой поведения лаунчера из критерия 1.
