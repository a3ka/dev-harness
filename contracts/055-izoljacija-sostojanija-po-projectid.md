## Frontier: границы и отвергнутые варианты

- **Граница-1 (изоляция — по ProjectId, не по корню репо).** Спека §4.3
  изолирует «от других проектов»; два репо ОДНОГО проекта (общий слой)
  делят state по слову спеки, а лок (М2) — по КОРНЮ: «одна сессия один
  репозиторий» (workshop:554) — два клона одного репо не блокируют друг
  друга. Отвергнуто: keying HOME по корню репо — противоречит §4.3
  («изоляция от других проектов», не от других репо своего проекта).
- **Граница-2 (state-корень — по формуле 028, вычисление ДО export HOME).**
  `PSTATE = <base>/dev-harness-projects/<projectId>`, где
  `<base> = ${HARNESS_SCRATCH:-${XDG_STATE_HOME:-$HOME/.local/state}}`,
  вычисленный ДО подмены HOME (прецедент workshop:75-80 — та же болезнь
  «разрешившийся внутрь» уже закрыта в 028). HOME = `$PSTATE/home`,
  скратч = `$PSTATE/scratch` (`export HARNESS_SCRATCH` — потребители
  существуют: guards/models_actual читают ручку), логи/журнал =
  `export XDG_STATE_HOME="$PSTATE/state"` — иначе УНАСЛЕДОВАННЫЙ глобальный
  XDG_STATE_HOME уводил бы журнал omp в общий каталог мимо изоляции.
  Дефолт-компонент `dev-harness-projects` — константа workshop; сегмент
  НЕ содержит `dev-harness-sessions` (дев-зона мастерской — другой мир).
  Dev-режим workshop не меняется.
- **Граница-3 (projectId санируется ДО пути — W4).** projectId — чужой ввод
  (слой проекта), вставляемый в путь. Вне класса `^[a-z0-9][a-z0-9_-]*$`
  → rc 1 W4 (лаунчер, не резолвер: грамматика 054-И-4 «непустая строка»
  не правится — резолвер остаётся совместим с замороженным 054; path-safety —
  НОВАЯ обязанность потребителя пути). Класс — ТОТ ЖЕ литерал, что у
  барьерных имён 054-И-4 (один класс в одном файле на потребителя).
- **Граница-4 (лок — PID-файл,staleness по kill -0).** Лок =
  `$PSTATE/sessions/<hash8>.lock`, hash8 = первые 8 hex sha256 от
  realpath корня репо (та же свёртка, что 028 применяет к корню мастерской;
  вычисление — в workshop, второй копии нет). Содержимое — PID владельца.
  Живой режим: лок есть и `kill -0 <pid>` жив → rc 1 W3; мёртв → замена.
  Лок пишется с `$$` ПЕРЕД `exec omp`: PID переживает exec, после смерти
  процесса лок становится мёртвым сам — отдельного релиза не существует
  и не нужно. Остаточный риск PID-reuse назван в §Модель угроз. Probe лок
  НЕ занимает (probe — не сессия), но живой лок проверяет: проба судит
  механизм без exec omp. Отвергнуто: mkdir-лок без staleness — зависшая
  сессия блокировала бы проект навсегда; отвергнуто: отказ по факту двух
  omp на машине — не этот предмет (Н-108: «на том же корне»).
- **Граница-5 (метеринг — env+баннер; буквальные заголовки — вне 055).**
  Workshop (probe и живой) экспортирует `METERING_PROJECT=<projectId>` и
  `METERING_ROLE=<SESSION_ROLE>` и печатает в баннере строку
  `METERING: project=<projectId> role=<SESSION_ROLE>`. Канал omp→прокси
  ДОСТОВЕРНО известен только для Bearer-токена роли (`${METERING_TOKEN_<ROLE>}`
  в .omp/models.yml — роль приписана токеном) и родных omp-заголовков
  (x-metering-model, x-request-id — контракт 005(м)); способность omp
  посылать ПРОИЗВОЛЬНЫЕ заголовки провайдера НЕВЕРИФИЦИРОВАНА (проба строк
  бинарря пуста). Строить инвариант на неверифицированной capability —
  запрет (правило «не предъявляй меру, которую не прогнал»); потому
  буквальные HTTP-заголовки x-factory-* — ВНЕ 055 (§НЕ ЗАЩИЩАЕТ), а предмет
  (в) закрыт тем, что владелец distrust-канала назвал «одной строкой»:
  env + баннер, зафиксированные пробой. Расширение — отдельный предмет,
  если боль измерена живой сессией.
- **Граница-6 (packs — несомое значение, слияние единицей).** `packs`:
  массив строк класса `^[a-z0-9][a-z0-9_-]*$` (литерал класса — тот же
  массив резолвера, что у барьеров; отдельной константы НЕ заводим);
  `[]` допустим на обоих слоях; отсутствует в обоих → вывод
  `packs.value = []`, `origin = "project"`. Слияние как ЕДИНИЦА:
  ключ репо-слоя замещает массив целиком (прецедент barriers, 054
  Граница-6). НЕ-массив → P6; элемент вне класса → P6 с ЭЛЕМЕНТОМ в
  причине. Потребитель значения — C0 (вне 055): резолвер несёт грамматику
  и происхождение, не семантику паков.
- **Граница-7 (объём).** НЕ входит: перенос резолвером schemas §4.2,
  lock-файл §4.3, snapshot §4.5, правка metering_proxy.ts (005 frozen:
  схема журнала/атрибуция — предмет 005, не 055), правка .omp/models.yml
  (005), живой запуск на odelix-stack (Г1 — владелец), release/очистка
  чужих мёртвых локов вручную (staleness — автоматическая).

## Инварианты

### М1 — изоляция state по ProjectId (workshop, режим проекта)

- **И-1 (санитизация projectId).** После резолвера лаунчер читает
  `projectId.value`; значение вне класса `^[a-z0-9][a-z0-9_-]*$` → rc 1,
  W4 (значение названо, класс назван). Проверка ДО любого использования
  в пути; резолвер при этом уже зелёный (его И-4 projectId — непустая
  строка — не правится).
- **И-2 (state-корень и три экспорта).** `PSTATE=<base>/dev-harness-projects/
  <projectId>` (Граница-2, base до подмены HOME); затем `export
  HARNESS_SESSION_HOME="$PSTATE/home"`, `export HOME="$PSTATE/home"`,
  `export HARNESS_SCRATCH="$PSTATE/scratch"`, `export
  XDG_STATE_HOME="$PSTATE/state"`. Ни один из четырёх путей не содержит
  `dev-harness-sessions` (дев-зона мастерской). Dev-режим (работа над
  инструментом) не меняется ни на байт.
- **И-3 (probe-баннер несёт state).** Probe печатает после `PROMPT:` строку
  `STATE: <PSTATE>` и строку `METERING: project=<projectId>
  role=<SESSION_ROLE>` (probe и живой режим — один код, 054 Граница-3).

### М2 — именованный отказ второй сессии (workshop, режим проекта)

- **И-4 (лок и отказ).** Лок `$PSTATE/sessions/<hash8(realpath(корень
  репо))>.lock`; hash8 = `sha256 | cut -c1-8`. Файл есть, содержимое —
  числовой PID живого процесса (`kill -0`) → rc 1, W3: корень и pid
  названы. Нечисловой/пустой содержимое — трактется как мёртвый
  (замена), не как отказ: битый лок не блокирует проект.
- **И-5 (живой режим занимает).** После всех проверок 054/055 и ДО
  `exec omp` живой режим пишет `$$` в лок (mkdir -p каталога). PID
  переживает exec — мёртвый процесс сам делает лок замещаемым.
- **И-6 (probe не занимает, но судит).** Probe не создаёт лок и не
  оставляет файлов в `$PSTATE/sessions/` после себя (баннер/промпт —
  в `$PSTATE/home`, это НЕ сессия-лок); при живом локе probe отказывает
  rc 1 W3 — механизм судим пробой без exec omp.

### М3 — метеринг-заголовок (env + баннер)

- **И-7 (env и строка).)** Режим проекта (probe и живой) экспортирует
  `METERING_PROJECT=<projectId>` и `METERING_ROLE=<SESSION_ROLE>` ДО
  exec omp; баннер несёт строку `METERING: project=<projectId>
  role=<SESSION_ROLE>` (grep -F дословно). Заголовки HTTP omp→прокси —
  вне 055 (Граница-5).

### М4 — ключ packs (profile_resolver, дельта массива алфавитов)

- **И-8 (алфавит).)** В SCHEMA_LEVELS резолвера добавляются строки
  `repo:packs:optional` и `defaults:packs:optional` (уровень defaults —
  в defaults-сканировании 054). Значение — массив; элементы — непустые
  строки класса `^[a-z0-9][a-z0-9_-]*$` (тот же литерал, что у барьеров).
  НЕ-массив → rc 1, P6 (`packs: <json-значение>`); элемент вне класса →
  rc 1, P6 (`packs: <элемент>` — ЭЛЕМЕНТ назван). Пустой массив допустим.
- **И-9 (слияние и вывод).)** Слияние единицей (прецедент barriers):
  ключ репо-слоя замещает массив целиком; иначе — defaults слоя проекта;
  нет нигде → `packs: {"value": [], "origin": "project"}`. Вывод несёт
  `packs {value, origin}` тем же форматом, что остальные листья.
- **И-10 (041-гигиена packs).)** packs — новое структурное поле чужого
  ввода: профиль батареи гигиены
  `fixtures/parsing_hygiene_battery/profiles/profile_resolver.sh`
  расширяется packs-кейсами тех же 4 классов (delimiter-collision: элемент
  с байтами `:`/`"`; regex-injection: элемент-метасимволы — класс отвергает;
  silent-drop: валидный packs присутствует в выводе побайтово;
  self-application-green); прогон `run_battery.sh profile_resolver` → rc 0.
- **И-11 (054 не ломается).)** Все существующие клетки семьи
  fixtures/workshop_project/ (батарея 054, 9/9) и parsing-батарея
  остаются зелёными после дельты: добавление ключа НЕ судит `packs`
  как неизвестный (клеток с packs-негативом в 054 нет — grep по батарее
  живьём: `grep -c packs fixtures/workshop_project/red_profil_dva_sloja.sh`
  = 0). Фикстуры 054 не правятся.

## Модель угроз (норма 041)

ЗАЩИЩАЕТ:
- утечку состояния между проектами: HOME/скратч/журнал проектной сессии
  выводятся из ProjectId; файл, записанный в HOME проекта A, не наблюдаем
  в дереве проекта B (включая унаследованный глобальный XDG_STATE_HOME —
  экспорт перекрывает);
- path-injection через projectId (слой проекта — чужой ввод): значение вне
  класса пути → именованный отказ ДО создания каталогов; `..`/слэши/
  пусто не проходят;
- вторую живую сессию на том же корне (Н-108): отказ именованный, с root
  и pid; мёртвый лок замещается автоматически — зависание не блокирует
  проект навсегда;
- тихую неприписку расхода: проект и роль видны в окружении и баннере
  с запуска, отсутствие строки — красная клетка (не «узнаем по гроссбуху
  спустя месяц»);
- тихий дрейф схемы при входе C0: ключ packs легален СЕЙЧАС с грамматикой
  и происхождением; C0 подключает потребителя без правки замороженного
  алфавита; НЕ-список и мусорный элемент отказывают с именем элемента.

НЕ ЗАЩИЩАЕТ:
- буквальную доставку x-factory-project/x-factory-role до прокси:
  capability omp НЕВЕРИФИЦИРОВАНА (Граница-5); если фабричный прокси
  требует именно заголовки — отдельный предмет с живой пробой omp;
- PID-reuse: мёртвый процесс, чей PID занят посторонним, продлевает отказ
  W3 до ручного удаления лока (остаточный риск PID-файла, класс общий;
  ловец — живый запуск, не фикстура);
- гонку двух ОДНОВРЕМЕННЫХ стартов (TOCTOU check-then-write без атомарного
  O_EXCL): окно между проверкой и записью лока; цена — два omp на корне
  в узком окне; закрывается отдельным предметом, если боль измерена
  (Н-108 был последовательный случай);
- подделку слоя проекта/репо-слоя владельцем клона (TCB-класс 040);
- изоляцию ОТ ПРОЕКТА К РЕПО: два репо одного проекта делят state по
  слову спеки §4.3 (Граница-1) — это не дефект, а граница.
