## Предмет

Решение владельца (2026-09-21, Н-121, дословно): «вариант (в) — дизайн-фикс check:protected,
распознавать честный git-mv (контент существует по другому пути на HEAD) отдельно от
исчезновения; это КОРРЕКЦИЯ под инвариант ROADMAP §5 «существовал → существует на HEAD», НЕ
ослабление. Красный тест: генуинное удаление без ALLOW → красный; rename → зелёный».

Сегодня `excuse_for` (scripts/check_protected.sh:194-220) требует `ALLOW-ARTIFACT-DELETE`
именно в удаляющем коммите — и честный `git-mv` протокольного артефакта (515d0c5,
539b759: контент байт-в-байт, жив на HEAD) красится как исчезновение; постфактум-разрешение
кодом не засчитывается, а перепись запушенной истории запрещена отдельным барьером — тупик
Н-121. Коррекция: путь, исчезнувший из дерева в коммите c, считается СУЩЕСТВУЮЩИМ, если
перенесён (§Семантика); истинное исчезновение блоба — по-прежнему требует ALLOW-строку в
удаляющем коммите. Анти-гейминг: rename-с-изменением-контента ≠ rename — блоб другой,
переноса нет.

## Семантика

Единый источник грамматик — этот контракт; реализация несёт строки отчёта ПОБАЙТОВО.

1. **Перенос** (НОВОЕ, единственная правка предмета). Путь p из missing считается
   перенесённым, если:
   - c — удаляющий коммит p по ДЕЙСТВУЮЩЕЙ мере `excuse_for` (`git log HEAD --full-history
     --no-renames -m --diff-filter=D --format=%H -- <p>`, первый);
   - B — блоб p в родителе c; если коммит слияния и p живёт в нескольких родителях РАЗНЫМИ
     блобами — переноса нет, fail-closed (требуется ALLOW);
   - в c появился путь q ≠ p (статус A той же мерой `--no-renames -m`) с блобом ровно B;
   - блоб B присутствует в `git ls-tree -r HEAD` хотя бы под одним путём — ЛЮБЫМ, внутри или
     вне области защиты. Пункт 4 отделён от пункта 3 намеренно: перенос с последующей смертью
     носителя (R5) и цикл с конечным исчезновением (R6) — исчезновения, а не переносы.
   Способ переноса (mv, копия, восстановление) НЕ различается: инвариант от результата, не от
   способа (шапка барьера :4-10); git-детекция переименований (diff -M, сходство) мерой быть
   не может — :181-185.
2. **Порядок проверок** p из missing: разрешение `excuse_for` (БЕЗ ИЗМЕНЕНИЙ: грамматика,
   кавычки, первая колонка, именной удаляющий коммит) → перенос → иначе FAIL. Разрешение и
   перенос не конкурируют: любое достаточно.
3. **Строки отчёта.** FAIL-строка и ok-строка разрешения — байт-в-байт без изменений
   (`защищённый артефакт существовал и на HEAD его нет: <путь>`;
   `исчез с явного разрешения: <путь>`). НОВАЯ ok-строка переноса, дословно:
   `перенесён, контент жив на HEAD: <путь>`. Суммарная строка отчёта не меняется.
4. **НЕ меняется всё остальное**: область из `roles/*.md` по всем достижимым коммитам,
   грамматика поля verdict и отказ на неразобранное, `plans/` явно, объединение деревьев
   достижимых коммитов, отказ на shallow (rc 1), env-гигиена, коды 0/1/2, обратная сверка
   разрешений не делается.
5. **Зелёная ветвь переноса запирается дриллом** `scripts/drill_protected_rename.sh`
   (НОВЫЙ, по прецеденту drill_protected_exception.sh: анти-плацебо доказывает только
   красное): герметичное игрушечное дерево, ДВА случая — перенос внутри области
   (verdicts/adversary/v-1.md → verdicts/adversary/v-2.md, байт-в-байт) и перенос наружу
   (plans/001-p.md → notes/001-p.md); для каждого барьер рядом с дриллом обязан дать rc 0 И
   назвать перенос в отчёте ok-строкой из п.3; иначе rc 1 с именем отказа «ОТКАЗ: перенос не
   распознан — …». Коды возврата 0/1/2 объявлены в шапке. Активация — с реализацией (вместе
   со скриптом), НАПЕРЁД реализации не прогоняется: на текущем барьере его зелёная ветвь
   красна по построению.

## Приёмка

Стаб-привязки Н-39 — в КОДЕ фикстур (шапки case-файлов), здесь инварианты и rc-команды.
Ожидания каждой пробы ДО и ПОСЛЕ фикса названы; красные пробы обязаны быть красными в ОБОИХ
мирах (узлы развилки — в шапках фикстур). Команды — из корня дерева.

Перенос обязан удерживать ОБА условия §Семантика п.1 ОДНОВРЕМЕННО, ни одно не заменяет
другое: (А) путь q появился статусом A ИМЕННО в удаляющем коммите c (третий подпункт п.1) и
(Б) блоб B присутствует в `git ls-tree -r HEAD` хотя бы под одним путём (четвёртый подпункт
п.1). Реализация, проверяющая только (Б) и пропускающая (А), зеленеет по одному лишь следу
блоба на HEAD — блокер Б1 (verdicts/critic/contracts-039-v1.md, круг 1, dccde2d). Проба R7 —
прямая фикстура этого контрпримера: q появляется коммитом РАНЬШЕ удаляющего, а не в нём
самом.

## Риски (named residual)

1. Перенос по блобу не отличает mv от копии — намеренно (инвариант контента); артефакт,
   «спасённый» копией наружу области, жив по контенту. Привязка существования к путям внутри
   области — отдельный предмет и слово владельца, НЕ этот контракт.
2. Modify/delete в слиянии с разными блобами родителей → fail-closed (требуется ALLOW):
   скучно, безопасно, живых случаев на дереве нет.
3. Постфактум-коммит 619cbc2 с ALLOW для 515d0c5 остаётся в истории: обратная сверка (есть
   строка, а файл на месте) не делалась и не делается — вреда нет, grep-след санкции сохранён.
