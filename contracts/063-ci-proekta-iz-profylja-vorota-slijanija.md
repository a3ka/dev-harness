## Предмет

Боли измерены пилотом ODX-STK-001 (Н-167, `.harness/pilot-pains.md` на
odelix-stack 6bd25c9): **Б-3** «нет test target/CI: регрессия issue-map не
поймается ничем; ревьюер дороже»; **Б-8** «нет механизма приземления:
слияние держалось словом владельца, не механизмом» + профиль объявляет
несуществующий workflow (закрыт 059 наполовину: сверка есть, запуска нет).
Дыры нейрослопа (HANDOFF, блок Д1-Д9): **Д3** «работает у меня», **Д4**
«выдуманные API/слабые типы → typecheck+тесты гейтом».

Решения владельца (сводная редакция §11, раздел IV; ROADMAP:308-315
дословно): харнесс даёт МЕХАНИЗМ — CI-шаблон, гоняющий команды и барьеры
из профиля, + ворот слияния; merge gate = закоммиченный вердикт ревьюера
accept ∧ нет `.review/`-файлов status ready/partial; merge только `--no-ff`;
обе полярности проверить на odelix-workstation, rc в отчёте. Проверка
issue-map ≡ ISSUES.json (schema-check, Б-6) — задача сессии odelix-stack,
НЕ предмет 063.

Три механизма:

- **(а) генератор** `scripts/gen_ci_workflow.sh --repo <корень>` — строит
  CI-джобу проекта из резолва профиля и пишет её в объявленный профилью
  `ci.workflow`-файл репо проекта;
- **(б) ворот слияния** `scripts/check_merge_gate.sh --repo <корень>` —
  rc 0 ⟺ закоммиченный accept-вердикт ∧ нет незакрытых `.review/`-находок;
- **(в) land-путь проекта** `scripts/land_project.sh --repo <корень>
  --branch <ветка>` — единая дверь слияния: гейт (б) впереди, merge только
  `--no-ff` с identity оркестратора (прецедент 016).

## Frontier: границы и отвергнутые варианты

- **Граница-1 (механизм, не проверка).** Предмет — шаблон CI + ворота;
  WHAT джоба проверяет содержательно (schema-check, тесты самого проекта) —
  сессии проекта. Отвергнуто: вшивание в шаблон проверки issue-map —
  решение владельца «не наш код».
- **Граница-2 (профиль — единственный источник джобы).** Шаги джобы =
  объявленные команды + обязательные барьеры; ручная правка сгенерированного
  файла не предполагается (заголовок GENERATED, И-6). Отвергнуто: `--check`
  режим сверки регенерации — отдельная боль (драйв-детект), не мешающая
  предмету; завести при первой живой боли.
- **Граница-3 (гейт судит два свойства, не качество ревью).** Гейт НЕ судит
  содержание вердикта/находок: первая строка `accept` и статус-строка —
  единственные чтения. Отвергнуто: парсинг тела вердикта/чекбоксов —
  semantic-суд ревьюера, механизмом не дублируется.
- **Граница-4 (барьер = объявленный путь, паритет 059).** Шаг барьера
  `<имя>` исполняет `bash <workflowPaths.fixtures>/<имя>.sh`; файла в дереве
  нет → именованный отказ генератора (класс «профиль объявляет
  существующую инфраструктуру» — та же семантика, что 059 для ci.workflow).
  Отвергнуто: исполнение барьеров из dev-harness-чекаута в CI проекта —
  межрепо-пин слова владельца о закреплённых копиях (§11 «репо
  самодостаточен»), не этого слайса.
- **Граница-5 (объём).** НЕ входит: правка `scripts/land_agent.sh` (дверь
  016 харнесса), `scripts/profile_resolver.sh`, workshop (grep по `workshop`
  — auto-merge/land-вызовов нет; проводка = сама дверь `land_project.sh`),
  branch-protection GitHub API (токен — только чтение, отдельное слово),
  генерация для monorepo-зон (по боли).

## Инварианты (кодовые)

- **И-1 (конъюнкция гейта).** `check_merge_gate.sh --repo R` → rc 0 ⟺
  (а) в R есть закоммиченный accept-вердикт (И-2) ∧ (б) нет блокирующих
  `.review/`-файлов (И-3). Любой иной исход — rc 1 с именованной причиной на
  stderr, stdout пуст. Порядок проверок: сначала `.review/` (свежая боль
  старше), затем вердикт.
- **И-2 (закоммиченность вердикта).** Вердикт = файл `*.md` под
  резолвнутым `workflowPaths.verdicts` (рекурсивно), у которого ПЕРВАЯ
  строка блоба `HEAD:<путь>` — литерал `accept` (чтение `git show`,
  не рабочая копия: незакоммиченный/изменённый после коммита файл не
  считается). FAIL-вердикты и пустой каталог — не accept.
- **И-3 (грамматика .review/).** Судятся файлы `.review/*.md` верхнего
  уровня репо. Frontmatter: первая строка `---`, до следующей `---`; строка
  вида `status: <значение>` — самостоятельная строка; алфавит значений
  замкнут: `ready` | `partial` | `done`. `ready`/`partial` → rc 1, фраза
  дословно `merge gate ОТКАЗ: незакрытая находка ревьюера: <файл>
  (status: <значение>)`, `<файл>` — путь от корня репо (`.review/<имя>`);
  `done` — не блокирует; значение вне алфавита → rc 1 `merge gate ОТКАЗ:
  нечитаемый статус находки: <файл> (status: <значение>)` (fail-closed);
  файл без status-строки — не находка, игнорируется. Незакоммиченность
  `.review/`-файла не разблокирует (находка свежести не обязана).
- **И-4 (перенос профиля в джобу).** Генератор после резолва (И-8) пишет
  workflow в `<R>/<ci.workflow>`: джоба `harness` с шагами в фиксированном
  порядке — каждая объявленная непустая команда ключа из
  {test, build, typecheck, lint} → СВОЙ шаг `- name: commands.<ключ>` с телом
  блок-скаляром (`run: |`), строка команды — с отступом ровно 10 пробелов
  (многострочная команда — каждая строка с тем же отступом); каждый элемент
  `barriers.mandatory` → СВОЙ шаг `- name: barriers.<имя>` с телом
  `bash <workflowPaths.fixtures>/<имя>.sh` (отступ 10). Шаг переноса несёт
  ровно два ключа — `name` и `run`; тело шага — ТОЛЬКО строки самой команды
  (вызова барьера): транспортные обёртки, превращающие команды в данные
  неисполняемого шага (heredoc-нооп `: <<'…'` и подобные), запрещены —
  исполнимость предъявляет И-9. Барьер без файла в дереве → rc 1, фраза
  дословно `ci-генератор ОТКАЗ: объявленный барьер отсутствует в дереве:
  <имя> (<путь>)`, файл-цель не тронут. Тело команды не переизобретает
  YAML-структуру (блок-скаляр держит произвольные байты строки — свойство
  представления).
- **И-5 (vacuous).** Резолв не объявляет НИ команд, НИ барьеров → rc 0,
  stderr дословно `ci-генератор: профиль не объявляет команд и барьеров —
  vacuous, файл не тронут`, файл-цель байт-в-байт неизменен. `ci.workflow`
  не объявлен вовсе → rc 0, stderr дословно `ci-генератор: профиль не
  объявляет ci.workflow — генерировать некуда`, ничего не пишется.
- **И-6 (детерминизм).** Повторный прогон на том же дереве — те же байты
  файла-цели; первая строка файла — `# GENERATED by dev-harness
  gen_ci_workflow — не править руками; источник — harness.project.json`.
- **И-7 (ленд: гейт впереди, --no-ff литерален).** `land_project.sh` до
  merge зовёт `check_merge_gate.sh --repo R`; красный → rc 1 (stderr гейта
  проксировается), HEAD целевой ветки неизменен. Зелёный → merge ТОЛЬКО
  `--no-ff`, identity оркестратора литералом в ОДНОЙ строке с `git merge`
  (канарейка 016 И-5), subject `land: <ветка>`, committer == orchestrator
  (сверка после merge, 016 И-9). ff-слияние невозможно по построению.
- **И-8 (единый резолв).** Гейт и генератор зовут
  `scripts/profile_resolver.sh --repo R` и читают его merged-JSON; отказ
  резолвера → rc 1 с дословным прокси stderr; собственный парсинг
  harness.project.json в новых скриптах запрещён.

- **И-9 (исполнимость шагов; правка по РЕШЕНИЮ арбитража 063-Б4, `dea4268`).**
  После успешной генерации непустого профиля локальное исполнение
  сгенерированной джобы `harness`: (i) раннер читает файл-цель, переданный
  АРГУМЕНТОМ, — результат клеток ИНВАРИАНТЕН к stdin батареи (раннер не
  блокируется на stdin и не подъедает его); (ii) тело каждого `run: |`-шага
  исполняется `bash --noprofile --norc -eo pipefail -c` в корне репо — форма
  `shell: bash` GitHub по умолчанию (ненулевая команда тела гасит тело:
  `after`-эффекты отсутствуют); шаг без `run` (например `uses:`)
  пропускается, отказ шага = отказ джобы с тем же rc, шаги после упавшего не
  исполняются — (а) производит эффекты КАЖДОЙ объявленной команды и КАЖДОГО
  барьера в фиксированном порядке И-4, (б) отказ объявленной команды — rc
  джобы, шаги после упавшего эффектов не дают; (iii) раннер условий НЕ
  вычисляет: строка вне контура И-10 и вне тела шага не «пропускается», а
  делает файл неконформным по И-10 — сверка И-10 в клетках к6/к11 стоит
  РАНЬШЕ исполнения, раннер полагается на неё (выбор автора по П2/П3
  РЕШЕНИЯ). Способ локального предъявления — раннер батареи, извлекающий
  шаги по фиксированному лейауту И-4; внешний GitHub в круге судьи не
  требуется.
- **И-10 (закрытая форма файла-цели; новый, арбитраж 063-Б4 П1/П2).**
  Файл-цель = литеральный контур ниже + шаги И-4, ДРУГИХ СТРОК НЕТ (контур
  дословно, построчно):

```yaml
# GENERATED by dev-harness gen_ci_workflow — не править руками; источник — harness.project.json
name: harness
on: [push, pull_request]
jobs:
  harness:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
```

  Любой ключ джобы или шага сверх контура (`if`, `continue-on-error`,
  `defaults`, `env`, `timeout-minutes`, `shell`, `strategy` — перечень
  иллюстративный, правило — «ничего сверх контура»: отключение джобы или
  шага, подавление отказа, смена события, смена shell) делает генератор
  неконформным. Сверка — литеральная: эталон рендерится БАТАРЕЕЙ из этого
  контура и значений игрушки (случайных) по правилу И-4, приёмка —
  `cmp -s <файл-цель> <эталон>` → rc 0, отказ с `diff` в stderr (замер 2
  арбитража: шесть форм одного дефекта — отключение джобы/шага,
  `continue-on-error`, смена триггера, смена shell, несуществующий раннер —
  все зелёные для раннера, читающего только лейаут).

## Единый источник семантик

- Профиль (команды/барьеры/пути/CI-цель) — `scripts/profile_resolver.sh`
  (054/055/059), вызовом, не копией грамматики.
- Форма вердикта — живой прецедент `verdicts/review/*.md` (первая строка

- **`--no-ff` + identity-канарейка** — литералы `scripts/land_agent.sh:182`

## Модель угроз

ЗАЩИЩАЕТ:
- слияние в репо проекта без закоммиченного accept-вердикта ревьюера
  невозможно механизмом (Б-8: «слияние держалось словом владельца»);
- незакрытая находка (`.review/` ready|partial) блокирует слияние именованным
  отказом с именем файла и статусом — норма ролей получает исполнителя;
- несуществующий барьер профиля не попадает в CI молча — именованный отказ с
  путём (паритет 059 для объявленной инфраструктуры);
- строка команды профиля не вводит новые YAML-ключи джобы (блок-скаляр:
  байты данных не переиспользуются как разделители структуры — норма 041);
- нестабильный CI-файл не расползается: регенерация детерминирована (И-6).
- «джоба» без исполнения команд профиля (транспорт «команды как данные»,
  heredoc-нооп) не проходит приёмку: эффекты каждого шага проверяются
  локальным исполнением, отказ шага распространяется на джобу (И-9);
- грязная рабочая копия tracked-вердикта (первая строка переписана после
  коммита) ворота не открывает: судится блоб `HEAD:<путь>`, не рабочий
  файл (И-2).
- ключ workflow сверх литерального контура (отключение джобы или шага,
  подавление отказа, смена shell, смена события) не проходит приёмку: форма
  файла закрыта (И-10), раннер интерпретирует всё, что в ней есть (И-9) —
  арбитраж 063-Б4, класс «локальный исполнитель считает исполняемым всё,
  чего не понимает»;

НЕ ЗАЩИЩАЕТ:
- подмена `git`/`jq` в PATH исполнителя (TCB-класс 040-II/III, тот же
  остаток, что у check_zones/land_agent; лечение — доверенный вызов, не
  предмет 063);
- автор репо, комитящий себе accept-вердикт без ревью: гейт судит процедуру
  (наличие закоммиченного артефакта), не подлинность ревьюера — TCB
  «доверенное дерево проекта»;
- **`.review/`**-файл с УДАЛЁННОЙ status-строкой (вне граммиты находок — не
  находка): сознательно, ловец — ревьюер следующего круга (гейт не обязан
  угадывать намерение файла без формы);
- TOCTOU между проверкой гейта и merge (окно в land_project): исполнитель
  двери — доверенная сторона, как в 016;
- содержательное качество самих команд/барьеров профиля («тесты-пустышки»
  проходят) — предмет ревью, гейт переносит объявления байт-точно.
- семантика самого контура в GitHub (что push/PR на ubuntu-latest с checkout
  исполняет `run:`-шаги подряд с отказом на первом ненулевом) — TCB
  «платформа CI», локально не воспроизводится;
- генератор, различающий игрушку и живой репо по значениям
  (input-discriminating мутант), — вне демаркации: случайные значения делают
  подсмотр констант непрактичным, остаток — ревью кода харнесса.
