## Предмет

Переходный допуск лендов в main при красном известном debt. Дословно владелец (п.1, императивы
перенесены без пересказа):

- доверенный список известных дефектов main `registry/main-ci-exceptions.json` (читается из
  ПРИНЯТОЙ ревизии main, не из дерева кандидата); запись: target, устойчивый код дефекта, точный
  объект (путь/фикстура, НЕ маска case_\*, НЕ целый job), версия определения проверки, main SHA
  свидетельства, условие устранения, срок действия;
- список пополняет/расширяет ТОЛЬКО канал владельца отдельным решением; только сокращается;
  исправленный дефект снимается до следующего допуска; срок истёк — отказ; при нуле записей
  механизм удаляется и возвращается строгий допуск;
- скрипт `gitw_preflight_071.sh`: ЗАМЕНИТЬ предикат «хотя бы один успешный PR-workflow» на: все 12 job
  PR-CI реально выполнены, и каждая находка ⊆ списка; иначе отказ;
- красные клетки: новая находка при том же числе/пути — отказ; раннее завершение, скрывшее
  проверки — отказ; отсутствующий job, skipped/neutral/cancel/timeout/сбой API — отказ; подмена
  списка/workflow/скрипта/отчёта кандидатом — нет допуска; чужой SHA/старый запуск/движение базы —
  отказ; исчезновение дефекта — разрешено, возврат после снятия — отказ; положительные контроли
  «всё зелёное» и «только разрешённые»;
- бутстрап: гейт НЕ лендит сам себя; готовый проверенный коммит устанавливает канал владельца
  однократно; не переименовывать ленды и не вводить флагов пропуска;
- первый список дефектов подписывает владелец; после установки — ленды по одному:
  098 → 097 → 092 → 095 → 093 → 094.

Основание Astra §1 (дословно): «новый допуск **заменяет** прежнее условие PR-CI, не добавляет
параллельный путь»; «Заменять надо этот предикат; оставленный рядом shortcut обесценит новый гейт»;
§2: «исполняющий допуск читает его из закреплённой принятой ревизии… Защищена от записи кандидатом»;

исчезнуть — равенство множеств не требуется».

## Решения

1. **Замена предиката чека 3** (`scripts/gitw_preflight_071.sh`, implementer). Для каждого
   land-мержа (второй родитель `p`, грамматика `wip/[0-9]{3}/<автор>` — без изменений):
   - запуск: из `workflow_runs?event=pull_request&head_sha=<p>` берутся ТОЛЬКО строки с
     литеральным равенством `event=="pull_request"` ∧ `head_sha=="<p>"`; судится запуск с
     МАКСИМАЛЬНЫМ `id`; пусто → `запусков PR-CI нет: <ветка> (<p>)`;
   - `status=="completed"` иначе → `запуск не завершён: <status>`;
   - `conclusion ∈ {success, failure}` иначе → `запуск не исполнен: <conclusion>`;
   - актуальность базы: `pull_requests[0].base.sha == <rmain>` (вершина main на цели, тот же
     источник, что чек 3 сегодня) иначе → `движение базы: запуск не актуален`; до печати строки
     допуска rmain ПЕРЕЧИТЫВАЕТСЯ и сверяется повторно с тем же значением (движение базы ПОСЛЕ
     первой сверки — тот же отказ; клетка И-16 двигает цель между сверками);
   - **связка запуска со строками** (Б3): у выбранного запуска берётся `check_suite.id`; строки
     читаются из `commits/<p>/check-runs` и судятся ТОЛЬКО те, у которых `check_suite.id` равен
     suite выбранного запуска; при нескольких строках одного имени в выбранном suite судится
     строка с МАКСИМАЛЬНЫМ `id` (последняя попытка); строки чужих suite не судятся вовсе
     (принадлежат другим запускам того же SHA);
   - job: ожидаемое множество job и их ключей читается из доверенного ci.yml ПРИНЯТОЙ ревизии
     `<rmain>` (матрицы include: shard apN / lane lN), НЕ из отправляемого дерева; имя check-run —
     `<префикс> (<job>)`; каждый ожидаемый job обязан иметь (по связке выше) check-run со
     `status=="completed"` ∧ `conclusion ∈ {success, failure}`, иначе → `job не выполнен: <job>
     <причина>` (причина ∈ `отсутствует|skipped|neutral|cancelled|timed_out|in_progress|
     неразобранный результат: <conclusion>`); check-run выбранного suite вне ожидаемого множества
     → `посторонний job: <имя>`; несоответствия печатаются ВСЕ до отказа;
   - отказ curl → существующая фраза `PR-CI не сверяем: API` (fail-closed, байт-в-байт);
   - успех: строка допуска (молчания нет): `gitw ПРЕДПОЛЁТ: PR-CI допуск: <ветка> (<p>): jobs
     <исполнено>/<ожидается> исполнено, находки <покрыто>/<всего>`.
   Чеки (4)→(2)→(1), их фразы и порядок — байт-в-байт 071; предикат «≥1 успешный PR-workflow
   run» из кода удаляется (замена, не наслаивание; Пять правил §2).
2. **`registry/main-ci-exceptions.json`** (implementer, формат/схема; записей до подписи владельца
   нет — файл несёт пустой список). Грамматика (041, замкнутые алфавиты):
   `{"schema":"main-ci-exceptions/1","exceptions":[{target,key,object,defect_code,check_version,
   evidence_main_sha,removal_condition,expires}]}` — ЕДИНСТВЕННАЯ форма входа (голая запись или
   иной JSON-контейнер — отказ схемы, Б7); `target` ∈ {ap1..ap5,l1..l7}; `key` — токен
   `[a-z0-9][a-z0-9:_-]*` из ключей доверенного ci.yml этого job, ДОСЛОВНО, без нормализации
   (совет 1: реальные lane-ключи `check:charter`, `check:gitw-predpolet-family-selftest` содержат
   `:` и `-`; терминальная строка ключа `<ключ>: PASS|FAIL: <фраза>` однозначна — префиксный якорь
   `^<ключ>: (PASS|FAIL)`); `object` — непустой точный путь/фикстура без глобов (`*?[`
   запрещены) и БЕЗ перевода строки, ≠ имени job и ≠ ключа (дословно: НЕ маска case_\*, НЕ целый
   job); `defect_code`/`check_version` — 64 hex; `evidence_main_sha` — 40 hex;
   `removal_condition` — непустая однострочная UTF-8; `expires` — `YYYY-MM-DD`. Нарушение →
   `список не разбирается: <причина>` (fail-closed отказ, не пропуск). Чтение источника
   различает (совет 3): `git ls-tree <rmain> -- registry/main-ci-exceptions.json` пуст ⇒ путь
   ДОСТОВЕРНО ОТСУТСТВУЕТ в принятой ревизии ≡ пустой список (строгий допуск); запись ls-tree
   есть, но `git show <rmain>:…` падает (объект недоступен) ⇒ `список не читается: <что>` —
   именованный fail-closed отказ, НЕ пустой список молча (`git show … || empty-list` запрещён).
3. **Находка и соответствие записи** (круг 2: идентичность дефекта — из структурированного
   результата, Б1). Отчёт job (`output.summary` его check-run) обязан нести: строку
   `def-sha256 <64hex>` — отпечаток определения job = sha256 канонической строки
   `<job>\t<ключи через запятую в порядке матрицы>\n` из доверенного ci.yml — отпечаток ВЫЧИСЛЯЕТ
   ГЕЙТ по принятой ревизии, строка в отчёте — лишь заявление, принимаемое ТОЛЬКО вместе с
   байт-идентичностью слоя определений (Решение 5б); и для каждого ключа терминальную строку
   `<ключ>: PASS` либо `<ключ>: FAIL: <фраза>` (фраза без перевода строки). Находка = непустой
   набор FAIL-строк одного ключа одного job. Идентичность находки = ДВОЙНАЯ: (i) текстовая —
   sha256 отсортированных LC_ALL=C FAIL-строк ключа, каждая с `\n`; (ii) структурная — у check-run
   job запрашиваются failure-аннотации `check-runs/<id>/annotations` (`annotation_level=="failure"`):
   на КАЖДУЮ FAIL-строку — аннотация с той же `message` побайтно, и `path` ВСЕХ этих аннотаций —
   один и тот же точный путь. Запись соответствует находке ⟺ `target==job` ∧ `key==ключ` ∧
   `defect_code == (i)` ∧ `check_version == отпечатку определения job` ∧ `сегодня ≤ expires` ∧
   `object == path` из (ii). Нарушение (ii) — в том числе отсутствие/нехватка аннотаций — та же
   `находка вне списка`: совпадение диагностического текста не может быть единственным
   свидетельством (дословно Astra §1: «одинаковый ключ и путь могут обозначать разные дефекты»).
   `defect_code` — механическая идентичность текста находки, `object` — механическая привязка к
   точному объекту через аннотации (документационной роли больше нет). Равенство множеств находок
   и записей НЕ требуется: исчезновение дефекта разрешено; запись без находки не действует.
4. **Отказы соответствия** (именованные, `grep -F`, префикс `gitw ПРЕДПОЛЁТ-ОТКАЗ: PR-CI: `):
   `нет результата: <job>/<ключ>` — в отчёте ЛЮБОГО исполненного job (success или failure, Б5)
   нет терминальной строки обязательного ключа; `job не выполнен: <job> отказ без находки` —
   completed/failure job, у которого при полных терминальных строках НОЛЬ FAIL-строк (отказ
   неизвестной природы: setup/публикация — «находки 0/0» недопустимы); `отчёт не из доверенного
   определения: <job>` — строки `def-sha256` нет или она ≠ доверенному отпечатку; `находка вне
   списка: <job>/<ключ>` — находке не соответствует ни одна запись (новая находка при том же
   числе/пути; возврат после снятия; текст совпал, объект аннотаций — нет); `срок исключения
   истёк: <object>` — соответствие есть, но `сегодня > expires`; `определение проверки не
   совпадает с записью: <object>` — соответствие есть, но `check_version` ≠ отпечатку.
5. **Источник доверия и неизменность политики.**
   (а) Список, ci.yml (состав job/ключей) и отпечатки — читаются из ПРИНЯТОЙ ревизии `<rmain>` на
   цели обмена (`git show <rmain>:…` после обеспечения объектов), НЕ из отправляемого дерева.
   (б) **Слой определений CI байт-идентичен p↔rmain** (Б2): `.github/workflows/ci.yml`,
   `registry/ci-steps.tsv`, `package.json` (разрешение команд шагов) — содержимое `<p>:<файл>` и
   `<rmain>:<файл>` побайтно равно (отсутствие с обеих сторон допустимо для ci-steps.tsv/package.json;
   ci.yml обязан существовать); иначе → `CI-код не из доверенной ревизии: <путь>` — подмена
   проверяющего кода/определений при ПРАВИЛЬНОМ def-sha256 не легализуется: генератор отчёта
   обязан изменить разрешение шагов, чтобы стать генератором. Земли, меняющие слой определений CI,
   в переходном режиме НЕ транзитны — им канал владельца/строгий путь (дословно Astra §2:
   «Кандидат не может изменить применяемую к себе политику»).
   (в) **Список байт-идентичен p↔rmain** (Б4): `<p>:registry/main-ci-exceptions.json` ≡
   `<rmain>:…` (отсутствие с обеих сторон ≡ пустой); иначе печатается
   `список не из доверенной ревизии: registry/main-ci-exceptions.json`, судейство находок
   ПРОДОЛЖАЕТСЯ по принятой ревизии (обе фразы в выводе), но допуск НЕ выдаётся — самовнесённая
   кандидатом запись (дормантная или используемая) никогда не становится политикой.
   Порядок суда: читаемость списка (2) → схема (2) → самовнесение (5в, печать) → слой определений
   (5б) → job/находки (1,3,4) → перечитывание базы (1) → допуск.
6. **Жизненный цикл списка** (нормы, ПРОВОДКА role-каналом; механическая часть — 5в и записи):

## Демаркация контрпримеров

Конформные входы: job ∈ {ap1..ap5, l1..l7}; ключи — токены `[a-z0-9][a-z0-9:_-]*` из ключей
доверенного ci.yml (дословно, с `:` и `-`); имена check-run `<префикс> (<job>)`; `check_suite.id` —
целое; sha — 64 hex (defect_code/check_version/def-sha256), 40 hex (evidence_main_sha, p, rmain);
`expires` — YYYY-MM-DD; FAIL-фразы — UTF-8 без перевода строки; failure-аннотации —
`{path: непустой путь без глобов, annotation_level: "failure", message: FAIL-строка побайтно}`;
список — валидный контейнер по грамматике Решения 2. Валидный контрпример = инвариантность к
значениям (фразы, пути, состав списка, даты, suite id) ∧ расхождение честной и проверяемой
реализаций на КОНФОРМНОМ входе (например: находка, чей текст совпадает с записью побайтово, но
чья аннотация указывает другой объект, — конформна и обязана отказывать). Неконформные (не
контрпримеры): невалидный JSON/грамматика списка — сам по себе отказ Решения 2 (клетка И-17а/б
судит ИМЕННО это различение, но не является контрпримером к допуску); глобы в object, job вне
доверенного множества, conclusion вне алфавита — их отказ тривиален по грамматике.

## Остаточный риск

- Тела шагов за неизменным слоем определений (ci.yml/ci-steps.tsv/package.json) не проверяются
  байт-идентичностью (Б2-остаток): раннер, исполнивший подменённый код с честным отчётом при
  неизменном разрешении шагов, не ловится этим срезом — материализация доверенного замыкания —
  предмет 099 (M^1). Слой определений закрыт: генерация ложного отчёта требует правки разрешения
  команд шагов и ловится И-12.
- Земли, меняющие слой определений CI или список (включая легитимные разработки самого харнесса,
  добавляющие npm-ключи), в переходном режиме не транзитны — это сознательное следствие
  «кандидат не может изменить применяемую к себе политику»; их путь — owner-канал до 099.
- Живое поведение GitHub (check-runs матричных job, base.sha в ответе runs, annotations) до
  owner-репетиции Решения 7 принято по документированной грамматике; toy-стаб не доказывает
  живой API.
- Жизненный цикл списка (пополнение только владельцем, сокращение, снятие до допуска) — нормы
  role-канала; механические ловцы — байт-идентичность списка/слоя определений (И-12/И-14),
  записи (defect_code/object/expiry) и судьи круга.
- Бутстрап не самозакрыт: до установки первого подписанного списка механизм эквивалентен строгому
  допуску (пустой список), тупик снят только подписью владельца — ожидаемое состояние.
