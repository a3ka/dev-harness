## Решения

1. **Замена предиката чека 3** (`scripts/gitw_preflight_071.sh`, implementer). Для каждого
   land-мержа (второй родитель `p`, грамматика `wip/[0-9]{3}/<автор>` — без изменений):
   - запуск: из `workflow_runs?event=pull_request&head_sha=<p>` берутся ТОЛЬКО строки с
     литеральным равенством `event=="pull_request"` ∧ `head_sha=="<p>"`; судится запуск с
     МАКСИМАЛЬНЫМ `id`; пусто → `запусков PR-CI нет: <ветка> (<p>)`;
   - `status=="completed"` иначе → `запуск не завершён: <status>`;
   - `conclusion ∈ {success, failure}` иначе → `запуск не исполнен: <conclusion>`;
   - актуальность базы: `pull_requests[0].base.sha == <rmain>` (вершина main на цели, тот же
     источник, что чек 3 сегодня) иначе → `движение базы: запуск не актуален`; до печати строки
     допуска rmain перечитывается и сверяется повторно (движение базы ПОСЛЕ проверки — тот же
     отказ);
   - job: из `commits/<p>/check-runs` — ожидаемое множество job и их ключей читается из
     доверенного ci.yml ПРИНЯТОЙ ревизии `<rmain>` (матрицы include: shard apN / lane lN),
     НЕ из отправляемого дерева; имя check-run — `<префикс> (<job>)`; каждый ожидаемый job обязан
     иметь check-run со `status=="completed"` ∧ `conclusion ∈ {success, failure}`, иначе →
     `job не выполнен: <job> <причина>` (причина ∈ `отсутствует|skipped|neutral|cancelled|timed_out|in_progress|неразобранный результат: <conclusion>`); check-run вне ожидаемого
     множества → `посторонний job: <имя>`; несоответствия множеств печатаются ВСЕ до отказа;
   - отказ curl → существующая фраза `PR-CI не сверяем: API` (fail-closed, байт-в-байт);
   - успех: строка допуска (молчания нет): `gitw ПРЕДПОЛЁТ: PR-CI допуск: <ветка> (<p>): jobs
     <исполнено>/<ожидается> исполнено, находки <покрыто>/<всего>`.
   Чеки (4)→(2)→(1), их фразы и порядок — байт-в-байт 071; предикат «≥1 успешный PR-workflow
   run» из кода удаляется (замена, не наслаивание; Пять правил §2).
2. **`registry/main-ci-exceptions.json`** (implementer, формат/схема; записей до подписи владельца
   нет — файл несёт пустой список). Грамматика (041, замкнутые алфавиты):
   `{"schema":"main-ci-exceptions/1","exceptions":[{target,key,object,defect_code,check_version,
   evidence_main_sha,removal_condition,expires}]}`; `target` ∈ {ap1..ap5,l1..l7}; `key` — токен
   `[a-z0-9_]+` из ключей доверенного ci.yml этого job; `object` — непустой точный путь/фикстура
   без глобов (`*?[` запрещены) и БЕЗ перевода строки, ≠ имени job и ≠ ключа (дословно: НЕ маска
   case_\*, НЕ целый job); `defect_code`/`check_version` — 64 hex; `evidence_main_sha` — 40 hex;
   `removal_condition` — непустая однострочная UTF-8; `expires` — `YYYY-MM-DD`. Нарушение →
   `список не разбирается: <причина>` (fail-closed отказ, не пропуск). Файл отсутствует в принятой
   ревизии ≡ пустой список (строгий допуск — все находки отказ).
3. **Находка и соответствие записи.** Отчёт job (`output.summary` его check-run) обязан нести:
   строку `def-sha256 <64hex>` — отпечаток определения job = sha256 канонической строки
   `<job>\t<ключи через запятую в порядке матрицы>\n` из доверенного ci.yml; и для каждого ключа
   терминальную строку `<ключ>: PASS` либо `<ключ>: FAIL: <фраза>` (фраза без перевода строки).
   Находка = непустой набор FAIL-строк одного ключа одного job. Запись соответствует находке ⟺
   `target==job` ∧ `key==ключ` ∧ `defect_code == sha256(отсортированных LC_ALL=C FAIL-строк ключа,
   каждая с \n)` ∧ `check_version == <отпечаток определения job>` ∧ `сегодня ≤ expires`.
   `defect_code` — единственная механическая идентичность дефекта (дословно Astra §1: «одинаковый
   ключ и путь могут обозначать разные дефекты»); `object` — документационная привязка, участвует
   в фразах отказов. Равенство множеств находок и записей НЕ требуется: исчезновение дефекта
   разрешено; запись без находки не действует.
4. **Отказы соответствия** (именованные, `grep -F`, префикс `gitw ПРЕДПОЛЁТ-ОТКАЗ: PR-CI: `):
   `нет результата: <job>/<ключ>` — в отчёте FAIL-job нет терминальной строки обязательного ключа
   (раннее завершение скрыло проверку); `отчёт не из доверенного определения: <job>` — строки
   `def-sha256` нет или она ≠ доверенному отпечатку (подмена workflow/скрипта/отчёта кандидатом);
   `находка вне списка: <job>/<ключ>` — находке не соответствует ни одна запись (новая находка при
   том же числе/пути; возврат после снятия; подменённый кандидатный список не прочитан);
   `срок исключения истёк: <object>` — соответствие есть, но `сегодня > expires`;
   `определение проверки не совпадает с записью: <object>` — соответствие есть, но
   `check_version` ≠ отпечатку (определение сместилось после свидетельства).
5. **Источник доверия.** Список, ci.yml (состав job/ключей) и отпечатки — читаются из ПРИНЯТОЙ
   ревизии `<rmain>` на цели обмена (`git show <rmain>:…` после обеспечения объектов), НЕ из
   отправляемого дерева; дерево кандидата эти файлы не переопределяют. Недоступность объекта/файла —
   именованный отказ fail-closed, не пропуск.
6. **Жизненный цикл списка** (нормы, ПРОВОДКА role-каналом): пополняет/расширяет ТОЛЬКО канал
   владельца отдельным решением; список только сокращается; исправленный дефект снимается ДО
   следующего допуска; истёкший срок — отказ без автопродления; при нуле записей и подтверждённом
   полном зелёном CI механизм удаляется и возвращается строгий допуск. Универсального флага
   пропуска и переименования лендов нет и не заводится.
7. **Бутстрап** (дословно Astra §4): «Новая дверь не разрешает собственную установку. Владелец
   отдельно санкционирует точный подготовленный коммит, базу, операцию публикации и установку
   проверенной версии через защищённый owner-канал; репетиция и независимая проверка предшествуют
   публикации… Затем первый настоящий ленд проходит новый гейт; бутстрап-полномочие исчерпано».
   Порядок (дословно владельца): репетиция через gitw → консультант приносит владельцу точный
   коммит на подпись → установка owner-каналом → ленды по одному: 098 → 097 → 092 → 095 → 093 → 094.

Конформные входы: job ∈ {ap1..ap5, l1..l7}; ключи — токены `[a-z0-9_]+` из доверенного ci.yml;
имена check-run `<префикс> (<job>)`; sha — 64 hex (defect_code/check_version/def-sha256), 40 hex
(evidence_main_sha, p, rmain); `expires` — YYYY-MM-DD; FAIL-фразы — UTF-8 без перевода строки;
список — валидный по грамматике Решения 2. Валидный контрпример = инвариантность к значениям
(фразы, пути, состав списка, даты) ∧ расхождение честной и проверяемой реализаций на КОНФОРМНОМ
входе (например: находка, чьи FAIL-строки не совпадают побайтово ни с одной записью, — конф ормна
по грамматике и обязана отказывать). Неконформные (не контрпримеры): невалидный JSON/грамматика
списка (сам по себе отказ Решения 2), глобы в object, job вне доверенного множества, conclusion
вне алфавита — их отказ тривиален по грамматике.

## Модель угроз

ЗАЩИЩАЕТ:
- протаскивание новой поломки под видом известного дефекта — И-4 (идентичность по sha256
  FAIL-строк, не число/путь/текст-совпадение);
- «зелёную оболочку» без фактического исполнения — И-1/И-6 (все job доверенного множества
  completed с terminal conclusion; skipped/neutral/cancel/timeout/in_progress — отказ);
- неполноту исполнения (раннее завершение скрыло остальные проверки) — И-5 (терминальная строка
  каждого обязательного ключа FAIL-job);
- изменение кандидатом применяемой к себе политики — И-7 + Решение 5 (список/определения из
  принятой ревизии, отправляемое дерево не читается);
- подмену workflow (переименование/выпадение job) и отчёта — И-7 (доверенное множество job,
  посторонний job, отпечаток определения в каждом отчёте);
- судейство чужого/старого запуска и движение базы — И-8 (литеральный head_sha, максимум id,
  сверка base.sha с rmain до и после проверки);
- вечное исключение — И-9/И-10 (снятие, срок, версия определения; список только сокращается).

НЕ ЗАЩИЩАЕТ:
- содержательную силу самих проверок (зелёный key = проверка исполнена и прошла, не «правильна»);
- компрометацию раннера/API GitHub между исполнением и опросом — граница доверия Astra §1.5
  (доверенные результаты, не их повторное исполнение); полная защита — серверные правила 099 §5.2;
- исполненный внутри job код: отпечаток связывает ОПРЕДЕЛЕНИЕ (набор job/ключей), не тела скриптов;
  материализация доверенного замыкания — предмет 099 (M^1), не этого среза;
- поведение живого GitHub до live-репетиции Решения 7 (клетки несут toy API-стаб).
