## Предмет

`_task`-субагенты (в отличие от `spawn_agent.sh`+`./workshop`) не несут ни
`WORKTREE`-пина, ни `env.WORKTREE` — `.omp/extensions/path-guard.ts` судит их
как unpinned, и ЛЮБАЯ прямая запись (`write`/`edit`, `bash`-формы записи) в их
собственный рабочий каталог блокируется («Н-85/А-122: не в null-allowlist»).
Для `isolated:true`-дозвонов (harness даёт им ОТДЕЛЬНЫЙ btrfs-клон,
`.omp/config.yml` → `task.isolation.mode: btrfs`) это чистый паразитный
блок — клон САМОДОСТАТОЧЕН, писать в НЕГО не рискует ничьим чужим деревом. Для
голых (неизолированных) `_task`-дозвонов, работающих в ОБЩЕМ с родителем
cwd, блок ЗАЩИЩАЕТ (дыра B, резолюция владельца 2026-09-11) — предмет НЕ
должен снимать его вслепую. Для случая «голый `_task` под оркестратором/
main, cwd = главный чекаут» защита остаётся структурной БЕЗ участия М1
(главный чекаут — СНАРУЖИ `$HOME`, М1 п.4 не пропускает его никогда, см.
§Инварианты). Для случая «голый `_task`, вложенный ИЗНУТРИ self-contained
cwd уже-изолированного родителя» (байт-в-байт одна директория с точки
зрения входа `judge()` — Б4 критика contracts-037-v1.md) 037 закрывает
его СТРУКТУРНО через §Инварианты М1 п.5 (владелец-корреляция
`.omp-isolation-owner.json` × `sessionId` — решение владельца (в), детали
в §Развилки), не подменой ceremony-обязательством: `isolated:true` у
вложенного `_task` остаётся рекомендованной практикой (§Инварианты М3
п.4) — как defense-in-depth и обход остаточного риска гонки владения при
создании клона (§Остаточный риск), уже не единственная защита этого
случая.

037 даёт ДВА независимых, дополняющих друг друга механизма на два разных
случая одной и той же боли:

1. **М1 — self-contained-cwd allowlist** (расширение `.omp/extensions/path-guard.ts`):
   `isolated:true`-клоны получают эффективный пин БЕСПЛАТНО, структурным
   распознаванием, без единого байта нового транспорта.
2. **М2 — приёмник `scripts/accept_task_commit.sh`** + **М3 — чек-лист
   ceremony** (`roles/orchestrator.md`): стандартизация РУЧНОГО обхода
   (скретч-клон агента → fetch+cherry-pick на целевую wip-ветку), который
   сегодня каждая пачка изобретает заново прозой — механизирует РОВНО тот
   класс ошибки, что уже стоил дня 029–031 («критик закоммитил в чужую
   ветку», `contracts/032-spawn-pinning-worktree.md:29-30`).

М1 закрывает БОЛЬШУЮ часть сегодняшней боли (норма 012 предписывает
`isolated:true` штатным режимом для параллельных architect/implementer-пачек).
М2/М3 закрывают то, что М1 НЕ закрывает: голый `_task` в общем cwd, которому
нужно передать результат на именованную wip-ветку (ровно случай ЭТОГО САМОГО
дозвона — architect пишет контракт и не может сам его закоммитить).

(Обязательна: `scripts/accept_task_commit.sh` — НОВЫЙ гард, парсящий чужой

ЗАЩИЩАЕТ:
- честную проверку заявленного автора против фактического %an/%ae каждого принимаемого коммита независимо от того какие байты встречаются в имени ветки или пути источника предотвращая класс ошибки дня 029-031 когда чужая работа была cherry-pick нута под неверной identity без проверки
- различение владельца self-contained изолированного клона от вложенного голого task субагента делящего с ним тот же самый рабочий каталог через литеральное сравнение sessionId текущего вызова с полем id артефакта owner json который пишет сам харнесс при создании клона а не гостевой код сессии предотвращая класс ошибки где путь каталога ошибочно принимается за доказательство идентичности вызывающей сессии
- различение отсутствия целевой ветки от пустого диапазона коммитов от несовпадения автора именованной причиной первой красной проверки вместо молчаливого отказа без диагностики
- защиту грамматики имени ветки и имени автора от подмены смысла через regex или glob инъекцию untrusted значения argv в сравнение с чужими git метаданными

НЕ ЗАЩИЩАЕТ:
- враждебное окружение вызывающего процесса за пределами базового экспорта PATH включая sourced исполнение и экспортированные функции это отдельный класс ENV-TRUST и SOURCED-EXEC контракта 038 и не входит в область этого контракта
- гонку владения в узком окне между созданием изолированного клона и записью owner json харнессом переиспользование директории клона между несвязанными по времени сессиями без гарантированной перезаписи owner json и недокументированную семантику поля startToken артефакта владения которое этот инвариант сознательно не использует
- содержательную корректность самого патча источника скрипт проверяет identity и целостность диапазона коммитов а не то что код субагента качественно решает задачу это остаётся судом критика адверсария ревьюера
- атаку на git объекты уже находящиеся в object store главного репозитория через коллизию sha это угроза криптографии git а не этого приёмника

## Инварианты

### М1. Self-contained-cwd allowlist (`.omp/extensions/path-guard.ts`)

Расширяет ТУ ЖЕ implementer-зону, что контракт 032 (union-семантика 033 —
переобъявление ниже явное, не тихое наследование).

`envActual` — значение, которое `judge()` СЕГОДНЯ уже получает как `input.actual`
(фабрика — `register()` строка `actual = eventActual ?? envActual`,
`.omp/extensions/path-guard.ts:1060,1085,1088,1093,1097` — заполняется ВСЕГДА,
включая unpinned-ветвь; `judge()` сегодня его там просто НЕ читает, т.к. весь
блок сверки висит на `if (worktree)`, `path-guard.ts:904-926`).

Новый allowlist-путь применяется ⟺ ОДНОВРЕМЕННО:

1. `worktree === null` (все три источника М2/032 пусты: событие, env, пин
   задания) — сессия unpinned;
2. `<canonicalActual>/.git` существует и ЭТО КАТАЛОГ (не gitfile-указатель
   линкованного worktree) — та же категория структурной проверки, что
   `gitOracle` уже делает для `.git`-файла (`path-guard.ts:232-239`), здесь
   зеркально для каталога;
3. git-оракул (переиспользует `GIT_PATH`/`buildSanitizedEnv`,
   `path-guard.ts:160-226`, тот же санированный spawn, что `gitOracle`):
   `git -C <canonicalActual> worktree list --porcelain` возвращает РОВНО ОДНУ
   запись `worktree <path>`, и `realpath(<path>) === canonicalActual` (нет
   зарегистрированных linked-worktree-соседей — ни живых, ни prunable);
   git отсутствует/spawn-ошибка/rc≠0 → условие НЕ выполнено (fail-closed,
   тот же контракт, что `gitOracle`: git-отсутствие НИКОГДА не даёт pass);
4. **`isWithin(realpath(process.env.HOME), canonicalActual)`** — `envActual`
   обязан быть ПОТОМКОМ (или самим) реального `$HOME` этой сессии.
   `process.env.HOME` пуст/не задан → условие НЕ выполнено (fail-closed).

   **Почему п.4 нужен, но НЕ достаточен сам по себе** (живой замер ЭТОЙ
   пачки, а не гипотеза): п.1–3 буквально повторяют владельческое «`.git` —
   каталог, `git worktree list` возвращает ровно одну строку, себя» — но
   ДВОЙНАЯ живая проба показала, что этих двух условий НЕДОСТАТОЧНО. Прогон
   `git -C /home/aka/Documents/dev-harness worktree list` в МОМЕНТ ПИСЬМА
   этого контракта вернул РОВНО ОДНУ строку (главный чекаут ПРЯМО СЕЙЧАС не
   несёт ни одного живого linked-worktree-соседа) — т.е. САМ главный,
   ОБЩИЙ чекаут в этот момент проходит п.1–3 буквально. Отдельно, живой
   дозвон `isolated:true`-пробы (`IsolatedGitProbe037c`, `sonic`) снял
   `.git/config`/`reflog`/`remote` изолированного btrfs-клона и сравнил с
   ТЕМИ ЖЕ полями главного чекаута в ТОТ ЖЕ момент: `origin` СОВПАДАЕТ
   байт-в-байт (`ssh://git@github.com/a3ka/dev-harness.git` — у ОБОИХ),
   `git reflog show HEAD | wc -l` СОВПАДАЕТ (`1541` — у ОБОИХ), HEAD-коммит
   СОВПАДАЕТ. **На git-уровне изолированный клон и главный чекаут в момент
   нулевого числа linked-worktree-соседей НЕРАЗЛИЧИМЫ** — п.1–3 сами по себе
   открыли бы дыру B (резолюция 2026-09-11) КАЖДЫЙ РАЗ, когда главный чекаут
   транзиентно не несёт ни одной живой wip-ветки (обычное, а не редкое
   состояние — ровно сегодняшнее). Подтверждённый различающий сигнал ДЛЯ
   ЭТОЙ ПАРЫ — АБСОЛЮТНЫЙ ПУТЬ: изолированный клон живёт ВНУТРИ `$HOME`
   сессии (`.../dev-harness-sessions/<hash>/zones/dev/.omp/profiles/
   <профиль>/wt/<hash>/m`), главный чекаут — СНАРУЖИ
   (`/home/aka/Documents/dev-harness`).

   **Это СЛЕДСТВИЕ 028 в ОДНУ сторону, не в обе** (владелец лично указал на
   инференс-ошибку предыдущей редакции этого абзаца — дословно: «путь
   различает ГЛАВНЫЙ-чекаут-vs-клон, какое дерево, а НЕ владельца-vs-
   вложенного-ребёнка, кто именно имеет право писать»). 028
   (`contracts/028-home-sessii-vne-dereva.md` §Инварианты п.2) гарантирует:
   канонический результат разрешения ZONE сессии, запущенной С ДАННОГО
   чекаута, лежит ВНЕ этого чекаута. Она НЕ гарантирует обратного («чекаут
   никогда не лежит внутри HOME») и не касается btrfs-клонов
   `_task(isolated:true)` вовсе — те создаются ВНУТРИ уже вычисленного HOME
   родителя, ДРУГИМ кодом харнесса, не `./workshop`'s ZONE-блоком. Для
   ИЗМЕРЕННОЙ пары (главный чекаут / изолированный клон) п.4 даёт
   корректный, но УЗКИЙ результат: различает КАКОЕ дерево (главное vs
   клон), а НЕ КТО владеет ДАННЫМ деревом. Для владельца self-contained
   cwd и вложенного голого `_task`, порождённого ИЗНУТРИ него,
   `canonicalActual` — БАЙТ-В-БАЙТ ОДИН и тот же путь: п.1–4 дают им
   ОДИНАКОВЫЙ ответ, и никакая переформулировка ПУТЕВОГО условия этого не
   изменит — путь в принципе не несёт информации об идентичности
   ВЫЗЫВАЮЩЕЙ СЕССИИ, только о РАСПОЛОЖЕНИИ каталога. Различает их п.5
   ниже (владелец-корреляция) — не путь, а `sessionId`.

5. **Владелец-корреляция.** `<dirname(canonicalActual)>/.omp-isolation-owner.json`
   существует, парсится как JSON, несёт строковое поле `id`, и оно ЛИТЕРАЛЬНО
   (`===`) равно `sessionId` текущего вызова — новое поле
   `JudgeInput.sessionId`, заполняемое в `register()`'s `tool_call`-
   обработчике ТЕМ ЖЕ вызовом `getSessionId(ctx)` (`path-guard.ts:320-327`),
   который М2/032 уже использует для ключа `sessionPins`
   (переиспользование существующего, не новый источник). Отсутствие файла /
   ошибка парсинга / `id` не строка / несовпадение → условие НЕ выполнено
   (fail-closed, та же дисциплина, что п.1–4).

   **Почему п.5 обязателен** (Б4 критика contracts-037-v1.md + арбитраж
   `verdicts/arbitration/037-b4-freeze-authority.md`, П3: владелец выбрал
   (в) — построить реальную машинную привязку сессия↔клон, НЕ принимать
   процедурное М3 п.4 как достаточное, «автономный caller забудет
   isolated:true»): п.1–4 видят БАЙТ-В-БАЙТ ОДИН `canonicalActual` у
   владельца self-contained cwd и у вложенного голого `_task`,
   порождённого ИЗНУТРИ него — и потому дают ОДИНАКОВЫЙ ответ обоим. Живой
   замер ЭТОЙ пачки (`agent://Architect037Redesign/IsolatedProbeParent037`,
   read-only проба: isolated-родитель + вложенный голый `_task`-внук БЕЗ
   собственного `isolated:true`) подтвердил ТРИ факта одновременно: (1) оба
   процесса резолвят ОДИН И ТОТ ЖЕ `pwd` (`.../wt/t13d757982/m`) и читают
   ОДИН И ТОТ ЖЕ `.omp-isolation-owner.json`
   (`{"pid":11838,"id":"Architect037Redesign.IsolatedProbeParent037",
   "startToken":"207978"}`, побайтово совпал у обоих) — файл лежит В
   `dirname(canonicalActual)`, СНАРУЖИ самого клона (не в `m/`), пишется
   ХАРНЕССОМ при создании клона, не гостевым кодом сессии: ни родитель, ни
   внук не могут его переписать через `write`/`edit`/`bash` — сам
   `dirname(canonicalActual)` не проходит п.2 (там нет `.git`-каталога) и
   не входит в scratch, поэтому п.1–5 fail-closed защищают САМ файл
   владения от подделки внутри модели угроз этого стража; (2)
   `getSessionId()` УЖЕ используется М2/032 и УЖЕ доказанно различает
   сессии (иначе `sessionPins` кросс-контаминировал бы пины между
   параллельными `_task` — регрессии, которой на практике нет); (3) омп
   ведёт `sessionId` ИМЕННО ИЕРАРХИЧЕСКИМ агент-id (живой `grep
   '"sessionId"' .omp/profiles/dev/logs/omp.*.log` этой же пачки:
   `"Architect037Redesign"` для родительской сессии этого дозвона,
   `"Architect037Redesign.IsolatedProbeParent037"` для её isolated-
   потомка) — ТОТ ЖЕ формат и ТО ЖЕ значение, что поле `id` файла владения.
   Отсюда: вложенный голый внук получает СВОЙ, отличный от родительского,
   `sessionId` (иерархия растёт минимум на сегмент) при СОВПАДАЮЩЕМ
   `canonicalActual` и НЕИЗМЕНИВШЕМСЯ (родительском) owner.json — п.5
   расходится РОВНО там, где п.1–4 совпадали: `getSessionId(внук) !==
   ownerId` → block; `getSessionId(родитель) === ownerId` → pass (при
   выполненных п.1–4). Вложенный `_task` со СВОИМ `isolated:true` (М3
   п.4) получает СОБСТВЕННЫЙ клон — собственные `canonicalActual`/
   owner.json — п.1–5 проходят для ЕГО дерева независимо,

**Грамматика структурных полей (041 §Инварианты п.2, обязательна — гард НОВЫЙ,
парсит чужой ввод):**

1. **Замкнутый алфавит.**

     `extractPin`'s branch-author-сегмент (`path-guard.ts:303`) и

     заякорены (не префикс-матч) — тот же алфавит, что `spawn_agent.sh:266`
     конструирует (`wip/${nnn_padded}/${author}`).

     `^[0-9a-f]{40}$`, заякорено.
   - `--source <путь>`, `--root <корень>`: ЛОКАЛЬНЫЕ файловые пути
     (абсолютные или относительные от cwd вызывающего), НЕ git-transport
     выражения (`ssh://`, `https://`, `git://` и т.п.) — единственный
     документированный сценарий М3 ceremony ниже подаёт скретч-клон агента,
     уже локальный каталог. Оба идут ТОЛЬКО через `git -C <путь>`

     существованием git-репозитория там (rc 2, §Коды возврата ниже) —
     закрытость здесь путевая (argv-only, local-only, git-провалидировано),
     не символьный класс, каким закрыты author/branch/sha выше (СОВЕТ
     критика contracts-037-v1.md:58).
2. **Представление без переиспользования байта разделителем.** `--source`,
   `--branch`, `--author` — ТРИ раздельных argv/bash-переменных на всём пути
   исполнения; НИКОГДА не склеиваются в одну строку одним разделителем с
   последующим сплитом (байт `/` легален ВНУТРИ `--branch`, поэтому
   join+split по `/` немедленно неоднозначен с `--author`, если бы поля
   когда-либо были слиты — они не сливаются).
3. **Литеральное untrusted-untrusted сравнение.** Проверка identity —
   ИСКЛЮЧИТЕЛЬНО `[ "$actual_an" = "$expected_an" ] && [ "$actual_ae" =
   "${expected_an}@dev-harness.local" ]` (bash-равенство строк). Author-argv
   НИКОГДА не интерполируется в `grep -E`/glob, построенный из другого
   untrusted значения (коммитного `%an`/`%ae`) без экранирования — класс,
   которым 038 круг 13 (`guard-ere-metacharacters`) уже был пробит на ДРУГОМ
   гарде.
4. **Точечный якорь терминатора.** Границы `--branch`/`--author` — `^…$`
   целиком, не подстрочный `grep`/prefix-match (`wip/201/implementer` не
   обязан совпасть с `wip/201/implementer-old` частичным сравнением).
5. **Self-application green-фикстура — НЕ применяется буквально** (нет поля
   этого гарда, которое встречается КАК ПОЛЕ ВНУТРИ markdown-текста
   контракта 037, отличие от ПРОВОДКА/038 и «## Модель угроз»/041 —
   `--author`/`--branch`/sha не парсят прозу контракта). Функция

   самоприменения ДОКАЗЫВАЕТ смежное свойство: грамматика author/branch
   ОТКАЗЫВАЕТ плейсхолдерам `<автор>`/`wip/<NNN>/<автор>`, дословно
   встречающимся ВЫШЕ в §Инварианты этого самого контракта (`<автор>` не
   матчит `^[A-Za-z0-9_-]+$` буквально — угловые скобки вне алфавита) —

**Механика (implementer-деталь, не пиннуется буквально — пиннуется
НАБЛЮДАЕМОЕ поведение ниже):**
1. Отказ (rc 1), если `--branch` не существует как `refs/heads/<branch>` в

4. КАЖДЫЙ коммит диапазона: `%an`/`%ae` == `<--author>`/`<--author>@dev-harness.local`
