## Предмет (дословно из докса владельца, строки 383–411)

**Проверяется не только CI (10 пунктов):**

1. связь критериев issue с приёмкой;
2. живой изменённый путь;
3. зоны;
4. линт/типы/сборка, зависимости и секреты согласно классу задачи;
5. необходимые документы;
6. открытые находки по предмету;
7. реализация предмета действительно опубликована;
8. issue и проектные поля;
9. учёт расхода;
10. опубликованный done-тег.

**Выход (5 пунктов):**

- чистая среда выполняет реальные команды профиля, включая установку окружения;
- отсутствующая обязательная команда даёт именованный отказ;
- нельзя закрыть кодовую задачу одной батареей без реализации;
- отказ отправки тега или закрытия issue не выдаётся за полный `done`;
- повтор завершает оставшиеся действия без повторной поставки;
- отчёт содержит результат, commit, доказательства, время, CI-минуты, расходы и вмешательства; неизвестные расходы помечены неизвестными.

## Решения

1. Субъект — ОДНА дверь `scripts/done_project.sh` с глаголами `gate` (`--repo R --class C --task T [--issue I] [--pr N] [--commit-sha S] [--project-id P] [--object-id O] [--resume] [--dry-run]`), `consume-094` (`--repo R [--object-id O]`, явный канал потребления 094 — для тестов), `mark-step` (`--repo R --step name`, внутренний — для `--resume`). Грамматика CLI и фразы закреплены честной моделью `fixtures/done_task_096/model/dover.sh` (субъект обязан принимать её CLI дословно; детали реализации — implementer). Отказы rc 1 «ОТКАЗ: …» с ИМЕНОВАННОЙ причиной; rc 0 — `DONE`, БАЙТЫ отчёта в stdout (см. Решение 6); rc 2 — `NOT_IMPLEMENTED`.
2. Класс задачи: `--class code|doc|research` (по умолчанию `code` для совместимости с батареей); на этом круге класс ОБЪЯВЛЕН аргументом; реестр `doneProfile.contracts` (`<NNN> TAB class`) — минимальный словарь, проверка соответствия объявленного класса и контракта ЗДЕСЬ НЕ делается (Решение 8); в рамках одной задачи класс фиксирован при первом `gate`-вызове (повтор `--resume` не меняет класс).
3. Объект доказательства «опубликовано» — `--object-id OID` ОБЯЗАТЕЛЕН (по умолчанию вычисляется как `bash scripts/accept_publish.sh object --repo R --task T --target <target> --base B --candidate C --merge M`; флаги база/кандидат/merge/ветка вычисляются из текущего HEAD репо проекта — запрещены ссылки на чужой контекст, Б-стиль 094). Дверь 096 НЕ вычисляет object_id из чужого CI (полная ответственность за цепочку — на оркестраторе); на тестовом мира `--object-id` подаётся явно. Строка `published` читается в `registry/candidates.tsv` РОВНО для этого OID.
4. Теги: `done/contracts/<NNN>/<v>` (харнес, существующая 038) + `done/project/<projectId>/<v>` (эта пачка). Оба файла должны СУЩЕСТВОВАТЬ на момент `DONE`; отсутствие одного — отказ (П-10); отказ не удаляет уже существующий тег.
5. Идемпотентность `--resume`: дверь ведёт `<repo>/.omp/done/<NNN>.state.tsv` (TAB-строки `step TAB status TAB ts`) вне git-индекса (как `.omp/context/` 095); выполненные ступени (`class-commands`/`findings-scan`/`consume-094`/`issue-done`/`tag-set`/`spend-written`) отмечаются; повтор не перевыполняет их и не пишет новых строк в `candidates.tsv` (дверь 094 вызывается только в непубликационной части — а тут её нет). Гард читает состояние ДО любых side-effects; при первом успешном шаге пишет сразу (Решение 5).
6. Отчёт — БАЙТЫ на stdout, формат УСТОЙЧИВЫЙ:
   - первая строка — `DONE <projectId> <NNN> <commit_sha> <object_id>` (или `DONE-PARTIAL <projectId> <NNN>` при прерванной последовательности после `consume-094`, в этом коде НЕ done по форме);
   - затем маркер `--- REPORT ---` и блок `key: value` (Result, Commit, ObjectId, IssueUrl, PR, Tags[contracts,project], Class, StartedAt, DurationMin, CIMin, Cost, Interventions, Notes, Steps[<step>=ok|skipped|failed …]);
   - `notes` — литеральная причина отказа/частичности; неизвестные поля помечены `unknown` ДО сериализации;
