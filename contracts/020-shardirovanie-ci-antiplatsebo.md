## Боль (измеренная)

Разброс длительности CI на сопоставимом коде: **105 с** ↔ **35–42 мин** ↔ **5 мин**;
доминирует шаг «Анти-плацебо». Локально тот же прогон — секунды–минуты; на судейской фазе
019 накоплено ~2 ч чистого ожидания CI, и гейт 4б делает КАЖДОЕ ожидание блокером
судейского конвейера. Два измеренных класса дефекта того же шага: Н-87 (`--changed`
видит только последний пуш — красная семья жила под маской docs-only пушей) и Н-63
(scoped «0 задетых» — зелёное, ничего не доказывающее).

Масштаб по дереву (замер 2026-09-17, мера раннера `find fixtures/<барьер> -maxdepth 1
-name 'case_*.sh'`): **38 каталогов, 350 `case_*.sh`** на HEAD; с семью пробами пачки
020 (четыре исходные + три добавленные по вердикту критика v1) — **357**. Вторая мера —
полный рекурсивный `find` — те же 350; вложенных глубже уровня каталога нет (в HANDOFF
было 330, верить дереву). Обход в раннере последовательный, шардинга нет.

## Решения владельца (Р1–Р4, закрыты 2026-09-16)

- **Р1:** matrix по `fixtures/<барьер>/`; барьер НЕ делится между шардами; **N = 5**
  (обоснование профилировкой — ниже); инвариант «сумма шардов = полный набор» — дословно.
- **Р2:** остаёмся на GitHub-hosted, self-hosted НЕ покупаем. `concurrency` в ci.yml:
  `group: ci-${{ github.ref }}`, `cancel-in-progress: true` — садится **ПЕРВЫМ коммитом
  пачки 020, до остального шардинга**.
- **Р3:** `timeout-minutes: 20` на matrix-джобу шардов.
- **Р4:** шаги scoped-селектора (`check:scope-select`, `check:scoped-run`) остаются
  отдельными шагами главной джобы как сегодня, в matrix НЕ едут. Шардируется ТОЛЬКО
  «Анти-плацебо».

## Профилировка и выбор N=5

Верхняя оценка цены одного case (посадочное состояние пачки, 357 case): 42 мин / 357 ≈
**7,1 с** (худший измеренный прогон). Тогда: N=4 → 90 кейсов/шард ≈ 10,6 мин (запас до
timeout 1,9×); **N=5 → 72 ≈ 8,5 мин (запас 2,4×)**; N=6 → 60 ≈ 7,1 мин (запас 2,8×,
выигрыш стены ~1,4 мин против N=5). Раннеры гуляют (105 с ↔ 42 мин на одном коде),
поэтому запас важнее последней минуты стены; при трёх параллельных сессиях каждый
дополнительный шард — плюс слот в очереди (очередь — часть боли). Выбрано **N=5**:
середина диапазона владельца 4–6.

Референс-разбиение (LPT по числу `case_*.sh`, ties по имени; посадочное состояние
пачки 357 = 72/72/71/71/71, разброс 1; на HEAD без проб — 350 = 70×5):

## Предмет (грамматика проводки фиксирована)

1. **ЕДИНСТВЕННАЯ форма запуска «Анти-плацебо» в CI** — matrix-джоба `antiplacebo` в
   `.github/workflows/ci.yml`: `strategy.fail-fast: false`; `matrix.include` из N=5
   записей `{shard: ap<K>, keys: <ключи барьеров через пробел>}`; шаги checkout
   (`fetch-depth: 0`), setup-node (26), run-шаг:
   `run: npm run check:antiplacebo -- --scope ${{ matrix.keys }}` — имя скрипта
   СТАТИЧНО, шаблон — только в аргументах; `timeout-minutes: 20` (Р3).
2. **Concurrency (Р2)** — верхнего уровня: `group: ci-${{ github.ref }}`,
   `cancel-in-progress: true`. ПЕРВЫЙ коммит пачки, до остального шардинга.
3. **Чистый cutover:** прежний единственный шаг «Анти-плацебо» с
   `--changed ${{ github.event.before }}` УДАЛЯЕТСЯ; запусков анти-плацебо вне
   matrix-джобы в `.github/**` не остаётся. Классы Н-87/Н-63 для этого шага закрываются
   по построению: каждый пуш прогоняет ВСЕ фикстуры статическими шардами.
4. **`package.json` не расширяется:** правило 6 держится существующим пунктом
   `check:antiplacebo`; новых скриптов и исключений проводка не вводит.
5. **Грамматика боевой проводки ≠ грамматика подставных дерев проб** (ответ на совет
   критика v1): параметры Р1–Р4 (N=5, `fetch-depth: 0`, node 26, `timeout-minutes:
   20`, `concurrency`) — требования к БОЕВОМУ `ci.yml`. Подставные деревья проб несут
   только структурную форму (matrix-джоба + `keys` + `--scope`); положительный
   контроль из двух шардов КОНФОРМЕН, и барьер не обязан его отвергать — барьер не
   сверяет N, fetch-depth, node и timeout (граница — в приёмке). В боевом CI — пять
   шардов (Р1 не переоткрывается).

## Инварианты

1. **Правило 6 (гейт не зеленее CI):** каждая команда из `run:` каждого шарда имеет
   пункт в приёмке (`scripts` в `package.json` либо объявлена в
   `config/ci_parity_exceptions.txt` с причиной); `scripts/verify_ci_parity.sh` —
   зелёный на новой проводке.
2. **Scoped-режим для судей (Н-48) сохраняется:** `bash scripts/verify_antiplacebo.sh
   <корень> --scope <ключ>` работает дословно как сегодня — шардирование меняет ТОЛЬКО
   CI-проводку, не раннер и не CLI.
3. **Сумма шардов = полный набор фикстур, В ОБЕ СТОРОНЫ:** ни одна
   `fixtures/<барьер>/case_*.sh` не выпадает из всех шардов и не попадает в два
   шарда; зеркально ни один ключ шарда не остаётся без каталога фикстур (мёртвый
   ключ), и если в проверяемом дереве есть `fixtures/<каталог>/case_*.sh`, шардный
   запуск анти-плацебо ОБЯЗАН быть объявлен — отсутствие matrix-джобы тоже красное.
   Проверка живёт в `scripts/verify_ci_parity.sh` (та же область `.github/**`, тот же
   YAML-разбор), активна для любого дерева с `fixtures/<каталог>/case_*.sh` и молчит
   для дерев без фикстур (минимальные основы остальных проб барьера).
4. **Исключительность шардного запуска (чистый cutover):** каждый запуск
   `check:antiplacebo` в `run:` любого файла `.github/**` — ТОЛЬКО шардный шаг
   (`npm run check:antiplacebo -- --scope ${{ matrix.keys }}`); сохранённый прежний
   `--changed`-шаг или иной запуск вне matrix — красное с текстом команды.

## Приёмка (КРАСНЫЕ ТЕСТЫ)

Демаркация (критерий валидности контрпримера): конформные входы — фикстуры по
документированной грамматике раннера (`fixtures/<ключ барьера>/case_*.sh`, ключ = путь
в `scripts/` без расширения) и проводка по грамматике §Предмет. Валидный контрпример =
инвариантность к значениям ∧ расхождение на КОНФОРМНОМ входе. Каждый обманный стаб — к
тому входу, где его дефект НАБЛЮДАЕМ (Н-39). Пробы лежат в
`fixtures/verify_ci_parity/`; зелёная форма шардинга собрана в одном месте — хелпер
`_shard_tree.sh` (не `case_*`, фикстурой не считается).

- **Красное на выпавшую** — `case_shard_vypavshaja.sh`: из соответствия «шард →
  фикстуры» изымается ключ (правкой `keys:` шарда, НЕ правкой фикстуры) → барьер rc=1,
  сообщение содержит `check_ccc не покрыт шардингом — ключ не назван ни одним шардом`.
- **Красное на задублированную** — `case_shard_zadublirovannaja.sh`: ключ приписан двум
  шардам (`keys:` обоих) → rc=1, сообщение содержит
  `check_aaa приписан двум шардам: ap1, ap2` (порядок шардов — по объявлению).
- **Красное scoped-режима** — `case_shard_scope_sloman.sh`: стаб проводки, ломающий
  `--scope` (run-шаг шарда теряет `--scope ${{ matrix.keys }}`, заменён на `--changed
  ${{ github.event.before }}`) → rc=1, сообщение содержит `не несёт --scope с ключами`.
  Класс Н-63: шард без явных ключей может быть зелёным, ничего не прогнав.
- **Красное правила 6** — `case_shard_komanda_vne_priemki.sh`: run-шаг шарда
  `npm run ${{ matrix.cmd }} -- --scope ${{ matrix.keys }}` (имя скрипта шаблоном,
  в include добавлено `cmd: check:antiplacebo`) → отказ СУЩЕСТВУЮЩЕЙ ветви правила 6 с
  текстом команды (`есть в CI, но нет пункта в приёмке и не объявлена исключением`).
  Ветка живёт с находки адверсария про `&&`-хвосты; проба — регрессионная защита на
  форме шардинга: матричное разрешение НЕ имеет права легализовать шаблонное имя
  (грамматика §Предмет п.1: имя статично), иначе проба это поймает.
- **Красное на необъявленный шардинг** — `case_shard_bez_matrixy.sh`: matrix-джоба
  вырезана, в главную джобу возвращён прежний `--changed`-шаг (исполненный обход
  критика v1 «no-shard-job») → rc=1, сообщение содержит `шардный запуск анти-плацебо
  не объявлен: fixtures/check_aaa есть, а matrix-джобы в .github/** нет`. Проводка
  остаётся легальной для правила 6 (команда покрыта пунктом, скрипт используется),
  поэтому красное предъявляет именно ветвь полноты, а не посторонний отказ.
- **Красное на мёртвый ключ** — `case_shard_mertvyj_kljuch.sh`: в `keys:` шарда ap2
  дописан `check_zzz` без каталога фикстур (исполненный обход «dead-key») → rc=1,
  сообщение содержит `check_zzz назван шардом ap2, но каталога fixtures/check_zzz
  нет — мёртвый ключ`. Объединение ключей остаётся покрывающим, дублей нет: красное
  именно мёртвого ключа.
- **Красное на сохранённый прежний шаг** — `case_shard_legacy_shag.sh`: полная
  корректная matrix + прежний `--changed`-шаг в главной джобе (исполненный обход
  «legacy-step-retained») → rc=1, сообщение содержит `запуск анти-плацебо вне
  шардной matrix (не несёт --scope с ключами): npm run check:antiplacebo --
  --changed ${{ github.event.before }}`. Та же ветвь несёт красное
  `case_shard_scope_sloman` (подстрока «не несёт --scope с ключами»): ветвь одна,
  переходы два.
- **Зелёное:** полная сумма шардов на чистом чекауте эквивалентна сегодняшнему полному
  прогону (тот же набор барьеров/фикстур); `bash scripts/verify_ci_parity.sh` — rc=0;
  scoped-режим Н-48 — существующие фикстуры раннера без изменений.

**Красность проб до предмета (прецедент шагов 011/015: «шаг красен, пока предмет не
реализован»).** Пробы «выпавшая», «задублированная», «scoped», «без матрицы»,
«мёртвый ключ» и «legacy-шаг» обязаны быть красными на честном дереве ДО реализации
(барьер не несёт ветвей полноты и исключительности):
`bash scripts/verify_antiplacebo.sh --scope verify_ci_parity/<проба>` → rc=1,
«красное не предъявлено»; зелёными они становятся вместе с предметом. Слабый барьер
(три проверки: выпавшие ключи, дубли известных, отсутствие `--scope` в последнем
анти-плацебо-запуске) ловит первые три и НЕ ловит последние три — измерено прогонами
против дословного слабого критерия критика (19/22 зелёных, отказы ровно на новых
пробах; прогоны — в verify-зоне пачки). Проба правила 6 зелёная и до, и после — её
ветвь уже живёт, и требовать её красноты до реализации значило бы требовать ЛЖИ в
диагнозе (Н-39): дефект наблюдаем на её входе сегодня.

**Граница параметров Р1–Р4 (ответ на совет критика v1).** Барьер НЕ сверяет
`concurrency`, `timeout-minutes`, N=5, node и `fetch-depth`: это tuning-решения
одного файла `ci.yml`, судимого чтением (критик до freeze, адверсарий и ревьюер
после реализации; ровно пять шардов видно и в артефакте CI-прогона). Механическая
привязка числа шардов в барьере отвергала бы легальный решард при дрейфе дерева и
положительный контроль проб из двух шардов — ложное красное опаснее скучного.
Проверка ПОРЯДКА коммитов пачки (concurrency первым) не переживает land (rebase) и
механизмами приёмки не закрепляется: порядок назван в §Порядок пачки и виден в
истории ветки до land.
