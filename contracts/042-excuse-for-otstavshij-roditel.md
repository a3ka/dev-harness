# Контракт 042 — `excuse_for()` теряет ALLOW за мержем с отставшим родителем (Н-127)

Статус: самоприменение (architect, одним заходом — обоснование в §Зоны). Точечный фикс
`excuse_for()` и распознавания мерж-артефактов (`is_lagging_merge_artifact`, `blob_at`) в
`scripts/check_protected.sh`; красная пачка на toy-репозиториях написана и прожита живыми
прогонами ДО и ПОСЛЕ правки в дереве до раздачи; предмет приземляется с кодом уже живым,
критик проверяет его прогоном, а не заявлением.

## Предмет

`check_protected.sh:excuse_for()` требует строку `ALLOW-ARTIFACT-DELETE:` ИМЕННО в удаляющем
коммите пути `p`; удаляющий коммит ищется командой

```
git log HEAD --full-history --no-renames -m --diff-filter=D --format=%H -- <p> | sed -n 1p
```

`-m` показывает диф МЕРЖ-коммита ОТДЕЛЬНО против КАЖДОГО его родителя (находка круга 2
контракта 039, нужна для честного modify/delete в теле мержа). Если удаление уже случилось на
одной ветке РАНЬШЕ, а вторая ветка форкнулась ДО удаления и слита в первую уже ПОСЛЕ него, то
относительно этой второй, «отставшей» (не видевшей удаления) ветки-родителя сам мерж-коммит
показывает путь как `D` — он и есть первая (самая свежая) строка вывода команды выше, хотя
ничего не удалял: он лишь унаследовал уже-отсутствующее состояние от НЕ-отстающего родителя.
`sed -n 1p` брал именно его, тело мержа не несёт ALLOW-строку (её незачем повторять — разрешение
уже сказано в настоящем удаляющем коммите), и `excuse_for` честно отвечал «не разрешено» —
легитимное удаление читалось как нарушение.

## Диагноз (живые доказательства на реальном дереве dev-harness)

Живой прогон ДО фикса: `bash scripts/check_protected.sh .` → `rc=1`, три FAIL на файлах,
легитимно удалённых коммитом `4b3666f` (три корректные строки `ALLOW-ARTIFACT-DELETE:`):
`verdicts/critic/contracts-040-v{2,3,4}.md`.

## Направление фикса — выбор и обоснование

Запись Н-127 называет два кандидата, не решая между ними. Оба разобраны здесь.

**Кандидат А (отвергнут): искать ALLOW по ВСЕМ diff-filter=D событиям пути, а не только по
первому.** Реализация — тривиальная (снять `sed -n 1p`, пройти по всем строкам, принять первое
совпадение). Но `excuse_for` — это ИМЕННО тот механизм, что уже был ослаблен и уже был закрыт
после адверсария на плане 005 (комментарий шапки, :202-205 текущего файла): «Прежняя редакция
собирала разрешения из тел ВСЕХ достижимых коммитов… разрешение годилось ПОВТОРНО после
восстановления файла, и его можно было положить ЗАРАНЕЕ в посторонний коммит». Кандидат А не
собирает разрешения из ЛЮБЫХ коммитов — только из diff-filter=D-кандидатов ЭТОГО пути — но это
ТОЧНО ТА ЖЕ дыра в узком виде: путь `p`, удалённый С разрешением коммитом `D1`, восстановленный
коммитом `R`, затем удалённый БЕЗ разрешения коммитом `D2` — `D1` и `D2` ОБА присутствуют в
списке diff-filter=D для `p` (оба — реальные события «путь исчез из дерева относительно
родителя»), и «искать по всем» нашло бы ALLOW у `D1`, ошибочно извинив `D2`. Закрывать ЭТУ
дыру кандидату А потребовалось бы отдельной логикой «событие следует засчитывать, только если
после него путь не восстанавливался» — а это по сложности не меньше кандидата Б, при этом
идёт ПРОТИВ явно защищённого антигейминг-инварианта, а не рядом с ним. Риск: реген старой,
уже найденной и закрытой дыры чужим адверсарием (план 005) — неприемлемо для точечного фикса.

**Кандидат Б (принят): исключать мерж-коммит из кандидатов на «удаляющий коммит», если
бесконфликтный трёхсторонний мерж его родителей дал бы то же самое отсутствие пути `p` БЕЗ
единого ручного действия.** Наивная формулировка «путь отсутствует хотя бы у одного родителя»
НЕДОСТАТОЧНА: путь `p`, удалённый С разрешением (`D1`), может быть ВОССТАНОВЛЕН на главной
ветке (`R`) и УДАЛЁН ЗАНОВО явным действием внутри мерж-коммита (`git merge --no-ff
--no-commit` независимой ветки `side`, не трогавшей `p`, затем `git rm p` и коммит `D2` БЕЗ
ALLOW). У ВТОРОГО родителя `D2` (`side`) путь действительно отсутствует — но НЕ потому, что
мерж унаследовал это состояние: бесконфликтный трёхсторонний мерж этих же двух родителей взял
бы версию ПЕРВОГО родителя (путь присутствует, восстановлен `R`), а не отсутствие. «У родителя
пути нет» и «мерж унаследовал его отсутствие» — РАЗНЫЕ утверждения, и наивный предикат путает
их. Правильный вопрос — сравнение с базой слияния (`git merge-base` двух родителей): мерж —
артефакт, ТОЛЬКО если СУЩЕСТВУЕТ родитель, чьё состояние пути `p` совпадает с базой (родитель
«молчит» — ничего не менял), И состояние пути `p` у ДРУГОГО родителя — тоже отсутствие (то,
что бесконфликтно взял бы мерж от «молчащего» родителя, совпадает с заявленным исчезновением
в самом мерже). Если путь присутствует У ВСЕХ родителей, ИЛИ «молчащий» родитель есть, но
состояние другого родителя — присутствие (случай `D2` выше), — отсутствие в дереве мержа
создано ИМ САМИМ (настоящее удаление, требующее собственного ALLOW), и мерж остаётся
кандидатом без изменений. `excuse_for` пропускает распознанные артефакты по порядку `git log`
и ОСТАНАВЛИВАЕТСЯ на первом кандидате, который артефактом не является, — это и есть настоящий
удаляющий коммит; ДАЛЬШЕ поиск не идёт. Именно это «дальше не идёт» держит антигейминг-
инвариант: разрешение всё ещё берётся из РОВНО ОДНОГО, однозначно определённого коммита, а не
из произвольного более старого — уточнение критерия НЕ ослабляет эту границу, оно лишь чинит
то, ПО КАКОМУ признаку коммит считается артефактом. Сложность — три функции (`blob_at`,
`is_lagging_merge_artifact`, неизменённый `excuse_for`), один `git merge-base` и три
`git ls-tree` на кандидата — не на историю целиком (Н-126-класс рисков не касается: вызывается
только для коммитов, УЖЕ найденных diff-filter=D-фильтром, которых для одного пути единицы).
Октопус-мержи (3+ родителя) и неоднозначная/отсутствующая база слияния — fail-closed, никогда
не признаются артефактом (§Риски). Не-ослабление уточнения проверено живым прогоном на ИМЕННО
той топологии восстановления-и-повторного-удаления через мерж (§Приёмка, R6): наивная
формулировка «путь отсутствует хотя бы у одного родителя» на этом дереве ошибочно извиняла
`D2` разрешением `D1` (rc=0); уточнённая — распознаёт `D2` как настоящий удаляющий коммит без
ALLOW (rc=1).

Выбран кандидат Б.

## Семантика (точная, реализация несёт эти строки побайтово в логике, не в тексте)

`blob_at(c, p)` → блоб пути `p` в дереве коммита `c` (третье поле `git ls-tree c -- p`), пусто
— пути там нет.

`is_lagging_merge_artifact(c, p)` → 0 (артефакт), если у `c` РОВНО два родителя `P1`, `P2`;
`base = git merge-base(P1, P2)` вычисляется успешно и непусто; И (`blob_at(P1,p) ==
blob_at(base,p)` И `blob_at(P2,p)` пусто) ИЛИ (`blob_at(P2,p) == blob_at(base,p)` И
`blob_at(P1,p)` пусто). Иначе 1 (не артефакт): у `c` не 2 родителя, либо `git merge-base` не
дал однозначного ответа, либо условие «молчащий родитель + отсутствие у другого» не выполнено
ни в одном порядке.

`excuse_for(p)`: перебирает коммиты из `git log HEAD --full-history --no-renames -m
--diff-filter=D --format=%H -- p` В ПОРЯДКЕ ВЫВОДА; пропускает (`continue`) кандидатов, для
которых `is_lagging_merge_artifact` истинно; НА ПЕРВОМ не-артефакте — читает его тело ТОЙ ЖЕ
логикой разбора строк `ALLOW-ARTIFACT-DELETE:`, что была всегда (кавычки, первая колонка,
безымянное/безпричинное разрешение — `bad()`), и ЗАВЕРШАЕТСЯ на этом кандидате: `return 0`
при найденном валидном разрешении для `p`, иначе `return 1` БЕЗ дальнейшего поиска. Пустой
список кандидатов (не должно происходить для пути из `missing`, но fail-closed) → `return 1`.
НИКАКАЯ другая функция (`moved_for`, область по `roles/*.md`, разбор поля `verdict`, `comm`-
разность, env-гигиена, коды 0/1/2) не тронута.

1. **Каскад из НЕСКОЛЬКИХ подряд «отставших» слияний одного пути теоретически разобран**
   (каждый пропущенный артефакт по определению указывает на «молчащего» родителя с историей,
   строго не включающей мерж — рекурсия терминирует по конечности DAG), но живым прогоном
   проверена только ОДНА глубина отставания (реальное дерево, R2, R3, R6). Второй уровень
   (мерж мержа) на дереве dev-harness не встречался — не заводится отдельной фикстурой этим
   контрактом; кандидат для будущего адверсария, если встретится живьём.
2. **Октопус-мержи (3+ родителя) — fail-closed ПО ПОСТРОЕНИЮ, не «покрыты кодом».**
   `is_lagging_merge_artifact` требует РОВНО двух родителей (`[ "${#parents[@]}" -eq 2 ]`);
   при 3+ родителях функция сразу возвращает «не артефакт», и мерж остаётся кандидатом на
   общих основаниях — безопасное направление ошибки (требует ALLOW, а не прощает), но не
   решает семантику октопуса, а уклоняется от нее. На дереве dev-harness октопус-мержей нет;
   отдельной фикстурой не заводится.
3. Три `git ls-tree`(`blob_at`) и один `git merge-base` на КАЖДОГО двухродительского
   diff-filter=D-кандидата пути (не на всю историю) — Н-126-класс риска (масштаб на
   органическом росте) не активирован: количество кандидатов на один пропавший путь
   ограничено числом реальных событий удаления этого пути, а не размером репозитория.
4. Критерий сравнивает состояние пути `p` С ОБЕИХ сторон мержа независимо для каждого
   diff-filter=D-кандидата; если у мержа ОБА родителя одинаково изменили путь (например, оба
   независимо удалили его без ALLOW) — ни один не «молчит» относительно базы, и мерж НЕ
   признаётся артефактом, остаётся кандидатом сам по себе (fail-closed: требует собственный
   ALLOW). Отдельной фикстурой этот под-случай не заведён — на дереве dev-harness не
   встречался, поведение выведено из кода и рассуждения выше, не из живого прогона.
