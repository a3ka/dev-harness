> `git config receive.denyCurrentBranch refuse` — ПРОВЕРКОЙ в bootstrap: без настройки —
> именованный отказ с командой-исправлением;

Тот же план, приёмка: «./workshop стартует на игрушечном внешнем репо и на клоне
odelix-stack; правила видны в промпте сессии; без профиля — именованный отказ». Спека
(docs/spec §17, этап 1): «прошлый self-сценарий работает, а второй тестовый проект
разрешается в профиль без изменений Core и копирования харнесса. Ошибочный профиль даёт
точную диагностику». Правило переноса плана: «механизм перенесён ⇔ прогон на репо Odelix
(или игрушечном внешнем репо в фикстуре) дал ожидаемый rc на честном входе И красный на
обманном; минимум ДВА репо разных стеков (Rust и TS)».

Вход — карта 052 (frozen/2): строка `workshop` (замена/параметризация = «В3: bootstrap
пина/.env/metering для проекта; боль 1 — правила 1-16 проекта должны доходить»), строки
параметров-профиля (gitw-канон, лимиты, домен почты) — профиль В2 их НЕСЁТ; подключение
потребителей к этим значениям — их собственные следующие контракты (вне 054).

Три механизма:

- **М1 `scripts/profile_resolver.sh`** (НОВЫЙ файл): чтение двух слоёв, замкнутые
  алфавиты, отказ на неизвестном ключе, слияние с происхождением.
- **М2 лаунчер**: `workshop` в режиме проекта — вызов резолвера, denyCurrentBranch-проверка
  (4.3), компоновка промпта с правилами, probe-режим для фикстур/CI.
- **М3 `scripts/gen-harness.ts --agents-rules`**: извлечение секции правил мастерской из
  ЕДИНОГО источника (AGENTS.md) для промпта проектной сессии.

## Frontier: границы и отвергнутые варианты

- **Граница-1 (машинная форма слоя проекта — JSON, не markdown).** Слой проекта = один
  JSON-файл в корне клона слоя (по умолчанию `registry/harness-project.json`; путь задаёт
  репо-слой). `development/ODELIX-PROJECT-PROFILE.md` — документация, на которую слой
  опирается (Б6-факт), резолвером НЕ парсится: замкнутый алфавит и «неизвестный ключ» на
  markdown не выражаются (правило 7 требует именованный отказ по ключу — 041-класс).
  Каталоги Odelix ВРЕМЕННЫЕ (слово владельца): профиль-путь — параметр, не константа.
- **Граница-2 (binding машины — вне git).)** Корень клона слоя проекта резолвер получает
  из env `HARNESS_PROJECT_LAYER_ROOT`; в версионируемом `harness.project.json` живут ТОЛЬКО
  пин версии (`projectLayer.version`) и относительный путь (`projectLayer.profilePath`).
  Отвергнуто: абсолютный путь в версионируемом файле — спека §4.3 помещает локальный
  binding вне Git; прецедент ручек `HARNESS_SCRATCH`/`GIT_EXCHANGE_GUARD_CANONICAL`.
- **Граница-3 (probe — режим лаунчера, не второй скрипт).)** Приёмка «./workshop на
  игрушечном репо» в CI — это `./workshop --probe <репо>`: ТОТ ЖЕ код режима проекта
  (окружение, пин omp, резолвер, 4.3-проверка, раскладка ролей, компоновка промпта),
  исполненный ДО `exec omp` и выходящий rc 0 строкой `workshop PROBE OK`. Отвергнут
  отдельный дублирующий скрипт пробы: две копии логики режима расходятся молча — измерено
  в этом же workshop («ОДНА реализация на оба входа»).
  Имя входа режима проекта — `--probe` (CI/фикстуры) и `./workshop <репо>`
  (живой); флаг `--project-mode` из брифа НЕ вводится: одно имя — один вход.
- **Граница-4 (правила — секция по литеральному заголовку, один читатель).** В промпт
  идёт секция `## Правила, каждое из которых уже стоило времени` (правила 1–16 — боль 1
  карты 052), извлечённая `gen-harness.ts --agents-rules <AGENTS.md>`: заголовок —
  константа одного места; секции нет → отказ (fail-closed). Отвергнуто: sed/awk-извлечение
  в workshop (второй читатель одного инварианта — класс дрейфа) и «весь AGENTS.md»
  (30 381 Б — свод включает воркфлоу мастерской, проектной сессии не нужный).
- **Граница-5 (4.3 — только явная настройка).)** Проверка: `git -C <репо> config --get
  receive.denyCurrentBranch` обязан вернуть ЛИТЕРАЛЬНО `refuse`; пусто или иное →
  именованный отказ с командой-исправлением. Дефолт git не принимается за исполнение
  слова владельца: слово — «выставить», значит настройка обязана существовать явно
  (прецедент Н-143: `updateInstead` мутировал рабочее дерево клона).
- **Граница-6 (объём = этап 1 спеки).)** Скалярное слияние с происхождением;
  замкнутые алфавиты перечислены ниже. НЕ входит: полный профиль §4.2
  (Identity/Sources/Architecture/Integrations/Policy/Limits/Knowledge),
  слияние коллекций по ID, lock-файл (§4.3 `harness.lock.json`), snapshot
  (§4.5), gitw-потребление `git.canonicalRemote` (карта 052, строка gitw:
  «ждёт финального каталога»), ПОТРЕБИТЕЛЬ настройки CI репо (В5: профиль
  НЕСЁТ `ci.workflow` как данные — норма В2 включает CI дословно, — но В5
  решает, что с ним делать), живой запуск на клоне odelix-stack (Г1 —
  владелец, отдельной сессией; каталоги UNVERIFIED).
- **Граница-7 (bootstrap не создаёт).)** Отсутствие пина/.env/профиля — именованный отказ
  с ТОЧНОЙ инструкцией (что и куда положить), не молчаливое умолчание и не генерация
  файла за проект: профиль — принятые настройки проекта, пишет их проект (спека §4.1).

## Инварианты

### М1 — `scripts/profile_resolver.sh` (новый)

- **И-1 (вход и отсутствие репо-слоя).** Вызов `bash scripts/profile_resolver.sh --repo
  <корень>`; файла `harness.project.json` в корне нет → rc 1, P1. Никаких чтений слоя
  проекта до этого отказа.
- **И-2 (слой проекта и его корень).** Корень слоя = `${HARNESS_PROJECT_LAYER_ROOT}`;
  переменная пуста или каталога нет → rc 1, P2. Файл слоя
  `<корень>/<projectLayer.profilePath>` (умолчание `registry/harness-project.json`)
  отсутствует → rc 1, P3.
- **И-3 (замкнутые алфавиты — правило 7).** Верхний уровень репо-слоя:
  {schemaVersion, repoId, language, workflowPaths, commands, git, ci, barriers,
  projectLayer}; `projectLayer`: {version, profilePath}; верхний уровень слоя
  проекта: {schemaVersion, version, projectId, workspaceId, defaults};
  `defaults` ⊆ {language, workflowPaths, commands, git, ci, barriers};
  `workflowPaths`: {contracts, verdicts, registry, fixtures}; `commands`:
  {test, build, typecheck, lint}; `git`: {canonicalRemote}; `ci`: {workflow} —
  путь CI-конфига репо (например `.github/workflows/ci.yml`); настройка CI —
  часть предмета В2 дословно («…язык, CI, обязательные/необязаемые барьеры…»),
  ПОТРЕБИТЕЛЬ значения — В5 (Граница-6); `barriers`: {mandatory, optional}.
  Ключ вне множества ЛЮБОГО уровня → rc 1, P4 с точным путём ключа (например
  `workflowPaths.contrete`). Алфавиты — ОДИН массив в теле резолвера; контракт
  несёт его побайтово (единый источник — §Семантики).
- **И-4 (значения и обязательность полей).)** `schemaVersion` обоих слоёв = 1
  (литерально); `language` ∈ {rust, typescript}; `repoId`, `projectId`,
  `workspaceId`, `canonicalRemote`, `version`, `profilePath`, `ci.workflow` —
  непустые строки; элементы `barriers.mandatory`/`barriers.optional` — непустые
  строки класса `^[a-z0-9][a-z0-9_-]*$`; значения `workflowPaths`/`commands` —
  непустые строки. Обязательные поля репо-слоя: `schemaVersion`, `repoId`,
  `language`, `projectLayer` (без пина слоя И-5 не судить); остальные ветви
  опциональны — умолчание из `defaults` слоя проекта. Обязательные поля слоя
  проекта: `schemaVersion`, `version`, `projectId`, `workspaceId`; `defaults`
  опционален. `version`/`projectLayer.version` — непустые строки, semver не
  требуется (этап 1). `barriers.mandatory`/`barriers.optional` сливаются как
  ЕДИНИЦА: ключ, заданный репо-слоем, замещает массив целиком (поэлементное
  слияние массивов — вне этапа 1, Граница-6). Нарушение → rc 1, P6 с полем и
  значением.
- **И-5 (пин слоя проекта).** `projectLayer.version` (репо-слой) обязан литерально
  равняться `version` слоя проекта; расхождение → rc 1, P5 с обоими значениями.
- **И-6 (слияние с происхождением).** Скалярный лист алфавита берётся из репо-слоя, если
  ключ там есть, иначе из `defaults` слоя проекта. Вывод — один JSON на stdout: для
  каждого листа `{"value": <значение>, "origin": "repo"|"project"}`; ключи вывода — тот же
  замкнутый алфавит; `projectId`/`workspaceId` — всегда origin `project`, `repoId` —
  всегда `repo`. Битый JSON любого слоя → rc 1, P7 (файл назван, ошибки jq не глотаются).
- **И-7 (гигиена парсинга — норма 041).)** Чужой ввод — оба JSON; структурные поля —
  замкнутые множества И-3; парсер — jq (разделители представления — синтаксис JSON,
  байты данных не переиспользуются как разделители); сравнения значений — литеральные
  равенства строк; точечный якорь терминатора — конец JSON-документа (jq сам отказывает
  на мусоре, отказ проксирован P7). Self-application: профиль
  `fixtures/parsing_hygiene_battery/profiles/profile_resolver.sh`, прогон
  `bash fixtures/parsing_hygiene_battery/run_battery.sh profile_resolver` → rc 0
  (4 класса: delimiter-collision, regex-injection, silent-drop, self-application-green).

### М2 — лаунчер `workshop` в режиме проекта

- **И-8 (probe — тот же код, до exec).)** `./workshop --probe <репо>` исполняет путь
  режима проекта (load_env → bootstrap_env → пин omp → резолвер И-1..И-6 → 4.3-проверка
  И-10 → раскладка ролей И-12 → промпт И-9) и выходит ДО `exec omp` rc 0, печатая в
  stdout `workshop PROBE OK: <репо>` и строку `PROMPT: <путь-файла-промпта>`. Любой отказ
  по пути — rc 1 с именованной причиной шага. Отсутствие `--probe` не меняет поведение
  живого режима. Второй реализации этого пути нет (граница-3).
- **И-9 (правила доходят до промпта — целиком и в порядке).)** Файл промпта
  проектной сессии = тело роли (`gen-harness.ts --prompt <роль>`) + пустая
  строка + правила (`gen-harness.ts --agents-rules <AGENTS.md>`), в этом
  ПОРЯДКЕ: роль, затем правила. Правила = заголовок секции + ВСЁ тело секции
  до следующего `## ` — побайтово; вывеска без тела правил правилом не
  является. Заголовок присутствует в файле промпта самостоятельной строкой
  (grep -Fx). AGENTS.md репо в промпт НЕ подмешивается — его область читает
  сам omp (В3(а), вторая половина).
- **И-10 (4.3-проверка — литерал, не непустота).)** В режиме проекта (probe и
  живой) ДО раскладки ролей: `git -C <репо> config --get
  receive.denyCurrentBranch` обязан вернуть ЛИТЕРАЛЬНО `refuse`; пусто, unset
  или иное значение (включая `updateInstead` — класс Н-143 «updateInstead
  мутировал рабочее дерево») → rc 1, W2: значение названо в причине, дана
  команда-исправление. Проверка «значение непусто» исполнением И-10 не
  является. Значение читается в репо проекта, не в мастерской.
- **И-11 (без профиля — именованный отказ).)** Все отказы И-1..И-5, И-10, И-13
  лаунчер проксирует ДОСЛОВНО (побайтово) — свой текст не добавляет;
  bootstrap-инструкция (P1/P2/P8/P9) — часть отказа.
- **И-12 (роли — как сейчас).)** `gen-harness.ts --into "$AGENTS"` и `--check` в
  изолированном HOME сессии — семантика не правится; дрейф agents/↔roles/ судится
  существующей семьёй `fixtures/gen-harness/` (не дублируется).
- **И-13 (bootstrap: именованные отказы, ничего не создаёт).)** В режиме проекта
  (probe и живой) отсутствие `.env` репо → rc 1, P8 (путь + инструкция), ДАЖЕ
  если METERING_PROXY_URL экспортирована в окружение; отсутствие
  `config/harness_pin.json` → rc 1, P9 (точная форма содержимого). Молчаливый
  return `load_env` и skip «сверять не с чем» — контрмодели (клетки к12/к13).
  Probe судит НАЛИЧИЕ и грамматику пина (JSON; `.version` — непустая строка;
  нарушение формы — P7/P6 с именем файла/поля); сверка значения пина с
  `omp --version` — шаг живого режима (omp в probe/CI не заявлен —
  §Демаркация). Отказы И-1/И-2/И-10 несут инструкцию; никакая ветка bootstrap
  не создаёт файлов за проект (граница-7: профиль пишет проект).

## Модель угроз

ЗАЩИЩАЕТ:
- тихое «умолчание» профиля: любой ключ вне заявленного множества и любое значение вне
  алфавита дают именованный отказ ДО сессии — несанкционированная настройка не действует
  молча (правило 7);
- дрейф слоя проекта: репо, запинившее старую версию слоя, отказывает с обоими
  значениями, а не разрешается половинчатой смесью;
- push в CHECKED-OUT ветку клона проекта (класс Н-141/Н-143): сессия не стартует, пока
  `receive.denyCurrentBranch` не выставлен явно в `refuse` — инцидент класса
  «updateInstead мутировал рабочее дерево» предотвращён до первой сессии;
- подмену правил сессии: правила идут из AGENTS.md мастерской одним извлечением с
